# Этап 1, стенд: находки по ходу

Рабочие заметки прототипа (Chrome 155.0.8059.39, Linux, свой стенд без Fansly).
Итог с цифрами серий — в отчёте этапа 1. Каждая находка проверена прогоном;
сценарий или скрипт указан в скобках.

## Поправки к плану

1. **Перехват `Fetch` на browser-цели не действует на вкладку, открытую до
   `Fetch.enable`.** Запрос из вкладки `about:blank`, с которой Chrome
   стартовал, ушёл в прокси без `Fetch.requestPaused`. Во вкладке, открытой
   после `Fetch.enable` (`Target.createTarget`), запрос встаёт на паузу.
   Следствие для §4.1: рабочая вкладка открывается после включения
   перехвата, стартовая закрывается; восстановление вкладок при запуске
   запрещено политикой (`RestoreOnStartup`), иначе сайт загрузился бы до
   перехвата. (запуск оператора, самопроверка)
2. **CORS-preflight перехватывается.** План (§4.2, шаг 6) считал, что CDP
   preflight не видит. В Chrome 155 preflight приходит в `Fetch.requestPaused`
   отдельным запросом (`OPTIONS`, свой `networkId`, заголовок
   `Access-Control-Request-Method`) перед основным. Решение владельца №1
   (preflight + запрос — одна операция под одним допуском) исполняется
   буквально: допуск спрашивается на паузе preflight, основной запрос
   отпускается под тем же допуском, если срок не истёк. (`smoke`)
3. **Порядок событий между сессиями CDP не гарантирован.** Пауза основного
   запроса (сессия браузера) может прийти раньше, чем `loadingFinished` его
   preflight (сессия страницы). Связь preflight → запрос ставится в момент
   выпуска preflight; окно «ворот» — своё на каждый физический запрос.
4. **`Runtime.addBinding` ставит привязку в новые контексты только при
   включённом `Runtime`.** Без `Runtime.enable` обёртка сокета не может
   отчитаться оператору. Классическая проба обнаружения `Runtime.enable`
   (геттер `stack` у ошибки в `console.debug`) в Chrome 155 не срабатывает.
   (`ws-detect`)
5. **В воркере, ждущем отладчик, `Runtime.evaluate` не возвращается:**
   контекста скрипта ещё нет. Обёртка ставится через
   `Debugger.setInstrumentationBreakpoint("beforeScriptExecution")`: воркер
   стартует, останавливается перед первым скриптом, обёртка встаёт
   (`Debugger.evaluateOnCallFrame`), отладчик выключается. (`ws-contexts`)
6. **Service worker подключается дважды** — через browser-цель и через сессию
   страницы; две сессии к одному воркеру зависают на старте. На уровне
   страницы service worker исключён из автоподключения фильтром.
7. **Chrome сам повторяет запрос, и CDP об этом не сообщает.** После
   `REFUSED_STREAM` (тем же соединением), `GOAWAY` и обрыва повторно
   использованного соединения (новым соединением) на сервер приходят два
   запроса на один допуск; `requestWillBeSentExtraInfo` приходит один раз.
   Обнаружить повтор по событиям нельзя. (`retry-*-nogate`)
8. **Потоковое чтение тела кончается в CDP «отменой».** Если JS читает тело
   потоком (`getReader()`, `for await`, `pipeTo`) и тело ещё доезжает во время
   чтения, запрос завершается `Network.loadingFailed (ERR_ABORTED, canceled)`,
   хотя JS получил всё. При `text()` и `arrayBuffer()` — `loadingFinished`.
   Если тело не читают вовсе, события конца нет. Следствия:
   - запрос Hub в изолированном мире дочитывается `arrayBuffer()`;
   - правило §4.2, шаг 7 («тело собрано полностью, если запрос закончился
     `loadingFinished`») для запросов сайта неверно: полнота судится по длине
     (`content-length`) или форме тела, а «отмена» после заголовков ответа —
     обычный конец;
   - у операции нужен предел по времени: непрочитанное тело не кончается.
   (`/tmp/endvar.mjs`, `hub-slow-body`)
9. **В Chrome есть второй API сокета — `WebSocketStream`.** Он шлёт мимо
   `WebSocket.prototype.send`. Обёртка убирает его из глобального объекта.
10. **Сокет поверх HTTP/2.** Chrome кладёт сокет на уже открытую сессию
    HTTP/2 к хосту сокета (с учётными данными), и тогда отдельного туннеля у
    сокета нет. Оператор отказывает любым не-сокетным запросам к хосту
    сокета, поэтому такой сессии не возникает: каждый сокет — свой туннель и
    свой допуск. (`ws-h2`)

11. **WebGL без видеокарты выключен.** На Mesa `llvmpipe` Chrome 155 держит
    WebGL в чёрном списке (`WebGL1 blocklisted`), автоматического отката на
    SwiftShader больше нет. С флагом `--ignore-gpu-blocklist` WebGL работает:
    `ANGLE (Mesa/X.org, llvmpipe (LLVM 15.0.6 128 bits), OpenGL 4.5)` —
    честное серверное «устройство», как задумано в §3.1. Панели
    «неподдерживаемый флаг» нет (снимок экрана Xvfb). Нужны пакеты
    `libgl1-mesa-dri libegl1 libgles2`.
12. **Язык страницы в Linux-сборке задаётся окружением процесса**
    (`LANGUAGE`, `LANG`), а не флагом `--lang`; список языков — политикой
    `ForcedLanguages`. Тогда совпадают `navigator.language(s)`, `Intl` и
    заголовок `Accept-Language` (`de-DE,de;q=0.9,en-US;q=0.8,en;q=0.7`).
    Часовой пояс — `TZ`, геолокация — `Emulation.setGeolocationOverride` в
    каждой странице до запуска и `Browser.grantPermissions` для сайта.
13. **Расширение с правилами ставится политикой с порта прокси.** Chrome
    упаковывает и подписывает его сам (`--pack-extension` при сборке
    образа); политика `ExtensionSettings` ставит его с
    `http://127.0.0.1:3128/pb-extension/update.xml` — к loopback Chrome
    ходит мимо прокси, так что правила ОС не мешают. Правила видят запрос
    раньше перехвата: запросы, отменённые расширением, в `Fetch` не
    приходят вовсе, и самопроверка узнаёт их по
    `net::ERR_BLOCKED_BY_CLIENT`. Запрос Hub выпускается с подменного хоста —
    правила API продублированы для него.

14. **Chrome 155 убивает службу сети на CORS-запросах под перехватом.**
    Preflight, пойманный перехватом на browser-цели, идёт с тем же
    `request_id`, что и основной запрос. Клиент preflight в службе сети
    заканчивает по заголовкам ответа и закрывает загрузчик; браузер снимает
    задание перехвата только когда заметит разрыв (асинхронно). Если основной
    запрос успел попросить задание под тем же ID, браузер видит «DevTools:
    Duplicate request ID» (`devtools_url_loader_interceptor.cc:822`),
    считает службу сети скомпрометированной и убивает её: рвутся все
    соединения, включая сокет сайта, страница может зависнуть навсегда.
    На стенде — 2 из 300 CORS-запросов; все четыре дампа падений —
    `mojo-message-error = Received bad user message: DevTools: Duplicate
    request ID`. Исправление: preflight отпускается с перехватом стадии
    ответа, и его настоящий ответ передаётся дальше `Fetch.fulfillRequest` —
    задание заканчивается синхронно, раньше, чем клиент увидит ответ.
    0 из 300. OPTIONS по-прежнему уходит на сервер. Дополнительно оператор
    раз в 2 с проверяет, что страница отвечает и процесс службы сети прежний;
    иначе — закрытый выход и перезапуск браузера (на старой версии страница
    после такого падения висела без конца).
15. **Service worker, остановленный Chrome и запущенный снова, работает в
    той же сессии CDP** (`Inspector.targetCrashed` →
    `Inspector.targetReloadedAfterCrash`, нового `attachedToTarget` нет).
    Обёртка, поставленная один раз через точку останова, в перезапущенном
    воркере отсутствовала: запрещённое сообщение ушло на сервер. В живом
    Chrome воркеры сайта останавливаются после ~30 с простоя. Исправление:
    у service worker отладчик и точка останова «перед скриптом» живут всю
    сессию, обёртка ставится заново на первой паузе после каждого
    перезапуска. (`ws-sw-restart`: 10 из 10)
16. **«Ворота» решают по каждой записи TLS, у окна — бюджет записей.**
    Chrome пишет кадр HTTP/2 одним вызовом, BoringSSL делает из вызова
    запись (`SpdySession::DoWrite`). Тип записи и её длина видны в открытом
    заголовке. Поэтому:
    - запись размером с кадр управления (PING, WINDOW_UPDATE, RST_STREAM,
      SETTINGS ACK; TLS 1.3 — до 39 байт) проходит всегда, если перед ней
      в туннеле ничего не задержано;
    - любая другая — только в окне допущенного запроса и в пределах его
      бюджета: HEADERS плюс по записи DATA на каждые 16 375 байт тела;
      у нового соединения ещё Finished TLS 1.3 и преамбула HTTP/2;
    - задержанная запись держит весь туннель (поток TLS не переставить);
      к следующему окну такой туннель рвётся, а не отпускается.
    Замеры стенда: GET — 76–84 байта, preflight — 81–93, первый запрос на
    новом соединении — около 400; кадры управления — 31–39.
    Было (до ревью Astra): одна запись на окно без тела, а новое соединение
    и запросы с телом — до объявления отправки и 5 мс тишины.
17. **Фаза ответа пропускала всё (`loss-cdp-break-late-inflight`, 45 из 50).**
    Когда заголовки ответа пришли, «ворота» отпускали придержанное и
    пропускали все байты. Обрыв CDP в этот момент при медленной реакции
    оператора выпускал задержанные запросы. Теперь в фазе ответа большие
    записи задерживаются (`loss-responding-late`).
18. **Кадр DATA маленького тела неотличим от кадра управления**
    (`retry-post`). Тело в 2 байта — запись в 33 байта. Повтор POST после
    `REFUSED_STREAM` уходил: DATA не расходовала бюджет. Теперь после HEADERS
    запроса с телом каждая запись туннеля идёт в счёт бюджета.
19. **Новое соединение при обрыве CDP** (`loss-new-connection-late`). С
    окном «до объявления» отпущенные Chrome запросы шли следом за допущенным
    по тому же новому соединению (3 из 3 с утечкой). С бюджетом — 0.
20. **PING перед запросом.** После 10 с без чтения Chrome 155 шлёт PING
    (`MaybeSendPrefacePing`), на стенде — сразу после HEADERS, а не перед
    ним (`idle-ping`, журнал записей). Записи управления проходят в любой
    фазе, так что порядок не важен.
21. **Обёртка сокета: встроенные функции берутся до сайта** (`ws-tamper`).
    Прежняя обёртка звала `Reflect.apply`, `JSON.parse`, методы `Set` и
    `WeakMap` во время вызова. Подмена `Reflect.apply` или
    `WeakMap.prototype.get` из страницы отдавала нативный `send` (2 из 2 на
    прежнем коде); подмена `JSON.parse` или геттер `t` на `Object.prototype`
    выдавали запрещённое сообщение за разрешённое. Теперь всё нужное взято
    при установке, авторизация проверяется по ключам (`t`, `d`; в `d` —
    `token`, `v`). `send` с чужим `this` или на неоткрытом сокете уходит в
    нативный `send` (та же ошибка, без кадра обёртки в стеке).
22. **Сбой установки обёртки или перехвата останавливает страницу**
    (`halt`): выход закрыт, Chrome остановлен. Страница стартует только по
    команде движка `restart` и после любого перезапуска оператора или
    контейнера снова стоит (на диске ничего не хранится). Цель, которая
    исчезла сама (`Session with given id not found` при обрыве CDP),
    остановкой не считается — иначе первый же обрыв CDP останавливал стенд.
27. **Chrome не бросает CONNECT, который ждёт ответа прокси**, даже когда
    сокет страницы закрыт или страница ушла на другой адрес: ожидание
    кончает срок оператора (10 с). Исход каждого допуска сокета оператор
    сообщает движку под номером допуска: «открыт, 101» или «не удалось»
    (`ws-handshake-outcome`).

23. **Редирект запроса с preflight под перехватом убивает службу сети.**
    На редиректе Chrome 155 делает preflight следующего шага под номером
    основного запроса, а его задание перехвата ещё зарегистрировано (оно
    живёт всю цепочку редиректов): `FindJobByGlobalId` → «DevTools:
    Duplicate request ID» → служба сети убита
    (`devtools_url_loader_interceptor.cc:822`). На стенде — на каждом
    редиректе запроса к API, с перехватом стадии ответа и без, с
    `continueResponse` и с `fulfillRequest` (`site-redirect*`, 0 из 3).
    Поэтому редирект запроса к API не исполняется вообще: ответ 3xx уходит
    странице конечным, без `Location`, движок получает адрес редиректа.
    Запросы к статике и CDN перехватываются только на стадии запроса: если
    сайт шлёт туда запросы с preflight и они редиректятся, служба сети
    упадёт, а проверка здоровья перезапустит браузер. Счётчик таких
    перезапусков — на тестовом аккаунте.
24. **Ответ, тело которого страница не читает, для CDP не кончается.**
    `fetch()` без чтения тела: `loadingFinished` нет, операция ждёт свой
    предел 21 с (репетиция движка теста). По пределу соединения к API
    рвутся: тело, которое ещё идёт, не накладывается на следующую операцию
    (`slow-body-limit`). Клиент Fansly (Angular, `XMLHttpRequest`) тела
    читает.
25. **Прежнее окно «объявление + 5 мс тишины» под нагрузкой держало сам
    допущенный запрос** (`expiry-hub-socks` на `8be717db`: 60 прогонов не в
    счёт, пока на маке шла сборка образа). Chrome записал заголовки запроса
    позже 5 мс после преамбулы — окно уже закрылось, запрос ждал 20 с.
    Бюджет записей от времени не зависит.
    Поправка: главная причина прогонов «не в счёт» в этом сценарии была
    другая и осталась после бюджета. На `d9895c0e` их 57, и сценарий не
    набрал 50 зачётных (45). Каждый второй прогон начинался с отказа
    первого запроса: предыдущий оставлял недоустановленное соединение
    (п. 32), потому что запрос Hub отменялся за секунду до срока (п. 34).
26. **Репетиция движка теста на стенде.** Страница сама делает запросы
    (загрузка, сокет, вход, опрос). По журналу сервера стенда между началами
    соседних операций — не меньше 2 575 мс при паузе 2 500; ответ 429
    останавливает сессию за 20 мс (после него к серверу не пришло ничего);
    `restart` возвращает страницу. Запрос Hub по `XMLHttpRequest` с
    заголовками сессии сайта совпадает с запросом сайта по набору и порядку
    заголовков (`xhr-parity`).
28. **Ответ на команду CDP и события, которые она вызывает, приходят в любом
    порядке** (`body-capture` на `d9895c0e`, 19 из 20). Оператор отменял
    ответ Hub больше лимита (`Fetch.failRequest`) и ждал ответа на команду,
    а `Network.loadingFailed` той же отмены успевал раньше: операция
    закрывалась как «ошибка транспорта», а не «превышен размер». Сама отмена
    срабатывала в обоих порядках, тело не скачивалось. То же место — у
    редиректа (`Fetch.fulfillRequest` → `loadingFinished`): движок получил бы
    302 без адреса; на стенде этот порядок ни разу не выпал. Исправление:
    исход физического запроса решается до команды, а не после её ответа.
    Проверка — ручка стенда `cdpReplyDelayMs` (ответы на команды оператор
    получает позже событий): без исправления `body-capture`, `hub-redirect`
    и `site-redirect` падают 3 из 3, с ним проходят. С этой задержкой
    (100 мс) прогнаны ещё 28 сценариев по 3 прогона — других таких мест не
    нашлось; в серии это часть G.
29. **Срок допуска: остальные случаи плана** (§4.2, шаг 4). Допуск кончается,
    а запрос ещё не записан, потому что:
    - TLS-рукопожатие зависло на открытом туннеле (`expiry-*-tls`);
    - соединение HTTP/2 тёплое, но служба сети Chrome стоит (`SIGSTOP`) и
      пишет запрос после срока (`expiry-*-reused`);
    - стоит сам оператор — отправитель: и после того, как отпустил запрос
      (`expiry-site-operator-stop`), и до того, как прочёл допуск
      (`expiry-*-late-grant`: срок — момент, а не остаток от чтения);
    - стоит процесс страницы (`expiry-hub-page-stop`).

    С «воротами» не уходит ничего. Без них (контрольные прогоны) запрос
    приходит через 1,5–3 с после срока. Прогон идёт в счёт, только если
    помеха сработала: задержка применена сервером стенда, окно «ворот»
    дошло до срока с неотправленным запросом, запрос не пришёл вовсе.
30. **408 на повторно использованном соединении HTTP/1.1** (`retry-408`,
    хост API на время сценария отдаёт только `http/1.1`). Chrome 155
    повторяет запрос по новому соединению: без «ворот» на сервер приходят
    два запроса на один допуск. С «воротами» повтор упирается в отказ в
    новом туннеле, приходит один.
31. **Признак «отправлено» в результате операции — слово CDP**
    (`requestWillBeSentExtraInfo`), а не отправителя. «Ворота» знают точнее:
    ушли ли записи запроса. В Hub признак берётся у «ворот» (этап 3). Чем
    это было опасно в прототипе — п. 34.
32. **После операции, которая кончилась раньше, чем установилось её новое
    соединение, следующая операция может не уйти** (пробная серия
    `expiry-hub-page-stop`: каждый второй прогон начинался с отказа первого
    запроса, 8 из 16). Chrome не бросает подключение отменённого запроса.
    Оно доустанавливается, когда окно уже закрыто, и его ClientHello
    задерживается. К следующему окну «ворота» рвут такой туннель, Chrome тут
    же подключается снова (повтор рукопожатия после обрыва) и занимает
    единственное место нового туннеля в окне; соединению самого допущенного
    запроса достаётся отказ. Запрос не уходит, страница видит обычную ошибку
    сети; следующий проходит. Пока прежний запрос действительно отменён,
    страдает только доступность. Если он жив — это уже отправка по чужому
    допуску (п. 34). Исправление для этапа 3: туннель, открытый для окна,
    рвётся вместе с окном, если запрос по нему не пошёл. На стенде каждый
    прогон начинается без соединений к API.
33. **Сто запусков Chrome короче 10 с — и расширение с правилами больше не
    ставится** (серия на `dd4efbb2`: `loss-operator-kill-inflight` и
    `loss-cdp-break-late-inflight`, по одному провалу — оба на сотом
    перезапуске Chrome свежего стенда). Chrome записывает установку
    расширения в настройки профиля примерно через 10 с, а лишние каталоги
    версий убирает через 30 с после запуска. Если его убивают раньше, каждый
    запуск ставит расширение заново в новый каталог (`1.0.0_0`, `_1`, …). На
    сотом каталоге установка отказывает: «Could not find a home for
    extension». Самопроверка не проходит, выход не открывается — страница
    закрыта, но сама не восстанавливается. Исправление: перед каждым
    запуском Chrome супервизор удаляет каталоги версий, которых нет в
    настройках профиля, — то же, что сделал бы сам Chrome. Каталог,
    записанный в настройках, не трогается: повторной установки нет. Версия,
    ждущая установки (`idle_install_info`), тоже остаётся. Если файл настроек
    есть, но не читается, не удаляется ничего.
34. **Отмена запроса Hub из страницы за секунду до срока убрана** (ревью
    Astra 6, п. 1). Это был кандидат плана (§4.2, шаг 4). Оператор не мог
    узнать, исполнилась ли отмена: через полсекунды он сообщал движку «конец,
    не отправлено». Если страница в этот момент висела, запрос оставался жив.
    Движок выдавал следующий допуск, и прежний запрос уходил в его окне.
    На стенде (`next-admission-expired`, `next-admission-slow`, прежний
    оператор, 2 из 2 в каждом): первый запрос пришёл на сервер через
    2,0–2,4 с после своего срока, а допущенный второй не пришёл вовсе. Теперь
    срок держат одни «ворота»: к сроку соединения к API рвутся, операция
    кончается, когда Chrome сообщил о конце запроса или вышел её предел. Те
    же сценарии на исправленном операторе проходят.
35. **Не исправлено в прототипе, задачи этапа 3** (ревью Astra 6, п. 2).
    - Предел операции (21 с) проверяет только её конец. Если исход уже
      решён, но ждёт записи файла тела или ответа на команду CDP, предел
      может объявить другой исход: тело «не снято» или редирект без адреса.
    - Предел тела запроса Hub при приёме: оператор просит страницу отменить
      запрос и сразу объявляет конец. Передача может ещё идти. Надёжнее —
      рвать соединение, как делает предел операции.

    В пилоте тела не снимаются: второй путь выключен, запись файла тоже.
    Редирект, ответ на который придёт ровно на 21-й секунде, достижим и
    без снятия тел.
36. **Операция, конец которой Chrome не подтвердил за её предел,
    останавливает страницу** (`stale-after-limit`). Служба сети Chrome
    стояла (`SIGSTOP`) 25 с с уже отпущенным запросом. К сроку «ворота»
    порвали соединения, на 21-й секунде вышел предел операции, и оператор
    объявлял её конец. Движок выдавал следующий допуск, служба сети оживала
    и писала прежний запрос в его окне: на сервер он приходил через 10 с
    после своего срока (2 из 2), а допущенный не приходил. «Ворота» не
    отличают один запрос от другого. Теперь, если к пределу нет ни ответа,
    ни сообщения Chrome о конце запроса, страница останавливается: выход
    закрыт, Chrome завершается, запрос умирает вместе с ним (4 из 4 — не
    пришло ничего). Ответ, тело которого идёт дольше предела, по-прежнему
    просто обрывается: запрос уже отправлен.
37. **Страница отменила выпущенный запрос до ответа — страница
    останавливается** (ревью Astra 7, п. 1; `cancel-next-admission`,
    `cancel-next-admission-pending`). Отмена — слово страницы: она бросает
    запрос сразу, а служба сети Chrome узнаёт об этом отдельно. Если та в
    этот миг стоит, запрос у неё ещё жив и мог бы уйти в окне следующего
    допуска. На стенде Chrome 155 отменённый запрос не записал и без
    остановки (6 из 6: и на тёплом соединении, и пока новое
    устанавливалось). Но доказать это снаружи нельзя, поэтому правило
    строгое: отмена до ответа → выход закрыт, Chrome завершается сам (через
    5 с убивается), страница стоит до `restart`. Ответ считается пришедшим,
    когда его заголовки дошли до браузера, а не до страницы. Цена: навигация
    сайта в момент, когда выпущенный запрос ещё в пути, останавливает
    страницу. Как часто это бывает на живом сайте, покажет пилот; для Hub
    это решение владельца №16.

    Вход после такой остановки может не сохраниться (ревью Astra 8): по
    `SIGTERM` Chrome записывает настройки, но не обязательно localStorage,
    где сайт держит сессию. Чтобы на это полагаться, нужно обычное
    завершение браузера с ожиданием и проверка меткой в хранилище —
    этап 3. В пилоте остановка после входа заканчивает сессию.
38. **Движок пилота после перезапуска Chrome не замечал запросы с прежними
    номерами** (ревью Astra 7, п. 2). Chrome нумерует задержанные запросы с
    начала при каждом запуске, а движок помнил номера вечно: новые запросы
    под старыми номерами ждали до таймаута. Репетиция
    (`stand/live/rehearse.mjs`: стоп, `restart`, сайт сам шлёт запросы):
    прежний движок — 1 ответ за 16 с после перезапуска, исправленный — 5,
    запрос Hub проходит.
    Теперь по сообщению оператора о новом запуске Chrome движок забывает
    номера и ожидавшие запросы прежнего; паузы и счёт за час остаются.

    Та же репетиция с убитым Chrome показала: на один обрыв CDP оператор
    шлёт две тревоги (сокет CDP, затем связь с держателем). Правило движка
    «два обрыва за 10 минут» срабатывало на первом же. Правило сделано
    явным: первая сессия останавливается на любом обрыве CDP, страницу
    возвращает только `restart` владельца. Шесть шагов репетиции проходят:
    запросы идут; Chrome убит — сессия стоит, ничего не уходит; `restart` —
    запросы идут (5 за 16 с); `/stop` — ничего; `restart` — запросы идут;
    запрос Hub — 200. Между началами операций не меньше 2 519 мс.
39. **Ответ на `hello` шёл после повторных запросов допуска.** При
    подключении движка оператор сначала заново спрашивал допуски ждущих
    запросов сайта и только потом отвечал на `hello` (репетиция: движок
    принял это за отказ). Теперь ответ на `hello` идёт первым.

40. **Остаток решения №10 случился на стенде** (итоговая серия на
    `87d024e1`, часть G — ответы CDP приходят на 100 мс позже;
    `loss-cdp-break-late-inflight`, 19 из 20). Оператор в этом сценарии
    нарочно реагирует на обрыв на 300 мс позже: держат одни «ворота». Обрыв
    CDP пришёлся на миг, когда окно основного запроса допущенной операции
    уже открылось, а сам запрос ещё не был записан: команда
    `Fetch.continueRequest` до Chrome не дошла, связь уже оборвалась.
    Отсоединяясь, Chrome отпустил все задержанные запросы. Первым записался
    preflight (OPTIONS) другого задержанного запроса сайта, на соединении
    без учётных данных, — и занял окно. Допущенный запрос и остальные
    задержаны. На сервер пришёл один OPTIONS без допуска, через 3 мс после
    обрыва. Это остаток, описанный с первого ревью (Astra 1, п. 4; запасное
    правило №10): уходит не больше одного уже задержанного запроса, и только
    тот, что пропускает расширение. В остальных сценариях потери управления
    серии такого не было.

    Замер на том же коде, по 100 прогонов, запрос в пути при обрыве CDP:
    - держат одни «ворота» (оператор нарочно реагирует на 300 мс позже):
      1 утечка из 100, и 1 из 100 при ответах CDP на 100 мс позже;
    - оператор реагирует сразу, как в жизни: 0 из 100 и 0 из 100.

    Вместе с серией: держат одни «ворота» — 3 утечки на 270 прогонов, обычная
    реакция — 0 на 250. Каждый раз уходил один preflight уже задержанного
    чтения, через 3–7 мс после обрыва.

    Тревога об обрыве в прототипе берёт фазу «ворот» в миг, когда оператор
    узнал об обрыве. Окно к этому мгновению может быть уже занято, фаза —
    «держит», и тревога скажет, что окна не было. В замере так и вышло: из
    двух утечек тревога сказала «окно было открыто» в одной, «не было» — в
    другой. Исправление — этап 3:
    тревога говорит «мог уйти чужой запрос», пока движок не получил
    подтверждения, что ушёл допущенный.

## Подтверждено

- После отключения CDP Chrome отпускает все задержанные запросы
  (`loss-cdp-break-late-nogate`: 5 из 5 ушли через 7–13 мс).
- Подмена хоста в `Fetch.continueRequest` (запрос Hub выпускается с
  недостижимого хоста `<хост>.pb-hold.invalid`, оператор при допуске ставит
  настоящий) серверу не видна: набор и порядок заголовков запроса Hub и
  запроса сайта совпадают, включая `sec-fetch-*`, `origin`, `referer`.
- Момент отправки из Chrome (`1000 × requestTime + sendStart`) — на
  `CLOCK_MONOTONIC`; расхождение с прибытием на сервер 0,2–1,6 мс.
- Скрипт `Page.addScriptToEvaluateOnNewDocument` успевает в свежий
  `about:blank`-фрейм, созданный скриптом страницы. (`ws-blank-iframe`)
- Сборка мусора не отменяет `fetch` Hub (ссылка на него держится из
  глобального объекта изолированного мира). (`hub-gc-body`)
- Тела ответов снимаются полностью потоком на диск (`Fetch` на стадии
  ответа → `Network.streamResourceContent` → `Network.dataReceived` с
  данными): gzip, Brotli, chunked, медленные, 304 из кэша (источник —
  `revalidated_304` по `responseReceivedExtraInfo`), 40 МБ; SHA-256 каждой
  копии совпадает с тем, что прочитала страница. Десять ответов по 15 МБ
  подряд (больше буфера Chrome в 100 МБ) при операторе, отстающем на 300 мс,
  — тоже целиком. Предел запроса Hub держится и по заявленному размеру (до
  тела), и по мере приёма (chunked). (`body-capture`, `body-burst`)
- Кадры сокета из CDP — все и по порядку: 1 000 подряд, 200 после
  переподключения, 100 из воркера. (`ws-frames`)
- Правила расширения без оператора: прочтение, typing, статус и любые
  неизвестные записи отменяются и при отключённом операторе (он отпускает
  всё без спроса), операция входа проходит, страница не достаёт до
  `localhost` и частных адресов. (`rules`, `rules-bypass`)
- Окружение: часовой пояс, язык, геолокация и экран совпадают с заданными;
  `navigator.webdriver` — false; ядра и память — сервера. (`site.environment`)

## Артефакты стенда (не свойства Chrome)

- Задержка ≈ 37 мс у второго запроса нового соединения — алгоритм Нейгла в
  SOCKS-ретрансляторе сервера стенда; выключен (`noDelay`).
- После обрыва соединений к API Chrome может сразу открыть новое сам, без
  запроса (своё задание подключения). С «воротами» оно получает отказ; в
  контрольных прогонах без «ворот» проходило и «грело» соединение — задержка
  сценария не срабатывала. Сценарии с холодным соединением рвут соединения,
  пока они не перестанут возвращаться (`coldApi`).
- `ws-h2`: после `location.reload()` готовность проверялась по старому
  документу — один прогон серии на `d9895c0e` не в счёт (страница
  перезагружалась в момент команды). Сценарий теперь ждёт новый документ по
  метке в адресе, как остальные.
