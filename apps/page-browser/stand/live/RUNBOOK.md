# Тест на тестовом аккаунте Fansly — этап 1, пп. 4–17

Прототип, не Hub. Одна страница: контейнер браузера с профилем Fansly и тестовый движок (`engine.ts`) с паузой Fansly. Запускается вручную на маке владельца, не в CI. Перед первым запуском — ревью Astra max (план §5).

## Что нужно от владельца

- Тестовый аккаунт Fansly (решение №13): лучше креаторский. Логин, пароль и 2FA — в 1Password.
- Тестовый прокси SOCKS5, не из прокси рабочих страниц: хост, порт, логин, пароль, выходной IP, регион — в 1Password.
- Присутствие на время входа: вход делает только владелец, на экране страницы (KasmVNC).

Секреты читаются через `op` в окружение запуска. В файлы, журналы и чат они не попадают.

## Образ

```sh
docker build --build-context chrome=$HOME/code/.cache/page-browser/chrome \
  --build-context kasmvnc=$HOME/code/.cache/page-browser/kasmvnc \
  --build-arg PROFILE=fansly -t pb-browser:fansly apps/page-browser
```

Профиль `fansly` ставит правила расширения из `extension/profiles/fansly.json` (`node extension/build-rules.mjs fansly`):

- «никогда» — прочтения, typing, статус, лайки, аккаунт, деньги, 2FA, пароль, сессии, управление, выход;
- разрешены только записи входа: `/login`, `/login/twofa`, `/login/email*`, `/email-challenge/v1/*`;
- любые другие записи на `*.fansly.com` запрещены, сокет `chatws` закрыт.

## Запуск

```sh
cd apps/page-browser/stand/live
export PB_SOCKS_HOST=$(op read "op://<сейф>/<прокси>/host")   # и так же порт, логин, пароль
export PB_PINNED_IP=…   # выходной IP прокси
export PB_TZ=…          # часовой пояс региона прокси; PB_LANG, PB_GEO — по нему же
export PB_RPC_TOKEN=$(openssl rand -hex 24)
export PB_VNC_PASSWORD=$(openssl rand -base64 18); printf %s "$PB_VNC_PASSWORD" | pbcopy
docker compose -p pb-live up -d
```

Порядок старта (план §4.1): выход закрыт → самопроверка (выход, правила, ядро) → проверка выходного IP → выход открыт → сайт. Если IP не совпал или самопроверка не прошла, выход не открывается.

## Ход теста

1. **Старт.** `docker exec pb-live-engine-1 node -e "fetch('http://127.0.0.1:7801/status').then(r=>r.text()).then(console.log)"`. Проверить: состояние `ready`, самопроверка пройдена, IP совпал.
2. **Вход.** Владелец открывает `http://127.0.0.1:16901` (пользователь `owner`, пароль в буфере обмена), входит и вводит код 2FA. Движок пропускает запросы сайта с паузой; расширение пропускает только записи входа. Незнакомый экран (капча, проверка) — стоп, решает владелец.
3. **Проверка аккаунта.** Запрос Hub `GET /api/v1/account/me` через `POST /hub`; ID аккаунта сверяет владелец.
4. **Спокойная вкладка, 30–60 минут.** Журнал (`stand/results/live-*.jsonl`) даёт:
   - запросы сайта в час и по маршрутам (п. 10);
   - типы сообщений сокета, исходящие и входящие (пп. 5, 9);
   - отчёты обёртки сокета о задержанных сообщениях (п. 9);
   - события «ворот» (п. 2 стенда на настоящем сайте).
   Ресурсы — `docker stats pb-live-browser-1` (п. 13).
5. **Запросы Hub.** Несколько GET по маршрутам каталога. Набор и порядок заголовков Hub и сайта — события `headers` (п. 15). Тела — в `/data/buffer/bodies` контейнера (п. 17).
6. **Перезапуск.** `docker compose -p pb-live restart browser`: окружение и «устройство» те же (пп. 11, 16), сессия жива.

Медиа CDN запросами Hub на этом шаге не трогаем: «ворота» на хостах CDN — этап 3 (ревью Astra, п. 6).

## Стоп сразу

- 429 от Fansly — движок сам ставит всё на паузу;
- капча или незнакомый экран входа;
- тревоги `halted`, `client_check_mismatch`, повторные `cdp_lost`;
- аккаунт или выходной IP не те.

Сначала воспроизводим на стенде, потом продолжаем.

## После теста

```sh
docker compose -p pb-live down -v   # профиль с сессией и снятые тела удаляются
```

Журнал без секретов остаётся в `stand/results/` (в git не попадает).
