# Тест на тестовом аккаунте Fansly — этап 1, пп. 4–17

Прототип, не Hub. Одна страница: контейнер браузера с профилем Fansly и тестовый движок (`engine.ts`). Запускается вручную на маке владельца, не в CI. Перед первым запуском — ревью Astra max (план §5); пока оно не «зелёное», тест не начинается.

## Что нужно от владельца

- Тестовый аккаунт Fansly (решение №13): лучше креаторский. Логин, пароль и 2FA — в 1Password.
- Тестовый прокси SOCKS5, не из прокси рабочих страниц: хост, порт, логин, пароль, выходной IP, регион — в 1Password.
- Присутствие на время входа: вход делает только владелец, на экране страницы (KasmVNC). Автоматического повтора входа нет.

Секреты читаются через `op` в окружение запуска. В файлы, журналы и чат они не попадают.

## Образ

```sh
docker build --build-context chrome=$HOME/code/.cache/page-browser/chrome \
  --build-context kasmvnc=$HOME/code/.cache/page-browser/kasmvnc \
  --build-arg PROFILE=fansly -t pb-browser:fansly apps/page-browser
```

Правила расширения — `extension/profiles/fansly.json` (`node extension/build-rules.mjs fansly`):

- «никогда»: прочтения, typing, статус, лайки, аккаунт, деньги, 2FA, пароль, сессии, управление, выход; любым методом — отписка по ссылке, проверка NSFW, авторизации Intercom и Zendesk;
- из записей разрешён только вход: `/login`, `/login/twofa`, `/login/email*`, `/email-challenge/v1/*`;
- любые другие записи на `*.fansly.com` запрещены, сокет `chatws` закрыт.

## Первая сессия — узко

Что включено:

- вход владельца;
- одно чтение Hub для сверки аккаунта: `GET /api/v1/account/me` — единственный путь, который принимает движок;
- спокойная вкладка.

Что выключено: тела ответов не пишутся (`PB_CAPTURE_BODIES=0`), других запросов Hub нет, медиа нет, перезапусков нет.

Страница запускается только командой `restart`. После любой остановки, после перезапуска контейнера или оператора она стоит, пока владелец снова не скажет `restart`. На диске это нигде не хранится — сбой файловой системы не может превратить остановку в запуск.

Страница останавливается (выход закрыт), если:

- пришёл 429 — на запрос, на preflight или на рукопожатие сокета;
- рукопожатие сокета не удалось;
- сайт пытается отправить неизвестное сообщение сокета (оно не уходит; в журнале — его тип и имена ключей);
- не удалось поставить обёртку или перехват;
- `fansly-client-check` сайта не совпал с нашим;
- операция не закончилась за 25 с (рукопожатие сокета — за 15 с). Ответ, тело которого идёт дольше 21 с, обрывается: соединение к API рвётся, и только потом идёт следующая операция;
- CDP потерян дважды за 10 минут;
- пропала связь с движком теста.

Пауза между операциями: следующая начинается не раньше 2,5 с (+0–20 %) после **конца** предыдущей. Одна операция в полёте; рукопожатие сокета — тоже операция, до ответа сервера.

Тело запроса — не больше 16 КБ: на первом этапе это только вход. Если сервер успеет что-то прислать между частями входа (заголовки, тело), остаток не уйдёт: вход может уйти частично и не состояться, сам он не повторится. Нажимать «Войти» ещё раз — только когда сайт показал ошибку: значит, прежняя попытка закончилась (через 20 с соединение рвётся). Это решение №1б.

## Запуск

```sh
cd apps/page-browser/stand/live
export PB_SOCKS_HOST=$(op read "op://<сейф>/<прокси>/host")   # и так же порт, логин, пароль
export PB_PINNED_IP=…   # выходной IP прокси
export PB_TZ=…          # часовой пояс региона прокси; PB_LANG, PB_GEO — по нему же
export PB_RPC_TOKEN=$(openssl rand -hex 24)
export PB_VNC_PASSWORD=$(openssl rand -base64 18); printf %s "$PB_VNC_PASSWORD" | pbcopy
docker compose -p pb-live up -d
```

Управление (из контейнера движка):

```sh
c() { docker exec pb-live-engine-1 node -e "fetch('http://127.0.0.1:7801$1',{method:'$2',...(process.argv[1]?{body:process.argv[1]}:{})}).then(r=>r.text()).then(console.log)" "${3:-}"; }
c /status GET
c /command POST '{"name":"restart"}'   # запуск страницы
c /stop POST                            # остановить: выход закрыт до restart
c /hub POST '{"path":"/api/v1/account/me"}'
```

После `up` страница стоит. Старт — только командой `restart`; после перезапуска контейнера или оператора — тоже.

Если движок теста упал или потерял связь, страница останавливается сама. Продолжение: `docker compose -p pb-live up -d engine`, затем `restart`.

## Ход

1. **Проверки до входа.** После `restart`: состояние `ready`, самопроверка пройдена (выход, правила, ядро), выходной IP совпал, экран KasmVNC открывается только с паролем. Проверить `/stop` и `restart` один раз до входа.
2. **Вход.** Владелец открывает `http://127.0.0.1:16901` (пользователь `owner`, пароль в буфере обмена), входит и вводит код 2FA. Незнакомый экран (капча, проверка) — стоп, решает владелец.
3. **Сверка аккаунта.** `c /hub POST '{"path":"/api/v1/account/me"}'` возвращает ID и имя аккаунта (в журнал они не пишутся). Владелец сверяет их с ожидаемыми; не совпало — `/stop`.
4. **Спокойная вкладка.** Сначала 10–15 минут. Если чисто — до часа. Журнал (`stand/results/live-*.jsonl`) даёт:
   - запросы сайта по маршрутам и в час (п. 10);
   - сообщения сокета по типам (пп. 5, 9);
   - события «ворот»;
   - имена заголовков запросов сайта и Hub (п. 15).
   Ресурсы — `docker stats pb-live-browser-1` (п. 13).

Позже, отдельными сессиями: тела ответов (п. 17, с белым списком путей), другие чтения Hub, перезапуск (пп. 11, 16), медиа (после «ворот» на CDN, этап 3).

## После теста

```sh
docker compose -p pb-live down -v   # профиль с сессией удаляется
```

Журнал без секретов остаётся в `stand/results/` (в git не попадает).
