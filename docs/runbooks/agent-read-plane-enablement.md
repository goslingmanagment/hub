# Runbook — включение Agent Read Plane на проде

Составлен 2026-08-01 по итогам сборки семи слайсов. Все шаги owner-gated.
Плоскость спроектирована так, что **после деплоя она полностью выключена** и
не влияет ни на один существующий путь: агентских ключей не выпущено, ни один
клиент не знает новых операций.

**Инертность держится на ОДНОМ флаге — `agentReadPlaneMode=off`.** Пока он в
`off`, каждый агентский роут отвечает 503 `agent_plane_disabled` до того, как
прочитает любую другую настройку, поэтому значения остальных флагов в этот
момент ни на что не влияют. Формулировка «все семь стоят в `off`/`false`» была
бы неверной буквально: `agentSearchBackend` по умолчанию `fts` (поиск включён,
но недостижим за выключенной плоскостью), а `agentExportPolicyValue` — не
булев флаг, а строка-заглушка `no_raw_transcript_export_endpoint_yet`, которую
клиентам и надо отдавать сегодня (см. §5). Источник дефолтов —
`packages/shared/src/config-registry.ts`.

Связанные документы: `.agentic/agent-read-plane/PLAN.md` (что построено),
`.agentic/pipeline-agent-read-plane.md` (леджер: рулинги, прод-факты),
`docs/agent-read-skill.md` (как агент пользуется CLI),
`investigations/agent-read-api-design-2026-07-31.md` (архитектура).

## 0. Перед деплоем

1. **Проверить паузу тиринга.** До этого деплоя она держится удалением строки
   расписания pg-boss и слетает при каждом рестарте:
   ```sql
   select count(*) from pgboss.schedule where name='retention-tiering';
   ```
   Ноль — хорошо. После деплоя эта возня больше не нужна: появляется
   долговечный флаг `retentionTieringEnabled` с дефолтом **false**, и хендлер
   тиринга становится no-op независимо от расписания.
2. **Убедиться, что январские партиции на месте** (они и есть цель догрузки):
   ```sql
   select count(*) from pg_inherits
   where inhparent='domain_events'::regclass
     and inhrelid::regclass::text like '%2026_01%';
   ```
3. Снять бэкап по обычному ритуалу деплоя.

## 1. Деплой

Обычный `scripts/deploy-production.sh`. Новых внешних зависимостей нет.
Миграции: `0115` (ключи, аудит, поколение архива), `0116` (конкурентные
индексы, `CREATE INDEX CONCURRENTLY` вне транзакции), `0117` (заявки на
догрузку). Индексы строятся без ACCESS EXCLUSIVE — блокировок записи не будет.

**После деплоя проверить, что ничего не включилось:**
```sql
select key, value from config_settings
where key in ('agentReadPlaneMode','agentObservationsEnabled','agentSearchBackend',
              'agentHydrationMode','agentExportPolicyValue','fanslyReplayMode',
              'retentionTieringEnabled');
```

**Пустой ответ — это НОРМА, а не ошибка.** `config_settings` хранит только
ПЕРЕОПРЕДЕЛЕНИЯ: у ключа, который никто не менял, строки нет вовсе, и работает
дефолт из реестра. Так что сразу после деплоя ожидаемый результат этого запроса
— ноль строк. Читать надо так: строки нет => действует значение из колонки
«дефолт»; строка есть => её `value` должен совпасть с дефолтом, иначе кто-то
уже флипал флаг.

| ключ | дефолт (инертное значение) |
|---|---|
| `agentReadPlaneMode` | `off` — **единственный, который держит плоскость выключенной** |
| `agentHydrationMode` | `off` |
| `agentObservationsEnabled` | `false` |
| `retentionTieringEnabled` | `false` |
| `fanslyReplayMode` | `off` |
| `agentSearchBackend` | `fts` (НЕ `off`; недостижим, пока плоскость в `off`) |
| `agentExportPolicyValue` | `no_raw_transcript_export_endpoint_yet` |

Живые значения целиком (дефолты плюс переопределения) видны в дашборде:
Settings → Configuration, подсистема Agent.

Проверить, что тиринг действительно не работает: дождаться 04:40 UTC и
убедиться, что партиции на месте, либо посмотреть лог хендлера — он должен
сообщить о пропуске по флагу.

## 2. Флаги — по одному, каждый со своим окном (ритуал #70)

Порядок выбран так, чтобы каждый следующий шаг опирался на проверенный
предыдущий. **Никогда не флипать два флага одной правкой.**

### 2a. `agentReadPlaneMode: off -> read_only`

Что происходит: операции начинают отвечать, но плоскость сознательно
консервативна — рампа. Ключей ещё нет, значит трафика нет; шаг проверяет
только то, что роуты поднялись и ничего не сломали.

Проверка: `/health` живой, `contractHash` совпадает с задеплоенным,
существующие клиенты (десктоп, расширение, дашборд) работают как раньше.
Откат: вернуть `off`.

### 2b. Выпустить первый агентский ключ

Дашборд → Settings → агентские ключи. Дать МИНИМУМ прав для первой задачи
(для разбора истории фана хватает `read:messages`; деньги — отдельным правом).
Сырой токен показывается **один раз** — сохранить в 1Password сразу.

Проверка (CLI не опубликован — запускается из чекаута; `HUB_AGENT_KEY` в
окружении, `HUB_BASE_URL` по умолчанию уже прод):

```
pnpm hub capabilities --pretty
pnpm hub threads --page-label lora-2 --limit 5 --pretty
```

Флаг именно `--page-label`: парсер строгий, неизвестный флаг — это отказ с
кодом 4, а не молча проигнорированный фильтр. Оба вызова должны отдать ровно
один JSON-документ; `blockers` в нём будет НЕпустым (`claim_not_declared`) —
это норма, а не поломка, и код возврата всё равно 0. Убедиться, что ключ **не**
проходит никуда, кроме `/api/v1/agent/*` (изоляция запинена тестами, но одна
ручная проверка на живом стенде не повредит).
Откат: revoke ключа — мгновенный.

### 2c. `agentReadPlaneMode: read_only -> full`

Только после суток без расхождений на 2b.
Откат: вернуть `read_only`.

### 2d. `agentSearchBackend` и `agentObservationsEnabled` — по потребности

Поиск уже работает в `fts`. `agentObservationsEnabled` открывает журнальные
операции (9a/9b) — включать только когда понадобится форензика; 9b отдаёт
сырые вендорные payload'ы владельцу и имеет суточный потолок 25.

### Fansly: запрос истории у движка синхронизации

Старая целевая догрузка треда (owner-CLI `dm backfill-thread`, очередь
`sync.thread.backfill`) и Fansly-линия исполнителя заявок удалены на шаге 4
(S4-15): каждая страница Fansly читается движком синхронизации Fansly, и
старую переписку он читает только по запросу истории.

Владелец просит историю напрямую:

```
docker exec agency-hub-api-1 node /app/apps/runtime/dist/cli.js sync history request \
  --page lora-2 --conversation 810272281019305984 --all --reason "январь Рика"
docker exec agency-hub-api-1 node /app/apps/runtime/dist/cli.js sync history status <ref>
```

`--all` — весь чат, доказанный пустой страницей; `--latest <n>` — последние N
сообщений. Запрос идёт в общем темпе страницы и не требует решения владельца.

Агент подаёт заявку по HTTP (команды в `hub` для этого нет):
`POST /api/v1/agent/pages/lora-2/threads/810272281019305984/hydration-requests`
с `target.kind = thread_backfill_before` и ровно одной границей (`beforeAt`
либо `beforeMessageRef`), текстовой `reason` и UUID `idempotencyKey`. Пока
`agentHydrationMode=off`, роут отвечает 503 `agent_plane_disabled`. На
странице Fansly заявка сразу становится запросом истории на один чат: строка
заявки — `dispatching` с линией `fansly_sync_engine` и ссылкой на запрос, её
чтение отражает состояние запроса, а цикл гидрации закрывает её, когда запрос
завершён (`completed` — дочитано до пустой страницы, `partially_completed` —
до границы, `failed` — чат отклонён или заблокирован, `expired` — запрос
отменён). Решение владельца по такой заявке не принимается (409
`engine_managed`), а аппрув Fansly-заявки, которую движок не взял, отвергается
(409 `hydration_not_admissible`): исполнителя для него нет.

Проверка после чтения:
```sql
select min(occurred_at), max(occurred_at), count(*) filter (where occurred_at >= '2026-01-01' and occurred_at < '2026-02-01') as jan
from message_archive where account_id = 2 and platform = 'fansly' and conversation_ref = '810272281019305984';
```
Ожидание: `jan` > 0 и `min(occurred_at)` уехал раньше 2026-02-21.

### OnlyFans: заявка и решение владельца (слайс C)

Флаг здесь двухступенчатый, и это не мелочь: **`request_only`** позволяет
подать и решить заявку, но НИЧЕГО не исполняет; **`dispatch`** — исполнитель
начинает разбирать аппрувы. Промежуточная ступень и есть безопасный способ
попробовать путь: заявка подаётся, владелец видит её в очереди, вендор при
этом не трогается вообще.

Агент подаёт заявку тем же роутом; ответ — **200, а не 202**: заявка
зафиксирована, работа НЕ поставлена.

Владелец решает в дашборде (страница Agent hydration; там же чекбокс согласия
на побочный эффект «пометить прочитанным») или тем же кодом из owner-CLI:

```
docker exec agency-hub-api-1 node /app/apps/runtime/dist/cli.js agent hydration list --state requested
docker exec agency-hub-api-1 node /app/apps/runtime/dist/cli.js agent hydration decide \
  --request <requestRef> --decision approve --expected-version <rowVersion> \
  --coverage-fingerprint <тот, что был ПОКАЗАН> \
  --max-calls 20 --max-credits 1 --max-pages 20 --allow-mark-read
```

Аппрув обязан назвать ВСЕ три потолка (`--max-calls`, `--max-pages`,
`--max-credits`) и явно высказаться про побочный эффект «прочитано» (#158) —
контракт отвергает аппрув, где что-то из этого опущено. Чтение истории
OnlyFans помечает чат прочитанным, поэтому аппрув без согласия на этот эффект
отвергается, как и аппрув с `--max-credits` меньше 1.

Исполнитель создаёт задание захвата OFAPI (`ofapi_capture_jobs`) с потолками
аппрува. **Один аппрув — одна попытка к вендору**: упавший прогон не
переигрывается сам, нужно новое решение. Заявка закрывается по записи своего
задания (сверка каждые 2 минуты); `dispatching` дольше 6 часов без живого
задания закрывается как `failed` с `timeout`. Если покрытие треда сдвинулось,
пока аппрув ждал (`coverage_fingerprint` уже не совпадёт), он не исполняется и
истекает своим сроком.

Автопилот заявок (decision #202) удалён на шаге 4 (S4-15): он одобрял только
Fansly-догрузку, которой больше нет. Строки с `decision_source='auto_policy'` и
события `rearmed` остаются в журнале как история; настройки автопилота удалены
вместе с остальными настройками старого движка Fansly (S4-26).

## 4. Реплей Fansly (`fanslyReplayMode`)

`off -> shadow` — прогон считает и **ничего не пишет**; смотреть отчёт.
Только потом `shadow -> on`.

```
docker exec agency-hub-api-1 node /app/apps/runtime/dist/cli.js fansly:replay \
  --from 2026-01-01T00:00:00Z --to 2026-02-01T00:00:00Z --max-pages 5
```

Прогон резюмируемый и печатает отчёт JSON. Гоча shadow-режима: он ничего не
штампует, поэтому сам по себе дальше первой пачки не уедет — следующий запуск
должен получить `--after-id` из `coverage.nextAfterId` предыдущего отчёта.
Отказ (`refused`) и ошибки канонизации дают ненулевой код возврата.

Предполётная проверка внутри раннера откажет, если партиция, релевантная
диапазону реплея, отцеплена. **Известный прод-факт:** четыре запаркованные
партиции (`domain_events_2024_05|06`, `2025_11|12`) держат 30 строк
`transaction.posted` страницы `lilly-1` — они вне диапазона и вне типов
реплея, поэтому отказа не вызывают (ценз скоуплен по типу и диапазону).

## 5. Что ЗАБЛОКИРОВАНО до действия владельца

**Флип `agentExportPolicyValue`** на `agent_read_plane_v1` требует ре-вендора
SDK в двух клиентах — проверено загрузкой их рантайм-схем:

| клиент | вердикт на новое значение |
|---|---|
| `of-desktop` `packages/kernel-sdk` | отвергает |
| `fansly-ext` `vendor/kernel-sdk` | отвергает |
| дашборд (workspace SDK) | принимает |

Порядок: `node scripts/vendor-sdk.mjs ../onlyfans-chat/packages/kernel-sdk` и
`node scripts/vendor-sdk.mjs ../fansly-chat/vendor/kernel-sdk` → релиз обоих
клиентов → только потом флип значения. Сейчас отдаётся старое значение, всё
работает.

## 6. Откаты

| Что | Как |
|---|---|
| Любой флаг | вернуть прежнее значение в дашборде (живое применение) |
| Агентский ключ | revoke |
| Догрузка | нечего откатывать — она только ДОБАВЛЯЕТ захваченные факты |
| Реплей | события append-only; проекции аддитивны (двигают полы только назад) |
| Тиринг | вернуть `retentionTieringEnabled=true`, когда догрузка января закончена |

Ничто из перечисленного не удаляет данные: capture-first и запрет плановых
удалений действуют на весь новый код (пин `tests/retention-deleters.test.ts`).
