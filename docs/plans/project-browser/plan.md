## 1. Коротко

- У каждой страницы свой контейнер. В нём:
  - Google Chrome Stable с окном на виртуальном дисплее и постоянным профилем;
  - наш процесс-**оператор**;
  - экран KasmVNC.

  Входит владелец через форму в дашборде; экран нужен для незнакомых экранов Fansly и для диагностики.
- Оператор управляет Chrome по **CDP** — протоколу управления Chrome, тому же, что у DevTools. Он:
  - держит каждый HTTP-запрос браузера до допуска движка;
  - выполняет запросы Hub внутри вкладки сайта;
  - читает сокет, который открыл сам сайт;
  - хранит неподтверждённые данные в буфере на диске;
  - служит единственным выходом браузера в сеть. Это обеспечивают сетевые правила ОС, а не только настройка Chrome.
- Постоянные запреты — статические правила **DNR** (`declarativeNetRequest`, встроенная в Chrome блокировка запросов по шаблонам). Они лежат в расширении, которое ставится политикой, и действуют без оператора.
- В движке работы больше, чем одна замена транспорта:
  - путь допуска для запросов, которые движок не выбирал сам: запросов сайта и операций ручного входа;
  - приём буфера с подтверждениями и восстановлением;
  - подключение новой страницы через браузер;
  - переключение транспорта с откатом.
- Три требования Chrome без доработки не выполняет. Это **обязательные условия**: прототип должен показать, что каждое выполнимо. Если хоть одно невыполнимо, архитектуру пересматриваем вместе с владельцем до написания кода.
  1. Ни одной отправки без допуска, даже если управление пропало (обрыв CDP — §8 №10).
  2. Ни одного незаметного повтора запроса или отправки по просроченному допуску (если надёжной отмены по сроку нет — §8 №16).
  3. Запреты действуют и для сообщений сокета.
- Порядок работ: спецификация → прототип (сначала обязательные условия, §5) → проверка сбоями и общая нагрузка на стенде → интеграция → пилот на одной странице → остальные страницы.

## 2. Границы

Входит (первый этап требований):
- все текущие чтения движка по его реестру ресурсов, включая скачивание медиа для ИИ;
- события из сокета сайта;
- вход владельца с 2FA;
- подключение новой страницы.

Не входит:
- отправка сообщений, посты, отложенные публикации, Vault — второй этап, отдельный план;
- публичный поиск аккаунтов — остаётся отдельным каналом вне браузеров;
- OnlyFans.

## 3. Состав

### 3.1 На одну страницу — один контейнер

| Компонент | Что это | Чей код |
|---|---|---|
| Google Chrome Stable | Linux-сборка Google, версия закреплена в образе. Окно на виртуальном дисплее (сам KasmVNC или Xvfb — решит прототип). Профиль (`--user-data-dir`) на томе страницы, настройки — enterprise-политиками. CDP на фиксированном порту `127.0.0.1` внутри контейнера | Google |
| Оператор | Наш процесс на TypeScript. CDP-клиент через держателя, локальный прокси — единственный выход Chrome в сеть, буфер и журналы на томе страницы, RPC с движком | наш |
| Держатель CDP-соединения (кандидат, §4.1) | Простейший процесс без логики: держит соединение CDP с Chrome и пересылает сообщения оператору. Живёт дольше оператора; от самостоятельного обрыва CDP не защищает | наш, если прототип подтвердит |
| Расширение | MV3, ставится политикой `ExtensionSettings` (`force_installed`) из нашей CRX. Только статические правила DNR, без скриптов | наш (JSON) |
| Экран для владельца (запасной путь входа) | KasmVNC: веб-клиент по HTTPS/WebSocket, сжатие с подстройкой качества, общий буфер обмена. Открывается через дашборд Hub под входом владельца; браузеру дополнительного выхода в сеть не даёт (§4.8) | готовый |

Chrome и оператор работают от разных пользователей ОС. Сетевые правила ОС разрешают:
- Chrome — только локальный прокси оператора и нужные локальные службы;
- оператору — только SOCKS5 страницы.

Остальное запрещено (§4.5).

Тома названы по профилю, а не по странице: при подключении новой страницы готовый профиль привязывается к ней без копирования (§3.2). Связь «страница — профиль» хранит Hub (§3.4). Снимки профиля лежат на диске сервера рядом с томами |

На хосте в цепочке `DOCKER-USER` для этого адреса разрешены только IP и порт SOCKS5 его страницы. Сегодня в `docker-compose.production.yml` сетей нет, все сервисы в сети по умолчанию |

**Запуск Chrome.** Флаги: `--user-data-dir=/data/profile`, `--remote-debugging-port=9222`, `--window-size=1920,1080`, `--lang=<язык региона>`, `--no-first-run`. Часовой пояс задаёт переменная `TZ` процесса Chrome. С Chrome 136 порт отладки работает только с собственным `--user-data-dir`, а он у нас и так свой. Флагов автоматизации нет: `--enable-automation`, `--headless`, `--remote-debugging-pipe` и порт 0 включают `navigator.webdriver`, а `--disable-blink-features` вызывает предупреждение о неподдерживаемом флаге.

**Политики** (`/etc/opt/chrome/policies/managed/hub.json`; окончательный список — в спецификации, самопроверка сверяет применённые политики):
- сеть: `ProxySettings` → `127.0.0.1:3128`; `QuicAllowed: false`; `WebRtcIPHandling: disable_non_proxied_udp`; `NetworkPredictionOptions: 2` — без предзагрузки и предварительной отрисовки страниц, которые сделали бы лишние запросы;
- пароли: `PasswordManagerEnabled: false` — пароль из формы входа не сохраняется в профиле; `PasswordLeakDetectionEnabled: false` — хэши учётных данных не уходят в Google; автозаполнение выключено;
- аккаунт Google и фон: `BrowserSignin: 0`, `SyncDisabled: true`, `BackgroundModeEnabled: false`, `TranslateEnabled: false`, `DefaultNotificationsSetting: 2`, `DownloadRestrictions: 3` — браузер не сохраняет файлов, медиа Hub получает запросами из вкладки (§3.2);
- расширения: наше ставится через `ExtensionSettings` (`force_installed`), остальные запрещены (`"*"` → `blocked`);
- политики отладки (`RemoteDebuggingAllowed`, `DeveloperToolsAvailability`) её не запрещают: иначе порт CDP не откроется.

Новое приложение в монорепо — `apps/page-browser/` (название обсуждаемо), раскладка кода — §3.3.

### 3.2 В движке (`apps/runtime/src/sync/`) и рядом

- **Браузерный транспорт** — `fansly/browser-transport.ts`, `createBrowserPageTransport`. Реализует тот же `PageTransport` (`engine/ports.ts:192-209`), что и нынешний undici-транспорт: `prepare`, `send` — не больше одного физического запроса, `storedCredentialsGeneration`, `close`.
  - `prepare` строит запрос по реестру, как сейчас, но без заголовков, которые ставит сам Chrome (`user-agent`, `accept-encoding`, `sec-fetch-*`, `origin`, `referer`), и без заголовков сессии (`authorization`, `fansly-client-id`, `fansly-session-id`, `fansly-client-ts`, `fansly-client-check`). Их оператор берёт из живой сессии сайта в момент запроса (§4.7). Сегодня все они собираются в `buildFanslyRequestHeaders` (`packages/fansly/src/request-headers.ts`) из записанного HAR Firefox.
  - `send` — RPC `send`. Когда оператор присылает `check`, транспорт вызывает синхронный `hooks.check()` — ту же проверку, что сегодня срабатывает в undici `onRequestStart` (`packages/fansly/src/send-guard.ts:154-163`), — и возвращает результат с абсолютным сроком допуска.
  - Порт расширяется. Сегодня транспорт не знает ни ID попытки, ни срока: у него есть только `check()` (`engine/ports.ts:181-207`). `send` получает контекст допуска — ID попытки, поколение владельца, абсолютный срок по монотонным часам ядра.
  - Привязка к сессии. Во всех полях движка — одно значение поколения учётных данных: хэш страницы, account ID, отпечатка сессии браузера и прокси. Его ставит `prepare` в `credentialsGeneration` запроса — так же, как сегодня ставит хэш сохранённой сессии (`fansly/transport.ts:155-180`), — и его же возвращает `storedCredentialsGeneration`. Подтверждённая проверка личности записывает в `sync_pages.credentials_generation` поколение своей попытки (`engine/commit.ts:1709-1714`), а актор сравнивает с ним `storedCredentialsGeneration` (`engine/actor.ts:576-578`): разные представления здесь зациклили бы страницу в режиме «только проверки». Сам отпечаток сессии браузера идёт в RPC отдельным полем, для проверки у оператора. При `send` и `check` оператор сверяет с ним живую сессию. Сессия сменилась между подготовкой и отправкой — запрос не отпускается, исход `aborted_before_send`, дальше обычный `account.verify`. Ответ несёт отпечаток, с которым запрос ушёл; ответ чужой сессии новой не приписывается (требования).
  - Ответ превращается в существующий `TransportOutcome` (`packages/fansly/src/wire/types.ts:425-443`): `response` со статусом, заголовками (имена в нижнем регистре, повторы через `", "`, как сейчас), декодированным телом и `bodyBytes`; для медиа — `bodyBuffer` с прежним пределом 5 МиБ. Ошибка до начала отправки — `transport_error` с `sent: false`, после — с `sent: true`; отказ проверки — `aborted_before_send`. Недоступность оператора — отдельный класс ошибки: она не должна открывать сетевые остановки страницы, как ошибки Fansly.
  - Момент отправки. Сегодня его отмечает сама проверка (`engine/pacer.ts:270`). В браузере проверка идёт до соединения и preflight, поэтому ответ приносит фактический момент из Chrome, и `pacer.complete` переносит отметку на него — так же, как сегодня переносит её `completion_fallback` (`engine/pacer.ts:279-293`). Новое значение `send_mark` — `transport_reported`. Если момента нет — момент завершения.
  - `storedCredentialsGeneration` — то же поколение, что выше. Владелец вошёл заново или сменился прокси — поколение сменилось — существующий механизм запускает `account.verify` через браузер (`engine/actor.ts:296-312`).
  - RPC-клиент — `apps/runtime/src/services/egress/page-browser-rpc.ts`: ESLint разрешает сетевые импорты и WebSocket только в `services/egress`.
- **Выбор транспорта страницы.** Сегодня такого флага нет: `#liveTransport` всегда вызывает `createPageTransport` (`engine/host.ts:606-614`), и это закреплено тестами.
  - Новая колонка `sync_pages.transport`: `node` или `browser`, по умолчанию `node`. Хост читает её, когда берёт страницу (`#acquire`, `engine/host.ts:470-588`), и строит нужные транспорт и источник событий.
  - Переключение — смена колонки. Цикл режимов (раз в 2 с) завершает слот страницы (`#endSlot`: остановка сокета, закрытие транспорта, безопасное освобождение) и берёт её снова с новым транспортом. Новый слот — новое поколение владельца (`owner_generation`) и пауза не меньше 1,2 × S от последней отправки по журналу (`paceFloorFromDb`). Так переключение пользуется уже существующими правилами передачи страницы.
  - Команда CLI `sync page transport <страница> browser|node` записывается в аудит, как `sync page pause`.
- **Путь допуска для запросов, которые движок не выбирал сам.** Сейчас пейсер — единственный, кто даёт допуск, и выдаёт его только на работу, которую актор выбрал сам (`engine/pacer.ts`). Реестр маршрутов знает только GET (`fansly/routes.ts`), а пауза владельца закрывает ворота актора целиком (`engine/actor.ts`). Нужно:
  - очередь ожидающих запросов сайта с их ID. Источник истины — оператор: запросы стоят у него на паузе. После рестарта `sync` он присылает `siteAdmit` заново;
  - соответствие маршруту по методу и пути. Сегодня маршрут — это ID спецификации запроса (`fansly/routes.ts:214-217`), сопоставления адреса с маршрутом нет. Нужен `fansly/route-match.ts` по шаблонам путей реестра; пути, которых в реестре нет, идут в семейство `site` со своим бюджетом;
  - класс работ `site`. Сегодня цикл классов — 5:4:1 (срочное, заявки, плановое; `engine/scheduler.ts`). Предложение: один слот за цикл, пока у движка есть работа, и любой свободный слот, когда работы нет; плюс потолок в час. Числа — в спецификации, по замеру трафика сайта;
  - общие бюджеты маршрутов;
  - запись в журнал отправок, чтобы проверка паузы видела все отправки страницы. Отправки сайта и входа пишутся в тот же `sync_attempts` с новой колонкой `origin` (`engine`, `site`, `login`), классом `site` и пустым `work_id`. Тогда нижняя граница паузы при передаче страницы (`paceFloorFromDb`), часы маршрутов (`readRouteJournal`) и аудит паузы (`sync check live-hour`) видят все отправки без отдельного кода;
  - отчёт о завершении: статус, 429, `Retry-After` идут в остановки маршрутов тем же путём, что ответы движка (`engine/errors.ts:537-564`).

  Путь допуска сайта работает при любом транспорте страницы: движок подключается к оператору, как только у страницы есть контейнер. Поэтому вход владельца до переключения (этап 4) идёт через тот же пейсер, что и запросы Node-транспорта.

  Через этот же путь при паузе страницы проходят разрешённые операции ручного входа. Сегодня ворота актора закрывает и пауза владельца, и остановка по учётным данным после 401: под ней проходят только проверки личности (`engine/actor.ts:539-562`). Поэтому нужно узкое исключение: в режиме оператора «ручной вход» при `paused_all`, при остановке по учётным данным и в режиме «только проверки» (непроверенная сессия, `engine/actor.ts:296-312`) допускаются только операции входа и чтения экранов входа. Пауза, бюджеты, владение страницей и сетевые остановки при этом действуют. Обычная работа возобновляется только после проверки личности.
- **Приём буфера и восстановление.**
  - Устойчивые ID попыток и событий.
  - Привязка к исходным странице, сессии и поколению владельца страницы (`sync_pages.owner_generation` — растёт при каждом взятии страницы движком; в прежних ревизиях плана — «эпоха»).

## 4. Как работает

### 4.1 Запуск и готовность

Оператор проходит состояния строго по порядку. Любой сбой отправляет его в начало.

1. **Выход закрыт.** Прокси оператора отклоняет все соединения.
2. **Окружение страницы применено** по региону её прокси (требования, «Окружение браузера»):
   - часовой пояс — переменная `TZ` процесса Chrome; язык — флаг `--lang` и `intl.accept_languages` в начальных настройках профиля;
   - геолокация — `Emulation.setGeolocationOverride` в каждой новой цели до её запуска (шаг 4) и разрешение на неё для fansly.com (`Browser.grantPermissions`);
   - постоянные характеристики из образа и профиля: размер окна, шрифты, WebGL.

   Значения хранятся в настройках страницы в Hub и приходят оператору при подключении движка (§4.13). После перезапуска и после обновления Chrome оператор сверяет фактические значения в браузере: `Intl.DateTimeFormat().resolvedOptions().timeZone`, `navigator.languages`, геолокацию, разрешение экрана.
3. **Chrome запущен** с профилем страницы на пустой вкладке (`about:blank`), командой s6.
4. **Контроль подключён** — через держателя, одной сессией к browser-цели в режиме `flatten`:
   - `Fetch.enable` на browser-цели с шаблоном `*` на стадии запроса — перехват всех загрузчиков всех вкладок, воркеров и service worker. Стадия ответа включается только для запросов Hub — через `interceptResponse` в `Fetch.continueRequest` (§4.2);
   - `Target.setAutoAttach` (`autoAttach`, `waitForDebuggerOnStart`, `flatten`) на browser-цели и затем в каждой вкладке — для её воркеров и фреймов из других процессов. Каждая новая цель стоит на паузе, пока оператор не выполнит в ней настройку и `Runtime.runIfWaitingForDebugger`;
   - в каждой вкладке и каждом воркере: `Network.enable` — для кадров сокета, времени отправки и тел ответов сайта; `Page.addScriptToEvaluateOnNewDocument` — проверка сокета (§4.3) до кода сайта; переопределение геолокации;
   - в воркерах — та же проверка сокета через `Runtime.evaluate` до снятия паузы.
5. **Самопроверка при закрытом выходе.** Каждый защитный механизм проверяется отдельно, и по ответу видно, какой именно остановил запрос:
   - расширение отменяет запрос по шаблону из списка «никогда»: `fetch` из изолированного мира к `POST /api/v1/message/ack` получает `net::ERR_BLOCKED_BY_CLIENT`;
   - расширение отменяет неизвестную запись (§4.6): `POST` к несуществующему пути API — та же ошибка;
   - разрешённый запрос доходит до прокси оператора и получает отказ закрытого выхода: Chrome видит `net::ERR_TUNNEL_CONNECTION_FAILED`, а журнал прокси — отказ с ID этого запроса;
   - сетевые правила ОС не пускают Chrome мимо прокси: служба `net-selftest` от пользователя `pb-chrome` пробует соединиться с IP SOCKS5 и с внешним адресом и должна получить отказ ядра. Результат она пишет в файл, который читает оператор.

   Перехват `Fetch` пропускает запросы самопроверки без допуска движка: выход закрыт, им некуда уйти. Оператор ждёт `Network.loadingFailed` по каждому: ни один запрос не должен остаться в очереди и уйти потом. На всё — не больше 10 с. Если любой результат иной, страница стоит, владелец получает тревогу. Пока выход закрыт, такая проверка ничего не отправляет в Fansly.
6. **Проверка выходного IP** через SOCKS5 страницы. IP должен совпасть с закреплённым.
7. **Выход открыт.**
8. **Сайт загружается:** `Page.navigate` на `https://fansly.com/`. Его API-запросы идут по допуску движка (§4.3).
9. **Сессия подтверждена:** движок через браузерный транспорт читает текущий аккаунт; account ID совпадает с ожидаемым, контекст сессии свежий (§4.7).
10. **Готов:** движок начинает отправлять.

Переходы и их причины оператор пишет в журнал и передаёт движку (`state`, §4.13). Шаги 1–7 без сайта занимают секунды; сбой на любом шаге — страница стоит с понятной причиной, повтор через нарастающую паузу: 10 с, 30 с, 2 мин, дальше раз в 5 мин.

**Потеря управления — обязательное условие №1.** Требования: «каждая фактическая отправка получает свой допуск движка». При отключении CDP Chrome сразу отпускает задержанные запросы без изменений (`InterceptionJob::Detach`, исходники Chrome 155). Закрытие выхода после этого не гарантирует, что ни один запрос не успеет уйти по уже открытому соединению. Поэтому:
- Плановая остановка всегда сначала закрывает выход и только потом отключает CDP.
- Соединение CDP не должно пропадать при сбое оператора. Кандидат — держатель CDP-соединения (§3.1):
  - оператор упал или завис — соединение живо, задержанные запросы стоят;
  - держатель читает Chrome непрерывно, даже когда оператор завис: при переполнении буфера соединения (256 МБ) Chrome молча выбрасывает сообщения CDP (`net/server/http_connection.cc`). Тогда задержанные запросы зависают, а кадры сокета пропадают без метки пропуска;
  - держатель упал или оборвалась его связь с Chrome — удержание запросов через CDP больше не обеспечено. Обрыв возможен и при живых держателе, операторе и Chrome.
- Как устроен держатель (около двухсот строк, CDP не разбирает):
  - держит одно соединение с browser-целью Chrome; оператор подключается к нему по unix-сокету;
  - нумерует каждое сообщение Chrome и хранит его, пока оператор не подтвердит номер (предел — 128 МБ);
  - перезапущенный оператор восстанавливает своё состояние с диска и получает неподтверждённые сообщения заново. Иначе он не узнал бы о запросах на паузе: списка задержанных запросов в CDP нет;
  - переполнение держателя — сбой: оператор закрывает выход и перезапускает Chrome по шагам этого раздела.
- Нужен рубеж отправки, который независимо от CDP не пропускает запрос без действующего допуска. Держатель и остановка Chrome после обнаружения сбоя его не заменяют. Остановка годится в рубеж, только если выход гарантированно закрывается раньше, чем Chrome отпускает задержанные запросы.
- Прокси знает только соединения, не отдельные запросы, поэтому одного быстрого закрытия выхода недостаточно.
- Прототип проверяет это намеренными сбоями. Критерий — ноль отправок без допуска.
- Рубеж на случай обрыва CDP оставляем, если прототип найдёт недорогой способ (§8 №10). Если ноль при обрыве CDP требует расшифровки трафика на проде или смены архитектуры, действует **запасное правило**: допустим разовый выход уже задержанных запросов, которые пропускает расширение (на первом этапе — чтения и операции входа); страница останавливается, владелец получает тревогу, событие пишется в журнал. При плановой остановке и сбое оператора критерий остаётся нулём.

### 4.2 Запрос Hub

1. Движок строит запрос (`prepare`) по реестру маршрутов, как сейчас, но без заголовков браузера и сессии (§3.2).
   - Токен и клиентские заголовки ставит оператор из живой сессии сайта (§4.7).
   - `fansly-client-check` оператор считает по алгоритму сайта для каждого запроса Hub. Сегодня Node-клиент хранит готовые значения по группам маршрутов (`packages/fansly/src/request-headers.ts`), а для маршрутов вне этих групп не шлёт заголовок вовсе.
2. Пейсер выдерживает паузу страницы, затем вызывается `send()` с ID попытки — RPC `send` к оператору (§4.13). Оператор кладёт заголовки сессии и запускает запрос.
3. Оператор выполняет `fetch()` в изолированном мире вкладки fansly.com. Это отдельная JS-среда в той же вкладке: для сети запрос идёт от сайта, но код сайта эту среду не видит.
   - Мир создаётся `Page.createIsolatedWorld` для главного фрейма вкладки и пересоздаётся после каждой загрузки страницы. Запрос запускается `Runtime.callFunctionOn` в этом мире; результат оператор берёт из событий CDP, а не из JS.
   - `redirect: 'manual'`: перенаправления не исполняются.
   - Режим кэша — как у сайта, по умолчанию: `no-store` добавил бы заголовки `Pragma` и `Cache-Control`, которых сайт не шлёт. `mode`, `credentials` и политика referrer — как у запросов сайта к тому же маршруту; их снимает прототип.
   - Запрос Hub оператор связывает с его событием CDP не по адресу: сайт может одновременно запросить тот же адрес. Кандидат — уникальный фрагмент адреса `#hub-<ID попытки>`. Фрагмент не уходит в сеть (его нет ни в запросе, ни в preflight, ни в Referer), а CDP показывает его в `request.urlFragment`. Если прототип покажет, что фрагмент до `Fetch.requestPaused` не доходит, запасной вариант — служебный заголовок, который оператор снимает в `Fetch.continueRequest`: перехват стоит до сетевой службы Chrome, а preflight строится уже в ней.
4. Перехват `Fetch` ставит запрос на паузу. Оператор вызывает проверку отправки движка: сегодня это синхронный `SendHooks.check` перед записью заголовков, в браузере — RPC `check` в момент паузы (§4.13).
   - При допуске — `Fetch.continueRequest` с `interceptResponse: true`, чтобы ответ остановился на стадии заголовков (шаг 7). Иначе — `Fetch.failRequest` (`Aborted`).
   - Срок действия допуска проверяется отправителем непосредственно перед передачей в сеть; истёкший допуск отменяет отправку. Проверки в момент отпускания `Fetch` недостаточно. Это часть обязательного условия №2: механизм проверяется прототипом; если надёжного нет — решение владельца №16. Замер обычной задержки гарантией не служит.
   - Срок передаётся абсолютным моментом по монотонным часам ядра, а не остатком: остаток, пересчитанный после задержки RPC, продлевал бы допуск.
   - Кандидаты на такую проверку. Ни один из них пока не гарантия:
     - для запросов Hub — `AbortController` в изолированном мире: если CDP к сроку минус 1 с не показал начала отправки, оператор вызывает `abort()`. Отмена идёт через оператор и процесс страницы; если они задержатся, срок будет пропущен;
     - для запросов сайта — прокси обрывает ещё не установленный туннель к хосту API. Это не закрывает случаи, когда туннель уже есть: задержку TLS и запрос по открытому соединению HTTP/2.

     Прототип проверяет кандидатов на открытых туннелях, зависшем TLS, повторно используемом соединении HTTP/2 и при зависании оператора и процесса страницы. Какое событие CDP надёжно означает начало отправки (`Network.requestWillBeSentExtraInfo`, `timing.sendStart`), тоже определяет прототип. Если надёжного механизма нет — решение владельца №16. До этого решения и правки требований условие №2 остаётся блокирующим, запасное правило не реализуется.
5. **Момент отправки.** Сегодня пройденная проверка и есть отправка (undici `onRequestStart`, `engine/pacer.ts`). В браузере после допуска ещё идут соединение и preflight. Поэтому:
   - в пейсер передаётся фактическое время отправки из Chrome по `timing` из `Network.responseReceived`: `1000 × requestTime + sendStart` в миллисекундах (`requestTime` — в секундах, `sendStart` — в миллисекундах от него). Это монотонные часы ядра (`CLOCK_MONOTONIC`), общие для всех процессов сервера. Движок считает время через `performance.now()` (`engine/ports.ts:41`), поэтому переводит их одним постоянным сдвигом: `process.hrtime` минус `performance.now()`. Прототип это подтверждает;
   - если его нет, берётся момент завершения — безопасная верхняя оценка, которую пейсер уже поддерживает.
6. **Сколько физических запросов.**
   - Браузер сам шлёт CORS-preflight (`OPTIONS`), если его нет в кэше, и сразу за ним запрос. CDP preflight не перехватывает. Владелец решил (№1): пара preflight + запрос — одна операция под одним допуском, пауза соблюдается между операциями.
   - **Обязательное условие №2.** Сетевой стек Chrome сам повторяет запрос, если считает, что сервер его не обработал: 408 на повторно использованном соединении HTTP/1.1, отказ потока HTTP/2 (исходники Chrome 155). Это происходит ниже перехвата. Требования же говорят: «браузер не повторяет запросы незаметно». Прототип проверяет, можно ли такие повторы отключить или выдавать на каждый отдельный допуск, — в том числе намеренно вызывая их на своём стенде. Если нельзя, это противоречие требованиям решает владелец (§8 №1б), до кода. Частота повторов критерием приёмки не служит.
7. **Ответ.** Статус и все заголовки оператор снимает через CDP на сетевом уровне, тело — потоком.
   - Пока запрос ещё стоит на паузе стадии запроса, оператор включает потоковую выдачу (`Network.streamResourceContent` по его ID в домене `Network`) и ждёт подтверждения; только потом отпускает запрос. Данные ответа приходят в событиях `Network.dataReceived` и сразу пишутся в буфер. Включить выдачу позже нельзя: быстрый ответ успеет закончиться, а начало тела — уйти из буфера Chrome.
   - На стадии заголовков статус и заголовки приходят в `Fetch.requestPaused`. Если заявленный размер больше предела (API — 32 МиБ, медиа — 5 МиБ, как сегодня), запрос отменяется до скачивания тела: для медиа это прежний `bodyOverflow`. Иначе — `Fetch.continueRequest`: ответ доходит до изолированного мира как обычно, и процесс страницы присылает `Network.responseReceived` со временем отправки и источником.
   - Пределы действуют и во время приёма: тело без заявленного размера (по частям, сжатое) считается по мере прихода, и при превышении запрос отменяется. `Fetch.getResponseBody` не используется: он собирает тело целиком в памяти без предела.
   - Тело считается собранным полностью, если запрос закончился `Network.loadingFinished`, а не ошибкой, и поток не прерывался: учтены данные из ответа `Network.streamResourceContent` и все события `Network.dataReceived`, у каждого длина данных равна его `dataLength`. В событиях — распакованное тело, а `encodedDataLength` у `loadingFinished` — закодированный объём передачи; сравнивать их нельзя. Закодированный объём считается отдельно — для `bodyBytes`.
   - Если `Network.responseReceived` так и не пришёл, время отправки — момент завершения (верхняя оценка), источник ответа — неподтверждённый.
   - Перенаправление (3xx) возвращается движку как есть, с заголовком `Location`; изолированный мир видит только непрозрачный ответ, но оператору это не мешает.
   - Сетевая ошибка (`Network.loadingFailed`) отдаётся движку с признаком, была ли отправка: ошибка до начала отправки — запрос точно не ушёл; после — исход неизвестен, как сегодня.
   - Ответ хранится в буфере под ID попытки, пока движок не подтвердит запись.
   - Если движок перезапустился посреди запроса, при восстановлении он сначала забирает ответы из буфера (§3.2).
   - Байты медиа идут описателю по своему подтверждению и в `observations` не пишутся.
8. **Откуда ответ.** Hub знает, откуда пришёл ответ: из сети, из кэша браузера после подтверждения сервером (`304 Not Modified`), через service worker сайта. Ответ без подтверждения актуальности сервером не считается успешным обновлением данных. Оператор видит источник по событиям CDP: `fromDiskCache` и `fromServiceWorker` в `Network.responseReceived`, фактический статус от сервера (в том числе 304) — в `Network.responseReceivedExtraInfo`.

Оператор ничего не повторяет сам. Повтор — решение движка по его правилам.

Добавка оператора — единицы миллисекунд, это предстоит подтвердить замером. Заметная добавка от браузера — preflight: ещё одно обращение к Fansly через прокси.

### 4.3 Собственные запросы сайта

Предложение режимов (утверждает владелец):

| Трафик | Режим |
|---|---|
| API Fansly | Только по допуску движка через путь допуска запросов сайта (§3.2): общий пейсер, бюджеты маршрутов, классы работ. Ответы (статус, 429, `Retry-After`) идут в движок, данные платформы — в `observations` (§3.2). Список «никогда» и неизвестные записи отменяет расширение (§4.6). Разрешённые записи на первом этапе — только операции ручного входа (§4.8) |
| Страница, скрипты, стили, шрифты, картинки и превью с CDN | Без пейсинга, с записью в журнал: хост, объём, время |
| CORS-preflight | Часть своего запроса: одна операция под одним допуском (§4.2, решено владельцем, №1) |
| Подключение к сокету | **Обязательное условие №3.** Каждое подключение — по допуску движка. CDP подключение сокета не перехватывает, а новое подключение может пойти по уже открытому соединению HTTP/2, поэтому выход его не различает. Допуск даётся внутри страницы, до создания соединения |
| Исходящие сообщения сокета | **Обязательное условие №3.** Проверка до отправки внутри страницы, во всех её контекстах, включённая до запуска кода сайта. Разрешены только известные типы (по коду Hub — авторизация и ping; что ещё шлёт сам сайт, покажет прототип). Неизвестное сообщение не отправляется: тревога и остановка страницы. CDP только сообщает об уже отправленном сообщении, поэтому наблюдения недостаточно (требования: «запреты… охватывают… WebSocket») |
| Служебный трафик Chrome (обновления компонентов, Safe Browsing) | Через тот же прокси, в журнал соединений |

Проверка сокета внутри страницы меняет среду самой страницы сайта. Цену и способ её связи с оператором определяет прототип (§8 №11).

**Как оператор решает по каждому запросу** (`Fetch.requestPaused` на стадии запроса):
1. Запрос Hub (по метке, §4.2) и запрос самопроверки (§4.1) — по своим правилам.
2. Хост и путь сверяются с картой операций. Карта одна для оператора и расширения (§4.6):
   - страница, статика и CDN — сразу `Fetch.continueRequest` и запись в журнал;
   - API (`apiv3.fansly.com`) — путь допуска запросов сайта: RPC `siteAdmit` (§4.13) с методом, путём, параметрами, типом ресурса и маршрутом по карте. Запрос стоит до решения движка;
   - неизвестный хост — отказ (`BlockedByClient`) и запись в журнал. Список хостов составляет прототип (этап 1, п. 10), утверждает владелец (№2).
3. Ожидание допуска ограничено: если движок не дал допуск за 60 с (предварительно), запрос отменяется (`Failed`), сайт видит сетевую ошибку, причина пишется в журнал.
4. Ответ API сайта не задерживается и не теряется. Для маршрутов «с данными платформы» оператор включает потоковую выдачу тела (`Network.streamResourceContent`, есть в Chrome 155) ещё во время паузы, до допуска запроса, и ждёт подтверждения. Данные приходят в событиях `Network.dataReceived` и пишутся в буфер на диске по мере прихода, а оттуда уходят в `observations`. Перед записью оператор сверяет, что тело собрано полностью. Включать выдачу по `Network.responseReceived` поздно: это событие доставку не останавливает, быстрый ответ успеет закончиться, а начало тела — уйти из буфера Chrome. Сам буфер Chrome (100 МБ всего, 20 МБ на ответ, задаётся при `Network.enable`) — только запасной путь. Предела размера для сохранения нет: сайт ответ уже получил, и выбрасывать полученное нельзя. Тело пишется на диск потоком, память оператора не растёт, а объём держат допуск и потолок буфера. Те же правила полноты, что в §4.2, шаг 7.
   - Если буфер оператора не принимает запись, новые запросы сайта не получают допуск.
   - Если тело всё же снять не удалось, это не считается сохранённым фактом: в `observations` пишется отметка, движок ставит догрузку этих данных своим запросом, если маршрут есть в реестре, а пропуск виден в Hub.
   - Статус, 429 и `Retry-After` уходят в движок (`siteDone`).

**Как устроена проверка сокета в странице** (кандидат для прототипа):
- `Page.addScriptToEvaluateOnNewDocument` встраивает обёртку `WebSocket` в главный мир каждого фрейма до кода сайта; в воркерах её ставит `Runtime.evaluate` до снятия паузы.
- Подключение: обёртка не создаёт настоящий сокет, пока не получит допуск. Запрос допуска идёт оператору через `Runtime.addBinding`: обёртка сохраняет функцию у себя и сразу удаляет её глобальное имя, чтобы сайт её не видел. Ответ оператор передаёт вызовом `Runtime.callFunctionOn` по ссылке на объект обёртки, тоже без глобальных имён.
- Исходящее сообщение проверяется синхронно в странице по списку разрешённых типов, который оператор встроил в обёртку при запуске. Неизвестное сообщение не отправляется; обёртка сообщает о нём оператору, оператор закрывает выход и поднимает тревогу.
- Сайт не должен заметить обёртку: `instanceof WebSocket`, свойства прототипа, порядок событий. Это проверяется на стенде и на тестовом аккаунте (этап 1).

Чем больше запросов делает открытая вкладка, тем меньше потолка страницы (≈ 1 300 запросов в час при паузе 2,5 с) остаётся Hub. Сейчас Hub занимает в среднем 5–9 %, в пиковый час до 77 %. Долю сайта измеряет прототип.

### 4.4 События сокета

1. Сокет открывает сайт; собственный сокет движка для этой страницы выключен.
2. Кадры приходят оператору из CDP (`Network.webSocketFrameReceived`).
3. Каждый кадр получает ID события: номер растёт в пределах страницы и переживает перезапуски. Кадр дописывается в журнал на диске с `fsync` (принудительной записью) и потоком уходит в движок.
   - Буфер — файл SQLite на томе страницы (встроенный модуль `node:sqlite`; в Node 22 он ещё помечен экспериментальным, запасной вариант — `better-sqlite3`), режим WAL, `synchronous=FULL`. Записи собираются в пачку не дольше 20 мс и фиксируются одним `fsync`: это укладывается в «доли секунды» требований. Прототип замеряет задержку.
   - ID события — пара `(ID буфера, номер)`. ID буфера — UUID, созданный вместе с томом. Если том пересоздан, номера начинаются заново, но пары не совпадают со старыми.
   - Что лежит в буфере: кадры сокета (`ws.open`, `ws.in`, `ws.close`), метки пропуска (`gap`), ответы сайта для `observations` (§4.3), ответы на запросы Hub — отдельно, под ID попытки (§4.2).
4. Движок принимает кадр по ID, независимо от того, открыто ли ещё соединение, и подтверждает после записи в `observations`. Только тогда оператор удаляет кадр из буфера.
   - Поток: движок подписывается парой «ID буфера, последний подтверждённый номер» (`events.subscribe`), оператор шлёт пачки до 500 событий или 1 МБ, движок фиксирует их и подтверждает (`ack`). ID буфера есть в подписке, в каждой пачке и в каждом `ack`. Подтверждение чужого буфера оператор отвергает: иначе после пересоздания тома старый номер 5000 подтвердил бы или пропустил новые события. Подтверждается только непрерывная зафиксированная часть. Неподтверждённое после переподключения приходит снова.
   - Подтверждённые записи оператор удаляет пачками; место в файле освобождается постепенно (`auto_vacuum=INCREMENTAL`).
5. Повторная доставка не даёт дублей: движок различает кадры по ID и, как сейчас, по ID сообщений.
6. Любой разрыв оставляет метку пропуска, и движок догружает его обычным механизмом:
   - переподключился сокет сайта;
   - перезапустились браузер или оператор;
   - недоступен Hub.

   Метка `gap` несёт интервал «последнее событие до разрыва — первое после» и причину. Оператор ставит её сам: при закрытии и новом открытии сокета сайта, при своём старте (от последнего записанного события) и после перезапуска Chrome.
7. Деплой Hub и недоступность базы сокет не рвут: кадры ждут в буфере.
8. У буфера есть потолок объёма и возраста (§8).
   - Предварительно — 2 ГиБ и 72 часа на страницу; тревога на 50 % и 80 %. Окончательные значения — по замерам (№6).
   - При исчерпании диска или потолка страница останавливается, пропуск помечается и потом догружается.
   - Буфер живёт на томе страницы, не на томе Postgres.

### 4.5 Сеть и прокси

- **Единственный выход обеспечивает ОС.**
  - Chrome и оператор работают от разных пользователей.
  - Правила сетевого фильтра разрешают пользователю Chrome только локальный прокси оператора и нужные локальные службы, а пользователю оператора — только адрес и порт SOCKS5 страницы.
  - Настройка прокси в Chrome — лишь удобство, не защита.
  - Правила внутри контейнера (nftables, ставит `init-net`; адрес SOCKS5 — IP, имя Hub разрешает сам):

    ```
    table inet pb {
      chain output { type filter hook output priority 0; policy drop;
        ct state established,related accept                        # ответы на входящие RPC и VNC
        meta skuid pb-chrome oif lo tcp dport 3128 accept           # Chrome — только локальный прокси
        meta skuid pb-operator oif lo tcp dport 9222 accept         # оператор и держатель — CDP
        meta skuid pb-operator ip daddr $SOCKS5_IP tcp dport $SOCKS5_PORT accept
      }
      chain input { type filter hook input priority 0; policy drop;
        iif lo accept
        ct state established,related accept
        ip saddr $SYNC_IP tcp dport 7700 accept                     # RPC движка
        ip saddr $API_IP tcp dport { 6901, 7700 } accept            # экран KasmVNC и форма входа через API
      }
    }
    ```

    У `sync` и `api` постоянные адреса в `pb-control` (`ipv4_address`): деплой Hub пересоздаёт эти контейнеры, но адреса не меняются, и правила в работающих контейнерах страниц остаются верными. Каждый вызов RPC — ещё и с токеном.

    Chrome по умолчанию ходит к `localhost` мимо прокси. Поэтому правило для `pb-chrome` пускает его только на порт прокси: страница сайта не достучится ни до CDP, ни до RPC оператора. UDP и DNS у Chrome закрыты целиком.
  - Второй слой — на хосте: правило в цепочке `DOCKER-USER` пропускает из адреса контейнера в `pb-egress` только IP и порт SOCKS5 этой страницы.
- **Локальный прокси оператора** — HTTP-прокси с методом `CONNECT` на `127.0.0.1:3128`:
  - выход закрыт — на любой `CONNECT` ответ `403` с причиной, соединение в журнал;
  - выход открыт — туннель через SOCKS5 страницы с паролем, имя хоста уходит в SOCKS5 как есть (адрес типа «домен»);
  - отказ к локальным и частным адресам, даже при открытом выходе;
  - на каждый туннель — строка журнала: хост, порт, время открытия и закрытия, байты в обе стороны, результат;
  - закрытие выхода рвёт все открытые туннели сразу.
- **Независимая проверка при приёмке.** Журнал прокси видит только то, что прошло через прокси, поэтому отсутствие трафика мимо прокси проверяется отдельно, на уровне ОС: захватом трафика на сетевом интерфейсе контейнера.
- Оператор открывает соединения к SOCKS5 страницы с паролем — Chrome сам такого не умеет. Правило расширения против локальных и частных адресов работает только по адресу в запросе и служит дополнением к отказу прокси.
- DNS разрешается на стороне прокси, оператор передаёт ему имя хоста. QUIC выключен политикой, WebRTC пускается только через прокси.
- При недоступности прокси, отказе в авторизации или смене IP ожидающие отправки браузера отменяются, их допуски аннулируются; новые запросы браузера отклоняются, а не копятся. Уже полученные данные в буфере и сохранённая работа движка остаются. После разрешённого возобновления по правилам ниже и проверки сессии движок планирует новые запросы; отменённые запросы браузера не возобновляются.
- Выходной IP проверяется перед открытием выхода и периодически во время работы: оператор через SOCKS5 страницы запрашивает `https://api.ipify.org` — тот же сервис, что сегодня у `pnpm cli page proxy-ip` и проверки прокси в дашборде. Закреплённый IP хранится в `egress_endpoints.pinned_exit_ip` (§3.4); сегодня Hub его не хранит и не проверяет.
  - Если IP сменился, страница стоит до решения владельца.
  - Если прокси вернулся с прежним IP, работа возобновляется сама, владелец получает уведомление.
- Учётные данные SOCKS5 оператор получает от движка в `hello` (§4.13): движок расшифровывает их из `egress_endpoints.encrypted_auth`, как сегодня для undici. В образ, на диск и в журналы они не попадают.

### 4.6 Запреты — два независимых рубежа

- **Расширение — работает без оператора, в том числе при ручном доступе:**
  - на первом этапе любые записи к API Fansly (`POST`, `PUT`, `PATCH`, `DELETE`) запрещены. Исключение — явный список операций входа (логин, подтверждение 2FA). Так неизвестная запись не уйдёт, даже если оператор недоступен;
  - список «никогда» действует всегда, в том числе на втором этапе:
    - прочтение (`POST /message/ack`);
    - typing (`POST /message/typing`);
    - смена статуса (`POST /status`);
    - выплаты и вывод средств;
    - реквизиты, пароль, почта, настройки 2FA, удаление аккаунта;
  - обращения веб-страниц к локальным и частным адресам — как дополнение к правилам прокси (§4.5).
  - `POST /group` (создаёт диалог) и `POST /notes`, `/notes/edit` (заметки CRM) на первом этапе закрыты общим запретом записей; на втором этапе их судьба решается отдельно.
- Пути входа и подтверждения 2FA в коде Hub и в разборе FBuddy не встречаются: своего входа в Fansly у Hub нет. Их снимает прототип по бандлу сайта и трафику (этап 1, п. 12).
- **Оператор:** список разрешённого по режимам — «автоматика» и «ручной вход». Всё, что не разрешено, отменяется и пишется в журнал.
- Точную карту операций составляем в спецификации по коду сайта и трафику прототипа. Утверждает её владелец.
- **Одна карта — два рубежа.** Карта операций лежит в коде одним файлом (`apps/page-browser/src/policy/operations.ts`): хост, метод, шаблон пути, режим, маршрут движка, «с данными платформы». Из неё при сборке образа получаются правила расширения, а оператор берёт из неё свою таблицу решений. Тест проверяет, что список «никогда» в обоих одинаков.
- **Правила расширения** — статический набор DNR, приоритет сверху вниз:
  1. «никогда» — `block` по пути и методу, например `||apiv3.fansly.com/api/v1/message/ack` для `POST`;
  2. операции входа — `allow` по точным путям;
  3. любые `POST`, `PUT`, `PATCH`, `DELETE` к API — `block`. `OPTIONS` в этот список не входит: preflight строит сетевая служба Chrome, и правило не должно его ломать;
  4. запросы к `localhost` и частным адресам — `block`.

  Манифест MV3 с единственным разрешением `declarativeNetRequest`, без скриптов. CRX подписан нашим ключом, поэтому ID расширения постоянный. CRX и манифест обновления раздаёт оператор по локальному адресу: за расширением Chrome в интернет не ходит. Новая версия правил приходит только с новым образом.
- Запрещённое по HTTP уйдёт, только если одновременно откажут оба рубежа. Сокет — §4.3, потеря управления — §4.1.

### 4.7 Сессия и привязка к аккаунту

- Сессия живёт в профиле браузера. Владелец входит сам — через форму в дашборде или экран KasmVNC (§4.8). Вход идёт из серверного браузера через прокси страницы.
- Токен и клиентские заголовки оператор берёт из собственных запросов сайта, `fansly-client-check` — как в §4.2. Набор заголовков запроса Hub сверяется с запросами сайта того же маршрута. Если они расходятся, транспорт не готов: страница стоит, владелец получает тревогу. Так изменение протокола Fansly обнаруживается сразу, а не по отказам.
  - Откуда: из `Fetch.requestPaused` по запросам сайта к API — `authorization`, `fansly-client-id`, `fansly-session-id`. Оператор держит последние значения в памяти, на диск и в журналы они не попадают. `fansly-client-ts` — время в момент запроса, как у сайта.
  - `fansly-client-check` сайт считает сам для каждого своего запроса — хэш cyrb53 от пути запроса (по разбору публичного бандла сайта). Для запросов Hub оператор считает его так же. Сегодня Node-клиент хранит готовые значения для семи групп маршрутов, а у страниц, заведённых через форму дашборда, значений нет вовсе, и заголовок не уходит ни на одном маршруте (`packages/fansly/src/request-headers.ts:39-51`). Браузер это исправляет.
  - Сверка заголовков: по каждому маршруту, который запрашивает и сайт, оператор сравнивает набор и порядок имён заголовков запроса Hub с последним запросом сайта (значения не сравниваются, они меняются).
- Оператор сообщает движку отпечаток сессии (хэш токена и client id) — так же, как сегодня работает `storedCredentialsGeneration`. Если отпечаток сменился, сначала проверяется личность (`account.verify`), потом продолжается работа. Подтверждённый отпечаток движок хранит там же, где сегодня, — в `sync_pages.credentials_generation`.
- Каждая команда несёт поколение владельца страницы (`owner_generation`). Оператор не исполняет команды прежнего поколения.
- При передаче страницы оператор подтверждает, что отправок прежнего поколения нет и в полёте ничего не осталось (`quiesced`, §4.13). Завершения процесса `sync` для этого мало: браузер работает отдельно (требования). Поэтому шаг деплоя `sync ownership confirm-stopped` для браузерных страниц дополнительно ждёт `quiesced` от оператора.
- Ответ 401 или потеря входа означают «нужен вход»: работают существующие остановки и уведомления.
- **Откат на Node-транспорт** использует токен, который сейчас хранит Hub (`page_credentials.encrypted_session`). Пока основной транспорт — браузер, проверять этот токен запросами нельзя: все запросы идут через браузер. К моменту отката он может оказаться недействительным — решение владельца №12. У страниц, подключённых через браузер, такого токена нет вовсе: их откат идёт через владельца (§3.2, «Подключение новой страницы»).

### 4.8 Вход и ручной режим

Страница стоит на паузе: обычная работа движка не идёт. Оператор работает по списку «ручной вход»: разрешены вход, подтверждение 2FA и чтения, которые делает интерфейс. Эти операции идут через путь допуска запросов сайта (§3.2) под той же паузой и бюджетами. Список «никогда» действует.

**Основной путь — форма входа в дашборде** (владелец согласовал 2026-10-10, §8 № 5):
1. Hub пишет: «lora-1: нужен вход».
2. Владелец открывает в дашборде страницу входа. На ней живой снимок экрана серверного браузера и поля, которые сейчас просит Fansly.
3. Владелец вводит логин и пароль (пароль можно вставить из 1Password). Оператор вставляет их в поля сайта и нажимает «Войти». Запрос входа отправляет сам сайт из серверного браузера через прокси страницы — для Fansly это тот же вход с того же устройства и IP.
4. Fansly просит код 2FA — в форме появляется поле для кода, дальше так же.
5. Перед возобновлением проверяются account ID, отпечаток сессии и выходной IP.

Оператор узнаёт только известные экраны входа: логин, код, ошибку, успех. Если экран незнакомый (капча, проверка Fansly, новое соглашение, изменённая форма), он ничего не нажимает и просит открыть экран.

Как это устроено:
- **Путь команд.** API и `sync` сегодня общаются только через Postgres (`sync_work` и `NOTIFY`), а пароль и код не должны попадать в базу даже на миг. Поэтому поля формы идут напрямую: дашборд → API → оператор по сети `pb-control` (`login.*`, §4.13, со своим токеном). Оператор принимает их, только пока движок текущего поколения держит страницу в режиме «ручной вход». Включает и выключает этот режим движок, так что правило «команды браузеру — только от текущего владельца страницы» сохраняется.
- **Распознавание экрана.** Оператор смотрит DOM из изолированного мира: адрес страницы, поля логина и пароля, поле кода, текст ошибки, загруженный аккаунт. Признаки экранов хранятся в коде оператора с версией; изменилась вёрстка — экран считается незнакомым.
- **Ввод.** Поле получает фокус через `DOM.focus`, текст вводится `Input.insertText`, кнопка нажимается `Input.dispatchMouseEvent` в центр её прямоугольника (`DOM.getBoxModel`). Для сайта это обычный ввод с клавиатуры и мыши. Запись через `element.value` из JS не используется: такие события сайт отличает от настоящих.
- **Снимок экрана.** `Page.captureScreenshot` (JPEG) раз в секунду, только пока страница входа открыта в дашборде. Снимки никуда не сохраняются.
- **Секреты не попадают в журналы.** Оператор не пишет параметры `Input.insertText`, движок и API не пишут тела запросов `login.*`, в журнале остаются только факт и результат шага.
- **Режим.** На время входа движок ставит страницу на паузу, оператор переходит в режим «ручной вход». После успеха — проверки шага 5, режим «автоматика», движок снимает паузу.
- **Экран KasmVNC.** API проксирует HTTP и WebSocket со страницы дашборда на `page-browser-<страница>:6901` по сети `pb-control`, только под входом владельца. Пароль KasmVNC свой у каждой страницы, хранится в секретах Hub и подставляется API; владельцу его знать не нужно.

**Запасной путь — экран KasmVNC** во вкладке дашборда, для незнакомых экранов и диагностики. Пароль вставляется через общий буфер обмена. Соединение входящее: дашборд подключается к контейнеру страницы по внутренней сети, исходящего маршрута у браузера по-прежнему нет.

Как обращаемся с паролем и кодом:
- Hub их не хранит и не вводит по своей инициативе: только то, что владелец ввёл сейчас.
- Они проходят через Hub по HTTPS и внутренней сети и живут только в памяти на время передачи.
- В базу, журналы, снимки и метрики они не попадают. Поле пароля на снимке скрыто самим сайтом.
- Страница входа доступна только под входом владельца.

Если и KasmVNC окажется медленным, следующий вариант — поток по WebRTC (Neko, Selkies). Для него нужны отдельные UDP-порты или TURN-сервер.

### 4.9 Сбои

| Сбой | Что происходит | Восстановление |
|---|---|---|
| Оператор упал или завис | Соединение CDP держит держатель (§4.1): задержанные запросы стоят, выход стоит | Упавшего оператора перезапускает s6; зависшего — сторож в контейнере: оператор раз в секунду обновляет файл сигнала жизни, порог 5 с. Новый оператор восстанавливает состояние и сверяется с движком |
| Зависла управляющая часть оператора, пересылка работает | Новые запросы не получают допуск и стоят; уже допущенные доходят | Сторож по тому же сигналу убивает процесс оператора — выход закрывается вместе с ним; дальше как в строке выше |
| Потерян CDP, в том числе при живых процессах | Независимый от CDP рубеж не пропускает отправки без действующего допуска; без рубежа — запасное правило (§4.1). Выход закрывается, Chrome останавливается, тревога | Перезапуск с шага 1 §4.1, догрузка пропуска |
| Выход открывается снова после сбоя прокси | Прежние ожидающие запросы браузера отменены, их допуски недействительны; движок планирует новые запросы | Проверка IP и сессии по §4.5 |
| Деплой или рестарт `sync`, недоступна база, нет пинга 5 с | Допусков нет, поэтому API-запросы сайта ждут до 60 с, потом отменяются (§4.3). Сокет и буфер работают | Сверка с буфером (§3.2), допуски возобновляются, буфер выгружается |
| Диск или буфер заполнен | Страница стоит, тревога | Пропуск помечается и догружается |
| Прокси недоступен, не принимает авторизацию или IP сменился | Страница стоит; ожидающие отправки и их допуски отменены | §4.5 |
| Капча, проверка Fansly, 401/403/429 | Существующие остановки движка, капчу решает владелец | Как сейчас |
| Chrome упал или его остановило ядро по нехватке памяти | Задержанные запросы умирают вместе с Chrome; оператор закрывает выход | Перезапуск с шага 1 §4.1, метка пропуска сокета |
| Сайт перезагрузил вкладку или показал экран входа | Изолированный мир пересоздаётся (§4.2); экран входа — «нужен вход» | §4.8 |
| Неизвестное сообщение сокета, расхождение заголовков, сбой самопроверки | Выход закрывается, страница стоит, тревога | Решение владельца или правка карты операций |

### 4.10 Обновления Chrome

- Stable выходит раз в две недели, патчи безопасности — чаще.
- Сборка образа запускается сама, когда выходит новая версия. Образ получает тег версии Chrome. Пакет `.deb` и образ храним сами: старых версий Google не раздаёт.
- Порядок:
  1. снимок профиля;
  2. обновление одной страницы и окно наблюдения;
  3. остальные страницы.
- Что проверяем на первой странице:
  - самопроверка;
  - окружение (§4.1, шаг 2);
  - сессия жива;
  - сайт загрузился;
  - кадры сокета идут;
  - жёсткие проверки окна наблюдения.
- Откат — прошлый образ плюс снимок профиля. Профиль после нового Chrome старым не открывается.
- Как устроено:
  - На сервере, вне контейнеров Hub (у них нет доступа к Docker), раз в сутки по таймеру systemd запускается `scripts/page-browser-update.sh`. Он смотрит последнюю версию Stable в репозитории Google, скачивает `.deb`, проверяет подпись ключом Google и кладёт пакет в архив `/opt/agency-hub/page-browser/chrome/`.
  - Образ `hub-page-browser:<версия>-<коммит>` собирается на сервере; хранятся три последних.
  - Первая страница обновляется в спокойный час с 06:00 до 20:00 UTC, когда есть кому отреагировать. Окно наблюдения — 1 час (№7). Если всё чисто, остальные страницы обновляются по одной. Любая проверка не прошла — откат этой страницы и тревога, раскатка останавливается.
  - Снимок профиля: оператор закрывает выход и останавливает Chrome, профиль упаковывается в `/opt/agency-hub/page-browser/snapshots/<профиль>/`, хранятся три последних.
  - Буфер лежит на отдельном томе и при откате профиля не теряется (требования: «сохранность событий при откате»). Формат буфера версионирован, новый оператор читает старый.
  - Цель — все страницы на новой версии не позже трёх дней после выхода, если проверки чистые.

### 4.11 Наблюдаемость и управление

- Во вкладке «Синк», в CLI и для агентов видны:
  - состояние браузера;
  - нужен ли вход;
  - прокси и выходной IP;
  - объём и возраст буфера;
  - задержка доставки событий;
  - версия Chrome;
  - результат последней самопроверки.
- Причины ожидания и остановки — общие для всех трёх. При смене состояния владелец получает уведомление.
- Владелец может мгновенно остановить одну страницу или все: движок ставит паузу, оператор закрывает выход.
- Где это в коде:
  - вкладка «Синк» — новый блок «Браузер» в карточке страницы (`apps/dashboard/src/pages/settings/engine/`), данные — новые поля в `/api/v1/sync/pages`;
  - тревоги — существующие инциденты `fansly_sync_engine` с новыми подвидами: `browser_down`, `login_required`, `proxy`, `exit_ip_changed`, `buffer`, `selftest_failed`, `protocol_changed`, `cdp_lost`. Доставка в Telegram — прежним путём;
  - нет `state` от оператора 2 минуты на странице с браузерным транспортом — тревога `browser_down`. Это как сегодняшняя проверка сигнала жизни `sync` в API;
  - CLI (`apps/runtime/src/sync/cli.ts`): `sync page transport`, `sync browser status|stop|start|selftest|snapshot|pin-ip|log`; `stop --all` останавливает все страницы. CLI агентов `hub sync-status` показывает тот же блок;
  - метрики раз в 5 минут в `ops_metric_samples`: объём и возраст буфера, p95 задержки доставки событий, память Chrome, итог самопроверки.
- Журналы:
  - запросов: метод, хост, путь, допуск, время, результат;
  - соединений;
  - исходящих сообщений сокета.

  Пароли, коды 2FA, токены и cookies в журналы не пишутся.

  Журналы — файлы JSON Lines на томе буфера, по дню на файл, со сжатием; хранятся 30 дней (предварительно). Смотреть — `sync browser log <страница> --since … --path …`, например, чтобы убедиться, что `POST /message/ack` не уходил ни разу.

### 4.12 Ресурсы и общая нагрузка

- Прототип измеряет на страницу:
  - память и CPU Chrome со спокойной вкладкой и под потолком нагрузки;
  - диск профиля;
  - рост буфера, журналов и `observations` от ответов сайта.
- Требования говорят про одновременную работу всех страниц, поэтому замеров на одну страницу мало. Размер сервера утверждаем по общему нагрузочному тесту семи профилей на стенде (§5, этап 2), а перед переводом всех страниц тест повторяется на сервере прода.
- На нынешнем `agency` (2 vCPU, 7,7 ГиБ) места для семи браузеров нет. Пилот проводим после переезда на `agency-de` (8 ядер, 16 ГБ) — см. `~/code/8-docs/2026-10-10-server-migration-netcup/plan.md`.
- Оценка до замеров, на страницу: Chrome со вкладкой Fansly — 0,5–0,9 ГиБ памяти, KasmVNC — до 0,1 ГиБ, оператор и держатель — 0,1–0,15 ГиБ; итого около 1 ГиБ, на семь страниц — 6–8 ГиБ. Диск: профиль 0,3–1 ГБ, буфер до потолка (2 ГиБ), журналы — по сроку хранения. Эти числа прототип заменяет измеренными.
- Сайт видит число ядер и объём памяти сервера (`navigator.hardwareConcurrency`, `navigator.deviceMemory`). Переезд на другой сервер меняет «устройство», поэтому профили страниц создаём уже на `agency-de`.

### 4.13 Протокол движок ↔ оператор

Одно WebSocket-соединение от `sync` к оператору страницы (`ws://page-browser-<страница>:7700/rpc`), сообщения JSON; тела ответов — отдельными двоичными кадрами со ссылкой на ID. Первое сообщение несёт токен страницы из секретов Hub. Каждое сообщение движка несёт поколение владельца страницы (`owner_generation`); оператор отвергает поколение меньше текущего.

| Сообщение | Кто → кому | Поля | Зачем |
|---|---|---|---|
| `hello` | движок → оператор (ответ — ID буфера и состояние) | страница, поколение владельца, ожидаемый account ID, закреплённый IP, SOCKS5 (IP, порт, логин, пароль), окружение (часовой пояс, язык, геолокация), параметры (§4.14) | Привязать соединение к владельцу страницы. Новое поколение вытесняет старое: оператор завершает или отменяет его запросы и отвечает `quiesced` с моментом последней фактической отправки — от него движок отсчитывает паузу передачи |
| `state` | оператор → движок | состояние §4.1, выход, режим, отпечаток сессии, IP, версия Chrome, самопроверка, буфер (объём, возраст), причина остановки | Статусы, тревоги, вкладка «Синк» |
| `ping` / `pong` | оба | номер | Раз в 1 с. Нет ответа 5 с — оператор считает связь с Hub потерянной: новых допусков нет, запросы сайта ждут (требования: «без связи с Hub браузер не начинает новых запросов»). Движок по тому же признаку считает транспорт недоступным |
| `send` | движок → оператор | ID попытки, поколение владельца, поколение учётных данных и отдельно ожидаемый отпечаток сессии браузера, метод, адрес, заголовки маршрута, вид (API или медиа), предел времени | Запрос Hub (§4.2) |
| `check` / `checkResult` | оператор → движок, ответ | ID попытки; ответ — допуск с абсолютным сроком (монотонные часы ядра, мс) или отказ с причиной. Живая сессия не совпала с ожидаемой — оператор запрос не отпускает | Проверка отправки в момент паузы `Fetch` |
| `sent` | оператор → движок | ID попытки, монотонное и настенное время начала отправки, повторно ли использовано соединение | Фактический момент отправки для пейсера |
| `result` / `resultAck` | оператор → движок, ответ | ID попытки, отпечаток сессии, статус, заголовки, тело, источник ответа, время отправки в мс по монотонным часам, ошибка с признаком «до или после начала отправки» | Ответ хранится в буфере до `resultAck`: подтверждение приходит после записи в `observations` |
| `siteAdmit` / `siteAdmitResult` | оператор → движок, ответ | ID запроса сайта, метод, путь, параметры, тип ресурса, маршрут по карте, отпечаток сессии; ответ — допуск с абсолютным сроком или отказ | Путь допуска запросов сайта (§4.3) |
| `siteDone` | оператор → движок | ID запроса сайта, статус, `Retry-After`, время отправки | Учёт, остановки маршрутов, журнал отправок |
| `wsAdmit` / `wsAdmitResult` | оператор → движок, ответ | ID подключения, адрес | Допуск подключения сокета сайта |
| `events.subscribe` / `events` / `ack` | движок ↔ оператор | ID буфера и номер, пачка событий, подтверждённые ID буфера и номер | Кадры сокета, метки пропуска, ответы сайта (§4.4). Подтверждение чужого буфера отвергается |
| `command` | движок → оператор | `closeExit`, `openExit`, `stopPage`, `restartBrowser`, `selfTest`, `profileSnapshot`, `setMode` (автоматика или ручной вход) | Управление. Каждая команда несёт свой ID и не исполняется дважды |
| `login.*` | API → оператор | `login.state`, `login.submit` (логин, пароль), `login.code`, `login.screenshot`; свой токен API | Форма входа (§4.8). Принимается только в режиме «ручной вход», который включил движок текущего поколения |
| `alarm` | оператор → движок | вид, подробности без секретов | Неизвестное сообщение сокета, расхождение заголовков, сбой самопроверки, переполнение, обрыв CDP |

ID попыток и запросов сайта переживают перезапуски: повторное сообщение с тем же ID ничего не делает второй раз.

### Этап 1. Прототип

**Сначала три обязательных условия.** Проверяются на собственном стенде, без Fansly: тестовая страница и свой HTTPS-сервер, который записывает реально полученные запросы. Так точнее, и рабочие аккаунты не затрагиваются. Если хоть одно условие невыполнимо, архитектуру пересматриваем с владельцем до интеграции.

Стенд:
- **Сервер стенда** — HTTP/1.1, HTTP/2 и WebSocket (в том числе WebSocket поверх HTTP/2) с сертификатом тестового CA. CA доверен только в тестовом профиле. Сервер пишет каждый полученный запрос и кадр: время, соединение, поток, метод, путь, заголовки. Этот журнал — истина о том, что физически дошло.
- **Помехи по команде теста:** задержка установления TCP и TLS, ответ 408 на повторно использованном соединении, отказ потока HTTP/2 (`REFUSED_STREAM`, `GOAWAY`), обрыв соединения.
- **Тестовый движок** — заглушка RPC (§4.13): выдаёт и отклоняет допуски по сценарию и пишет свой журнал допусков. Критерии сравнивают два журнала.
- Каждый сценарий — 50 прогонов со случайными моментами сбоя, 5 запросов на паузе и тёплым соединением HTTP/2.

1. **Потеря управления.** Сбой оператора, держателя, CDP и Chrome при задержанных запросах и открытых соединениях. Отдельно обрываем CDP на стороне Chrome при живых держателе, операторе и Chrome, не закрывая существующие соединения к серверу стенда. Критерий — ноль отправок без допуска. Для обрыва CDP сначала ищем недорогой рубеж; если его нет, проверяем запасное правило §4.1: уходят только уже задержанные разрешённые запросы, разово, и страница останавливается.
2. **Повторы и время отправки.**
   - Можно ли отключить повторы, которые Chrome делает сам, или выдавать на каждый отдельный допуск. Их вызываем намеренно: 408 на повторно использованном соединении, отказ потока HTTP/2. Критерий — на каждый допуск в журнале сервера ровно одна операция (запрос или пара preflight + запрос).
   - Даёт ли Chrome фактическое время отправки; расхождение с журналом сервера — не больше 50 мс.
   - Тест срока допуска: удерживаем установление соединения дольше срока допуска (20 с при сроке 15 с), затем снимаем задержку. Ни один запрос по просроченному допуску не уходит; замера обычной задержки недостаточно. Те же проверки — при уже открытом туннеле, зависшем TLS, повторно используемом соединении HTTP/2 и при намеренно остановленных операторе и процессе страницы.
3. **Сокет.**
   - Проверка сообщений до отправки и допуск подключения внутри страницы во всех контекстах, до запуска кода сайта.
   - Тест: первое же запрещённое сообщение не уходит.
   - Тест: новое подключение поверх уже открытого соединения HTTP/2 тоже проходит через допуск.
   - Тест: сокет из воркера и из фрейма проходит те же проверки.

Код прототипа живёт в отдельной ветке репозитория Hub и в `main` не сливается; полезное переносится в PR этапа 3.

**Потом на тестовом аккаунте Fansly** (не из хаба, прокси тестовый, §8 №13; записывающий прокси стенда — этап 2):
4. Перехват на уровне браузера держит все запросы сайта, включая стартовые и запросы его service worker.
5. Кадры сокета снимаются полностью, в том числе после переподключений.
6. Расширение отменяет запросы из списка «никогда» и неизвестные записи без оператора, в том числе при ручных кликах.
7. Порядок запуска соблюдается: до открытия выхода наружу ничего не уходит; запросы самопроверки не уходят после открытия.
8. Источник каждого ответа на запрос Hub известен (§4.2); запросы Hub не путаются с одинаковыми запросами сайта.
9. Какие сообщения сайт сам отправляет через сокет; какими путями уходят прочтения, typing и статус.
10. Сколько запросов в час делает сам сайт в спокойной вкладке и сколько при загрузке; сколько данных его ответы добавляют в `observations`.
11. Окружение страницы, включая геолокацию, применяется до запуска сайта и сохраняется после перезапуска.
12. Вход: какие экраны показывает Fansly на новом устройстве (логин, код, подтверждение по почте, капча); проходит ли вход через форму; насколько отзывчив KasmVNC от вас до сервера.
13. Ресурсы на страницу (§4.12).
14. Метка запроса Hub (фрагмент адреса) видна в `Fetch.requestPaused` и не уходит в сеть (§4.2).
15. Запросы Hub, включая медиа, по набору и порядку заголовков не отличаются от запросов сайта к тем же маршрутам (§4.7).
16. Что сайт видит об «устройстве»: WebGL-рендерер, шрифты, экран, число ядер и память — и что это не меняется после перезапуска и обновления Chrome.
17. Тела ответов сайта с данными платформы снимаются полностью — сжатые gzip и Brotli, из кэша после проверки сервером, больше 32 МиБ, — в том числе при всплеске запросов, когда буфер самого Chrome переполняется, и при намеренно задержанной обработке команд CDP с ответом больше предела буфера Chrome на один ответ (§4.3).

Результат — отчёт с цифрами.

### Этап 2. Проверка сбоями и общая нагрузка (стенд)

- **Стенд.**
  - Записывающий прокси с нашим сертификатом в тестовом профиле видит каждый запрос к Fansly. На проде его нет.
  - Расшифровка меняет условия соединения, поэтому те же сбои прогоняются и через обычный туннель к собственному HTTPS-серверу стенда.
- **Сбои:**
  - обрыв CDP на стороне Chrome при живых процессах, открытых соединениях и запросах, которые ждут допуска;
  - истечение срока допуска во время установления соединения с последующим снятием задержки;
  - зависание и падение оператора; зависание управляющей части при работающей пересылке;
  - падение держателя и Chrome;
  - повторное открытие выхода после сбоя прокси: прежние ожидающие запросы отменены, а не выгружаются с паузами;
  - заполнение диска;
  - перезапуск с сохранённым профилем;
  - потеря прокси, отказ в авторизации и смена IP;
  - рестарт `sync` посреди запроса;
  - недоступность базы.
- **Критерии на каждый сбой:**
  - ноль запросов из списка «никогда» и неизвестных записей;
  - ноль API-запросов и подключений сокета без действующего допуска; если действует запасное правило §4.1, при обрыве CDP уходят только уже задержанные разрешённые запросы;
  - ноль отправок отменённых запросов браузера после восстановления прокси;
  - ноль запрещённых сообщений сокета;
  - нет трафика мимо прокси по захвату на уровне ОС;
  - пропуски найдены и догружены;
  - ответы из буфера приняты, дублей нет.
- Каждый сбой — 20 прогонов со случайным моментом.
- **Общая нагрузка.** Семь профилей одновременно: трафик сайтов, запросы движка у потолка, всплески событий, выгрузка буфера после простоя Hub — при работающих Hub и Postgres. Проверяются пороги из этапа 0. По результату утверждаем размер сервера.
  - Источник нагрузки — сервер стенда в роли Fansly: ответы по размерам из реального трафика, кадры сокета с интенсивностью из требований — 246 в минуту на страницу и 531 на все.
  - Сценарий: 2 часа у потолка (≈ 1 300 запросов в час на страницу), всплески событий, 15 минут без Hub, затем выгрузка буфера.
  - Критерии (уточняются в этапе 0): p95 от кадра на сервере стенда до строки в Postgres — не больше 5 с; добавка браузерного слоя к запросу — p95 не больше 300 мс; после простоя буфер выгружается без потерь и дублей; память, CPU и диск укладываются в лимиты контейнеров; задержки запросов Hub к Postgres не хуже базового замера без браузеров.

## 6. Что сознательно не делаем

- **Антидетект-браузеры и облачные браузеры:** сессии страниц оказались бы у третьей стороны.
- **Управление через интерфейс сайта:** медленно, а открыть чат — значит отметить «прочитано».
- **Отдельный сторожевой процесс сети:** соединения прокси не различают отдельных запросов, поэтому сторож не заменяет рубеж отправки (§4.1). Держатель CDP-соединения лишь сохраняет перехват при сбое оператора; от самостоятельного обрыва CDP он не защищает.
- **Авторизация на порту CDP:** в сети контейнера, кроме Chrome и оператора, никого нет, а Chrome отвергает подключения к порту с заголовком Origin.
- **Selenium и WebDriver.** У классического WebDriver нет перехвата с удержанием запросов. BiDi в Chrome работает поверх того же CDP.
- **Playwright в проде.** При перехвате он выключает HTTP-кэш, перехват запросов service worker у него экспериментальный, и на каждой вкладке он сам выполняет свои действия. Нам нужна предсказуемость каждой команды. Для быстрых опытов в прототипе он допустим.
