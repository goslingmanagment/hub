# Project Browser

**Контекст**

У агентства шесть страниц на Fansly. Чаттеры работают в своих браузерах с нашим расширением и отдельными менеджерскими доступами.

Hub круглосуточно собирает сообщения, подписчиков, доходы и другие данные для дашбордов, ИИ-функций и отчётов — даже когда чаттеры не в сети.

**Как работает сейчас**

В Hub сохранён токен из личной браузерной сессии владельца. Сервер самостоятельно обращается к API Fansly через прокси соответствующей страницы. Полноценный браузер в этом процессе не участвует.

Передаётся основной токен `authorization`, но дополнительные параметры — `fansly-client-id`, `fansly-session-id`, `fansly-client-check` — у нас не заполнены и не отправляются. Часть остальных заголовков воспроизводит ранее записанные браузерные запросы.

Основное опасение — возможное усиление проверок Fansly, при котором отличия нашего клиента станут проблемой.

**Что хотим**

Для каждой страницы на нашей инфраструктуре должен работать отдельный постоянный браузер со своим профилем и собственной авторизованной сессией Fansly.

Все обращения Hub к Fansly должны выполняться через этот браузер. Hub автоматически задаёт необходимые действия, получает результаты и сохраняет данные. Работа не зависит от браузеров чаттеров.

Цель — сделать работу максимально естественной и неподозрительной с точки зрения Fansly: использовать настоящий браузер, постоянную сессию и закреплённый за страницей прокси.

Конкретный способ управления браузером и выполнения операций внутри него выберем позже.

**Возможности и условия**

- Поддерживаются любые необходимые действия: сбор данных, отправка сообщений, публикация постов, создание и управление отложенными публикациями, загрузка медиа в Vault.
- Серверный браузер **не должен отправлять отметки о прочтении сообщений**.
- Остальные фоновые действия сайта, включая статус присутствия, должны быть понятными и управляемыми.
- На страницах включена **2FA**. Владелец вручную входит через удалённый экран и вводит код. При необходимости повторной авторизации система сообщает об этом.
- Прокси остаются прежними: резидентские SOCKS, по одному на страницу.
- Работа чаттеров и расширения не меняется.
- После перезапуска сохраняется браузерный профиль, а Hub продолжает работу с сохранённого места.

- [`of-api.actulus.net`](https://of-api.actulus.net/terms-of-service) также указывает backend `app.onlyfansapi.com` и того же оператора.

**Что из исследования особенно важно для Project Browser**

- **Вход через браузер и выполнение всех операций в браузере — разные вещи.** Например, CreatorAPI описывает захват сессии после браузерного входа, а Many-Fans прямо пишет о последующей серверной работе. Ни наличие расширения, ни слово Browser в названии не доказывают нужную нам архитектуру.
- **Many-Fans описывает именно недостающий нам контекст сессии:** при подключении расширение получает `authorization`, `fansly-session-id`, `fansly-client-id`, `fansly-client-check`. Это полезный материал для исследования; перенос заголовков сам по себе не равен нашему плану с постоянным браузером. [Техническое описание](https://many-fans.com/how-many-fans-connects-to-fansly).
- **Покрытие API нужно сверять по каждой операции.** OnlyMonster ограничивает Vault API платформой OF; Substy не разрешает прямые ответы в диалогах через API; Infloww обозначает API как beta. Наличие функции в интерфейсе CRM не доказывает доступность её для Hub.
- **Для публикаций отдельно изучить ModelVI, ApiFansly, CreatorAPI, OnlyFansAPI и FBuddy.** Проверять создание, перенос и отмену отложенных постов, загрузку и обработку медиа, аудиторию/платность, часовые пояса и восстановление после сбоев.
- **Требование не отправлять отметки о прочтении пока не подтверждено ни для одного кандидата.** Его нужно проверять отдельно для загрузки истории, фоновой синхронизации, webhooks и открытия интерфейса. Наличие отдельной операции «mark as read» ещё не доказывает отсутствие побочных отметок при других действиях.

**Что проверить на следующем этапе**

1. Какие операции действительно доступны на Fansly: сообщения и история, подписчики, доходы, посты, отложка, Vault и загрузка медиа. Какие ответы живые, а какие из кэша поставщика.
2. Где выполняются запросы, где хранится профиль/сессия и работает ли сбор круглосуточно при выключенных браузерах чаттеров.
3. Можно ли сохранить наши резидентские **SOCKS-прокси** с постоянным IP для каждой страницы. Заявление «свои прокси поддерживаются» без указания протокола этого не подтверждает.
4. Как проходят ручная 2FA, повторный вход и дополнительные проверки платформы; как Hub узнаёт об истёкшей сессии.
5. Как гарантировать отсутствие read receipts и контролировать статус присутствия, фоновые действия, повторы запросов и повторные публикации после сбоев.
6. Можно ли выгрузить накопленные данные, какие доступны webhooks, лимиты и стоимость для шести страниц. Какие функции требуют отдельного тарифа или подключения API со стороны поставщика.
