# FBuddy: полезные механизмы для Project Browser

Проверено **28 сентября 2026**, пакет **2026.927.830** из сервиса обновлений Chrome. Это предметный разбор реализации для требований [Project Browser](../context.md): шесть постоянных браузеров на нашей инфраструктуре, свой профиль и SOCKS у каждой страницы, операции Hub через браузер, отсутствие исходящих отметок прочтения.

**Главная польза FBuddy — проверяемые цепочки браузерных запросов, работы с сессией, сообщений, публикаций и медиа.** Одновременно код показывает ошибки, которые нельзя переносить в Hub: автоматические повторы отправок, скрытые изменения при сборе данных и ненадёжное восстановление некоторых очередей. Готовый исполнитель всех наших требований этим исследованием не подтверждён.

Первый этап Project Browser заменяет транспорт всех текущих чтений Hub. Поэтому приоритет этого разбора — сессия, полный захват фактов, отсутствие побочных действий, ограничения нагрузки и полнота истории, доходов, статистики и постов. Отправки, расписание и загрузка в Vault относятся ко второму этапу; остальные функции FBuddy нужны здесь только как доказательства поведения транспорта или фоновых эффектов.

## Что конкретно пригодится

### 1. Запросы можно выполнять в браузере без клика по каждой операции

В расширении есть полноценный клиент Fansly API: он использует токен активной сессии, наблюдённые клиентские заголовки и браузерный `fetch` с cookies. Перехват сетевых запросов страницы поставляет контекст; сами операции расширение выполняет из своего content script. Это полезный образец исполнения команд Hub внутри нужного профиля. Наличие браузера само по себе не доказывает, что любой способ вызова неотличим от штатного сайта. Точная схема и ограничения — в [транспорте](01-session-and-transport.md).

Практический вывод для проекта: нужно сохранять привязку операции к конкретной странице, профилю и текущей сессии вместе со снимком использованного контекста. У общего транспорта FBuddy нет ни общего барьера готовности клиентских заголовков, ни атомарного переключения сессии. Собственный успешный HTTP-ответ публикуется после разбора JSON; при ошибке разбора исходное тело может быть потеряно. Для Hub запись фактов до разбора должна обеспечиваться собственным транспортом.

### 2. Историю можно читать отдельно от подтверждения прочтения, но одного выключателя недостаточно

У FBuddy чтение истории и `POST /message/ack` — отдельные вызовы. Однако настройка автоматического прочтения имеет default `true`, а отключение обработчика может отправить уже накопленные подтверждения. Если выключение произошло во время ожидания подключения, подписка может появиться после него и обрабатывать новые сообщения. Это поведение подтверждено кодом и изолированной проверкой гонки; оно не описывает все источники подтверждений в родном коде Fansly.

Для нашего требования «никогда не отправлять read receipts» нужен контроль исходящих запросов всего браузерного профиля, включая страницу, её фоновые обработчики и расширения. Проверять следует запуск, открытие чата, получение WebSocket-сообщения, переключение настроек, переподключение и рестарт. Подробности и вызывающие цепочки — в [разделе о фоне](03-background-and-recovery.md).

### 3. Кажущиеся читающими функции могут изменять аккаунт

Получение списка онлайн-фанов включает создание диалога, если у найденного пользователя ещё нет `groupId`. Загрузка профиля собеседника может автоматически записать CRM note в Fansly. Обычная отправка сообщения при холодном кеше вызывает создание служебной bot group, затем запускает typing без ожидания его завершения. Для функции изменения online status найден метод, но это ещё не доказательство его регулярного вызова. Нельзя присваивать всему модулю статус read-only по названию экрана. [Фоновые действия и их условия](03-background-and-recovery.md), [цепочка отправки](02-operations-and-media.md).

Практический вывод: для каждой команды нужны полный набор исходящих действий и разрешённые побочные эффекты. Самостоятельный сбор истории, подписчиков и доходов не должен запускать создание диалогов, запись заметок или отправку статусов. Контроль должен работать до запуска сайта, включая ручную диагностику.

### 4. В одном продукте есть разные правила повторной отправки

Общая обёртка выполняет до **шести попыток**, включая обычные отправки сообщений и некоторые другие изменения. После принятого сервером запроса и потери ответа такой повтор может создать дубль.

В этой версии также найден реально подключённый интерфейс нативной массовой отправки: создание broadcast group → подготовка вложений → отправка broadcast. Для создания группы и отправки выставлено `retry: false`; интерфейс фиксирует начало попытки и при ошибке предупреждает, что Fansly мог уже принять запрос. Это более полезный образец работы с неопределённым результатом, но локальный флаг интерфейса не заменяет постоянное состояние команды в Hub.

Правило Hub остаётся строже: не более одной попытки выполнения команды; неопределённый результат требует сверки, а не повторной отправки. Две схемы массовых сообщений и их ограничения разобраны в [операциях](02-operations-and-media.md).

### 5. Загрузка файла, подготовка вложения и публикация — разные этапы

Найдена полная цепочка: создание upload → загрузка частей → завершение → ожидание обработки → создание account media/bundle → прикрепление к сообщению или посту. `mediaId`, `accountMediaId` и `bundleId` имеют разный смысл. Истечение URL/cookie для скачивания не означает, что сам объект медиа исчез или его нужно загрузить повторно.

Права доступа и платность могут находиться внутри вложений: нулевой верхнеуровневый `price` не доказывает бесплатность всего содержимого. В старом последовательном Mass DM есть опасный путь, где ошибка подготовки вложений превращается в готовый результат с пустым списком медиа. Для Hub это основание проверять полноту результата каждого этапа до отправки. [Медиа, permissions и сбои](02-operations-and-media.md).

### 6. Нативное расписание и работающий фоновый исполнитель решают разные задачи

Auto Posts пополняет нативную очередь отложенных постов Fansly из банка шаблонов. Story Scheduler хранит задания и исполняет публикацию при открытой вкладке; сама документация указывает эту зависимость. Наличие очереди в интерфейсе не доказывает выполнение после закрытия браузера. [Код и операции](02-operations-and-media.md), [публичные сценарии](04-sources-and-scope.md).

У некоторых исполнителей есть общая блокировка между вкладками, локальные отметки и сохранение результата на backend. Эти механизмы полезны как перечень состояний для проектирования, но не доказывают отсутствие дублей. У Template Send Queue игнорирование ошибки удаления задания из кеша позволяет повторить отправку уже на следующем проходе, без падения. Успешная отправка и сохранение её результата также могут расходиться. [Восстановление](03-background-and-recovery.md).

### 7. FBuddy использует несколько мест исполнения

В пакете различаются прямые Fansly-запросы, локальная обработка медиа в контексте страницы, background для auth/cookies и запросов к backend, удалённый watermark, management session для отдельных функций и специальная ветка Electron. Из наличия работающего расширения нельзя заключить, что все функции продукта исполняются в этой вкладке. Из Electron-ветки нельзя восстановить отсутствующий код desktop host. [Сессия и границы транспорта](01-session-and-transport.md), [внедрение media processor в страницу](/Users/dmitriy/code/1-platform/fbuddy-analysis/snapshots/2026.927.830/layout/readable/content-scripts/main.js:20068).

Для нашего проекта это принципиальная граница: каждую операцию нужно привязать к фактическому процессу, сессии и сетевому выходу. Обещание managed proxies не подтверждает использование именно наших SOCKS или единый маршрут для API, WebSocket, загрузки и скачивания медиа.

WebSocket FBuddy создаётся самим расширением. Он даёт сведения о протоколе и подписчиках, но не реализует требование Project Browser получать события из соединения, открытого сайтом. Переподключение этого socket также не доказывает восстановление пропущенных событий. [Топология и восстановление](03-background-and-recovery.md).

## Соответствие требованиям Project Browser

| Требование | Что даёт исследование FBuddy | Что остаётся проверить отдельно |
|---|---|---|
| Все операции Hub через браузер | Реальные цепочки API-вызовов из content script | Внешний интерфейс управления, изоляция команд и результатов |
| Готовая сессия перед запросом | Наблюдение заголовков, отдельные account/token guards | Барьер готовности и неизменный контекст запроса, проверка ожидаемого account ID |
| Шесть независимых страниц | Account-scoped части состояния и отдельные проверки смены аккаунта | Полная изоляция профилей, кэшей, очередей и сессий |
| Постоянный SOCKS каждой страницы | Публичное упоминание proxy у CRM | Настройка нашего SOCKS и фактический маршрут каждого типа трафика |
| Никогда не подтверждать прочтение | Отдельный ack endpoint, default и реальные фоновые callers | Покрытие исходящих ack из всего родного сайта и всех его контекстов |
| Предсказуемый фон | Карта WebSocket, typing, runners и скрытых изменений | Разрешённый набор фоновых действий собственного клиента |
| События из WebSocket сайта | Протокол отдельного socket расширения | Захват штатного socket, долговечный приём, подтверждения и восстановление пропусков |
| Ограниченная нагрузка | Пример общего limiter; после истечения двухсекундной lease он не учитывает поздний outcome, включая 429 | Учёт всех выполняющихся запросов, служебного трафика и поздних ответов; проверка под нагрузкой |
| Исходные факты до разбора | Наблюдение ответов; собственный fetch FBuddy сначала разбирает JSON | Журнал Hub до бизнес-разбора, сохранение непонятных ответов, дедупликация при повторной доставке |
| Переживать рестарты | Примеры очередей, checkpoints, leader и неоднозначных результатов | Долговечность браузерного профиля и восстановление без повторной отправки |
| Ручной вход и 2FA | Чтение существующей сессии, реакции на её утрату | Удалённый экран, уведомление владельца, повторный вход и безопасное возобновление |
| Текущие чтения Hub | История, аудитория, деньги, `/it/amoie/stats`, `/it/moie/statsnew`, `/timelinenew/:accountId`; примеры частичных результатов | Полная карта потоков Hub, покрытие каждой страницы/месяца, единицы, пропуски и сверка; скачивание медиа для ИИ учитывается отдельно |
| Сообщения, посты, расписание, Vault | Подробные последовательности операций и media lifecycle | Контракты собственной реализации и проверка исходов на выбранной странице |

## Границы результата

Это анализ поставленного кода и официальных инструкций с изолированными проверками отдельных функций на заглушках без сети. Расширение не устанавливалось, аккаунты не подключались, реальные операции Fansly не выполнялись. Проверки воспроизвели гонку auto-read, потерю позднего результата limiter, повтор Template Queue при отказе удаления и повтор POST при ошибке разбора ответа. Они подтверждают эти ветки кода, но не частоту их возникновения на живых аккаунтах. Числа limiter и UI-ограничения FBuddy не являются подтверждёнными лимитами Fansly.

Исходный CRX и его представления сохранены вне Hub, в [отдельном snapshot](/Users/dmitriy/code/1-platform/fbuddy-analysis/snapshots/2026.927.830/extracted/manifest.json). Здесь находятся описания поведения и ссылки на доказательства. Они заменяют июльский пакет как основную базу для дальнейшей работы; номера строк относятся именно к `2026.927.830`.
