## Как читать технические утверждения

- **Метод**: в коде есть построение и отправка конкретного запроса. Без caller это не свидетельство фонового выполнения.
- **Вызывающая цепочка**: проверены условие запуска, метод и обработка результата. Указанные условия обязательны для вывода.
- **Наблюдаемый трафик**: network hook реагирует на запрос страницы. Само наличие URL в matcher не означает отправку расширением.
- **FBuddy backend**: клиент делает запрос в собственный сервис FBuddy. Его дальнейшие обращения к Fansly, сетевой маршрут и политика повторов не видны в CRX.
- **Вывод для Project Browser**: предлагаемое применение находки к требованиям проекта; это не уже реализованная возможность Hub.

## Что этот пакет не раскрывает

Не установлен публичный API управления всем браузером FBuddy. Не подтверждены наш SOCKS на профиль, постоянно работающий browser host на нашей инфраструктуре, восстановление полного профиля после аварии, удалённый ручной вход с 2FA, сквозная блокировка read receipts, долговечная защита всех отправок от повторения или полнота восстанавливаемой истории.

Для первого этапа отдельно нужны проверка захвата WebSocket, открытого самим сайтом, и полная карта текущих чтений Hub. Socket расширения FBuddy, его кеши и частичные агрегаты этих гарантий не дают. Разобранные маршруты и примеры пропусков находятся в [операциях](02-operations-and-media.md); окончательную полноту определяют потоки Hub и их критерии покрытия.

Для desktop CRM в расширении видны Electron-маркеры и точки интеграции. Основного процесса desktop host в CRX нет, поэтому нельзя приписывать ему способ проксирования, изоляцию профилей или механизм подстановки токена на основании одного маркера.

У браузерного клиента есть конкретные настройки задержек, конкурентности и восстановления соединения. Ни одна из них не доказывает устойчивую работу 24/7 на шести страницах. Проверять это нужно на собственной реализации и фактическом маршруте запросов, с явной фиксацией пропусков данных и неопределённых исходов команд.
