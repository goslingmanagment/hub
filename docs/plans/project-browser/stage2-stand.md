## 2. Как устроен стенд и как защищён прод

| Условие владельца (№14) | Как выполнено |
|---|---|
| Отдельный compose-проект, своя сеть | Проект `pb-stand` в `/opt/pb-stand`; внутренняя сеть `10.231.0.0/24` без выхода наружу и без связи с сетями Hub. Боевые контейнеры и база не тронуты |
| Лимиты CPU и памяти | У каждого контейнера: вместе 2,6 CPU и 3,4 ГБ, без swap; сами не перезапускаются — после перезагрузки сервера стенд остаётся выключенным. Сборка — в контейнере BuildKit с 2 CPU и 3 ГБ |
| Доступ к Docker | Раннеру стенда — только узкий прокси: команда в браузере стенда, её запуск и перезапуск этого контейнера; остальное — 403. `Privileged` и чужие переменные отбрасываются |
| Хост | Одно изменение: профиль AppArmor загружен в ядро (`apparmor_parser -r`), в `/etc/apparmor.d` не записан. Сетевые правила хоста и `br_netfilter` не трогались |
| Сторож | Временная служба systemd: раз в 5 с ответ Hub и память хоста. Порог: один ответ дольше 500 мс, в среднем за 30 с дольше 50 мс, свободной памяти меньше 4 ГиБ или нагрузка выше 6 — все контейнеры стенда останавливаются, и до снятия отметки стенд не поднимается |
| «Заполнение диска», «недоступность базы» | В этой части не запускались: им нужны буфер и движок этапа 3. Для них — отдельный том фиксированного размера и своя база стенда (§5) |

## 3. Находки

1. **AppArmor.** Песочница Chrome включена и под стандартным профилем Docker `docker-default`: шаблон Docker закреплён на ABI 3.0, где создание user namespace не проверяется. Профиль `page-browser` оставлен — он разрешает `userns` явно, чтобы смена шаблона Docker не отключила песочницу (PR 2, `1694223a`).
2. **Сеть стенда.** Внутренние сети Docker не дают контейнеру маршрута по умолчанию: всё вне сети отвечает `ENETUNREACH` раньше правил nftables, и `net-selftest` справедливо не считает это доказательством. Для проверки образа стенд добавляет маршрут по умолчанию внутри своей сети (`stand-route.sh`); образ не меняется. На проде у `pb-egress` есть шлюз.
3. **Проверка здоровья образа** проходила при упавшем X-сервере (`a && b` под `set -e`). Исправлено в PR 2 (`804b5fba`).
4. **Замеры сторожа.** Первые полтора часа сторож показывал «всплески Hub» по 80–93 мс. Это был он сам: служба с `CPUQuota=10%` ждала своей квоты (2 993 урезанных периода из 4 907). Посекундная проверка вне этой квоты всплесков не видела. Квота поднята до одного ядра; дальше Hub — 1–3 мс.
5. **Сборка.** Загрузка собранного образа в Docker (`--load`) идёт в самом dockerd, вне лимитов сборщика; в эти минуты ответ Hub однажды был ≈ 80 мс (с учётом п. 4 — вероятно, тоже квота сторожа).
