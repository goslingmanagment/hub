  - **№3** — предложение по решению владельца №3, утверждается сейчас;

- Номера решений владельца — из плана §8. Сейчас владелец утверждает режимы трафика сайта и пороги (разделы 3 и 4, №3; список — раздел 11). Из неё при сборке образа получаются правила расширения (§2.7), оператор берёт из неё свою таблицу решений (план §4.3). Здесь таблица разбита на части для чтения.

Режимы строки: «автоматика», «ручной вход», «оба»; «закрыто» — запрещено, пока владелец не откроет операцию отдельным решением. Чего нет в карте среди путей API, то запрещено; сторонние хосты, которые грузит сам сайт, пропускаются (§2.1).

- Любой другой хост под `fansly.com` идёт как страница сайта: без пейсинга, с журналом; записи на него закрыты (PR 6).
- Хост сокета отдаёт только сокет сайта `wss://wsv3.fansly.com/` с любыми параметрами: остальное к нему отменяют и оператор, и расширение (этап 1, §3.2; PR 6).
- Локальные и частные адреса закрыты по адресу в запросе — имени или литералу. Адреса — все записи реестров IANA IPv4 и IPv6 Special-Purpose Address Registry, которые не адрес назначения: «Globally Reachable: False», плюс решения с причиной по остальным (`apps/page-browser/src/policy/special-addresses.ts`; тест сверяет таблицу с реестрами построчно — их CSV от 2026-10-13 лежит в `tests/fixtures/iana/`). Открыты записи «True»: `64:ff9b::/96` (RFC 6052 §3.1 — только глобальные IPv4), AS112 (`192.31.196.0/24`, `192.175.48.0/24`, `2620:4f:8000::/48`), AMT `192.52.193.0/24`. Закрыты с причиной: `2001::/23` целиком — вместе с вложенными записями «True» (anycast-службы, AMT, AS112, идентификаторы ORCHIDv2 и DET), Teredo `2001::/32` («N/A»); `2002::/16` 6to4 («N/A»: адрес содержит IPv4, в том числе частный); `192.0.0.0/24` целиком, вместе с anycast PCP и TURN; устаревший `192.88.99.0/24`; многоадресные `224.0.0.0/4` и `ff00::/8` (их нет в этих реестрах). `64:ff9b:1::/48` и `5f00::/16` — «False», закрыты. Литерал сравнивается в каноническом виде (IPv4 в десятичной записи, IPv6 по RFC 5952), так же как его пишет Chrome. Во что SOCKS5 страницы разрешает имя, не проверяется: DNS разрешается на стороне прокси страницы намеренно (план §4.5 — оператор передаёт имя и сам его не разрешает, иначе поведение DNS страницы стало бы другим), а частные адреса за прокси страницы — сеть его поставщика, не Hub: правила контейнера пускают оператора только на адрес и порт SOCKS5. Это сознательный остаток (разбор Astra PR 6).
- Наружу страница выходит только по TLS: обычный HTTP прокси отклоняет, навигации по `http://` Chrome поднимает до `https://` политикой (§8.1).
- Имена, которых нет в сети (`.invalid`, `.test`, `.example`, `.onion`, `.alt`), прокси не пускает вместе с локальными. Расширение их не трогает: под `.invalid` живёт подменный хост запросов Hub (`<хост>.pb-hold.invalid`), и Chrome должен такой запрос выпустить.

- Правило первого этапа: любые `POST`, `PUT`, `PATCH`, `DELETE` к API запрещены, кроме операций входа (план §4.6). Им закрыты `POST /group` (создаёт диалог), `POST /notes` и `/notes/edit` (заметки CRM) и записи второго этапа из разбора FBuddy: `POST /message`, `/message/broadcast`, `/message/delete`, `/post`, `/wall/postedit`, `/post/{id}/delete`, `/post/scheduled/{id}/cancel`, `/account/media`, `/account/media/bundle`, `/account/media/permissions`, `/vault/albums/media`, `/mediastories`, загрузка на `mediav2.fansly.com` (`fbuddy/02-operations-and-media.md:15-26`).
- Маршруты `auth.*` — POST, с бюджетом маршрута по умолчанию и вне семейства `site`: вход не ждёт неизвестных путей. Каталог сегодня знает только GET (`fansly/routes.ts:50-51`); POST добавляет PR 8.
- В режиме «ручной вход» проходят операции входа и чтения, которые делает интерфейс (план §4.8, решение №2; PR 15): все чтения API, открытые картой в автоматике, — строки §2.2 и `site.other`, в том числе `account.me`. Они идут через тот же допуск сайта, паузу между запросами и бюджеты; паузу владельца, остановку по учётным данным и режим «только проверки» проходят, как операции входа. Закрытые чтения (§2.5) и записи, кроме операций входа, закрыты и в нём; сокет сайта получает отказ `mode`.
- На `apiv3` закрыто всё, кроме открытых строк (PR 6): не только записи, но и `HEAD`, путь вне `/api/v1`, другой порт или схема, имя хоста с пользователем или точкой на конце — «чего нет в карте среди путей API, то запрещено». Другие операции входа, которые Fansly может попросить у нового устройства, не открыты: каждая открывается отдельным решением.
- **Подтверждение входа с нового устройства по почте** (решение владельца 2026-10-15: открыто только на время входа, в режиме «ручной вход», никогда в автоматике). По публичному бандлу сайта (`main.2e6b96097a4bb73b.js`, окно входа `app-login-modal`) это не отдельная операция: на `POST /login` Fansly отвечает не сессией, а `twofa` с типом 2 и адресом почты и присылает на неё код; сайт показывает в том же окне то же поле кода, что и для 2FA (`#fansly_twofa`, кнопка «Verify»), с пометкой «Login from a new device … we have sent a verification code to the following email address», и отправляет код тем же `POST /login/twofa {token, code}`. Ссылки из письма, чтения, которое ждёт подтверждения, и повторной отправки кода в бандле нет. Так, видимо, и выглядел второй шаг первой сессии на тестовом аккаунте без 2FA ([`stage1-stand.md`](stage1-stand.md), §9). Поэтому новых строк в карте нет: код из письма идёт строкой `/login/twofa` — маршрут `auth.twofa`, его бюджет, допуск сайта и пауза, только в режиме «ручной вход»; в автоматике и вне входа она закрыта. Что добавлено — распознавание этого экрана (§7) и поле «Код из письма» в форме дашборда. Почтовые операции бандла `/login/email`, `/login/email/verify`, `/login/email/verification` и `/login/email/verification/token` — смена и подтверждение адреса почты аккаунта в настройках, а не вход: их закрывает общее правило записей.

Выплаты (`/payments/payout*`, `/payouts/**`) поштучно не закрыты: записи держит общее правило (§2.4), а чтения каталога `payouts.methods` и `payouts.requests` разрешены.

В карте (PR 6) строка записей закрыта для `POST`, `PUT`, `PATCH` и `DELETE`, строка «любой метод» — для всех методов; `**` — путь и всё под ним, `password*` — сегмент с таким началом. Четыре строки «любой метод» — единственные закрытые чтения: чтения API открывает `GET /**` (§2.4), и общее правило за ними не стоит. Поэтому их закрытие держится в любом написании пути, которое может выпустить Chrome: любой регистр, повторные косые черты, косая черта в конце — их читает само правило строки; экранированные `%XX` буква, цифра, `-._~` или косая черта — их на API закрывает отдельное правило для любого пути (§2.7, уровень 350), так же решает таблица оператора. Такие экранирования клиенты не пишут, а сервер может прочитать их как сам символ. Путь с `;` или другим окончанием (`/emails/unsubscribed`) — другой путь и остаётся чтением.

Закрытое действует в обоих режимах, при ручном доступе и без оператора (план §4.6), пока владелец не откроет операцию (решение №2: постоянного «никогда» нет; выплаты из списка убраны). На первом этапе все записи, кроме входа, и так закрывает правило записей (§2.4). Когда записи начнут открываться, эти операции остаются закрытыми поштучно, пока их не откроют отдельно. Сайт сам, без людей, шлёт прочтения, typing и статус «онлайн»: открытые, они снимали бы непрочитанное у чаттеров и показывали модель в сети.

### 2.7 Правила расширения и тест одинаковости

Как собрано в PR 6 (`apps/page-browser/src/policy/rules.ts`; `rules.json` получается из карты при сборке образа):

| Уровень | Приоритет DNR | Правило | Действие |
|---|---|---|---|
| 1 | 400 | закрытые поштучно (§2.5): методы строки (у строки «любой метод» — все) и её путь; по правилу на строку для `apiv3.fansly.com` и для подменного хоста запросов Hub | `block` |
| 1а | 350 | путь на хосте API с экранированной `%XX` буквой, цифрой, `-._~` или косой чертой, любой метод: такого написания клиенты не пишут, а за ним закрытое чтение прошло бы уровень 2а | `block` |
| 2 | 300 | операции входа (§2.4): `POST` и точный путь, только настоящий хост | `allow` |
| 2а | 250 | чтения API и их preflight: `GET` и `OPTIONS` под `/api/v1` на `apiv3.fansly.com` и на подменном хосте; сокет сайта `wss://wsv3.fansly.com/` | `allow` |
| 3 | 200 | всё остальное на хосте API; любая запись (не `GET`, `HEAD`, `OPTIONS`) на любой хост под `fansly.com`; `chatws.fansly.com` и `mediav2.fansly.com` целиком; всё остальное на хосте сокета | `block` |
| 4 | 100 | `localhost` и частные адреса — по адресу в запросе | `block` |

- При равном приоритете DNR предпочитает `allow`, а не `block`, поэтому приоритеты строго разные: строка входа не откроет закрытое поштучно. `OPTIONS` правило 3 не закрывает: preflight строит сетевая служба Chrome (план §4.6).
- Уровень 2а делает уровень 3 точным: на хосте API закрыто всё, чего нет в карте, — так же решает таблица оператора. Без него `HEAD` или путь вне `/api/v1` расширение бы пропустило, а оператор — нет.
- Разрешающие правила точные и чувствительны к регистру: схема, имя хоста как есть, без порта и пользователя. Запрещающие уровня 3 берут хост в любом написании. Список типов ресурсов задан явно: без него DNR пропускает `main_frame`, а форма, отправленная кликом, — это `main_frame`.
- Запрос Hub выпускается с подменного хоста (`<хост>.pb-hold.invalid`), и правила видят его: уровни 1, 2а и 3 покрывают и этот хост, вход — нет.
- Chrome компилирует каждое выражение с пределом памяти и правило сверх предела молча выбрасывает. На Chrome 155 предел — около 112 инструкций RE2; первый вариант правил PR 6 так терял три закрытые строки. Сборка считает оценку сверху и отказывает выражению дороже 80; стенд спрашивает у самого Chrome (`isRegexSupported`, с запасом) и сверяет число включённых правил.
- Правило уровня 1 привязано к хосту в начале выражения, а не через `requestDomains`: иначе оно закрыло бы путь и на поддоменах хоста API, которые карта пропускает как прочие хосты Fansly.
- Тест одинаковости (`tests/page-browser-rules.test.ts`) собирает правила из `operations.ts` и проверяет:
  - правила уровня 1 и закрытые поштучно строки таблицы оператора — одно множество: у каждой строки ровно по одному правилу на каждый из двух хостов API, с её методами;
  - закрытое чтение отменяют оба рубежа в каждом написании пути, которое может выпустить Chrome (регистр, косые черты, каждая буква в `%XX`, косая черта в `%2F`), и только его: соседние пути остаются чтениями;
  - ни одно правило уровня 2 не совпадает с закрытой строкой, и ни одно правило уровня 1 — с операцией входа;
  - у каждой закрытой строки и у каждого общего запрета есть пример адреса, и его отменяют оба рубежа в обоих режимах;
  - по сетке написаний — хосты, схемы, методы, пути, больше 50 тысяч запросов — расширение отменяет ровно то, что закрывает таблица оператора.
- Стенд (`apps/page-browser/stand/rules-check.sh`, он же в `image-check.sh`) повторяет примеры на настоящем Chrome без оператора: на месте прокси слушает скрипт и записывает всё, что Chrome ему принёс.

Как работает класс `site`:
- Внутри класса запросы идут по времени паузы `Fetch`. Запрос, чей маршрут закрыт бюджетом, пропускается, как ключ при выборе работ (`apps/runtime/src/sync/README.md:1020-1021`).
- Отказ сразу, не дожидаясь 60 с: пауза страницы (кроме операций входа в «ручном входе», план §3.2), удержание страницы или маршрута дольше остатка ожидания, операция не из текущего режима, потолок часа, полный буфер.
- Пауза пейсера отсчитывается от фактической отправки самого запроса (`siteDone`); следующая операция со своим preflight начинается не раньше паузы. Так «одна операция» решения №1 выглядит в журнале.
- Попытка сайта пишется с маршрутом, и часы маршрутов считают её своему маршруту; отправку без маршрута движок считал бы на все маршруты (`apps/runtime/src/sync/README.md:1016-1019`). Ответ сайта движок разбирает как свой (`engine/errors.ts`): 429 держит только маршрут, 401 и 403 — остановка страницы по учётным данным.

**Доли слотов.** В цикле 11 позиций: U на 0, 2, 4, 6, 8; R на 1, 3, 5, 7; P на 9; S на 10. Как сегодня, класс без работы пропускается без ожидания и не копит долг (`engine/scheduler.ts:9-16`).

| Работа есть у | U | R | P | S |
|---|---|---|---|---|
| всех | 5/11 ≈ 45 % | 4/11 ≈ 36 % | 1/11 ≈ 9 % | 1/11 ≈ 9 % |
| R, P, S | — | 4/6 ≈ 67 % | 1/6 ≈ 17 % | 1/6 ≈ 17 % |
| U, P, S | 5/7 ≈ 71 % | — | 1/7 ≈ 14 % | 1/7 ≈ 14 % |
| U, R, S | 5/10 = 50 % | 4/10 = 40 % | — | 1/10 = 10 % |
| S и один класс | U, S: 5/6 ≈ 83 % | R, S: 4/5 = 80 % | P, S: 1/2 = 50 % | 1/6, 1/5 или 1/2 |
| только S | — | — | — | все слоты, до потолка часа |
| нет у S | как сегодня: 50 / 40 / 10 %, без срочной 80 / 20 % (`engine/scheduler.ts:13-16`) | | | |

**Что это значит при S = 2,5 с.**
- Пауза в среднем 2,75 с: S × (1 + u), u от 0 до 0,2 (`engine/pacer.ts:30`, `:208`). Потолок — ≈ 1 309 отправок в час на страницу.
- При полной занятости движку — 10 слотов из 11 (≈ 1 190 в час), сайту — 1 из 11 (≈ 119 в час, примерно запрос в 30 с).
- Обычный час: движок занимает 5–9 % потолка (`context.md:111`), сайт ограничен только своим потолком. Вместе — не больше ≈ 32 %.
- Пиковый час: движок — до ≈ 1 000 запросов (≈ 77 %). Свободно ≈ 309 слотов, сайт может взять 300: страница работает у самого потолка, без запаса. Свой объём движок успевает (≥ 1 190 > 1 000), но любая добавочная работа, например заявка на историю, ждёт дольше.
- Срочная работа: когда у сайта есть запрос, между U на позициях 8 и 0 стоят два слота, P и S. Худшее ожидание — три паузы вместо двух: до ≈ 9 с вместо ≈ 6 с. SLO срочных работ в `sync check live-hour` — 12 с (`apps/runtime/src/sync/checks/live-hour-rules.ts:68-69`); пилот проверяет их вместе с трафиком сайта.
- Заявки на историю при полной занятости получают 36 % слотов вместо 40 %.
- Сайт при загрузке: за 60 с ожидания проходит около 21 его запроса при свободном движке и около 2 при занятом, из них путей вне каталога — не больше 20 (на тестовом аккаунте — 15 за первую минуту после входа, 1–2 в минуту в спокойной вкладке). Если п. 10 покажет больше, известные пути сайта получат свои маршруты (§2.4), а при занятом движке часть запросов сайта всё равно получит `Failed`. Какие фоновые функции сайта тогда пускать, решает владелец (план §7).

| Что | Значение | Статус |
|---|---|---|

| Потолок возраста | 72 ч: выходные без Hub | №6 |

При исчерпании объёма, возраста или диска (план §4.3, §4.4, п. 8):
1. Новые запросы сайта получают отказ `buffer_full`.
2. Страница останавливается: движок ставит паузу, оператор закрывает выход. Сокет сайта рвётся вместе с туннелями (план §4.5).
3. Оператор ставит метку `gap` от последнего сохранённого события; движок читает пропуск назад не позже последнего принятого им события сокета (план §4.4, п. 6). Записанное в буфере не удаляется до `ack`.
4. Место освободилось — запуск заново по плану §4.1, движок догружает пропуск.

Оценка до замеров:
- Без Hub допусков нет, поэтому за простой копятся только кадры сокета и метки пропуска. Самая активная страница, ari-1, — ≈ 9,6 тыс. кадров в сутки (`context.md:112`), за 72 ч ≈ 29 тыс. Объём кадра снимает п. 13.
- На семь страниц нужно до 14 ГиБ диска под буферы. Это входит в расчёт диска сервера (`context.md:71`).

## 6. Протокол движок ↔ оператор

Транспорт — план §4.13: одно WebSocket-соединение `sync` → `ws://page-browser-<страница>:7700/rpc`, сообщения JSON, тела — двоичными кадрами. API подключается туда же со своим токеном и шлёт только `login.*`.

### 6.1 Типы

```ts
// MonoMs — CLOCK_MONOTONIC ядра, мс, общие для процессов сервера (план §4.2, шаг 5); WallMs — эпоха Unix, мс.
// Сроки — абсолютные моменты, не остатки. ID переживают перезапуски: повтор с тем же ID не исполняется дважды.
type MonoMs = number; type WallMs = number; type Sha256Hex = string;
type AttemptId = number;      // sync_attempts.id: попытка Hub, сайта, входа или сокета
type SiteRequestId = string;  // UUID; оператор пишет его в буфер до siteAdmit
type ConnectionId = string;   // UUID подключения сокета сайта; в буфер до wsAdmit
type CommandId = string; type BufferId = string; type BodyId = string;  // UUID
// Тело — двоичные кадры: 16 байт bodyId | 4 байта номер части | 1 байт «последняя» | до 1 МиБ данных.
// Пустое тело — тоже один кадр, последний. Флаг 2 «брошено» (без данных) отменяет уже присланные части
// тела после ошибки чтения: исход остаётся в буфере до следующей доставки. Часть 0 начинает тело
// заново — тела повторяются при каждой доставке исходов (PR 9).
interface BodyRef { bodyId: BodyId; decodedBytes: number; sha256: Sha256Hex }  // части приходят раньше JSON
type Mode = "automation" | "manual_login";  // «автоматика», «ручной вход»
type Step = "exit_closed" | "env_applied" | "chrome_started" | "control_attached" | "selftest_passed"
  | "exit_ip_verified" | "exit_open" | "site_loaded" | "session_confirmed" | "ready";  // план §4.1

### 6.2 Что добавлено к таблице плана §4.13

- `helloResult` — ответ на `hello`: версия, ID буфера и состояние или отказ. `commandResult` — исход команды; `command.notAfterMono` — срок: просроченная команда не исполняется (`context.md:130`).
- `recover` и `recoverResult` — сверка незавершённых попыток с буфером при старте движка. План описывает её в §3.2 («Приём буфера и восстановление»), но сообщения для неё в §4.13 нет.
- `wsDone` — исход Upgrade сайта. Без него движок не закроет попытку `ws.connect`, а в полёте может быть только одна.
- `resultAck` подтверждает исход любой попытки: `result`, `siteDone`, `wsDone`. Неподтверждённые исходы оператор повторяет после переподключения.
- Откуда у `hello` прокси и окружение браузера новой страницы (решение владельца 2026-10-15, план §3.2 «Подключение новой страницы через браузер», шаги 0–1): из черновика, начатого в дашборде. Владелец вставляет прокси в одно поле в любом привычном формате (разбор — `packages/shared/src/proxy-paste.ts`), проверяет её через Hub (`POST /api/v1/page-browser/proxy-check`: то же приветствие SOCKS5, что у оператора, и место выхода по сервису IP-информации через прокси), подтверждает окружение, предложенное по месту выхода; `add-profile` регистрирует профиль по черновику. Протокол не меняется: `socks5` и `env` приходят в `hello`, как раньше, а оператор сверяет окружение и выходной IP сам.

### 6.3 Совместимость версий

1. Версия — пара `major.minor`, начальная 1.0. Движок шлёт в `hello` все major, которые умеет, и свой minor. Оператор выбирает старший общий major и возвращает выбранную версию в `helloResult`.
2. Внутри major — только добавления. Новое поле — необязательное, незнакомые поля получатель пропускает. Новый тип сообщения, вид команды или значение перечисления — это следующий minor; отправитель шлёт их, только если minor другой стороны их знает.
3. Неизвестный тип или значение внутри major — ошибка протокола: получатель закрывает соединение, движок открывает тревогу `browser_down` с причиной `protocol_error`.
4. Поле, от которого зависит безопасность — срок, поколение, допуск, отпечаток сессии, — вводится или меняет смысл только с новым major: старый получатель пропустил бы его молча.
5. Соседние версии работают вместе. Движок выкатывается с Hub, оператор — с образом браузера, порознь: движок релиза R работает с оператором релиза R−1, и наоборот. Смена major — в три шага: движок учится новому major, не забывая старый; операторы переходят по одной странице; следующий релиз движка убирает старый.
6. Общего major нет — `helloResult` с отказом `protocol_major` и списком `supportedMajors`, соединение закрывается; форма этого отказа не меняется ни в одной версии. Оператор остаётся на шаге 1 плана §4.1, выход закрыт. Движок пишет причину `protocol_version` в состояние страницы (`page_browsers`), открывает тревогу `browser_down` и не выдаёт допусков: страница стоит. Те же правила действуют для API и `login.*`.

### 6.4 Запросы сайта у оператора (PR 7)

При завершении ещё ждущего запроса оператор отзывает его через `admissionCancel` (minor 2): kind/id и текущее RPC-соединение ограждают отмену. Движок удаляет ожидающий запрос; если допуск пересёк отзыв, его исход всё равно приходит обычным `siteDone`/`wsDone`. Поздний допуск не выпускает умерший запрос. Неотправленный исход не расходует ход сайта и паузу пейсера. Старому движку minor < 2 оператор новое сообщение не шлёт: сохраняется прежний путь таймаута и позднего результата.


Как оператор исполняет §3 и план §4.3 (`apps/page-browser/src/intercept/`); формы сообщений §6.1 не меняются.

- **Когда спрашивает.** ID запроса (UUID) пишется в буфер до `siteAdmit`; попытка допуска и «выпущен» — до выпуска; строка уходит одним коммитом с `siteDone`. Отказ сразу, без `siteAdmit`: выход закрыт, страница не поднята или остановлена, буфер не принимает запись. Без связи с движком запрос ждёт и спрашивается, когда связь появится; новое соединение спрашивает заново всё, на что не ответили, тем же ID. Ответ считается только на том соединении, на котором спрошен; допуск, который пришёл к ушедшему запросу, сразу закрывается `siteDone` с `sent: false`.
- **`siteAdmit`.** `method` у операции с preflight — метод её запроса (`Access-Control-Request-Method`), а `resourceType` — как Chrome показал вставший на паузу запрос (у preflight Chrome 155 называет тип его запроса, например `XHR`). `sessionFingerprint` — сессия самого запроса по его заголовкам; у preflight (своих заголовков сессии нет) — живая сессия; нет ни той, ни другой — `null`. Запрос после preflight с другой сессией не выпускается.
- **Тела.** Потоковая выдача включается на паузе стадии запроса, до `siteAdmit`, и подтверждается до выпуска (на Chrome 155 проверено: все байты приходят); если сессия запроса в этот момент ещё не известна — на стадии ответа, до первого байта тела. Тело целое, если запрос кончился `loadingFinished` и ни один кусок не потерян; у тела, которое страница читала потоком (в CDP это «отмена» после ответа, [`stage1-stand.md`](stage1-stand.md), поправка 8), — если длина совпала с заявленной (без сжатия) или тело — целый JSON-объект или массив. При любом конце пришедшее должно совпасть с заявленным: длина тела без сжатия — с `content-length`, а пустое тело годится, только если ответ и заявлен пустым (204, 205, 304, `content-length: 0`). Так отметкой становится ответ, который service worker сайта передал странице, не читая: Chrome 155 отдаёт его байты запросу самой страницы, а тот в `Fetch` не останавливается. Приложение сайта шлёт запросы к API с `ngsw-bypass=true`, мимо воркера (`packages/fansly/src/wire/public.ts`); на тестовом аккаунте тела 44 ответов из 44 пришли целыми ([`stage1-stand.md`](stage1-stand.md), §9). Иначе `site.response` идёт с `complete: false` и без тела; его `body` — ссылка на пустое тело, кадров нет. Редирект отдаётся странице конечным, без `Location`, и пишется как ответ с пустым телом. Растущее тело считается в потолке буфера уже по мере записи: кусок, которому места нет, не пишется — буфер полон (страница останавливается), тело — отметкой.
- **`site.response.sessionFingerprint`** запроса без сессии (чтения экранов входа) — отпечаток пустой сессии: sha256 от `fansly-session/1\n\n` (тип поля — sha256, `null` не допускает).
- **`siteDone.body`.** `not_platform_data` — ещё и когда писать нечего: ответа не было или ответом операции стал ответ preflight. Если буфер отказал в записи конца, движок слышит `siteDone` из памяти сразу, с `incomplete` там, где тело полагалось; конец и отметка дописываются, когда буфер снова принимает запись.
- **`sent`** — слово «ворот»: ушли ли байты операции. Ответ из кэша без обращения к сети — `sent: false` со статусом.
- **Перезапуск оператора.** Запросы, допущенные прежним оператором, закрываются `siteDone`: `sent` — был ли выпущен, статуса нет; ни разу не допущенные — молча.
- **Конец операции** — как у запроса Hub (§9): нет ответа и конца за 21 с или сайт отменил выпущенный запрос до ответа — страница останавливается (`request_unended`); ответ, тело которого идёт дольше 20 с от допуска, — обрыв туннелей к API, статус уходит движку, тело — отметкой. Запрос сменённого документа не выпускается (поправка 41). Страница остановилась, когда ответ уже начался, — у операции остаются статус и заголовки (`Retry-After`), тело — отметкой (`complete: false`, `siteDone.body: incomplete`).
- **Preflight и его запрос.** Chrome называет запрос, ради которого сделан preflight (`initiator.requestId`), и сообщает о конце этого запроса, даже пока на паузе или в пути только preflight. Запрос, который страница отменила, пока он ждал допуска, закрывает операцию сразу: preflight, всё ещё стоящий на паузе в Chrome, отменяется и не выпускается (на Chrome 155 он иначе ушёл бы по позднему допуску, а конца у него нет). Отменён, пока preflight в пути, — операция кончается ответом preflight. О конце preflight, переданного `Fetch.fulfillRequest`, Chrome 155 не сообщает: его концом служит стадия ответа.
- **Запрос preflight.** Под операцию preflight идёт только её запрос — тот, который Chrome назвал (`initiator.requestId`); по методу и адресу — лишь пока Chrome не назвал никакого; запрос, не узнанный ни так, ни так, — своя операция со своим допуском. Операция прошедшего (2xx) preflight ждёт свой запрос до своего предела (§9: дальше страница останавливается); запрос, чья операция preflight уже кончилась, отказывается и своей операцией не становится.
- **Preflight запросов, которые идут без допуска** (сторонние хосты, CDN), тоже отпускается с остановкой ответа на заголовках и передаётся `Fetch.fulfillRequest` (поправка 3).
- **Шаги 8–10 плана §4.1.** После открытия выхода оператор открывает `https://fansly.com/` в рабочей вкладке (`site_loaded` — документ пришёл; не пришёл — сбой запуска `proxy_unavailable` и повтор по лестнице). `session_confirmed` и `ready` — когда ответ на чтение аккаунта движком через браузер (`account.me`) назвал ожидаемый аккаунт под живой сессией; `state.accountId` — аккаунт из этого ответа. Сессия сменилась — назад к `site_loaded`.
- **Перезагрузка вкладки при подтверждении (один раз за запуск).** Пока живая сессия неизвестна, автоматике допускаются только GET `/versioning`, `/thirdpartyconnect/providers`, `/device/id`, `/account/me` (со своим preflight) под общим пейсером, паузой и бюджетами. После изучения сессии до проверки личности обычные чтения сайта закрыты, и первая загрузка сайта может увидеть, как её запросы к API падают — в перехвате, машину они не покидали. Если между навигацией шага 8 и подтверждением хоть один API-запрос сайта отказан, упал или отменён без отправки (закрытое картой и запросы сменённых документов не считаются), при подтверждении рабочая вкладка грузится заново: шаг — назад к `exit_open` с числом таких запросов в записи журнала состояний, затем загрузка как на шаге 8 и подтверждение уже с новым документом. Перед этим выпущенные запросы сайта дожидаются (до 30 с; не дождались — подтверждение без перезагрузки, отмена выпущенного остановила бы страницу), ждущие закрываются (допущенные — `siteDone` с `sent: false`), и ничто, допущенное до перезагрузки, в новый документ не выпускается. Второе подтверждение в том же запуске ничего не перезагружает; не падало ничего — перезагрузки нет.

## 7. Экраны входа

Распознавание — план §4.8. Оператор читает DOM окна входа из изолированного мира: адрес страницы, поля логина, пароля и кода, текст ошибки, пометку о входе с нового устройства (да или нет, без текста), есть ли поле пароля или кода вне окна входа, загруженный аккаунт. Признаки лежат в коде оператора с версией (`screenVersion`, §6; сейчас `fansly-login/2`, `apps/page-browser/src/login/screens.ts`). Совпали не все признаки — экран незнакомый. Перед каждым нажатием экран распознаётся заново.

| Экран | Признаки | Что видит владелец в форме | Что делает оператор |
|---|---|---|---|
| Логин | одна форма: поле логина, поле пароля, одна кнопка | поля «логин» и «пароль», снимок экрана | `login.submit`: фокус, `Input.insertText`, нажатие «Войти» |
| Код 2FA | одна форма: одно поле кода, одна кнопка | поле «код 2FA» | `login.code`, так же |
| Код из письма (вход с нового устройства, решение 2026-10-15) | то же, и в форме — адрес почты или заголовок «Login from a new device» (`codeFrom: "email"`) | поле «код из письма» и подсказка: Fansly отправил код на почту аккаунта | `login.code`, так же: сайт отправляет его как код 2FA (§2.4) |
| Ошибка | форма логина или кода с текстом ошибки сайта | текст ошибки (у кода из письма — то же поле «код из письма») | ничего не нажимает |
| Успех | формы нет, и сайт загрузил аккаунт, или его запросы несут новую сессию, или его код этого входа принят | «вход выполнен» | сообщает движку; проверки плана §4.8, шаг 5, затем режим «автоматика» |
| Незнакомый: капча, проверка Fansly, новое соглашение, изменённая форма, другое окно с паролем или кодом | не совпал ни один экран | «откройте экран» и ссылка на KasmVNC | ничего не нажимает |

Признаки версии `fansly-login/2` выписаны из публичного бандла сайта (окно входа `app-login-modal`) и проверены в Chrome на его разметке (`tests/page-browser-login-probe.test.ts`), но не на живом экране входа: до пилота их сверяют на тестовом аккаунте. По бандлу кнопки Fansly — элемент `app-button` (внутри `div` с обработчиком, без `<button>`), ожидающая кнопка — с классом `disabled`, ошибка у формы — `.auth-field-error`; признаки версии 1 этого не знали, и экраны сайта читались бы как незнакомые.

Считается только окно входа — элемент `app-login-modal`, который создаёт служба окон сайта; в нём все экраны входа (логин, код, код из письма, их ошибки). Своя форма входа на главной странице не выводится (`ngIf false`): её «Login» открывает это окно. Другие окна сайта тоже просят пароль или код тем же полем и кнопкой — 2FA для действий с аккаунтом (`app-twofa-session-create-modal`: `#fansly_twofa`, «Verify»), смена почты в настройках (`app-email-change-new-modal`) — и входом не являются. Поле пароля или кода вне окна входа делает экран незнакомым, и ни распознавание, ни поиск поля и кнопки вне окна не выходят: оператор там ничего не вводит и не нажимает (разбор Astra, P1). Адрес страницы ничего не доказывает: окно входа открывается поверх любого пути.

Отчёт п. 12 заполнит признаки, пути операций входа (§2.4), список экранов, которые Fansly показывает новому устройству, и отзывчивость KasmVNC.

```

- Сверх плана §3.1 добавлено:
  - `AutofillAddressEnabled` и `AutofillCreditCardEnabled` — так в политиках выражается «автозаполнение выключено»;
  - `RestoreOnStartup` и `RestoreOnStartupURLs` — Chrome всегда стартует на `about:blank` (план §4.1, шаг 3) и не открывает прошлых вкладок до подключения контроля;
  - `RemoteDebuggingAllowed` и `DeveloperToolsAvailability` — явно разрешены, чтобы порт CDP не зависел от значений по умолчанию (план §3.1);
  - `DefaultBrowserSettingEnabled` и `MetricsReportingEnabled` — Chrome не спрашивает про браузер по умолчанию и не шлёт статистику в Google; так работал образ прототипа на тестовом аккаунте;
  - `IncognitoModeAvailability: 1`, `BrowserGuestModeEnabled: false`, `BrowserAddPersonEnabled: false` (PR 6, разбор Astra) — ни окна, ни профиля, где не работает расширение с правилами: в окне Incognito и в гостевом окне расширения выключены, принудительно установленные тоже. Без этих политик при ручном доступе `Ctrl+Shift+N` открывал окно Incognito, и закрытое чтение из него доходило до прокси (проверено на Chrome 155). Сборка образа отказывает, если хоть одной из трёх нет (`policyWith`). Контекст, который создаёт по CDP сам оператор для проверки окружения (`Target.createBrowserContext`), политика не запрещает; в нём тоже нет расширения, но его страницу оператор отвечает сам, а каждый запрос стоит в его перехвате;
  - `HttpsOnlyMode: "force_enabled"` (PR 6, разбор Astra) — каждая навигация по `http://` поднимается до `https://`; если `https` не вышел, Chrome останавливается на своём предупреждении и обычный запрос не уходит. Прокси обычный HTTP отклоняет (403): страница выходит наружу только по TLS. Подресурс `http://` на странице `https` — это смешанное содержимое, его блокирует или поднимает сам Chrome. Страница проверки окружения `http://127.0.0.1/pb-env-check` не поднимается (loopback), остаётся безопасным контекстом, геолокация работает; запросы Hub и пробы самопроверки идут по `https` (стенд `stand/rules-check.mjs`);
  - `update_url` — на порту прокси. Правила ОС пускают Chrome только на `127.0.0.1:3128` (план §4.5), поэтому CRX и манифест обновления оператор раздаёт там же. К loopback Chrome ходит мимо прокси, и запрос приходит оператору обычным `GET`.
- `<ID расширения>` — ID расширения этого образа (PR 6). Ключ подписи создаётся при сборке образа в памяти процесса сборки, подписывает пакет один раз и нигде не сохраняется: ни в репозитории, ни в образе, ни в секретах. Поэтому ID у каждого образа свой, и запись о нём в `hub.json` образа добавляет сборка (`apps/page-browser/extension/build.ts`); в репозитории в `ExtensionSettings` только `"*": blocked`. Постоянный ID (план §4.6) не подошёл: Chrome обновляет установленное расширение только на версию выше и никогда назад — страница, которую откатили на прошлый образ, осталась бы с правилами нового (проверено на Chrome 155). Со своим ID у образа правила в браузере всегда его собственные: расширение прошлого образа политика блокирует, и Chrome его убирает, а новое ставит при первом запуске, пока выход закрыт, — через 1–2 с после запуска Chrome на локальном стенде; самопроверка этого дожидается.
- Самопроверка сверяет применённые политики с этим файлом (план §3.1). Chrome показывает их на `chrome://policy` строками: имя, значение, источник, уровень, статус. Стенд PR 2 читает их так (`apps/page-browser/stand/image-check.mjs`): все 25 политик применены, обязательные, с уровня платформы. Слова источника, уровня и статуса Chrome переводит на язык страницы, поэтому стенд запускает Chrome по-английски; самопроверке оператора (PR 4) нужен способ, не зависящий от языка.

Одна допущенная операция страницы за раз «ворота» держат и сами, не только по слову движка (правило владельца: одна управляемая операция в полёте на страницу). Место страницы принадлежит операции от её первого выпуска, пока путь не закончил её и у каждого выпущенного ею запроса нет подтверждённого конца: `loadingFinished` или `loadingFailed` именно этого запроса, ответ на стадии ответа, решённый и подтверждённый ответом Chrome на эту команду (у preflight, отданного `Fetch.fulfillRequest`, другого конца в Chrome 155 нет; решение без ответа Chrome концом не считается), — или пока Chrome не ушёл. Место не освобождают ни закрытие окна, ни конец preflight, пока операция ждёт свой запрос, ни отмена соседнего запроса, ни конец самой операции, ни закрытие выхода, ни сброс. Окно другой операции, пока место занято, не открывается: запрос не выпускается и кончается «не отправлен» (Hub — `aborted_before_send`, `pace`; сайт — `siteDone` с `sent: false`). `openExit` после `closeExit` отказывает, пока место занято (`restartBrowser` начинает с нового Chrome). Граница — срок допуска плюс предел операции; прошла, а конец не известен — сбой `request_unended`: выход закрыт, Chrome уходит, место освобождается только тогда. Иначе Chrome может записать просроченный и ещё не записанный запрос в новое соединение чужого окна (стенд t9 с наложенными допусками: preflight через 3,8 и 13,7 с после срока).

Параметры: запись управления — до 39 байт (TLS 1.3) или 46 (TLS 1.2); бюджет окна — HEADERS и одна запись DATA тела, у нового соединения ещё Finished TLS 1.3 и преамбула HTTP/2; тело больше 16 375 байт или неизвестной длины не отпускается.

### Повторное подтверждение сохранённой сессии после старта Chrome

Доверенный digest в sync_pages.credentials_generation не доказывает, что
новый процесс Chrome уже видел ответ identity. Когда оператор сообщает
site_loaded с известным sessionFingerprint и ещё без accountId, актор
переходит в checks-only и под обычным пейсером/ownership/holds поднимает
create-only account.verify с причиной browser_loaded. Это требуется и при
неизменившемся токене профиля; account.poll раз в час для запуска не ждут.
После ответа account.me оператор подтверждает свою текущую сессию и даёт
ready; accountId/step снимают условие, следующие проходы не поднимают новый
verify. Паузы и credentials/network/route holds не обходятся. Лог движка
identity verify raised for the current browser start не содержит digest.
