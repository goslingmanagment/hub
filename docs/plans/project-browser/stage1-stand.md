## 3. Как выполнены условия

### 3.1 «Ворота» в прокси оператора — рубеж отправки (условия №1 и №2)

Прокси не видит запросов внутри TLS. Но к API в полёте всегда один допущенный запрос, а остальные стоят в перехвате `Fetch`. И Chrome пишет каждый кадр HTTP/2 отдельным вызовом, а BoringSSL делает из вызова отдельную запись TLS (`SpdySession::DoWrite`). Тип и длина записи видны в её открытом заголовке. Поэтому «ворота» решают по каждой записи, которую Chrome пишет в туннель к API:

- **Запись размером с кадр управления** (PING, WINDOW_UPDATE, RST_STREAM, SETTINGS ACK; в TLS 1.3 — до 39 байт) проходит всегда, если перед ней в туннеле ничего не задержано. Запрос в неё не помещается: самый короткий HEADERS запроса — 47 байт и больше, на стенде 76–93.
- **Любая другая запись проходит только в окне запроса, который оператор только что отпустил, и в пределах бюджета окна:** HEADERS запроса и одна запись DATA его тела. У соединения, открытого в этом окне (не больше одного), к бюджету добавляются его Finished TLS 1.3 и преамбула HTTP/2.
- **После бюджета окно закрыто.** Повтор Chrome по тому же соединению (после `REFUSED_STREAM`), запрос, который Chrome отпустил сам при обрыве CDP, — это лишние записи, и они задерживаются. Повтор по новому соединению (`GOAWAY`, сброс, 408) упирается в отказ в новом туннеле.
- **Сервер что-то прислал после заголовков запроса — окно закрыто**, даже если бюджет не выбран. Chrome повторяет запрос только после отказа сервера, поэтому повтор всегда идёт после байтов сервера. Тело запроса Chrome пишет сразу за заголовками, раньше любого ответа.
- **Тело — не больше 16 375 байт** (один кадр HTTP/2 в Chrome). На первом этапе запросы с телом — только вход. Большему телу между кадрами нужно управление потоком сервера, а его байты «ворота» не отличат от отказа; такой запрос оператор не отпускает.
- **Задержанная запись держит весь туннель:** поток TLS нельзя переставить, и ничего из него не выбрасывается. К следующему окну такой туннель рвётся, а не отпускается.
- **Срок допуска** проверяет отправитель — прокси: если к сроку запрос не ушёл, туннели к API рвутся.
- **Ответа нет 20 с** после отправки — туннели к API рвутся.
- **Тело неизвестной длины** (поток) оператор тоже не отпускает: бюджет для него не посчитать.

«Ворота» не зависят от CDP: их держит процесс оператора, а с его смертью умирают и туннели. Расшифровка трафика не нужна.

**Что остаётся.** «Ворота» не различают два запроса внутри TLS, отсюда два остатка:

- **Обрыв CDP в миг открытого окна.** Если запрос ещё не записан, его место может занять запрос, который Chrome отпустил сам. Уйдёт не больше одного уже задержанного запроса, и только тот, что пропускает расширение: чтение или вход. Это запасное правило решения №10. На стенде это случается, когда держат одни «ворота» (оператор нарочно реагирует на обрыв на 300 мс позже): 3 раза на 270 прогонов с запросом в пути при обрыве. При обычной реакции оператора — 0 на 250. Каждый раз уходил один preflight уже задержанного чтения, через 3–7 мс после обрыва (§4.1). Тревога об обрыве в прототипе может сказать, что окна не было, хотя его только что занял такой запрос; на этапе 3 она должна говорить «мог уйти чужой запрос», пока не подтверждено, что ушёл допущенный.
- **Вход, разорванный байтами сервера.** Если сервер успел что-то прислать между частями запроса входа — между заголовками и телом или между кадрами тела, когда Chrome делит его из-за малого кредита потока, — остаток не уйдёт. Вход может уйти частично и не состояться; сам он не повторится. Владелец нажимает «Войти» ещё раз, только когда сайт показал ошибку: значит, прежняя попытка закончилась (через 20 с соединение рвётся). Это цена правила против повторов — решение №1б.

Третий случай закрыт остановкой страницы, и у этого есть цена. Запрос, который Chrome ещё держит после конца операции, «ворота» выпустили бы в окне следующего допуска. Поэтому страница останавливается, если Chrome не сообщил о конце запроса за 21 с или если сайт сам отменил выпущенный запрос до ответа сервера (§3.2). Второе бывает и при обычной работе сайта — например, при переходе на другой экран, пока запрос в пути. Как часто — покажет тест на аккаунте; решение для Hub — №16.

| Механизм | Зачем |
|---|---|
| Запрос Hub выпускается с недостижимого хоста `<хост>.pb-hold.invalid`; при допуске оператор ставит настоящий (`Fetch.continueRequest`, `url`) | Если Chrome отпустит запрос без нас (обрыв CDP), он уйдёт на хост, которого нет: прокси откажет. | Отказ любым не-сокетным запросам к хосту сокета | Иначе Chrome кладёт новый сокет на уже открытую сессию HTTP/2 к этому хосту — без туннеля и без допуска (проверено) |

| Сбой установки обёртки или перехвата в любом контексте — страница стоит: выход закрыт, Chrome остановлен | Контекст без обёртки не работает ни мгновения |
| Страница стартует только по явной команде движка `restart`. После остановки, после перезапуска оператора или контейнера она снова стоит; на диске это не хранится | Остановленная страница не запускается сама, и никакой сбой записи не превращает остановку в запуск |
| Операция, не закончившаяся за 21 с, обрывается: соединения к API рвутся раньше, чем движок узнаёт о её конце | Следующая операция не накладывается на тело ответа, которое ещё идёт |
| Операция кончается, только когда о конце её запроса сообщил отправитель — служба сети Chrome. Страница останавливается (выход закрыт, Chrome завершается), если за 21 с нет ни ответа, ни такого сообщения — или если сайт отменил выпущенный запрос до ответа: отмена — слово страницы, а не отправителя | Запрос, который Chrome ещё держит, иначе уходил в окне следующего допуска — уже после своего срока (§5, пп. 22 и 23) |
| Редирект запроса к API не исполняется: страница получает ответ 3xx конечным, движок — адрес редиректа | Chrome 155 на редиректе запроса с preflight под перехватом убивает свою службу сети (§5, п. 16) |
| Ответы входа, сессии и 2FA на диск не пишутся; параметры команд CDP для ввода и вычислений в странице в журнал не попадают | Секреты не оседают в буфере и журналах |
| Держатель соединения CDP | Сбой оператора не отпускает задержанные запросы |
| Проверка здоровья раз в 2 с: страница отвечает, процесс службы сети прежний | Chrome перезапускает упавшую службу сети молча, CDP остаётся, а страница может зависнуть навсегда (§5, п. 3) |
| Перед каждым запуском Chrome супервизор убирает каталоги версий расширения, которых нет в настройках профиля | Chrome, убитый раньше 10 с после запуска, ставит расширение заново в новый каталог; на сотом установка отказывает, и страница не стартует (§5, п. 24) |

## 5. Поправки к плану

Каждая найдена или проверена на стенде; доказательства — в `FINDINGS.md`. Пункты 20, 21, 25, 29, 32 и 33 в прототипе не сделаны: это задачи этапа 3.

1. **Рабочая вкладка открывается после `Fetch.enable`.** Перехват на browser-цели не действует на вкладку, открытую до него. Восстановление вкладок при запуске запрещено политикой (`RestoreOnStartup`). (§4.1, шаги 3–4)
2. **CORS-preflight перехватывается.** План (§4.2, шаг 6) считал иначе. Решение владельца №1 исполняется буквально: допуск спрашивается на паузе preflight, основной запрос отпускается под тем же допуском. У каждого из двух физических запросов — своё окно «ворот».
3. **Chrome 155 убивает свою службу сети на preflight под перехватом.** У preflight тот же `request_id`, что у основного запроса. Если задание перехвата preflight ещё не снято, когда основной запрос просит своё, браузер видит «DevTools: Duplicate request ID» и убивает службу сети. Рвутся все соединения, включая сокет сайта.
   - На стенде — 2 падения на 300 CORS-запросов; все дампы — эта причина.
   - Исправление: ответ preflight передаётся через `Fetch.fulfillRequest` — задание кончается синхронно. После него — 0 на 300. OPTIONS по-прежнему уходит на сервер, страница получает настоящий ответ.
4. **Нужен `Runtime.enable`:** без него V8 не ставит привязку в новые контексты, и обёртка сокета не может отчитаться. Классическая проба его обнаружения в Chrome 155 не срабатывает.
5. **Обёртка в воркерах ставится через точку останова «перед скриптом»** (`Debugger.setInstrumentationBreakpoint`). В воркере, ждущем отладчик, `Runtime.evaluate` не возвращается. Service worker Chrome останавливает и запускает снова в той же сессии: у него отладчик и точка останова живут всю сессию, обёртка ставится при каждом запуске.
6. **Свои повторы Chrome CDP не показывает.** После `REFUSED_STREAM`, `GOAWAY` и сброса соединения на сервер приходят два запроса на один допуск, а `requestWillBeSentExtraInfo` — один. Не пропускают повтор «ворота».
7. **Тело, прочитанное потоком, кончается в CDP «отменой».** Если JS читает тело потоком, а оно ещё доезжает, CDP сообщает `loadingFailed (ERR_ABORTED)`, хотя всё получено. Полноту ответов сайта поэтому судим по длине (`content-length`) или по форме тела, а не по событию конца (§4.2, шаг 7). Запрос Hub дочитывается `arrayBuffer()`.
8. **Допуск подключения сокета — на туннеле прокси**, а не обёрткой конструктора в странице (§4.3). Плюс правило отказа не-сокетным запросам к хосту сокета. Среда страницы меняется меньше: конструктор и все свойства `WebSocket` остаются нативными.
9. **WebGL без видеокарты** включается флагом `--ignore-gpu-blocklist`. Иначе Chrome держит Mesa `llvmpipe` в чёрном списке. Панели «неподдерживаемый флаг» нет.
10. **Язык в Linux-сборке задаётся окружением процесса** (`LANGUAGE`, `LANG`) и политикой `ForcedLanguages`, а не флагом `--lang`.
11. **Расширение ставится политикой с порта прокси оператора** (`http://127.0.0.1:3128/pb-extension/update.xml`). Правила видят запрос раньше перехвата: запрос, отменённый расширением, в `Fetch` не приходит.
12. **Рубеж отправки — «ворота» в прокси оператора** (§4.1, §4.2, шаг 4): решение по каждой записи TLS с бюджетом окна (§3.1 этого отчёта). Отмена запроса Hub из страницы по сроку не используется (п. 22).
13. **Ответы записей и путей входа, сессии и 2FA в буфер не пишутся** (§4.2, шаг 7): в них токен сессии. На первом этапе снимаются только чтения.
14. **Запрос Hub к Fansly — через `XMLHttpRequest`**, а не `fetch()` (§4.2, шаг 3): свои запросы к API сайт шлёт из Angular через `XMLHttpRequest`. Совпадение заголовков проверяет п. 15 на тестовом аккаунте. `fetch()` остаётся для других сайтов.
15. **Заголовки сессии для запросов Hub** берутся из последнего запроса сайта к API, в его порядке (§4.7). `fansly-client-ts` считается как у сайта (сейчас ± 5 с, не убывает), `fansly-client-check` — `cyrb53(ключ_путь_deviceId)`. Ключ сверяется с каждым значением, которое считает сам сайт: расхождение — тревога, запросы Hub не идут.
16. **Редирект запроса к API не исполняется** — ни у запросов Hub (как в плане), ни у запросов сайта. На редиректе запроса с preflight Chrome 155 делает preflight следующего шага под номером основного запроса, пока его задание перехвата ещё зарегистрировано, принимает это за «Duplicate request ID» и убивает свою службу сети. На стенде — на каждом таком редиректе, как бы оператор ни отвечал. Поэтому ответ 3xx уходит странице конечным, без `Location`, а движок получает адрес редиректа. Для этого стадия ответа перехватывается у каждого запроса к API, а не только у тех, чьи тела снимаются (§4.2, шаг 7).
17. **Страница стартует только по команде движка `restart`** (§4.1, §4.9), и остановка держится до следующей такой команды — в том числе после перезапуска оператора и контейнера. Останавливают страницу: сбой установки обёртки или перехвата, неизвестное сообщение сокета, команда движка, правила п. 23, в тесте — ещё и потеря связи с движком. В Hub этим стартом управляет движок по поколению владельца (§4.7).
18. **Ответ, тело которого страница не читает, для CDP не кончается:** `loadingFinished` нет, операция завершается по своему пределу (21 с), соединения к API при этом рвутся (§4.3). Клиент Fansly (`XMLHttpRequest`) тела читает.
19. **Исход запроса решается до команды CDP, которая его завершает** (§4.2, шаг 7). Ответ на команду и события, которые она вызывает, приходят в любом порядке: `Network.loadingFailed` отмены может опередить ответ на `Fetch.failRequest`. Иначе ответ больше лимита уходил движку как ошибка транспорта, а редирект — без адреса.
20. **Признак «отправлено» в результате операции ставит отправитель — «ворота»**, а не CDP (§4.2, шаг 7): «ворота» знают, ушли ли записи запроса. В прототипе признак ещё из CDP.
21. **Туннель, открытый для окна, рвётся вместе с окном, если запрос по нему не пошёл** (§4.1). Chrome не бросает подключение отменённого запроса; оно доустанавливается при закрытом окне, а при следующем занимает место нового туннеля — и следующий запрос не уходит (§8). В прототипе не сделано.
22. **Отмена запроса Hub из страницы за секунду до срока не используется** (§4.2, шаг 4 — кандидат плана). Оператор не узнаёт, исполнилась ли отмена. Он сообщал движку «конец, не отправлено», а при зависшей странице запрос оставался жив и уходил в окне следующего допуска — на стенде через 2,0–2,4 с после своего срока. Срок держат «ворота».
23. **Операция кончается, только когда о конце её запроса сообщил отправитель** (§4.2, §4.9). Если к пределу операции (21 с) нет ни ответа, ни сообщения о конце, страница останавливается. На стенде служба сети Chrome стояла 25 с: без этого правила запрос уходил через 10 с после своего срока, в окне следующего допуска. Останавливает страницу и отмена выпущенного запроса сайтом до ответа: о ней сообщает страница, а не служба сети. На стенде такой запрос не ушёл и без остановки (6 из 6), но снаружи этого не доказать. Ответ считается пришедшим, когда заголовки дошли до браузера.
24. **Перед запуском Chrome убираются каталоги версий расширения, которых нет в настройках профиля** (§4.1). Chrome записывает установку расширения в настройки примерно через 10 с и чистит лишние каталоги через 30 с. Убитый раньше, он на каждом запуске ставит расширение заново в новый каталог; после ста таких запусков установка отказывает («Could not find a home for extension»), самопроверка не проходит, страница закрыта и сама не восстанавливается.
25. **Предел операции не должен перебивать уже решённый исход** (§4.2, шаг 7): если исход ждёт записи файла тела или ответа на команду CDP, предел может объявить другой. И предел тела запроса Hub при приёме должен рвать соединение, а не просить страницу отменить запрос. В прототипе не сделано; в пилоте тела не снимаются.
26. **Ответ на `hello` идёт раньше повторных запросов допуска** (§4.13): при подключении движка оператор сначала отвечает, потом заново спрашивает допуски ждущих запросов сайта.
27. **Движок различает запуски Chrome** (§3.2): Chrome нумерует задержанные запросы с начала при каждом запуске. Номера и ожидающие запросы прежнего запуска движок забывает по сообщению оператора о новом; паузы и счёт за час остаются. Найдено в движке теста.
28. **Остановка страницы бывает двух видов** (§4.9): штатная — Chrome завершается сам, через 5 с убивается; и немедленная — когда не встала обёртка или перехват. Выход закрыт до любой из них. Сохранность входа не гарантирует ни одна: по `SIGTERM` Chrome записывает настройки, но не обязательно localStorage, где сайт держит сессию. Чтобы после остановки не входить заново, нужно обычное завершение браузера с ожиданием и проверка меткой в хранилище — этап 3.

29. **Тревога об обрыве CDP говорит «мог уйти чужой запрос», пока не подтверждено, что ушёл допущенный** (§4.1, запасное правило). В прототипе она берёт фазу «ворот» в миг, когда оператор узнал об обрыве, и может сказать «окна не было», хотя его только что занял запрос, который Chrome отпустил сам: в замере так вышло в одной из двух утечек. Подтверждение отправки нельзя брать из CDP (`requestWillBeSentExtraInfo` бывает раньше самой отправки). До исправления любой обрыв CDP считается «мог уйти один чужой разрешённый запрос». В прототипе не сделано.

30. **Запрос сменённого документа отменяется, а не отпускается** (§4.2, §4.9). Сразу после входа Fansly перезагружает страницу, а запросы старой ещё ждут допуска. Пропущенный после смены документа, такой запрос Chrome не отправляет и о его конце не сообщает, и п. 23 останавливает страницу. Документ запроса — `loaderId` из `Network.requestWillBeSent`; у preflight — документ запроса, ради которого он сделан (`initiator.requestId`), в любом порядке событий. Если документ не известен, решают навигации фрейма после того, как запрос встал в очередь. Цена: живой запрос новой страницы с ещё не известным документом может получить отказ, если `Page.frameNavigated` запоздал. Запрос, пауза которого пришла уже после навигации, а документ не известен, это правило не ловит — его держат допуск и п. 23. Найдено в сессиях 1 и 2 на тестовом аккаунте (§9).
31. **Подключение сокета, ждавшее допуска дольше 2,5 с, получает отказ** (§4.3). Fansly бросает сокет, который подключается дольше ~3 с, и открывает новый; подключение брошенного, пропущенное позже, по туннелю ничего не шлёт и не кончается. Сделано в движке теста; в Hub — правило очереди движка.
32. **Предел отправленного запроса считается от отправки** (§4.2, шаг 7). Предел операции — 21 с от допуска, а «ворота» рвут соединение без ответа через 20 с от отправки. Когда отправка отстаёт от допуска больше чем на секунду (медленный CDP под нагрузкой), предел опережает обрыв и зря останавливает страницу. У неотправленного запроса предел — по-прежнему от допуска. В прототипе не сделано.
33. **Супервизор снимает замок профиля Chrome** (§4.1). `SingletonLock` хранит имя хоста; после пересоздания контейнера Chrome считает профиль занятым другим компьютером и не запускается. Перед запуском Chrome убирать `Singleton*`, когда Chrome в контейнере нет, — или дать контейнеру постоянное имя хоста. В прототипе не сделано.

## 8. Ограничения

- Мак на arm64, Docker с 4 CPU и 4 ГБ на все стенды сразу. Серверная проверка — этап 2.
- В той же машине Docker другие сессии запускают свои контейнеры (e2e с Firefox). Серия, на которую легла такая нагрузка, остановлена и не учтена: Chrome на стендах перезапускался извне, память и своп кончились. Итоговая серия шла, когда чужих контейнеров не было.
- Сеть стенда быстрее настоящей. Помехи сервера стенда идут с круговой задержкой 30 мс; отдельные серии — с нулевой, как самый строгий случай для «ворот».
- Срок допуска на стенде короче, чем в плане: допуск 5 с при задержке 8 с вместо 15 и 20 с. Соотношение то же, прогон короче, и 15-секундный таймаут SOCKS оператора в проверку не вмешивается.
- После запроса, который страница отменила раньше, чем установилось его новое соединение, следующая операция может не уйти: страница видит обычную ошибку сети, следующий запрос проходит. Без допуска при этом не уходит ничего. Исправление — §5, п. 21, на этапе 3.
- Не исправлено в прототипе: §5, пп. 20, 25, 29, 32 и 33.
- Не проверялись: буфер на диске и его приём движком (PR 11, 13). Настоящий трафик Fansly — пока только 15 минут спокойной вкладки после входа (§9).
- Тело запроса — не больше 16 375 байт: на первом этапе это только вход.
- Хосты CDN под «ворота» не поставлены: запросы медиа Hub через браузер — этап 3.
- Запросы к статике и CDN перехватываются только на стадии запроса. Если сайт шлёт туда запросы с preflight и они редиректятся, служба сети Chrome упадёт, а проверка здоровья перезапустит браузер. Счётчик таких перезапусков — на тестовом аккаунте.
- Остатки «ворот» — §3.1.
- Смена владельца страницы (новое поколение) не дожидается окончания операций прежнего — это PR 4 и 7 этапа 3. В тесте движок один, и с его потерей страница останавливается.

Страница работает из копии ветки на проверенном коммите, через тестовый прокси SOCKS5 в Германии; часовой пояс и язык страницы — по нему. Входит владелец, на экране KasmVNC. Объём узкий: вход, одно чтение Hub для сверки аккаунта, 10–15 минут спокойной вкладки. Тела ответов не пишутся, после входа любая остановка заканчивает сессию. Журналы движка теста (`live-*.jsonl`) — рядом со стендом, в git не входят.

Во всех сессиях — ни одного ответа 429, неизвестного сообщения сокета, отмены выпущенного запроса сайтом, тревоги об обрыве CDP до остановки. Страница останавливалась только по своим правилам.

Третья сессия по пунктам плана:

- **П. 10, трафик.** Вход и загрузка после него — 26 запросов сайта за 90 с. В очереди по одному они ждали до 54 с, ещё один получил отказ на пределе ожидания (55 с). Спокойная вкладка: первые 4 минуты `mediastories/following` раз в 30 с (≈ 120 запросов в час), потом раз в 5 минут — всего ≈ 30 в час, вместе с `versioning`, `timeline/home`, `suggestionsnew`. Почему реже, не проверено: владелец закрыл экран или сайт счёл его неактивным. Между операциями — не меньше 2 514 мс.
- **П. 9, сокет.** Подключился с третьей попытки после входа (две получили отказ по §5, п. 31). После подключения — одно сообщение сайта (109 байт) и ответ (427 байт), дальше раз в ~20 с байт туда и 42 байта обратно.
- **П. 12, вход.** На экране KasmVNC вход работает. В первой сессии после `POST /login` был второй шаг (`/login/twofa`), хотя 2FA на аккаунте нет; что это был за экран, нужно уточнить у владельца.
- **П. 13, ресурсы.** Контейнер браузера в спокойной вкладке — ≈ 540 МБ памяти и 1–5 % CPU; во время входа с открытым экраном — 1,1 ГБ.
- **П. 15, заголовки.** Набор заголовков запроса Hub совпал с запросом сайта на живом сайте: 23 имени, с `authorization`, `fansly-session-id`, `fansly-client-*`.
- **Закрытое.** Внутри страницы закрыты `leaderboard.fansly.com`, шрифты Google, `googletagmanager` и виджет Intercom; на выходе — фоновые соединения Chrome к Google. Ответы на запросы сайта к API после входа — 200, кроме запроса старой страницы. Перезапусков Chrome проверкой здоровья не было.

Отклонения от объёма: в третьей сессии чтений Hub два вместо одного — ответ первого выведен неверно, и чтение повторено. В первой сессии движок теста сменён до входа (`322725c7`) без отдельного ревью; Astra смотрела это изменение в 11-м проходе.

Не проверено: работа дольше 15 минут, тела ответов (п. 17), другие чтения Hub, перезапуск страницы после входа, стартовые запросы и service worker сайта подробно (п. 4), «устройство» на живом сайте (п. 16).
