# Fable plan review

Model: claude-fable-5-1. Successful; 82 turns; no permission denials.

Review complete. Findings below, with the smallest architecture I would implement.

**Verdict:** both fixes are justified and the plan is mostly sound. Part 1 has one dead-end (ancestor-only rollback) and one missing piece (no way to run the new driver against an old source tree). Part 2 has one unverified premise about which stream actually captured the waiting messages, and the SQL can be smaller than the plan implies.

## Part 1: deploy ancestry guard

- **Incident cause confirmed.** Local `main` is 5d4cf1b1 while `origin/main` is 1cd78fa4 (`.git/refs/heads/main` vs `.git/refs/remotes/origin/main`). Someone deployed from a checkout behind the remote. Nothing in `initialize_deploy_metadata_and_tags` (`scripts/deploy-production.sh:491-505`) compares revisions. Only pull mode validates the checkout at all (`scripts/deploy-production.sh:1230-1244`).
- **Ancestor-only `--allow-rollback` is a dead end.** This repo squash-merges (Decision 373), and production has run local release commits that were never on main. The 2026-09-14 audit brief says so explicitly: production ran 3803263 while main had 74aac509, "ancestry checks lie". If production ever runs such a commit again, the deployed label is neither ancestor nor descendant of any main candidate, and the plan offers no path forward except editing the script. Replace `--allow-rollback` with one override, `--replace-deployed <12-hex>`, that must equal every observed role label. When given, ancestry is skipped but label parsing, full inventory, dirty and unknown rejection still apply. Covers rollback and divergence with one flag and no bypass.
- **Old checkout means old script.** `ROOT_DIR` is derived from `SCRIPT_DIR` (`scripts/deploy-production.sh:337-338`), and the build context, release-file tar, migration preflight and dist overlay all read `ROOT_DIR`. Checking out an old commit to roll back therefore runs the old, guard-less driver, which is exactly what the plan says must not happen. Add `--source-dir <path>` (env `DEPLOY_SOURCE_DIR`) that sets `ROOT_DIR` to a separate clean worktree while helpers stay sourced from `SCRIPT_DIR`. Every existing consumer already keys off `ROOT_DIR`, including both metadata helpers (`scripts/deploy-metadata.sh:21,45`). Rollback becomes: `git worktree add /tmp/rb <sha>`, then run the current script with `--source-dir /tmp/rb --replace-deployed <label>`. One thing I could not verify by reading: whether `rebuild-hub-cli-prod.sh` receives the source dir or assumes the driver's repo. Check that before shipping.
- **Label resolution details.** Labels are 12-hex short SHAs (`scripts/deploy-metadata.sh:47`), possibly `-dirty` or `unknown`. Resolve with `git rev-parse --verify --quiet "<label>^{commit}"` so ambiguity fails, then `git merge-base --is-ancestor <deployed> <candidate>`. The candidate must be a clean HEAD, matching the pull-mode regex at `scripts/deploy-production.sh:1234`. Extending that to full, dist-only and auto is a behavior change: dirty full deploys stop working. That is what the plan wants, but say so in the decision entry.
- **Inventory command.** Every existing inspection uses `compose ps -q <svc>`, running containers only (`scripts/deploy-production.sh:687,1149`). The plan wants stopped roles too, so use `ps -a -q` and loop over multiple IDs per service. Three roles present with resolvable labels is normal. All three absent is the valid empty case. Anything else fails closed. Beware `<no value>`, which `verify_service_image_labels` already normalizes at line 1154.
- **Placement.** Insert the guard right after `acquire_remote_deploy_lock` (line 1713) and again just before `quiesce_remote_legacy_sync_services` (line 1737). The generalized checkout validation already has hooks at lines 1709, 1727 and 1775. Leave `rollback_remote_stack` (line 883) untouched; it retags an existing image and must never be blocked.
- **Test harness gotcha.** The `run_remote` stub in `tests/deploy-production-behavior.test.ts:67-82` matches any command containing `agency-hub.source-revision` and returns the pull fixture. The new inventory command must carry a distinct marker or the stub needs a more specific case placed earlier. The Git DAG fixture at lines 184-196 extends naturally to parent, child and divergent commits. No existing test asserts main-flow order; a text-position test on the script (guard call index before `capture_remote_rollback_image` and before quiesce) is enough for "wiring precedes mutation".

## Part 2: DM fairness

- **Starvation mechanics confirmed.** Selection is priority desc, requested_at asc, stream order (`packages/db/src/repositories/page-sync.ts:2105-2107`). The reconcile budget yield returns no `continuationRetryAt` (`apps/runtime/src/services/sync/executor-handlers.ts:2640-2663`), so `yieldPageSync` leaves `retry_at` null (page-sync.ts:2578-2581), the executor re-enqueues the page immediately (`apps/runtime/src/services/sync/executor.ts:822-836`), and the next acquire picks reconcile again at 34 over 30.
- **Unverified premise, please confirm before coding.** The plan says dm_conversations is the live lane. But the WS hint projector dispatches `dm_messages` with source `event` (`apps/runtime/src/services/projections/fansly-ws-hints.ts:84`), and the event table gives it 25, with `event.dm_conversations` also only 30 (page-sync.ts:526-545). The event table is identical to scheduled. If the five Lora 2 messages were captured by the WS hint lane, the plan's group excludes the starving stream. Check the Lora 2 run records for which stream wrote them. If it was dm_messages under event source, the cheapest fix is a table edit raising the event-sourced DM lanes above 34, not a group change.
- **Fansly-only by construction.** OnlyFans pages have no `followers_reconcile` row (page-sync.ts:915-923), so the group needs no platform predicate, only a comment.
- **started_at semantics already fit.** Only acquire (line 2118) and the legacy repair (line 1497) write it. Yield, complete, fail, reclaim and the targeted lease leave it alone (line 2209). "Failed or reclaimed attempt counts as a turn" holds with zero extra code. Switching to `clock_timestamp()` is safe: no test asserts `page_sync_states.started_at` against a passed `now`, and the seed detection at lines 1309-1314 only checks null.
- **Smallest SQL.** One subquery layer inside the existing `candidate` CTE, no self join, no schema:
  ```sql
  grp   = case when stream in ('followers_reconcile','dm_conversations')
               and coalesce(dispatch_source,'scheduled') in ('scheduled','event','recovery','anomaly')
               then 'dm_fairness' else stream::text end
  peers = count(*) over (partition by grp)
  eff   = case when peers > 1 then max(own_priority) over (partition by grp) else own_priority end
  order by eff desc,
           case when peers > 1 then started_at end asc nulls first,
           own_priority desc, requested_at asc nulls last, stream_order asc
  ```
  `peers > 1` makes a lone member run at its own priority and leaves third streams untouched in the common case. Nothing sits between 30 and 34 in any source table, so same-source promotion changes no other ordering. Mixed sources (recovery reconcile at 44 plus scheduled dm_conversations at 30) lift dm_conversations above scheduled subscribers and followers. Acceptable, but state it in the decision.
- **Decide the null case explicitly.** The plan's "equal or absent timestamps fall back" is ambiguous when exactly one member has never started. Use `nulls first`: never-started work is the least recently started.
- **Manual demotion is already there.** Continuations rewrite `dispatch_source` to scheduled (executor.ts:785, page-sync.ts:2570-2573), so a manual reconcile joins the group after its first chunk, as the plan intends.
- **Tests.** Extend `tests/page-sync-lease-fencing.integration.test.ts`. dm_conversations depends on light, top_spenders, transactions, subscribers and followers (page-sync.ts:494); the fixture at lines 1214-1228 shows how to satisfy dependencies, then call `refreshPageSyncDependencies`. Consecutive acquires get strictly increasing `clock_timestamp()` values, so no sleeps are needed.

**Recommendation.** Implement Part 1 as one `verify_remote_revision_lineage` function called twice, plus `--replace-deployed` and `--source-dir`, plus the checkout validation generalized to all modes. Implement Part 2 as the windowed ORDER BY above plus `clock_timestamp()` on `started_at`, only after confirming which stream captured the Lora 2 messages. Drop the ancestor-only rollback flag from the plan. Everything else in the plan matches the code.
