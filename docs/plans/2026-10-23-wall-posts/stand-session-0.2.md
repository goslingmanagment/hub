# Сессия 0.2: снимок публикации на тестовом аккаунте

Что делаем: на стенде на agency-de открываем тестовый аккаунт Fansly в браузере страницы
(образ из main) с режимом «снимок публикации» (PR 0.1) и руками делаем посты из списка плана.
Браузер пишет журнал всех запросов публикации, которые шлёт сам сайт, с телами без секретов.
По журналу пишем `fansly-publish-contract.md` рядом со spec. Hub в этой сессии ничего не
читает и ничего не пишет: движок стенда только запускает и останавливает страницу.

Код: `apps/page-browser/stand/publish-capture/` (образ, `capture.sh`, движок стенда `engine.ts`,
читалка журнала `read.ts`), журнал — `apps/page-browser/src/capture/publish.ts`.

## 1. Что нужно от владельца

1. **«Да» на сессию**: время (1,5–2 часа, из них 15 минут ждём выхода отложенного поста) и
   «да» на запуск стенда на agency-de: одна страница браузера (до 2 ГБ памяти, до 2 CPU) под
   сторожем стенда, который сам всё остановит, если Hub начнёт тормозить.
2. **Тестовый прокси SOCKS5** — тот же, что в сессиях на тестовом аккаунте 11–12.10 (Германия),
   не прокси рабочих страниц: адрес (IP или имя) и порт, логин, пароль. В
   `~/.config/agency/secrets.env` его нет, 1Password агентам недоступен. Агент кладёт его в
   файл настроек стенда на сервере (root, 600) и проверяет, какой выходной IP видит
   api.ipify.org через этот прокси — владелец подтверждает, что IP тот.
3. **Вход в тестовый аккаунт** делает владелец сам, на экране браузера стенда (логин, пароль,
   код из почты, если Fansly спросит про новое устройство). Агент данных входа не получает и в
   форму их не вводит.
4. **Файлы для постов**: 4–5 фото и одно видео 30–100 МБ (чтобы загрузка шла несколькими
   частями) — то, что не жалко выложить на тестовом аккаунте. Или «да» на то, чтобы агент сделал
   нейтральные сам (цветные картинки с надписью «test N», ролик-заставка).
5. **Трафик прокси**: видео идёт через тестовый прокси (100 МБ видео — 100 МБ трафика). Ок?
6. **Аккаунт к сессии** (из своего браузера, не со стенда — на стенде эти записи закрыты), или
   ответ «пропустить этот пункт»:
   - вторая стена — для «поста на две стены»;
   - хотя бы один уровень подписки — для «поста для подписчиков одного уровня»;
   - может ли аккаунт делать платные посты (у Fansly для этого может быть нужна проверка
     личности создателя, spec §12).
7. **Кто нажимает «Опубликовать»**: владелец сам, или агент на экране — тогда «да» владельца на
   каждый пост (тексты постов — его или «тестовые, на усмотрение агента»).
8. **После сессии**: оставить ли профиль тестового аккаунта на сервере для проверки PR 9 (по
   умолчанию оставляем; удалить — только по слову владельца) и что делать с тестовыми постами на
   стене (удалить их можно только из своего браузера: на стенде удаление закрыто).

## 2. Как это устроено (и почему так)

- **Прод не может получить этот режим.** Правила расширения вшиты в образ. Образ стенда
  (`pb-suite/page-browser-capture:<rev>`) — это прод-образ того же коммита, у которого
  расширение пересобрано с `--capture publish`: правила снимка и метка
  `extension/dist/publish-capture.json`, по которой оператор включает свою часть. Прод-
  `Dockerfile` этот флаг не передаёт; у образа стенда метка Docker
  `agency.page-browser.capture`, и `page.sh up` такой образ на страницу не ставит. Тест
  `tests/page-browser-publish-capture.test.ts` держит: в прод-правилах ни одного разрешения
  снимка, сборка без флага не пишет метку.
- **Что открыто в снимке** (только запросы самого сайта, только скрипта, только точный путь на
  настоящем хосте): `mediav2.fansly.com` — `POST /media/upload/create`, `POST
  /media/upload/complete`, `GET /media/upload/{id}`, `POST /media` и preflight под `/api/v1`;
  `apiv3` — `POST /account/media`, `/account/media/bundle`, `/post`, `/mediastories`,
  `/post/scheduled/{id}/cancel`; `PUT` части файла на хост хранилища: сторонний хост открыт
  в любом образе (решение №2), хост под fansly.com — только в снимке и не роль Fansly (не
  apiv3, wsv3, chatws, metrics, mediav2, cdn*). Чтения (`GET /post/scheduled` и др.) открыты и
  так. Всё прочее закрыто как в проде: отметки прочтения, typing, статус, аккаунт, деньги,
  стены и уровни, удаление постов, метрики, трекеры.
- **«Ворота» и загрузка частей.** В main работает вариант Б: «ворота» пассивны
  (`operator.ts`: `gatePassive ?? true`) — они не держат записи, не режут туннели и не
  отказывают им; предел тела 16 375 байт и отказ телу неизвестной длины действуют только в
  `ApiGate.open()`, то есть для запросов самого Hub к API, и только для туннелей к `apiv3`.
  Собственные запросы сайта через ворота не проходят вовсе. Поэтому PUT частей (большие, на
  хост хранилища) идёт как у любого браузера: обычный туннель через SOCKS5 страницы, в журнале
  соединений — байты туда и обратно. Режим снимка ничего тут не добавляет: ни допуска, ни
  предела. Для тестового аккаунта этого достаточно: каждую загрузку запускает человек руками,
  повторы частей (до 10) и `complete` (до 5) — собственная логика сайта, как в любом браузере;
  Hub не шлёт ничего; выход по-прежнему только через прокси страницы, локальные адреса и
  закрытые хосты отклоняются. Для PR 8 (загрузка самим Hub) это ограничение: PUT части Hub
  пойдёт не через окно API, а через общий слот (`gate.takeSlot`, как медиа Hub), а тело
  `POST` к API больше 16 375 байт ворота не отпустят даже пассивными.
- **Что допускает движок.** Ничего: оператор варианта Б (протокол 1.4+) не спрашивает допуска
  на запросы сайта (`siteAdmit`/`wsAdmit` не шлёт), запросы сайта не стоят в `Fetch`, поэтому
  правила остановки страницы этапа 1 (`stage1-stand.md` §5, пп. 23, 30–32: отмена сайтом,
  нет конца за 21 с, сменённый документ, предел от отправки) к ним не применяются — они
  остались только за запросами Hub. Бюджет «300 запросов сайта в час» в варианте Б — тревога
  движка, не отказ (Б8); у движка стенда нет и её. Опрос `GET /media/upload/{id}` сайт ведёт
  сам (интервал растёт с 1 до 10 с, до 3 часов) — журнал покажет, сколько раз, и это темп,
  который Hub потом не должен превышать.
- **Движок стенда** (`engine.ts`): hello с прокси, IP и окружением из файла настроек, страница
  0 (профиль без страницы, как при подключении новой), ручной вход на всю сессию (человек в
  странице: выход сайта из аккаунта не останавливает страницу, Hub ничего не шлёт), запуск и
  остановка страницы, подтверждение наблюдений. Поток событий не читает: ответы сайта лежат в
  буфере страницы на томе стенда.
- **Журнал** — `publish-<день>.jsonl` в `/data/buffer/logs` страницы. В нём каждый запрос
  публикации (что ушло и что пришло: метод, адрес, тела JSON, статус, время), чтения, которые
  показывают загрузку, пост, сториз, стены и уровни, preflight к хранилищу и все прочие записи
  сайта (в том числе закрытые правилами — без тел). Без секретов: подписи CDN вырезаны так же,
  как Hub журналит чтения (`cdn-tokens.ts`), у подписанных ссылок хранилища вырезаны значения
  подписи (`X-Amz-Signature`, `X-Amz-Credential`, …), поля с почтой, токенами, паролями,
  сессией и IP — `[redacted]`, адреса почты в тексте — `[e-mail]`, у заголовков значения
  только безопасных (никогда `authorization`, `cookie`, `fansly-*`). Байты частей файла не
  читаются вовсе — только размер. Полный список запросов сайта (без тел) — в журнале
  `requests`, туннели — в `connections`.

## 3. Обновить стенд до main и поднять снимок

`/opt/pb-stand` на agency-de — стенд этапа 2 из ветки прототипа против поддельного Fansly, без
выхода в интернет; на нём настоящий Fansly недоступен, и его не трогаем. Сессия идёт на наборе
стенда из main (`/opt/pb-suite`, `apps/page-browser/stand/`), под его сторожем.

На маке, после слияния PR 0.1 (`<rev>` — 12 знаков коммита main):

```sh
cd ~/code/1-platform/hub && git pull
apps/page-browser/stand/push.sh --remote root@152.53.191.242 --rev origin/main
```

На сервере (`R=/opt/pb-suite/src/<rev>/apps/page-browser/stand`):

```sh
$R/stand.sh guard-start                    # без сторожа ничего не стартует
$R/stand.sh build                          # прод-образ этого коммита + образ инструментов, ~10–15 мин
$R/publish-capture/capture.sh build        # образ снимка поверх него, секунды
```

Настройки (агент пишет из того, что дал владелец; файл root, 600):

```sh
install -d -m 700 /opt/pb-suite/capture /opt/pb-suite/capture/media
umask 077; cat > /opt/pb-suite/capture/settings.json <<'EOF'
{"socks5": {"ip": "<IP прокси>", "port": <порт>, "username": "<логин>", "password": "<пароль>"},
 "pinnedExitIp": "0.0.0.0",
 "env": {"timeZone": "Europe/Berlin", "languages": ["de-DE", "de", "en-US", "en"],
         "geolocation": {"latitude": 52.52, "longitude": 13.405, "accuracyM": 1000}}}
EOF
$R/publish-capture/capture.sh exit-ip      # выходной IP прокси по ipify; владелец подтверждает
# вписать его в pinnedExitIp; страна прокси другая — поменять timeZone, languages, geolocation
```

Файлы для постов — в `/opt/pb-suite/capture/media/` (с мака: `scp <файлы>
root@152.53.191.242:/opt/pb-suite/capture/media/`). Потом:

```sh
$R/publish-capture/capture.sh up           # страница и движок; страница стартует сама
$R/publish-capture/capture.sh status       # шаг страницы, тревоги, память
```

`up` печатает, как открыть экран. С мака: `ssh -N -L 16901:<адрес>:6901
root@152.53.191.242`, затем http://localhost:16901, пользователь `owner`, пароль — строка из
`/opt/pb-suite/capture/secrets/vnc_password`. Файлы видны в диалоге выбора файла: Home → Media.

## 4. Сессия

Перед каждым действием агент пишет в чат время (UTC): по нему потом сопоставляем строки
журнала. Между действиями — минута паузы. Ничего лишнего в браузере: ни сообщений, ни лайков,
ни переходов по чужим профилям.

0. **Вход.** Владелец входит на экране. В журнале движка (`capture.sh status`) — номер
   аккаунта; это тестовый аккаунт.
1. **Пост с фото сразу.**
2. **Пост с видео на +15 минут** (расписание в редакторе). Открыть экран отложенных постов
   (это `GET /post/scheduled`). Через 15 минут — открыть стену и снова отложенные: вышел ли
   пост и с тем же ли ID (spec §12).
3. **FYP**: пост с `#fyp` в тексте и пост без него. По бандлу сайта (2026-10-08) `fypFlags` =
   2, если в тексте есть «#fyp», иначе 0; 4 — при `promotionOverwrite`. Журнал покажет, что сайт
   шлёт сейчас (в spec §5 записано 0/4 со слов OnlyFansAPI — сверить).
4. **Пост для подписчиков одного уровня** (если уровень есть).
5. **Платный пост**: с одним файлом; с пачкой файлов и превью (если аккаунт может).
6. **Пост на две стены** (если вторая стена есть).
7. **Пост со сроком жизни 1 день.**
8. **Сториз.** Потом открыть свой профиль/сториз: какое чтение показывает сториз.
9. **Снятие отложенного поста**: поставить пост на завтра и снять его на экране отложенных.

Сразу стоп (`capture.sh down`) и сообщение владельцу: ответ 401, 403 или 429 на что угодно,
капча, проверка Fansly, выход из аккаунта, письмо от Fansly. Если сайт показал ошибку при
публикации — пауза, агент смотрит журнал: запрос, закрытый правилами, виден в `read.ts` в
блоке «blocked by the rules». Открыть новый путь можно только отдельным PR (правила вшиты в
образ) и по слову владельца.

## 5. Собрать журнал

На сервере: `$R/publish-capture/capture.sh collect` — печатает каталог
`/opt/pb-suite/capture/results/<время>/` (журналы страницы `publish`, `requests`,
`connections`, `states`, `sockets` и журнал движка). На мак — вне репозитория (тестовый
аккаунт, хоть и без секретов):

```sh
mkdir -p ~/code/8-docs/2026-10-23-wall-posts/stand-0.2
scp -r root@152.53.191.242:/opt/pb-suite/capture/results/<время> ~/code/8-docs/2026-10-23-wall-posts/stand-0.2/
node --no-warnings apps/page-browser/stand/publish-capture/read.ts ~/code/8-docs/2026-10-23-wall-posts/stand-0.2/<время>
```

`read.ts` печатает ленту (время, класс, метод, путь, статус, мс, размеры тел, ID из тел), что
закрыли правила и ответы ≥ 400; `--line <id>` — один запрос целиком, `--json` — всё одним
массивом для `jq`.

## 6. Как писать fansly-publish-contract.md

Рядом со spec, без секретов и подписанных ссылок (журнал уже без них — но ID аккаунта, имена
файлов и тексты постов смотреть глазами). По каждой операции списка: путь и метод, тело запроса
и ответа (поля, единицы, что обязательно), статус, время.

- **Цепочка ID**: `create` → `response.id` загрузки, `partSize`, `parts[].uploadUrl` (какой хост
  хранилища, сколько живёт ссылка: `X-Amz-Expires`/`Expires`) → PUT частей (размер, ETag в
  ответе, заголовки, preflight) → `complete` (тело с `parts[].eTag`) → опрос `GET
  /media/upload/{id}` (`status`, когда появляется `parsedMedia`, сколько ждали фото и видео) →
  `account/media` или `account/media/bundle` (как связаны `mediaId`, `previewId`, права и
  цена: `permissionFlags`, цена в миллях) → `POST /post` (`attachments[].contentId/contentType`,
  `scheduledFor`, `expiresAt`, `wallIds`, `fypFlags`) → ID поста; отложенный → вышедший.
- **Сопутствующие запросы сайта** (класс `write` и `read` в журнале, журнал `requests`): что
  сайт шлёт вокруг публикации и закрыто ли это. По каждому — Hub его повторяет или нет и
  почему.
- **Вопросы spec §12 про Fansly**: ID отложенного поста при выходе; `fypFlags`; платные посты
  тестового аккаунта; предел отложенных (если видно); — или «на стенде не видно».
- Что из этого меняет план (PR 7–9) — правка плана в том же PR.

## 7. Вернуть стенд

```sh
$R/publish-capture/capture.sh down         # страница остановлена и удалена, сети удалены
$R/stand.sh guard-stop                     # сторож уходит последним
$R/stand.sh builder-remove                 # если сборок больше не будет
```

Остаются: тома `pb-publish-capture-profile` и `pb-publish-capture-buffer` (профиль тестового
аккаунта и его буфер — для PR 9), `/opt/pb-suite/capture` (настройки с прокси, файлы, журналы).
Удалить тома — только по слову владельца: `capture.sh forget --owner-said-yes`. Настройки с
паролем прокси — тоже по его слову. `/opt/pb-stand` не трогаем.
