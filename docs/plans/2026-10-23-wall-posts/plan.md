# Публикация постов через Hub — план реализации

Что строим и почему — [spec.md](spec.md). Здесь — порядок работ, состав PR и когда
работа считается сделанной. Ссылки на код — по main `79a9651bc` (23.10.2026); строки
могли уехать, ищите по имени.

## Как исполнять

- Один пункт — один PR в своём worktree, готовый сразу, `gh pr merge --auto --squash`.
  Локально — тайпчек, линт и тесты только затронутого. Свою слитую работу выкатывает
  тот, кто её сделал (`scripts/deploy.sh`). Браузер страниц выкатывается отдельно
  (`scripts/deploy-page-browser.sh`): выкатка Hub его не трогает.
- Новые выключатели по умолчанию выключены. Включает их владелец.
- На настоящей странице ничего не публикуется без «да» владельца в чате: ни пост, ни
  «сохранить на потом». На тестовом аккаунте стенда — можно.
- Hub никогда не повторяет отправку сам (правило Hub для всех исходящих команд).
- Тесты пишем на деньги (цена, вилка, единицы) и на хитрую логику (утверждённый вид,
  переходы статусов, неизвестный исход). Тексты и конфиги тестами не закрепляем.
- Расходится план с кодом или с тем, что показал стенд, — правим план в том же PR и
  пишем об этом в описании PR.

## Порядок

```
Этап 0 (стенд) ──────────────┐
                             ├─► Этап 3 (Fansly) ─┐
Этап 1 (ядро: PR 1–3, 10) ───┤                    ├─► Этап 4 (выкатка)
                             └─► Этап 2 (OnlyFans)┘
```

Этапы 0 и 1 идут параллельно. Этапы 2 и 3 не пересекаются по коду (действия
OnlyFansAPI против движка и браузера) и тоже могут идти параллельно. Большая часть
работы — этап 3: сейчас Hub в Fansly не пишет ничего.

Старт — сразу, до Chat Memory и параллельно с ней (владелец, 23.10.2026). С Chat
Memory (`docs/roadmap.md`) код почти не пересекается.

## Этап 0. Образцы запросов Fansly на стенде

Цель — точные запросы и ответы каждой операции публикации, снятые с самого сайта, а
не с FBuddy.

**PR 0.1 — режим «снимок публикации» только для стенда.** Тестовый аккаунт и
тестовый прокси (решение №13, `docs/plans/project-browser/stage1-stand.md`). В этом
режиме политика браузера (`apps/page-browser/src/policy/operations.ts`, `rules.ts`)
пропускает собственные запросы сайта на пути публикации из spec §5, включая хост
загрузки `mediav2.fansly.com` (в проде закрыт целиком), и журналит их с телами, вырезав
секреты (`src/capture/`). Hub сам ничего не пишет. Правила браузера вшиты в образ
(`extension/build.ts`), поэтому для стенда — отдельная сборка образа
(`apps/page-browser/stand/publish-capture/`); образ рабочих страниц этих правил не
получает, `page.sh` образ снимка не ставит, тест это держит. Сделано; как устроено и
почему «ворота» не мешают загрузке частей — [stand-session-0.2.md](stand-session-0.2.md),
§2.

**Сессия 0.2 (запускает владелец)** — по [stand-session-0.2.md](stand-session-0.2.md).
Поправка к прежнему тексту плана: `/opt/pb-stand` на agency-de — стенд этапа 2 из ветки
прототипа против поддельного Fansly, без выхода наружу; сессии на тестовом аккаунте
11–12.10 шли на маке владельца. Сессия 0.2 идёт на наборе стенда из main
(`/opt/pb-suite`, под его сторожем): прод-образ браузера с правилами снимка и движок
стенда, который только запускает страницу. Через ручной доступ к браузеру стенда руками
делаются: пост с фото сразу; пост с видео на +15 минут; FYP включён и выключен; пост для
подписчиков одного уровня; платный пост с одним файлом и с пачкой файлов, с превью; пост
на две стены; пост со сроком жизни 1 день; сториз; снятие отложенного поста. Вторую стену
и уровень подписки владелец заводит заранее из своего браузера: на стенде эти записи
закрыты.

**Готово, когда** рядом со spec лежит `fansly-publish-contract.md` без секретов и
подписанных ссылок: пути, тела, ответы, единицы, жизнь ID (загрузка → медиа →
вложение → пост; отложенный → вышедший), адреса хранилища для частей файла, время
обработки видео, все сопутствующие запросы сайта — и по каждому решение: Hub его
повторяет или нет и почему. Вопросы spec §12 про Fansly закрыты там же или помечены
«на стенде не видно».

## Этап 1. Ядро публикаций в Hub (без отправки)

  отправитель сверяет аккаунт, привязку и модель с утверждённым видом; расхождение

- `pnpm contracts:generate`.

Сделано (PR 1): объём считается по своим постам страницы — промо с чужим @аккаунтом не
в счёт (spec §8.1); стены Fansly по умолчанию — стены страницы с `default_wall`,
подставленные при сохранении черновика; агент правит только свои черновики; сверка
перед отправкой — `verifyApprovedPublication` (`apps/runtime/src/services/publications.ts`).

**Готово, когда** агент через API создаёт черновик, владелец утверждает пачку, правка
после утверждения возвращает публикацию в черновики, цена вне вилки, чужая модель и
второй экземпляр файла в той же пачке без «перезалива» не утверждаются.

**PR 2 — экран «Публикации» и настройки страниц** (spec §9). Образцы — «Зависшие
отправки» (`apps/dashboard/src/pages/ClientHeldSendsPage.tsx`,
`clientHeldSendsView.ts`) и `pages/OfapiActions.tsx` (статусы, действия в строке);
маршрут в `src/App.tsx`, вкладка в `src/lib/sections.ts`. На экране: список по дням,
фильтры, утвердить одну и выбранные, отменить, замечания, разбор «Неизвестно»; на
настройках страницы — выключатель, вилка цен, порог, предел. Владелец видит экран сам:
скриншот из `pnpm dev` в PR.

**PR 3 — файлы публикаций.** Загрузка в дашборде, у файла — модель; одно хранилище для
обеих площадок. Байты — не в `observations` и не в Postgres: собранные факты Hub по
расписанию не удаляет, а эти файлы удалять нужно (через 7 дней после выхода или
отмены), и база уже 51 ГБ. Каталог на диске сервера — по образцу `LAKE_DIR`
(`packages/shared/src/config.ts`); предел размера файла и общий предел — в этом PR.
Существующее `ofapi_media_sources` хранит байты как наблюдения и для этого не
подходит; его загрузчик в OnlyFansAPI переиспользуем в PR 4b.

Сделано (PR 3), с поправками к плану:
- Байты — `<PUBLICATION_FILES_DIR>/<model_id>/<sha256>`, загрузка идёт потоком в
  `.incoming/` и переименовывается на место; одна строка на (модель, sha256), тип —
  по первым байтам (JPEG, PNG, GIF, WebP, MP4, MOV, WebM). Миграция `0299`:
  `stored_at`, `bytes_deleted_at`; строка не удаляется никогда.
- `LAKE_DIR` на проде не подключён к диску (лежит внутри контейнера), поэтому образец —
  `OFAPI_EXPORT_ARTIFACT_HOST_DIR`: папка хоста
  `${PUBLICATION_FILES_HOST_DIR:-/opt/agency-hub-artifacts/publication-files}` в `api`
  и `worker`. Именованный том нельзя: выкатка приложения не меняет общие тома
  (`scripts/deploy-infrastructure.mjs`).
- Пределы — живые настройки: файл 500 МБ, все файлы 20 ГБ (десятичные).
- Хранение (spec §7): пока файл в публикации, которая не закончилась (черновик,
  утверждена, в пути, в расписании, «неизвестно»), — держим; потом 7 дней после
  последней закончившейся; файл без публикаций — 7 дней после загрузки. Задача
  `publications.files.retention` раз в час. Черновик с удалённым файлом не
  сохраняется (400) и не утверждается (`file_deleted`); та же загрузка возвращает
  файл под тем же id.
- Загрузки в дашборде в этом PR нет — только API
  (`POST /api/v1/admin/publications/files?pageLabel=…&name=…`, тело — сам файл).
  Кнопка — на экране PR 2: SDK шлёт только JSON, поэтому загрузка — прямым запросом
  с прогрессом (XHR), не через `kernel`. Размер (`fileMaxBytes` из списка файлов) и
  тип (`detectPublicationFileMime` по первым 16 байтам, есть в браузерной сборке
  `@agency_hub_core/shared`) экран проверяет до отправки: отказ Hub посреди большой
  загрузки браузер увидит как обрыв соединения, а не как ответ 413/415.
- На проде nginx `hub.gosling-agency.ru` пропускает тело до 1 МБ (своего
  `client_max_body_size` нет): до первой настоящей загрузки владелец поднимает предел
  для этого адреса (и `proxy_request_buffering off`).

## Этап 2. OnlyFans

**PR 4a — замок привязки и приоритет OnlyFans** (до любых публикаций OnlyFans).
- Сейчас действие держит замок страницы `pg_advisory_xact_lock(9003010, pageId)` всё
  время запроса — до 65 с (`dispatchOfapiAction` в
  `apps/runtime/src/services/ofapi-actions.ts`), а отправка сообщения той же страницы
  ждёт этот замок (`withOfapiBindingLock`,
  `packages/db/src/repositories/ofapi-bindings.ts`). `waitForRequestSlot`
  (`services/ofapi.ts`) приоритет игнорирует.
- Нужно: сообщения не ждут публикацию, а смена привязки аккаунта не проходит под
  идущим запросом. Например: смена привязки берёт замок исключительно, запросы — в
  общем режиме, а очерёдность сообщений держит свой отдельный замок. Приоритет — по-
  настоящему: сообщения впереди фоновых публикаций.
- Это трогает работающий конвейер сообщений. Интеграционный тест на медленной
  заглушке OnlyFansAPI: сообщение, отправленное после того, как публикация взяла
  замок, уходит сразу; смена привязки ждёт и то, и другое.

**PR 4b — действия OnlyFansAPI по расписанию.** Основа уже есть и на проде ни разу не
запускалась: `apps/runtime/src/services/ofapi-actions.ts` (подготовка, отправка,
кредиты), `ofapi-actions-publishing.ts` (запрос и подтверждение),
`packages/contracts/src/ofapi-actions-publishing.ts`, таблица `ofapi_action_intents`.
- Задача воркера превращает утверждённые публикации в действия и отправляет их сама,
  без кнопки: посты — за 7 дней до выхода, пачками по 5 через 10 минут; сториз — в
  назначенное время, окно 30 минут на начало отправки (ушедшая сториз пропущенной не
  считается).
- Снятие — `post_delete`, а он удаляет любой пост, в том числе вышедший. Поэтому
  снимать только не позже чем за 15 минут до выхода и после свежего `queue_list`, где
  пост ещё стоит; иначе отказ. Тест на гонку «вышел — снимаем»: запоздавший запрос,
  устаревшее состояние в Hub.
- Общий замок действий (`withActionLock`) не взят — значит, ничего не отправлено;
  попробовать позже можно.
- Ключ повтора площадки для постов и сториз не используем: OnlyFansAPI описывает его
  только для отправки сообщения. Одна попытка, сверка чтением (PR 5).
- Публикации — фоновые (замок и приоритет из PR 4a), по одной на страницу, со своим
  пределом кредитов внутри общего дневного бюджета
  (`ofapiMirrorGlobalDailyCreditBudget`).
- Одноразовые загрузки OnlyFansAPI закреплены за одним действием
  (`ofapi-action-media.ts`); публикация на замену берёт новую загрузку, медиа из
  волта — те же ID.
- Загрузчик (`buildOfapiMediaUploadRequest`, `services/ofapi-media-uploads.ts`) берёт
  строку `ofapi_media_sources` (страница, аккаунт, sha256, размер, имя, тип) и
  сами байты как `Buffer` в памяти (`loadOfapiMediaSourceBytes` достаёт их из
  наблюдения), собирает multipart (`async=true`, `file`) и шлёт
  `POST /{account}/media/upload` (одноразовый `ofapi_media_…`) или `/media/vault`;
  предел — `OFAPI_UPLOAD_MAX_BYTES` = 100 МБ. Пути и ссылки он не принимает. Файл
  публикации отдаёт `readPublicationFileBytes(app, fileId, { maxBytes })`
  (`services/publication-files.ts`): `Buffer` со сверкой sha256 и размера. Нужен
  второй источник байтов у задания загрузки вместо наблюдения; файл больше 100 МБ
  этим загрузчиком на OnlyFans не уйдёт.
- Цена при создании (`post_create`) — только если проверка этапа 2 покажет, что
  OnlyFansAPI её принимает; иначе платные посты OnlyFans остаются ручными.
- Свой выключатель в `config-registry.ts`, по умолчанию выключен.
- Статус — по готовому подтверждению (`ofapiPublishingResultConfirmed`): оно
  проверяет форму ответа, а не выход. Сториз с `isReady: false` — «Обрабатывается»,
  перепроверка через 1 и 6 часов; неожиданный успешный ответ — «Неизвестно».

Сделано (PR 4b): задача воркера `publications.onlyfans` раз в минуту
(`apps/runtime/src/services/publications-onlyfans.ts`); одна отправка на публикацию
закреплена в базе (`publication_dispatches`, unique по публикации и виду); пост, до
которого меньше 2 минут, уходит сразу, а не в расписание; пост, как и сториз, позже
30 минут после времени не уходит — «Пропущен»; принятый пост — «В расписании», пока
свежее чтение (PR 5) не покажет, что он вышел; автостоп при 401/403 выключает
публикацию страницы и открывает инцидент `publishing_stopped`. Отступления: снятие
(`post_delete`) перенесено в PR 5 — ему нужно свежее чтение очереди оттуда; новые файлы
на OnlyFans пока не публикуются (блокирующее замечание `onlyfans_file_upload_unsupported`)
— загрузка через OnlyFansAPI добавится поверх PR 3.

**PR 5 — очередь OnlyFans и сверка.**
- `queue_list` раз в час, пока у страницы есть публикации Hub в пути, иначе раз в сутки
  и по кнопке «Обновить» (чтение тратит кредиты). Ответ — не больше 100 записей за
  окно и без курсора (`limit` ≤ 100 в контракте): список собирается окнами, число
  сверяется с `queue_counts`. Обрезанный, несвежий или с `syncInProcess: true` список
  помечен «неполно» и не доказывает, что публикации в очереди нет.
- Отложенные посты, поставленные руками, видны на экране; сверка «Неизвестно».
- «Вышел» и «Не вышел» — свежим чтением этой публикации (`GET /posts/{id}`,
  `GET /stories/{id}`), не по `creator_posts`: этот сбор у OnlyFans идёт раз в
  6 часов (`packages/db/src/repositories/page-sync.ts`, поток `posts`) и может быть
  выключен на странице.

Сделано (PR 5a, «вышел ли»): задача `publications.onlyfans.checks` раз в минуту
(`apps/runtime/src/services/publications-onlyfans-checks.ts`), чтения —
`publications-onlyfans-reads.ts`; работает при любых выключателях (spec §8.4).
- Каждое чтение — действие владельца OnlyFansAPI: к `queue_list`/`queue_counts` добавлены `post_get`,
  `posts_list`, `story_get`, `stories_list` (их видно и в формах экрана «OFAPI actions» — для проверок
  владельца). Ответ сначала в `observations`, кредиты — из общего дневного бюджета, привязка сверяется.
  Чтения Hub помечены `origin = 'publication_read'` (миграция 0301) и не засоряют список действий владельца.
  Повтор чтения — новое действие; записи не повторяются никогда.
- Пост через 10 минут после времени: по ID; есть, по времени и числу файлов похож → «Вышел». ID не найден
  (404, не «нет аккаунта» и не «route not found») → свежая очередь (`queue_counts` + окна `queue_list` по
  ≤ 100), затем свежие последние посты — в этом порядке: пост, перешедший из очереди в посты между чтениями,
  виден в одном из них. Найден по содержимому → «Вышел» с настоящим ID поста (create вернул ID очереди;
  прежний ID — в `publication_checks.evidence`). Ни там ни там, оба чтения полные → «Не вышел» и инцидент
  `publication_not_published` (один на страницу, закрывает владелец на экране уведомлений). Остальное
  (очередь «неполно», пост ещё в очереди после времени, похожий пост без доказательства) → «Неизвестно».
- Сториз: по ID; `isReady: false` → «Обрабатывается», перечитывается через 1 и 6 часов от времени, на 6 часах
  всё ещё не готова → «Неизвестно»; ID не найден и нет среди текущих сториз → «Не вышел».
- Сопоставление: исключают пост только время и число файлов — переписанная OnlyFans подпись или новый ID
  медиа никогда не доказывают «нет»; узнаётся пост по той же подписи или тем же файлам волта, ровно один и не
  занятый другой публикацией страницы.
- «Неизвестно» (spec §8.2) ищется только чтением: свежие чтения через 10 мин, 1 ч, 6 ч и 24 ч после того, как
  стало «неизвестно» (по ID, очередь, последние посты или сториз), потом раз в сутки неделю — собранные
  `creator_posts`. Нашёл → «В расписании», «Вышел» или «Обрабатывается»; не нашёл — решает человек.
- Неудачное чтение повторяется через 10 минут; 12 подряд (около 2 часов) → «Неизвестно». Каждая проверка —
  строка `publication_checks` (0301), не меняется.
- Расход: обычно 1 кредит на публикацию, при 404 — до 5, поиск «неизвестно» — до ~20. Отступление: чтения не
  входят в предел `publishingOnlyfansDailyCredits` (он — на посты, чтобы проверки не останавливали выкладку),
  только в общий дневной бюджет OnlyFansAPI.
- Подтвердит проверка владельца (код готов к обоим ответам): сохраняет ли пост из расписания ID, который
  вернул create (да — «Вышел» по ID; нет — по содержимому с записью настоящего ID; содержимое не узнаётся —
  «Неизвестно»); чем OnlyFansAPI отвечает на чтение несуществующего поста (принято: 404; иначе —
  «Неизвестно», не «Не вышел»); совпадают ли ID медиа в посте с ID волта (нет — узнаём только по подписи).

**Проверка (с «да» владельца):** первый пост «сохранить на потом» на странице, которую
назовёт владелец, с попыткой цены при создании; смотрим, что пришло. Затем первый
настоящий пост, утверждённый владельцем.

**PR 6 — запись в движке.**
- У запроса появляются метод и тело: `FanslyWireRequest`

  диалога, догрузка живых событий): на ari-1 единственный отправитель уже бывает

- Запись — только на транспорте `browser` (`sync_pages.transport`); транспорт Node
  записи отклоняет.

Сделано (PR 6, двумя PR: #781 — провод, маршруты, транспорты; второй — очередь команд).
- Маршруты записи — семь спецификаций `publish.*` (`packages/fansly/src/wire/publish.ts`):
  загрузка (`upload_create`, `upload_complete` на хосте `upload` = mediav2), `account_media`,
  `account_media_bundle`, `post`, `story`, `post_cancel`. Все `writeContract: "unverified"`:
  движок не шлёт ни одну (`isFanslyWriteSendable`), пока PR после сессии 0.2 не сверит путь,
  тело и ответ с `fansly-publish-contract.md` и не переключит маршрут в `verified`. Коды
  `permissionFlags` и `fypFlags` — заглушки FBuddy (`*_UNVERIFIED`).
- Отпечаток запроса: sha256 от версии, метода, класса хоста (`api`/`upload`), пути с query
  и sha256 тела (`fanslyWriteFingerprint`).
- Команды — своя таблица `fansly_write_commands` (0300), не `publication_dispatches`: у
  Fansly одна отправка публикации — это цепочка запросов (загрузка, вложение, бандл, пост), у
  каждого своя попытка, отпечаток и результат. Каждая команда ссылается на отправку
  (`dispatch_id`): отправка остаётся «одним разом» публикации, как у OnlyFans, а команды —
  запросами внутри неё (как `ofapi_action_intents` у OnlyFans). Уникальность — по
  (отправка, шаг, файл), кроме `refused`.
- Состояния: `queued → sending` только в транзакции допуска (рядом со строкой попытки, с
  запросом и отпечатком — до отправки); `sending → answered | rejected | unknown`;
  `sending → queued` только если попытка точно не ушла (`aborted_before_send`);
  `queued → refused` (выключатель, утверждение, окно, Node, непроверенный маршрут). После
  падения процесса восстановление закрывает попытку `unknown`, следующий план переводит
  команду в `unknown` — она больше не планируется. `rejected` — только 4xx с ошибкой самого
  Fansly; 5xx, страница прокси, 2xx без нужного ID — `unknown`.
- Команда — работа движка с ключом `publish.background` (класс planned) или `publish.urgent`
  (urgent, только сториз в окне; срок — конец окна). Отступление, строже плана:
  `publish.background` с `yieldsToUrgent` не берёт даже свой слот P цикла, пока у страницы
  есть срочная работа.
- Отступление: 401/403/429 на запрос публикации сразу выключает публикацию страницы
  (`autostopPagePublishing`, запись в базе, spec §8.3); уведомление владельцу — PR 7 или 9.
- Снятие (`post_cancel`) движок не выводит ближе 15 минут до выхода (страховка; свежее чтение
  расписания перед снятием — PR 9).

Что сверху. PR 7: `PageTransport.canWrite` браузера сейчас `false` и `prepare` отказывает
записи — оператор объявляет запись при знакомстве; RPC `send` несёт метод, тело и отпечаток;
