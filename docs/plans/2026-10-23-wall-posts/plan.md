# Публикация постов через Hub — план реализации

Что строим и почему — [spec.md](spec.md). Здесь — порядок работ, состав PR и когда
работа считается сделанной. Ссылки на код — по main `79a9651bc` (23.10.2026); строки
могли уехать, ищите по имени.

## Как исполнять

- Один пункт — один PR в своём worktree, готовый сразу, `gh pr merge --auto --squash`.
  Локально — тайпчек, линт и тесты только затронутого. Свою слитую работу выкатывает
  тот, кто её сделал (`scripts/deploy.sh`). Браузер страниц выкатывается отдельно
  (`scripts/deploy-page-browser.sh`): выкатка Hub его не трогает.
- Новые выключатели по умолчанию выключены. Включает их владелец.
- На настоящей странице ничего не публикуется без «да» владельца в чате: ни пост, ни
  «сохранить на потом». На тестовом аккаунте стенда — можно.
- Hub никогда не повторяет отправку сам (правило Hub для всех исходящих команд).
- Тесты пишем на деньги (цена, вилка, единицы) и на хитрую логику (утверждённый вид,
  переходы статусов, неизвестный исход). Тексты и конфиги тестами не закрепляем.
- Расходится план с кодом или с тем, что показал стенд, — правим план в том же PR и
  пишем об этом в описании PR.

## Порядок

```
Этап 0 (стенд) ──────────────┐
                             ├─► Этап 3 (Fansly) ─┐
Этап 1 (ядро: PR 1–3, 10) ───┤                    ├─► Этап 4 (выкатка)
                             └─► Этап 2 (OnlyFans)┘
```

Этапы 0 и 1 идут параллельно. Этапы 2 и 3 не пересекаются по коду (действия
OnlyFansAPI против движка и браузера) и тоже могут идти параллельно. Большая часть
работы — этап 3: сейчас Hub в Fansly не пишет ничего.

Старт — сразу, до Chat Memory и параллельно с ней (владелец, 23.10.2026). С Chat
Memory (`docs/roadmap.md`) код почти не пересекается.

## Этап 0. Образцы запросов Fansly на стенде

Цель — точные запросы и ответы каждой операции публикации, снятые с самого сайта, а
не с FBuddy.

**PR 0.1 — режим «снимок публикации» только для стенда.** Стенд — `/opt/pb-stand` на
agency-de: тестовый аккаунт и тестовый прокси (решение №13,
`docs/plans/project-browser/stage1-stand.md`). В этом режиме политика браузера
(`apps/page-browser/src/policy/operations.ts`, `rules.ts`) пропускает собственные
запросы сайта на пути публикации из spec §5, включая хост загрузки
`mediav2.fansly.com` (сейчас закрыт целиком), и журналит их так же, как Hub журналит
чтения. Hub сам ничего не пишет. Правила браузера вшиты в образ
(`extension/build.ts`), поэтому для стенда — отдельная сборка образа; образ рабочих
страниц этих правил не получает.

**Сессия 0.2 (запускает владелец, стенд сейчас выключен).** Стенд работал из копии
ветки прототипа (`stage1-stand.md` §9): перед сессией обновить его до текущего кода
браузера из main. Через ручной доступ к браузеру стенда руками делаются: пост с фото
сразу; пост с видео на +15 минут; FYP включён и выключен; пост для подписчиков одного
уровня; платный пост с одним файлом и с пачкой файлов, с превью; пост на две стены;
пост со сроком жизни 1 день; сториз; снятие отложенного поста.

**Готово, когда** рядом со spec лежит `fansly-publish-contract.md` без секретов и
подписанных ссылок: пути, тела, ответы, единицы, жизнь ID (загрузка → медиа →
вложение → пост; отложенный → вышедший), адреса хранилища для частей файла, время
обработки видео, все сопутствующие запросы сайта — и по каждому решение: Hub его
повторяет или нет и почему. Вопросы spec §12 про Fansly закрыты там же или помечены
«на стенде не видно».

## Этап 2. OnlyFans

**PR 4a — замок привязки и приоритет OnlyFans** (до любых публикаций OnlyFans).
- Сейчас действие держит замок страницы `pg_advisory_xact_lock(9003010, pageId)` всё
  время запроса — до 65 с (`dispatchOfapiAction` в
  `apps/runtime/src/services/ofapi-actions.ts`), а отправка сообщения той же страницы
  ждёт этот замок (`withOfapiBindingLock`,
  `packages/db/src/repositories/ofapi-bindings.ts`). `waitForRequestSlot`
  (`services/ofapi.ts`) приоритет игнорирует.
- Нужно: сообщения не ждут публикацию, а смена привязки аккаунта не проходит под
  идущим запросом. Например: смена привязки берёт замок исключительно, запросы — в
  общем режиме, а очерёдность сообщений держит свой отдельный замок. Приоритет — по-
  настоящему: сообщения впереди фоновых публикаций.
- Это трогает работающий конвейер сообщений. Интеграционный тест на медленной
  заглушке OnlyFansAPI: сообщение, отправленное после того, как публикация взяла
  замок, уходит сразу; смена привязки ждёт и то, и другое.

**PR 4b — действия OnlyFansAPI по расписанию.** Основа уже есть и на проде ни разу не
запускалась: `apps/runtime/src/services/ofapi-actions.ts` (подготовка, отправка,
кредиты), `ofapi-actions-publishing.ts` (запрос и подтверждение),
`packages/contracts/src/ofapi-actions-publishing.ts`, таблица `ofapi_action_intents`.
- Задача воркера превращает утверждённые публикации в действия и отправляет их сама,
  без кнопки: посты — за 7 дней до выхода, пачками по 5 через 10 минут; сториз — в
  назначенное время, окно 30 минут на начало отправки (ушедшая сториз пропущенной не
  считается).
- Снятие — `post_delete`, а он удаляет любой пост, в том числе вышедший. Поэтому
  снимать только не позже чем за 15 минут до выхода и после свежего `queue_list`, где
  пост ещё стоит; иначе отказ. Тест на гонку «вышел — снимаем»: запоздавший запрос,
  устаревшее состояние в Hub.
- Общий замок действий (`withActionLock`) не взят — значит, ничего не отправлено;
  попробовать позже можно.
- Ключ повтора площадки для постов и сториз не используем: OnlyFansAPI описывает его
  только для отправки сообщения. Одна попытка, сверка чтением (PR 5).
- Публикации — фоновые (замок и приоритет из PR 4a), по одной на страницу, со своим
  пределом кредитов внутри общего дневного бюджета
  (`ofapiMirrorGlobalDailyCreditBudget`).
- Одноразовые загрузки OnlyFansAPI закреплены за одним действием
  (`ofapi-action-media.ts`); публикация на замену берёт новую загрузку, медиа из
  волта — те же ID.
- Цена при создании (`post_create`) — только если проверка этапа 2 покажет, что
  OnlyFansAPI её принимает; иначе платные посты OnlyFans остаются ручными.
- Свой выключатель в `config-registry.ts`, по умолчанию выключен.
- Статус — по готовому подтверждению (`ofapiPublishingResultConfirmed`): оно
  проверяет форму ответа, а не выход. Сториз с `isReady: false` — «Обрабатывается»,
  перепроверка через 1 и 6 часов; неожиданный успешный ответ — «Неизвестно».

**PR 5 — очередь OnlyFans и сверка.**
- `queue_list` раз в час, пока у страницы есть публикации Hub в пути, иначе раз в сутки
  и по кнопке «Обновить» (чтение тратит кредиты). Ответ — не больше 100 записей за
  окно и без курсора (`limit` ≤ 100 в контракте): список собирается окнами, число
  сверяется с `queue_counts`. Обрезанный, несвежий или с `syncInProcess: true` список
  помечен «неполно» и не доказывает, что публикации в очереди нет.
- Отложенные посты, поставленные руками, видны на экране; сверка «Неизвестно».
- «Вышел» и «Не вышел» — свежим чтением этой публикации (`GET /posts/{id}`,
  `GET /stories/{id}`), не по `creator_posts`: этот сбор у OnlyFans идёт раз в
  6 часов (`packages/db/src/repositories/page-sync.ts`, поток `posts`) и может быть
  выключен на странице.

**Проверка (с «да» владельца):** первый пост «сохранить на потом» на странице, которую
назовёт владелец, с попыткой цены при создании; смотрим, что пришло. Затем первый
настоящий пост, утверждённый владельцем.

## Этап 3. Fansly

**PR 6 — запись в движке.**
- У запроса появляются метод и тело: `FanslyWireRequest`
  (`packages/fansly/src/wire/types.ts`), `RequestPlan`
  (`apps/runtime/src/sync/engine/resource.ts`), маршруты
  (`apps/runtime/src/sync/fansly/routes.ts`; сейчас все GET, кроме входа).
- У актора страницы — очередь команд записи: тот же отправитель и пауза
  (`engine/pacer.ts`), ответ сначала в `observations`, одна попытка; состояние «ушло,
  ответа нет» переживает рестарт и не отправляется снова.
- Каждую команду движок выводит из утверждённой ревизии и записанных результатов
  предыдущих шагов (ID загрузки, части, медиа, вложение), сверяет отпечаток файла,
  цену и кто видит, и до отправки записывает отпечаток самой команды: метод, адрес,
  тело.
- Постановка в расписание не срочная и уступает срочным чтениям страницы (поиск
  диалога, догрузка живых событий): на ari-1 единственный отправитель уже бывает
  занят волнами новых фанов (`slo_find`, 23.10). Срочна только сториз в своё окно.
- Запись — только на транспорте `browser` (`sync_pages.transport`); транспорт Node
  записи отклоняет.

**PR 7 — браузер: запись по открытым путям.**
- RPC `send` принимает POST и тело (`apps/page-browser/src/rpc/protocol.ts` — сейчас
  `method: "GET"`, проверка отклоняет остальное); страница открывает нужный метод и
  отправляет тело (`src/hub-requests/page.ts` — сейчас `x.open("GET")`);
  `src/hub-requests/hub.ts` пропускает API и `mediav2.fansly.com` только по открытым
  путям; `apps/runtime/src/sync/fansly/browser-transport.ts` передаёт метод и тело.
- В политике — строки с новым режимом «публикация» (`src/policy/operations.ts`:
  сейчас POST пропускается только у входа, `mediav2` закрыт), правила DNR
  (`src/policy/rules.ts`); маршруты движка и правила держит одним набором
  `tests/page-browser-rules.test.ts`. Разрешающие правила DNR — только для служебного
  адреса запросов Hub (`*.pb-hold.invalid`); собственные записи сайта на настоящих
  адресах остаются закрытыми, в том числе при ручном доступе.
- Правила вшиты в образ, поэтому «включено на странице» проверяет оператор при
  остановке каждого запроса Hub (`cdp/control.ts`, `FETCH_PATTERNS`): запрос выходит,
  только если у него есть допуск движка, публикация на странице разрешена, метод,
  адрес и тело совпадают с отпечатком команды (PR 6), а её утверждённая ревизия всё
  ещё в силе.
- Два разрешения: «создавать и загружать» и «снимать и сверять». Выключение
  публикации снимает первое сразу, второе остаётся — снять поставленное можно и при
  выключенной публикации. Автостоп из-за входа или проверки Fansly снимает оба, и
  Hub пишет, что расписание на площадке осталось.
- Протокол движок ↔ оператор: оператор объявляет при знакомстве, что умеет запись;
  новый Hub со старым оператором продолжает чтения и отказывает публикации до
  отправки. Изменение — сразу в обоих файлах (`rpc/protocol.ts` и
  `apps/runtime/src/services/egress/page-browser-protocol.ts`), их держит
  `tests/page-browser-protocol-drift.test.ts`. Проверить оба порядка выкатки (сначала
  Hub, сначала браузер) и откат.
- Автостоп (spec §8.3): 401, 403 или 429 на пути публикации, капча, проверка Fansly,
  потеря входа — публикация страницы выключается, владельцу уходит уведомление.

**PR 8 — загрузка файла в Fansly через браузер.** Сейчас в браузере загрузки нет
совсем (ни выбора файла, ни частей, ни PUT в хранилище). Байты идут из хранилища PR 3
в страницу — способ выбрать в PR (например, оператор отдаёт файл внутри контейнера на
служебном адресе, как запросы Hub начинаются с `.pb-hold.invalid`). Дальше — как
сайт: `media/upload/create` → части PUT на адрес из ответа этой загрузки →
`complete` → ожидание обработки → вложение (`account/media` или
`account/media/bundle` с правами и ценой в миллях). Результат каждого шага
сохраняется; потерянный ответ сверяется по ID загрузки.
- Загрузка видео не держит единственный запрос страницы минутами: чтения и живые
  события страницы во время загрузки идут дальше. Части файла идут через прокси
  страницы, как у сайта; до браузера файл доходит по внутреннему адресу Hub, не через
  прокси.

**PR 9 — пост, сториз, снятие, расписание.** `POST /post` (`scheduledFor`,
`expiresAt`, `wallIds` из `page_walls`, `fypFlags`), `POST /mediastories`,
`POST /post/scheduled/{id}/cancel`. Новое чтение `GET /post/scheduled` раз в час в
реестре (`apps/runtime/src/sync/fansly/registry.ts`; сейчас его нигде нет): то, что

только не позже чем за 15 минут до выхода и после свежего `GET /post/scheduled`, где
пост ещё стоит; у снятия свой исход; замена ставится только после подтверждённого
снятия.
