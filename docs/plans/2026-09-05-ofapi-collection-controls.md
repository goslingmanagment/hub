# OFAPI: управление сбором данных и расходами

05.09.2026. Дополнение к плану PR #131, head a7381ff7. Статус: продуктовый и технический проект, настройки production не менялись. Fansly исключён.

## Решение владельца и изменение приоритета

Поддержка API означает возможность использовать функцию, а не обязательный регулярный сбор. Ожидаемое пополнение до 100k не является разрешением включить все потоки. Новые необязательные сборы по умолчанию выключены; текущую рабочую конфигурацию сначала показываем как baseline и не меняем автоматически.

Управление сбором входит в первый пакет. До появления серверных политик и UI новые периодические задания, обходы каталога и массовые исторические импорты не включаются. Исправления текущих контрактов, бесплатный balance probe и ручные команды можно выпускать независимо.

## Что именно регулируем

1. Новые обращения к провайдеру: категории, страницы, частота, глубина обхода, вложенные detail reads.
2. Новые подписки на события у провайдера: типы и фактическая область аккаунтов.
3. Одноразовые задачи: период истории, выбранные аккаунты, число строк/файлов, общий потолок credits/bytes.
4. Загрузку файлов отдельно от каталога: описание медиа и связи не подразумевают скачивание оригиналов/превью.

Уже полученные факты сохраняются по существующему capture-first контракту. Выключение прекращает новый сбор и не удаляет историю. Отказ от сохранения уже оплаченного ответа не экономит credits. Исключение отдельных полей из проекции обычно также не удешевляет ответ; UI предлагает реальные оплачиваемые источники и обходы, а не декоративные field toggles.

## Экран «Сбор данных»

Расположение: настройки Hub, рядом с существующей синхронизацией; ссылка с OFAPI Credits. Один основной экран, подробности категории раскрываются по необходимости.

Вверху — выбранная OF-страница либо все OF-страницы, текущий статус применения настроек, расход фонового сбора за день и 30 дней, лимит управляемых фоновых запросов. Отдельно показаны события OFAPI, действия чаттеров и внешние списания: общий vendor balance не выдаётся за бюджет одного коллектора. В подробностях — сохранённые строки/объём файлов и прирост, где измерение доступно; стоимость хранения не смешиваем с credits OFAPI. Срок хранения и удаление уже собранных фактов не меняются этим экраном.

Основная строка: **данные → для чего нужны → режим → свежесть/покрытие → фактические credits → настройки**. Примеры категорий:

| Категория | Польза | Предлагаемая политика для новой возможности |
|---|---|---|
| Сообщения, оплаты, подписки | Работа чаттеров, деньги, текущая аудитория | Сохранить действующий baseline; показывать последствия отключения источников |
| Online / typing | Индикаторы в чате | Отдельный видимый расход событий; общий scope текущей регистрации |
| Посты и комментарии | История публикаций и обсуждений | Выключено; включить выбранную глубину/частоту |
| Visitors и динамика подписок | Посещаемость и изменение аудитории | Выключено; по запросу или выбранному расписанию |
| Tracking / Smart Links | Результат источников трафика | Выключено; сначала выбранные ссылки/агрегаты, отдельное включение обхода людей |
| Vault: каталог | Поиск медиа, связи и доступность | Выключено; metadata без binary download |
| Файлы из vault | Локальная копия медиа | Только явная ограниченная задача по выбранным файлам |
| Balances / payout requests | Доступный/ожидаемый баланс, история выплат | Выключено; по запросу или расписанию |

Это проект категорий, не снимок их текущей реализации. Недоступная функция отмечается «ещё не реализована» и не получает работающий переключатель. Agent Read — полноценный потребитель, но наличие потребителя не включает сбор само по себе.

## Режимы

- **Выключено:** нет новых автоматических запросов категории, в том числе из Agent Read hydration. Сохранённые данные читаются с их реальной свежестью. Явная разовая задача доступна через отдельный preview, если разрешена владельцем.
- **По запросу:** ограниченное обновление после явного действия пользователя или разрешённого агента; фоновое расписание отсутствует. Экран сначала читает локальные данные, само открытие страницы не является согласием на платную гидрацию.
- **По расписанию:** интервал и окна, ограниченный overlap, дневной бюджет. Повторное включение продолжает допустимый checkpoint; пропущенная история не догружается автоматически.
- **Новые события:** только для категорий, которые реально предоставляет webhook. Этот режим не обещает полную историю и не создаёт скрытый REST-backfill.

В UI доступны только поддерживаемые режимы конкретной категории. Контроль сообщений по событиям, списка posts по расписанию и binary import — разные действия, хотя все они попадают в один экран.

Дополнительные настройки категории: актуальность по расписанию, выбранные страницы/ссылки, агрегаты либо подробный обход, общий лимит на задачу/день. Для исторического импорта отдельная кнопка с периодом и лимитом; «собирать с сегодняшнего дня» не запускает всю историю.

## Перед применением

Изменения сначала образуют черновик. Preview показывает:

- Что изменится и на каких страницах, включая общие webhook настройки.
- Какие экраны/Agent Read данные перестанут обновляться либо станут частичными.
- Дополнительный периодический расход отдельно от разового импорта и хранения файлов.
- Откуда оценка: vendor quote, измеренный расход аналогичных запусков либо неизвестно. Пустой источник не становится оценкой «0».
- Что уже выполняется: запросы в полёте и принятые провайдером exports/uploads могут завершиться и списать credits после паузы.

При неизвестной стоимости предлагаем ограниченный pilot с конкретным ceiling/числом вызовов, а не фоновый неограниченный старт. Сам preview не запускает платный discovery. Где получение quote имеет цену/side effect, это отдельный явный probe.

Кнопка «Применить» изменяет серверную политику. Показываем «сохранено», «применяется», «применено» и ошибку применения раздельно. Изменение webhook подтверждается remote readback; boot-only настройка не изображается немедленно действующей. Нужны actor, версия и список изменений; конфликт со свежей правкой другого окна не перетирается молча.

## Защита расходов

Лимиты контролируются сервером перед dispatch, а не только формой UI. У запроса есть категория/цель, page и инициатор; резервы нескольких worker атомарно учитываются в доступном остатке. Одна физическая операция учитывается один раз, даже если её используют два отчёта. Уже существующие caps и fair scheduling переиспользуются.

Разделяем бюджеты фоновых чтений, явных действий и разовых imports/uploads. Фоновый catalog не расходует резерв интерактивной работы. Частоты не увеличиваются и бюджеты не поднимаются автоматически после пополнения. Пользовательские паузы сохраняются при recovery/reconnect.

Называем лимит точно: **предел новых управляемых запросов**, не гарантия потолка всех списаний команды OFAPI. Webhooks, внешние клиенты того же ключа/команды, переменная цена и незавершённые операции требуют отдельного наблюдения; оценочные резервы не равны доказанной цене. При исчерпании лимита останавливаем новые задачи, сохраняем полученные ответы и видимость происходящего.

Для событий экономия требует изменения remote subscription. Сейчас Hub хранит одну global OFAPI webhook-конфигурацию. В MVP выбор типов событий применяется ко всем охваченным OF-страницам и так обозначается. Отдельные типы событий для каждой страницы требуют нескольких проверенных регистраций либо групп аккаунтов; не обещаем это обычным page toggle. По умолчанию не создаём пересекающиеся регистрации и не подписываем `*`.

При отключении сбора callbacks уже запущенных uploads/exports продолжают приниматься, а их результаты — сохраняться. Не создаём повторы/утечку бюджета из-за того, что перестали принимать завершение собственной задачи.

Текущие mirror controls не доказаны универсальной остановкой legacy pulls, desktop reads, Agent Read hydration и webhook расходов. Перед обещанием действия переключателя инвентаризируем все инициаторы категории и подключаем общий policy check. Explicit send-команды имеют собственное право и бюджет; они не становятся скрытым продолжением фонового сбора.

## Данные и реализация

Минимальный реестр категорий в коде: поддерживаемые режимы, связанные операции/события, consumers, prerequisites, единица цены и поддерживаемая granular scope. В БД — выбранная page/category policy, version, appliedVersion/state, actor/time; существующие сведения о конфигурации не дублируем без причины.

Проверка реестра в CI запрещает новые OFAPI call sites без явного назначения и policy/admission path. Один endpoint может обслуживать несколько категорий: проверяем operation + purpose/initiator, а не жёсткое «один endpoint = один поток». Для бесплатной диагностики и команд есть отдельные явные классы; общий capture-off не блокирует free balance или разрешённую отправку. Миграционный список существующих неперенесённых путей фиксирован и может только сокращаться.

Переход со старых конфигов — через один фасад effective policy. Источник решения виден: page override → default policy → явно разрешённый legacy baseline → off для новой категории. Глобальная аварийная пауза и действующие ограничения доступа/бюджета проверяются независимо и не обходятся page override. Legacy fallback допустим только при отсутствии новой политики для ещё не перенесённого пути; explicit off, ошибка чтения, конфликт версии или некорректная policy не означают «вернуться к включённому env». После миграции категории прежний конфиг больше не является второй управляющей записью.

Предусматриваем общий стоп нового фонового платного сбора с точным перечнем охваченных путей. Он не называется остановкой всех списаний: webhooks, уже принятые задачи и явные интерактивные действия видны отдельно. Карточка категории переиспользует последние jobs, checkpoints, причины блокировок и расход из существующих API; недоступная в API диагностика добавляется туда, а не требует ручного SQL.

В модели цены разделяем стоимость одного обхода и частоту: число страниц + detail requests + отдельные exports/bytes; суточный прогноз учитывает число запусков, ошибки и реальную пагинацию. Например, 933 элемента при limit=100 дают ориентир 10 list calls на обход, а не автоматически 10 credits в день. Количество объектов в примере не является текущим production-замером. Прогноз роста диска помечаем как частичную атрибуцию: индексы, WAL, проекции, входящие события и ранее запущенные операции не исчезают после выключения фонового потока.

Через contracts: GET каталог+effective policies+usage/coverage; preview изменения; versioned apply; отдельная bounded one-off job. Точные route names выбираем при реализации в существующем admin namespace. SDK, серверная ACL и actual policy одинаковы для dashboard, worker, legacy paths и Agent Read.

## Порядок выпуска

1. **Первый релиз:** инвентаризация текущего поведения, экран категорий/расходов, серверная page/category policy и существующие caps; free balance S4a. У новых категорий default off. Доступен только реально реализованный bounded on-demand либо конкретное расписание с заданным лимитом; универсальное «включить» без определённого объёма работы не выпускаем.
2. **Следующий срез:** supported on-demand/schedule, отдельные разовые backfills и preview стоимости/зависимостей. Shared webhook выбор с проверенным readback — вместе с S2/S3.
3. **По потребности:** групповые настройки для страниц, более точные прогнозы по измерениям и выделенные webhook группы. Нет обязательного конструктора правил, сотен endpoint toggles или автономного оптимизатора расходов.

Контроль является условием включения новых collectors. Он не требует закончить UI всех будущих категорий до исправления S0/S1 и не включает все предусмотренные планом функции при деплое.

Первое production-включение новой категории сохраняет действующий staged rollout: один поток, конкретные страницы, лимит и окно наблюдения; критерии — фактический расход, ошибки, полезные принятые данные и отсутствие ухудшения интерактивной работы. Связываем результат с версией политики через существующий audit/rollout механизм. Экран не превращает одновременное включение всех новых функций в обычный bulk apply.

## Приёмка

- Выключенная новая категория не делает paid reads ни из scheduler, ни из hydration; чтение сохранённого не запускает refresh.
- Две вкладки и два worker не обходят version/CAS и общий budget reservation.
- CI не пропускает новый вызов без назначения и допуска; explicit off и сбой чтения новой policy не оживляют старый enabled config.
- Пауза сохраняет checkpoint; продолжение не вызывает полный обход или автоматический backlog catch-up.
- Отключение не стирает факты и не выдаёт 0 вместо disabled/stale/partial.
- «Применено» соответствует effective состоянию worker и remote webhook, а не только записи формы.
- Исторический импорт и binary download требуют отдельной ограниченной задачи, не включаются соседним metadata toggle.
- Shared webhook scope явно показан; отключённые optional events не продолжают бесконечно оплачиваться из-за локального ignore.
- Уже принятые платные операции и их callbacks не теряются при паузе; UI показывает оставшийся риск списания.
- USD показывается только при известной фактической цене кредита; неизвестная оценка не выглядит бесплатной.

Источники OFAPI: [стоимость](https://docs.onlyfansapi.com/introduction/essentials/credits), [events и account scope регистрации](https://docs.onlyfansapi.com/api-reference/webhooks/create-webhook). Интерфейс и ограничения выше — проект Hub, не обещание новых возможностей провайдера.
