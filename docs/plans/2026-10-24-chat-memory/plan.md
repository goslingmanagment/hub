## Как исполнять

- Один пункт — один PR в своём worktree, готовый сразу, `gh pr merge --auto --squash`. Локально — тайпчек, линт
  и тесты только затронутого. Свою слитую работу выкатывает тот, кто её сделал (`scripts/deploy.sh`), выпуск
  chat-extension — `pnpm release` после зелёного main.
- Хаб не пишет фанам, расширение ничего не отправляет само. Автор берётся из запроса, который страница уже
  отправила, и из ответа на него: ноль лишних запросов к Fansly и OnlyFans.
- К архиву привязываем по id сообщения из ответа платформы, никогда по тексту и времени.
- Меняется контракт хаба — `pnpm contracts:generate`, затем SDK в chat-extension перевендоривается скриптом хаба
  (`node scripts/vendor-sdk.mjs ../chat-extension/vendor/kernel-sdk`).
- Параллельно в хабе идёт сессия «Публикация постов через Hub»: у неё миграции до 0304. Номер миграции берём
  следующий свободный в момент PR, перед мержем — ребейз на main.
- Тесты — только на хитрую логику: «первый отчёт выигрывает», расчёт смены и пауз, снятие «в разговоре»,
  отделение рассылок от личных сообщений. Тексты и конфиги тестами не закрепляем.
- Расходится план с кодом — правим план в том же PR и пишем об этом в описании PR.

## 1. Контракт «кто отправил»

### Что шлёт клиент

Тот же маршрут, шире и обратно совместимо (старые сборки шлют прежнее тело):

```
POST /api/v1/client/pages/:pageLabel/send-attributions
{ source: "chatspace-extension" | "fansly-extension",
  facts: [{ platformMessageId, fanRef, conversationRef?, observedAt, priced, withMedia,
            composedWith?, edited? }] }
```

- `platformMessageId` — id из ответа платформы на ровно эту отправку. ChatSpace: `id` ответа на
  `POST api/v0/accounts/{acc}/chats/{chat}/messages`. Fansly: `id` ответа на `POST /api/v1/message`, где
  отправитель — сама страница. На Fansly это тот же id, что `message_archive.message_ref`.
- `fanRef` — id фана на площадке. `conversationRef` — Fansly `groupId` (обязателен для `fansly-extension`), на
  OnlyFans нет: там чат и есть фан.
- `composedWith` — как написан текст: `hand` (руками или вставлен не нами), `reply`, `fix`, `hi`, `ping`,
  `coach` (вставлен кнопкой этой функции), `unknown` (не узнать, например файл с подписью на Fansly).
  Открытая строка: неизвестное хаб хранит как `unknown`. `edited` — текст правили после вставки.
- Автор — пользователь токена (`userId` из device token), никогда не поле тела. У каждого человека один
  аккаунт (`docs/identity-rights-matrix.md`).

### Какие отправки шлются

- **Fansly:** каждый ответ 2xx на `POST /api/v1/message` из вкладки, где отправитель — страница: текст, файлы,
  PPV, голосовые. Это сообщение ушло из браузера этого человека — этого достаточно для автора. Доказательство
  жестом нужно только чтобы связать отправку с черновиком (`composedWith`); без него — `unknown`. Отправки, которые
  делает фон расширения по клику человека («Новые», «Рассылка» из Спендеров), шлются из их собственной
  квитанции, как X8 в ChatSpace.
- **ChatSpace:** как сейчас (поле ввода и X8, включая PPV), плюс `composedWith`/`edited`.
- **Без автора остаются:** рассылки (Fansly `message_type = 2`, рассылки OnlyMonster), автосообщения,
  отправки с телефона и из других браузеров. Так и задумано (roadmap, «The core», п. 1).

### Что делает хаб

1. **Журнал.** Каждый факт сначала — одна строка `observations`: `source = 'client_capture'`, kind
   `client.send_attribution.v1`, producer `chat-extension@<версия>`, `actor_principal_id` = автор,
   `account_id` = страница, ключ идемпотентности `<userId>:send_attribution:<pageId>:<platformMessageId>`.
   Пишется в той же транзакции, до строки таблицы; конфликт тоже журналится. Kind регистрируется в
   `apps/runtime/src/services/observation-kinds.ts` и семье `client_capture`
   (`canonicalize/client-capture.ts`: валидация, событий не даёт).
2. **Автор.** Строка `client_send_attributions` (первый отчёт выигрывает) с новыми колонками `composed_with`,
   `edited`, `observation_id`; проверка `source` шире на `fansly-extension`. Миграция только добавляет —
   заголовок `-- agency-hub:rollback-compatible`.
3. **Привязка к архиву** — по ключу (платформа, страница, id сообщения) = `message_archive (account_id,
   platform, message_ref)`, у OnlyFans ещё `dm_message_archive (platform_account_id, platform_message_id)`.
   В `message_archive` колонку не добавляем: это пересобираемая проекция с двойником `message_archive_shadow`
   (W10), колонка потерялась бы при пересборке. Автор живёт рядом с сообщением под тем же ключом; читатели
   (лента, AI, отчёты) соединяют по ключу. Сообщение, которого архив ещё не видел, связывается само, когда
   придёт.

### Доля без автора

- **Личное исходящее** — `is_sent_by_me`, не рассылка Fansly (`message_type = 2`), не пачка (см. выше).
- **Из браузеров команды** — личное исходящее, ушедшее в минуту, когда хоть у одного чаттера страницы было
  открыто расширение на этой странице (п. 2). До выхода смен считаем по всем личным.
- Хаб показывает по каждой странице и дню: личных исходящих, с автором, без автора, доля без автора, сколько у
  каждого автора. Маршрут для владельца и тимлида, в дашборде — новая страница «Команда» (`/team`); сюда же в
  неделю 5 лягут восемь чисел.

## 2. Смена

**Расширение.** Вкладка сайта замечает ввод человека (`keydown`, `pointerdown`, `wheel`; без содержимого) и
добавляет время последнего ввода в `tab.presence`. Фон раз в 60 с, пока открыта хоть одна вкладка привязанной
страницы, шлёт в хаб пульс: `POST /api/v1/client/activity { instanceId, pages: [{ pageLabel, lastInputAt }] }`.
Последняя вкладка закрылась или человек вышел — пульс с `closed: true`. Запросов к сайтам нет.

**Хаб.** Пульсы ложатся в поминутную таблицу (человек, страница, минута, был ли ввод) и в состояние экземпляра
(последний пульс, закрыт ли). Пульсы — не данные площадки, в `observations` их не журналим. Смена считается из
минут при чтении:

- **Вход** — первая минута с вводом.
- **Пауза** — с 10-й минуты без ввода до следующего ввода; первые 10 минут простоя — работа (чтение, ожидание
  ответа фана).
- **Выход** — расширение закрыто (пульс `closed` или 3 минуты без пульсов) либо 60 минут без ввода; время
  выхода — последний ввод плюс не больше 10 минут.
- **Отработано** — смена минус паузы. Разбивка по страницам — по минутам с вводом на странице.

Расчёт — чистая функция с тестами (паузы, края, две вкладки, закрытие). Маршрут чтения смен — владелец и
тимлид; в дашборде — блок «Смены» на странице «Команда»: кто, вход, выход, отработано, паузы, страницы, сколько
сообщений с автором за смену.

## 3. «В разговоре»

- **Правило.** Фан страницы «в разговоре» с чаттером X, пока последнему сообщению X этому фану (по
  `client_send_attributions`) меньше 15 минут и расширение X не закрыто после этого сообщения (п. 2). Пишут
  двое — в списке оба, первым свежий. Никто фаном не владеет, сообщения без автора отметку не ставят.
- **API.** `GET /api/v1/client/pages/:pageLabel/in-conversation` → `{ serverNow, fans: [{ fanRef,
  conversationRef, userId, name, isMe, lastSentAt, until }] }`. Только база, узкий токен chat-extension.
- **Расширение.** Опрос раз в 30 с, пока открыта вкладка страницы (как «Новые»). Метка «в разговоре: Никита» —
  на строках фанов в наших списках: Спендеры, «Ожидают ответа», «Новые», ⌘K. В родные списки чатов сайта не
  встраиваем (решения Б9 и `docs/project-unite/spec.md` в chat-extension). В открытом чате с таким фаном —
  плашка «С ним сейчас говорит Никита · 4 мин назад» с «Понятно»; перед «Отправить» из превью (X8) —
  предупреждение по образцу `CG-SEND-STALE` с «Отправить всё равно». Отправку руками не перехватываем и не
  блокируем: плашка видна до того, как человек начал писать.
