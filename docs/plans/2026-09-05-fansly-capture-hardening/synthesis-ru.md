# Синтез (фаза 6) — Fansly capture hardening

Версия 2 (после подписи планировщиков и решений владельца 2026-09-06; v1 сохранена рядом). Дата: 2026-09-06. Источники: `plans/plan-fable.md`, `plans/plan-astra.md`, `cross-1/`, `cross-2/`, `answers.md`, `reference/prod-facts-2026-09-05.md`. Факты, помеченные «проверено», оркестратор сверил с репо сам.

## 1. Диагноз: что сегодня опасно, что нет

**Опасно (по убыванию):**
1. **Хаб реплеит личную сессию владельца.** Тот же токен живёт в браузере владельца и уходит через US-прокси страницы; Fansly хранит IP/город/last-used по каждой сессии (в HAR ответ `/sessions`: 29 сессий, 15 IP). Если машина владельца не ходит через прокси страницы (его выход не проверялся — условие, не факт), одна сессия чередует два IP и два гео. В любом случае это единственный субъект в схеме, чья сессия скопирована на второй транспорт; отзыв сессии — одно действие платформы.
2. **Запросы без идентичности.** На проде уходит только `authorization` + статичные Firefox-заголовки (ответ владельца §1): нет `fansly-client-id`, `fansly-session-id`, `fansly-client-check`, кук, OPTIONS-префлайта. Настоящий клиент так не ходит никогда. Принимается — значит терпится, не значит безопасно.
3. **TLS/HTTP1.1 Node под Firefox-UA.** undici без `allowH2`, OpenSSL ClientHello; апстрим — CloudFront + «Fansly Api Gateway»; в бандле есть интеграция AWS WAF (challenge.js, токен-сервис) — спит, но включается конфигом. Челлендж-страницу код сегодня не распознаёт (упадёт в `provider_bad_data`).
4. **Поведение.** Метроном 2,6 с 24/7, полный обход всех диалогов каждые 30 мин (lilly-2: ~13,5 тыс. диалогов × 48 раз/сутки ≈ 6,5 тыс. запросов), две статистики на каждого спендера ежедневно, 100 диалогов на страницу вместо 20/10 у приложения. ~29 тыс. observations/сутки на 6 страниц (≈ вызовы; без ретраев и фонового трафика браузеров).
5. Мелкое: Retry-After обрезается до 60 с (проверено, `http-client.ts:20`), 401/403/челлендж схлопнуты, кулдаун после 429 не общий между стримами, тип прокси нигде не записан.

**Нормально:** прокси на страницу, fail-closed без прокси; capture-first журнал; адаптер без write-маршрутов; 401/403 паркуют страницу; дневные капы bulk-лейнов; чаттеры — отдельные менеджер-сессии (свои identity), не копии токена.

**Ключевой факт по check (оба, независимо):** `fansly-client-check = cyrb53(константа + "_" + pathname + "_" + deviceId)` по точному пути, не по семейству; Astra сверил на 408 запросах из 6 HAR — 0 расхождений. Семейства маршрутов в коде (`FANSLY_CLIENT_CHECK_ROUTES`) неверны по построению; сейчас это не стреляет только потому, что check вообще не отправляется.

## 2. Решение

**Вариант B: свой постоянный браузер-профиль на каждую Fansly-страницу на инфре хаба, залогиненный один раз как модель владельцем через удалённый экран, за прокси страницы, в режиме capture по умолчанию всё запрещено кроме allowlist GET. Чаттеры и расширение не меняются. Сессия владельца из хаба уходит. До этого — сокращение трафика, не зависящее от транспорта.**

Отвергнуто обоими: A (импersonation TLS в Node — гонка вооружений, ломается при первом челлендже), C (только расширение — не собирает при закрытых браузерах), D (антидетект/облачный вендор — третья сторона на самом чувствительном пути, нет доказанного преимущества), E (свой логин из Node — тот же транспорт, плюс кастодия пароля и логин-маршрут как первое место для челленджа).

## 3. Этапы

**Этап 0 — базовая линия (1–2 дня, только чтение).** Отчёт «какие поля есть в bundle» без значений (`fansly:endpoint-probe --dry-run`); эффективный конфиг пейсинга (owner-session, `config_settings` read_only не видит); инвентарь прокси (провайдер, тип, static/rotating, протокол — sockS5 с auth решает конструкцию туннеля); IP выхода 3 раза за сутки (`page proxy-ip`); объяснить ~79 страниц followers/час у lilly-2; два 401 по `*:failed` сниппетам; измерить `k` — сколько диалогов меняют голову за 3 ч (по `page_dm_threads` между поколениями); отчёт по спендерам: N, с транзакцией за 1/7/30 дней. Записать в `docs/decisions.md`.

**Этап 1 — безопасность и объём, без смены транспорта (1–2 недели, каждый пункт за своим live-ключом, по одной странице за 48 ч, начиная с ari-1).**
- 1a. **Каденс `dm_conversations` 30 мин → 2 ч, SLA 4 ч**, полный обход как есть, 100/стр. Реализация — **page-resolved Fansly-политика за fail-closed allowlist** (OnlyFans-константы не трогать), одним резолвером в seeding/scheduler/status/health; **ребейз `last_scheduled_slot` в новые единицы в том же UPDATE** (проверено: `ensurePageSyncStates` переписывает cadence, но не slot → стрим застрянет на столетия), максимум один немедленный запуск, никаких «догнать пропущенные слоты»; health, деплой-гейт и пины тестов 1800 — в том же PR. Ожидание: lilly-2 ≈ 1 630 списочных вызовов/сутки вместо 6 500 (−75 % лейна, −38 % всего трафика).
- 1b. **Телеметрия попыток** (страница, транспорт, операция, статус, время старта/конца, retry deadline; наличие identity-заголовков — да/нет).
- 1c. **429:** первый 429 — запрос терминален, без inline-ретрая; durable-кулдаун `cooldown_until` на строке egress в `sync_rate_limits` + page-scope (GREATEST). Ожидание = max(серверный Retry-After **целиком, без потолка** — длинный дедлайн просто виден владельцу; наш пол 30 мин); без заголовка — лестница 60/120/240/360 мин (потолок только для нашего fallback). **Admission-hook в самом `adapter.request()`**, независимо от `syncSharedRateLimitEnabled` (при выключенном флаге адаптер уходит в in-process цепочки и хук через rate-limiter не сработал бы; `resolveEgress().pace()` адаптер не покрывает — проверено); второй 429 за сутки — инцидент; третий — пауза страницы. Расширение (отдельно, мелко): убрать клэмп 5 с и inline-ретраи, локальный кулдаун.
- 1d. **Классификатор челленджа/интерстишиала** (HTML-тело, 202/405 с `x-amzn-waf-*`, нет gateway-заголовка) → `failureKind: challenge`, `manual_action_required`, новый инцидент `fansly_challenge`; **латч «401/403 на ≥2 страницах за 10 мин»** — сигнал-гипотеза «возможно, Fansly включила проверку» для владельца, отдельно от одиночного `auth_blocked` (диагноз из двух кодов автоматически не выводится).
- 1e. **Head-режим обхода диалогов** (после 1a и измерения `k`): отдельный режим стрима, limit 20 от offset 0, стоп после 2 неизменённых страниц (окно расширяется автоматически при `head_mode_miss`), **не трогает поколение #214** (не инкрементит generation, не штампует `last_seen_generation`, не запускает visibility pass; новый тред — с `lastSeenGeneration: null`, примитив уже есть в `page-dm.ts:164-240`); полный обход 100/стр раз в сутки остаётся единственным сертификатором членства; head-обновления не пересекаются с активным полным поколением; свежесть головы — отдельный вход health. Сначала инструментировать `would_stop` в обычных полных обходах (без лишних запросов), включать при нуле пропущенных новых голов. Арифметика для lilly-2: 8·H + 136 вызовов/сутки (H — страниц на опрос); при H≈2–10 это 2–3 % от сегодняшнего лейна.
- 1f. **fan_earnings — решение владельца: ежедневный обход всех спендеров остаётся.** Модель due/dirty снята. Единственное изменение — убрать дубль-попытку: при падении второго вызова пары (monthly) не повторять успешный первый (stats); чекпоинт по фану с идентичностью запроса и durable-квитанцией, курсор двигается только после обоих. Эффект — только меньше ретраев.
- 1g. Followers: сначала объяснение из этапа 0; кап — только как resumable yield без штампа успеха. Джиттер — неотрицательный `floor + U(0, 0.3·floor)` внутри резервирования, опционально. Тихие часы — не сейчас (решение владельца); к слову, планировщик пропущенные слоты не догоняет (`page-sync.ts:1930-1952`), так что пауза уменьшает суточный объём, а не сжимает его; цена — только отставание архива на длину окна.

**Этап 2 — сервис page-browser, канарейка без смены транспорта (2–3 недели).** Роль `browser` (отдельный контейнер/хост), persistent-профиль на страницу, launch через **per-page loopback-туннель** с креденшалами прокси из резолвера (Playwright 1.60 отвергает socks5 с auth для любого движка — проверено обоими; без прямого fallback, DNS через прокси, TLS end-to-end); Xvfb + VNC/noVNC только через SSH-туннель владельца; таблица `page_browser_profiles` (статус, identity_kind, наличие device/session — булевы, exit_ip_last, last_login_at); два режима профиля — `login` (владелец на экране; узкие исключения только для маршрутов логина/2FA/WAF и boot-чтений приложения, guards ставятся ДО первой навигации) и `capture` (включается сразу после логина); suточная проверка IP выхода → инцидент при смене. Владелец логинится на ari-1 как модель. Parity-harness: `page.on('request')` записывает имена/порядок заголовков и длины (без значений) с собственных запросов приложения при логине. **Офлайн-прототип (go/no-go) — ДО первого живого логина:** фикстурная платформа + перехватчик из бандла доказывают, что мост и lock-down работают (включая блок `/message/ack`, `/status`, WS, service workers, попапов); если нет — стоп на этапах 1 + hardened undici, доложить владельцу.

**Этап 3 — транспортный шов и переключение канарейки (2–3 недели, после ≥7 дней `logged_in` на ari-1).** `FanslyTransport` интерфейс под `adapter.request()` (`adapter.ts:2006-2011` — единственный raw fetch): `UndiciTransport` (как сегодня) и `BrowserTransport`. В браузере: `fetch` из origin `fansly.com` с `credentials: include`; identity-заголовки ставит версионированный хелпер из состояния профиля (`localStorage` device_id / active_session, ts по правилу приложения); **ключ check** — проверенный рецепт для поддерживаемой сборки, валидированный по нативно и успешно отправленным запросам того же точного пути в той же identity/сборке; при несовпадении — **fail-closed**: разрешён только валидированный check для уже виденных путей, чтения по остальным путям ставятся на паузу + инцидент `check_key_drift` (вариант «слать без check» отклонён: форма «браузерная сессия без check» никем не проверена); неизвестная сборка/сессия — пауза, не подбор. **Capture-mode default-deny:** `context.route` до навигации — только GET на allowlist путей адаптера + boot-чтения приложения + статика/CDN; OPTIONS только для разрешённых GET; все POST/PUT/DELETE блокируются (в HAR: 14 `POST /message/ack`, 7 `POST /status`, `/it/*`, метрики, intercom — живая вкладка шлёт delivery-ack даже без открытия диалогов); `serviceWorkers: 'block'`; **WebSocket блокируется** (`routeWebSocket` до создания; session id от сокета не зависит); попапы закрыть. Хелпер GET-only по построению, тест пинит + тест «каждый `endpointTemplate` в allowlist». Egress: новый transport-класс через резолвер, custody-descriptor `browser_profile` в registry (без новых `platform ===`). Флаг `fanslyBrowserTransportPageAllowlist` fail-closed. `sync_http_attempts.transport` для сравнения. Парность: те же запросы, те же тримы, те же `persistRawPayload` — сравнивать счётчики и хэши по kind (±10 %). Отдельная блокировка: один владелец профиля, старый undici-bundle страницы не используется, свежий токен браузера в undici не экспортируется. **Откат** = пауза и дренаж страницы с сохранением кастодии; возврат на legacy-реплей — только явным решением владельца и только пока legacy-credential ещё существует (до этапа 4); автоматического «следующий чанк на undici» нет. Канарейка ari-1 → 7 чистых дней → lilly-1/busy page → остальные по одной за 48 ч.

**Этап 4 — флот, отзыв вставленной сессии, удаление эмуляции (1–2 недели).** Удалить bundles владельца из `page_credentials` (не отзывать его живую нативную сессию), форма вставки в дашборде → статус профиля + «открыть экран»; убрать `UndiciTransport` для Fansly, `buildFanslyRequestHeaders`, семейства check, raw-fetch budget 10→9; пробы через браузер; решения в `docs/decisions.md` (identity на страницу, политика прокси «static residential/mobile, US, один на страницу, IP проверяется ежедневно»).

**Этап 5 (опционально)** — зашифрованный пароль и автоперелогин через форму приложения с 2FA-кодом от владельца через Telegram. **Этап 6 (опционально, после 4)** — журналирование WebSocket-кадров как observations нового source → свежесть лучше сегодняшней при меньшем трафике. Оба не обязательны.

Зависимости: 0 → 1a/1b/1c/1d (параллельно, флипы по одному) → 1e, 1f (после измерений) ; 1c+1d → 2 → 3 → 4 → (5, 6).

## 4. Приёмка

- Этап 1: `dm_conversations` ≤ 30 % базы на lilly-2/lora-1 за 3 дня; свежесть на `/health/sync` ≤ каденс + 30 мин; деплой-гейт зелёный; 0 × 429; фикстуры 429/челленджа классифицируются; head-режим: ≤ 10 % базы, 0 пропущенных новых голов; борд «Ждут ответа» отстаёт ≤ 4 ч.
- Этап 2: `logged_in` 7 дней без перелогина; IP выхода неизменен; parity-отчёт показывает 4 identity-заголовка на собственных запросах приложения; рестарт роли восстанавливает `logged_in` без владельца; память в лимите.
- Этап 3: observations по kind ±10 % к undici-базе; 0 транспортных `provider/http` фейлов; хелпер и приложение header-идентичны (имена/порядок/длины, равенство check на общих путях); **100 % запросов хелпера несут все четыре identity-заголовка** (по колонкам 1b; у путей с id вроде `/group/{id}/` нет двойника у приложения); учение по откату (пауза → дренаж → owner-approved возврат на legacy); ни одного заблокированного POST, ушедшего наружу; crash-тесты квитанций (убить браузер/воркер на приёме, журнале и ACK; повторная доставка без повторного fetch) до переключения.
- Этап 4: 0 Fansly-токенов в `page_credentials`; raw-fetch budget 9; 14 дней без `auth_blocked`/`fansly_challenge`/`proxy_failed` от браузера.
- Всё измеряется по телеметрии, которую ядро уже пишет; ни один шаг не добавляет запросов к Fansly сверх обычного захвата.

## 5. Риски и допущения

- «На проде только authorization» — слова владельца, этап 0 подтверждает без значений.
- Прокси статичные — не проверено; ротация хуже в браузере, чем в реплее (device id постоянный, IP нет) → менять прокси до переключения страницы.
- Извлечение ключа check хрупко (декои в бандле, issue prof79/#115) → лестница валидации и fail-soft в «без check».
- Playwright Firefox — патченная сборка (патчи и ниже JS: `nsHttpChannel.cpp`, перехват, сертификаты; патч `Navigator::Webdriver()` возвращает true — снимается ли префами, не доказано); Playwright Chromium — CDP `Runtime.enable` артефакт. Транспортная парность (TLS/H2) со стоковыми сборками ни для кого не доказана: в HAR нет ClientHello. Ни у кого доказанного преимущества по банам; досье в `cross-4/`, решение владельца в §6 (D1): Chrome.
- Живая вкладка = поведение приложения (ack, presence) → default-deny обязателен, иначе хаб меняет то, что видят чаттеры и фаны.
- Память: 300–500 МБ на профиль (оценка) vs 16 ГиБ запас (страховка) — мерить в спайке на 1/3/6/8 профилях, покупать после.
- Хранение: тримы сайдкаров (#224, ~11:1 дедуп) остаются; полные тела — отдельное решение, не часть миграции.
- Остаточный риск после всего — поведенческий (объём автоматизации); противоядие — бюджеты, live-ключи, латчи инцидентов.
