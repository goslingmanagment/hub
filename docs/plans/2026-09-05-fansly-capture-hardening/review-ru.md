# Разбор планов (фаза 4) — Fansly capture hardening

Дата: 2026-09-06. Планы: `plans/plan-fable.md` (Fable 5.1, max), `plans/plan-astra.md` (gpt-6-astra, max).

## Главное

Оба независимо пришли к одной архитектуре: **свой постоянный браузер на страницу, залогиненный как модель, за прокси страницы; чаттеры остаются как есть; сначала режем объём обхода диалогов.** OFAPI/облачные браузеры/«только расширение» оба отвергли. Расходятся в деталях исполнения (Firefox или Chromium, как именно резать обход, насколько «зажимать» браузер, что входит в первый этап).

## Fable

**Плюсы.** Самая конкретная диагностика: таблица «что шлёт настоящий Firefox vs что шлёт хаб» по HAR (HTTP/2 vs HTTP/1.1, 10 кук vs 0, OPTIONS-префлайт vs ничего, device id / session id / check отсутствуют). Нашёл, что Fansly хранит IP и город по каждой сессии (в HAR ответ `/sessions`: 29 сессий владельца, 15 IP) — самый сильный аргумент, почему шарить сессию владельца между его машиной и прокси опасно. Разобрал бандл: check = cyrb53(константа + путь + device id) по точному пути; AWS WAF в бандле есть, но спит. Конкретный план сокращения трафика с цифрами (−80–90 %), с указанием файлов и констант. Чёткая последовательность 0→6 с критериями приёмки по телеметрии.

**Минусы.** Кое-где переоценивает готовность кода: пишет «egress через резолвер», а адаптер Fansly резолвер не вызывает (проверено: `resolveEgress` зовут только vendor-потребители, адаптер держит свой диспетчер). Инкрементальный обход диалогов (20 на страницу, стоп после двух неизменённых) описан уверенно, но не разобран против решения #214 (финализация видимости только при точном совпадении счётчика). Ночные «тихие часы» и джиттер подаёт как защиту, доказательств нет. Оценка памяти 300–500 МБ на профиль — на глаз.

## Astra

**Плюсы.** Самый осторожный и юридически честный текст: везде разделяет «доказано» и «предполагаем», не обещает «без банов». Нашёл реальные дефекты: Retry-After обрезается до 60 с (проверено), 401/403 схлопнуты в одно состояние, кулдаун после 429 не разделяется между стримами. Нашёл ловушку смены каденса: `last_scheduled_slot` хранится в единицах старого каденса, при увеличении каденса стрим «застрянет» (правдоподобно, надо проверить при реализации). Настаивает на write-guard: живая вкладка Fansly сама шлёт POST (`/message/ack`, статус, телеметрия) — браузер-сборщик должен это запрещать по умолчанию. Требует офлайн-прототип «как выполнить запрос через пайплайн приложения» как go/no-go до канарейки. Сверил алгоритм check на 408 запросах из 6 HAR — 0 расхождений.

**Минусы.** Слишком консервативен в цифрах и объёме: первый этап — только каденс 2 ч, остальные сокращения «после миграции по телеметрии»; хостинг 16–24 ГиБ RAM без обоснования; текст тяжёлый, много оговорок. Выбирает Chromium вместо Firefox по «поддержке инструментов», хотя все реальные клиенты на этом IP — Firefox. Арифметика «20 на страницу × 2 ч = 1,25× запросов» верна только если обход остаётся полным, а Fable предлагает инкрементальный.

## Сходятся (кандидат в общее ядро)

1. Архитектура B: постоянный браузер-профиль на страницу на инфре хаба, за прокси страницы, логин владельцем через удалённый экран, без сохранения пароля на старте.
2. Сессия владельца из хаба уходит; чаттеры и расширение не трогаем.
3. Первый этап — сокращение обхода диалогов (2–3 ч) с одновременной правкой SLA/health/деплой-гейта/тестов.
4. check вычисляется по точному пути, семейства маршрутов в коде неверны; AWS WAF в приложении есть, спит; TLS/HTTP1.1 Node под Firefox-UA — несоответствие.
5. Транспорт выносится в интерфейс под `adapter.request()`; undici остаётся откатом до доказанной парности; канарейка ari-1 → busy page → остальные по одной.
6. 401/403 не ретраить; кулдаун после 429 сделать длиннее и общим; классификатор челленджа/интерстишиала.
7. WebSocket и пассивный сбор расширением — потом, не обязательны.
8. Опции A (импersonation в Node), C (только расширение), D (антидетект-вендор), E (свой логин из Node) — отвергнуты обоими.

## Расходятся (в кросс-обмен)

| # | Вопрос | Fable | Astra |
|---|---|---|---|
| D1 | Браузер | Playwright Firefox (+ лестница: stock Firefox через BiDi, Camoufox) — как у чаттеров на том же IP | Обычный headed Chromium с песочницей; Playwright-Firefox — патченная сборка |
| D2 | Обход диалогов | Инкрементальный: limit 20, стоп после 2 неизменённых страниц, полный обход раз в 24–48 ч; каденс 3 ч | Полный обход 100/стр как сейчас, каденс 2 ч; «стоп на первой неизменённой странице может потерять факты», 20/стр умножает запросы |
| D3 | Как выполнять запрос в браузере | Инжект-хелпер собирает identity-заголовки сам (device id из localStorage, ключ из бандла, fallback — подсмотренный check); вкладка живёт, WS открыт | Только через HTTP-пайплайн приложения; `page.evaluate(fetch)` перехватчики не вызывает; capture-mode с запретом всех POST и WS; офлайн-прототип как гейт |
| D4 | 429 | Без ретрая, пауза страницы 30–60 мин, второй за сутки — инцидент | Уважать полный Retry-After (сейчас клэмп 60 с), общий durable-кулдаун, ретраи считать в бюджет |
| D5 | Объём этапа 1 | Каденс + инкрементальный обход + fan_earnings по изменениям (−85 %) + кап followers + джиттер + тихие часы | Только каденс; остальное после миграции по телеметрии; тихие часы и джиттер — нет |
| D6 | Где менять каденс | Общие константы `SYNC_STREAM_POLICY` | Fansly/page-политика за allowlist; ребейз слотов при переходе |
| D7 | Сырой захват | «Журналирование не меняется» | Сайдкары режутся до `persistRawPayload`; браузер должен журналировать оригинал; стоимость хранения |
| D8 | Хост | 3–4 ГБ на 6–8 профилей | 16–24 ГиБ |

Продуктовые развилки для владельца (после кросс-обмена): identity браузера (модель или отдельный менеджер-аккаунт), хранить ли пароль, ночная пауза, Firefox/Chromium если модели не сойдутся.
