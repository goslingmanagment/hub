# Questions — Fable (phase 2)

Each answer changes the diagnosis severity, the option ranking, or the migration path. Where I state a finding, it is what the repo shows today; correct me if production differs.

1. **What is the current session bundle actually carrying, per page?** Repo state: the dashboard paste form accepts only the scalar `fanslyClientCheck` (`apps/dashboard/src/pages/settings/PlatformCredentialsFields.tsx`), the adapter never uses that scalar since decision #234 and sends `fansly-client-check` only from `routeChecks` (`packages/fansly/src/request-headers.ts`), and the extension has no path that pushes a bundle to the kernel (credential routes are `owner-session` only in `packages/contracts/src/routes.ts`; no hub call in `~/code/goose/fansly-ext/src/background`). So unless `routeChecks` were loaded through `page add fansly --session-file`, every production request since 2026-08-23 goes out with **no** `fansly-client-check`. Which is it on prod today: (a) no check on any route, (b) route-family checks loaded by file on some/all pages? And has any page been re-pasted since 2026-08-23? This decides whether the replay evidence (0×429, 2×401 over 14 days per `backlog.md`) proves "Fansly ignores the check" or "the check is currently absent and tolerated".

2. **Where does the pasted bundle come from, and who owns the browser it was copied from?** Options: the owner's own login on a machine at the owner's location; a chatter's Firefox; a dedicated browser that stays open. Public reverse of the web client (fansly-downloader-ng `api/fansly.py`) says `fansly-client-id` is a server-issued device id (`GET /device/id`) and `fansly-session-id` is the id of a live WebSocket session (`wss://wsv3.fansly.com`). So the kernel replays a device id and a session id that belong to some browser. Is that browser still open and logged in (so the ids are "alive" in two places at once), or was it closed after the paste (so the kernel is the only user of a dead session id)? Also: what triggered the two 401s in the last 14 days (chatter logout, password change, Fansly forced re-login), and what was the re-paste procedure?

3. **Per-page proxy inventory.** For each of the six Fansly pages: provider, type (mobile / residential / datacenter), country/city, static or rotating (and rotation period), IPv4/IPv6, protocol (socks5/http). The code accepts any of `http/https/socks5` and records no type (`packages/shared/src/proxy-string.ts`, `backlog.md` FANSLY-007). Type and geography drive the network-identity part of the diagnosis and the cost of every option; a datacenter IP would move "harden the replay" from viable to not viable.

4. **Chatter workstation reality.** Per page: how many chatters log into the model account, from which countries, on what browser (Firefox with the extension only?), whether they route through the page's proxy, any proxy, a VPN, or their home IP; how many concurrent logged-in sessions per account are normal; whether the model also uses the Fansly mobile app or logs in herself. Concretely: is the rule "chatter browser and hub use the same egress" enforced anywhere today, or is it known that one account is simultaneously used from the hub proxy country and from chatters' home countries? (FANSLY-003 in `backlog.md` says this was never fixed; I need the actual state.)

5. **Observed Fansly signals so far.** Since kernel capture began (Stage 16, July 2026): any Fansly security emails ("new login", "new device", "unusual activity"), forced logouts, email/2FA code prompts on login, CAPTCHA/challenge pages, shadow limits (messages not delivered, reach drops), warnings, or bans on any model account, including before the kernel existed (extension-only era)? Is 2FA enabled on the model accounts, and of which kind (authenticator app vs email code)? This is the only ground truth on Fansly's enforcement I cannot get from the repo, and it sets the re-auth design for any browser-based option.

6. **Freshness requirements for the kernel's copy.** The largest traffic share is the 30-minute `dm_conversations` sweep with `/group/:id` lookups (about 60% per `backlog.md`), plus the daily bulk lanes (media_stats 300, post_replies 100, catalog 60, notifications 96 attempts/day). Which kernel consumers actually need DM/notification freshness below a few hours (workboard, Agent Read Plane, Telegram reports, AI features via clientContext)? If the extension stays the chatter's live reader, may the plan cut the kernel's Fansly request volume by an order of magnitude (longer cadences, no per-group detail calls, lanes paused on most pages) as its first shipped stage, or is current freshness a product commitment?

7. **Appetite for a browser-based transport on hub infrastructure.** The backlog's target picture (FANSLY-004) is a persistent Firefox per page owned by the hub, behind the page proxy, with the kernel's requests executed from the page context. Playwright and a Chromium headless shell are already in the runtime image (`Dockerfile`, `apps/runtime/package.json`), but Firefox is not, and a persistent profile per page costs roughly 300–500 MB RAM each. Constraints I need: (a) acceptable monthly spend for a larger VPS or a second host; (b) whether the model's password may be entered on hub infrastructure (login there), or whether only a session import from an existing browser is acceptable; (c) whether an owner-operated remote screen (noVNC-style) for login/2FA/challenges is acceptable operationally; (d) whether a third-party anti-detect/cloud-browser subscription (GoLogin/Multilogin-class) is acceptable or excluded on principle like OFAPI-for-Fansly is.

8. **Scope of the chatter-side change.** Two very different end states: (A) chatters keep working in their own Fansly tabs with the extension (multiple sessions per account remain, the kernel just needs to look like one more real browser), or (B) chatters eventually work through a hub-owned client so there is exactly one session/IP/fingerprint per page (FANSLY-006; needs a Fansly write path the adapter deliberately does not have). Is (B) an acceptable direction to plan toward in stages, or must the plan assume (A) indefinitely? The answer changes the recommended architecture, not just its later stages.

9. **Canary and experiment permissions.** May the plan designate one low-value page (e.g. ari-1, ~440 calls/day) as the canary for: pausing kernel replay entirely for a window, switching transports, and running a small number of owner-run probe calls (endpoint-probe class, read-only) to measure things like whether a stale session id or a wrong check is rejected on specific routes? Which pages are off-limits for experiments?

10. **Growth and horizon.** Expected number of Fansly pages in 6–12 months, and the time horizon for this work (weeks vs a quarter). A per-page browser and a per-page proxy scale linearly; the answer decides whether a single-host design is enough.

11. **Reference material access for phase 3.** The local 2026-08-19/20/21 Firefox HARs are cited in code comments but are not in the repo. Can the header order, `OPTIONS` preflight pattern, WebSocket frames (`wsv3`), and request timing from those HARs be shared with the plan (redacted), or must the plan treat them as unavailable and schedule a fresh capture as its first task?
