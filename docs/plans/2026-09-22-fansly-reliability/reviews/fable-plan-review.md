# Fable plan review

Model: claude-fable-5-1; 109 turns; successful; no permission denials.

Review complete. Everything below is based on the plan documents, the current source on this branch, the existing tests and migrations, and Decisions 344, 366 and 367. No commands were run and nothing was edited.

**Overall:** the four root causes are correctly identified and the fixes are the right size, with two design points that cannot be implemented as written (Plan 01's bulk-delete exclusion and Plan 03's account-verification precondition) and two places where the plans add durable state the code can already derive.

## Blockers

**B1. Plan 01 excludes the very deletes it needs to settle.** The plan says a "bulk" or "correlation-only" mutation receipt is not evidence. In `packages/shared/src/fansly-ws-hints.ts:61-70` every mutation_debt node already carries an exact `messageRef`; `bulk` is only `message.type === 3` and `correlationRef` is additive. There is no documentation in the repo of what type 3 means (I checked the corpus, runbooks and decisions). Counterexample: create hint for message 150 is routed, the deletion frame arrives with type 3 and id 150, REST head never shows 150 again. Under the plan's rule the group stays `target_unconfirmed` and re-reads the head every minute, which is the exact cap-burn the plan set out to stop.
Smallest correct change: evidence is an exact match on (page_id, group_ref, message_ref) against a mutation_debt receipt with `received_at >= create.received_at`. Drop the bulk exclusion, or keep it and give that path its own visible outcome so it is never mistaken for the fixed defect. Also measure first: the delete receipt's `group_ref` is nullable (`nativeRef(message?.groupId)`); if production deletion frames omit groupId the rule never fires. A read-only count of mutation_debt rows by `group_ref is null` belongs in the pre-implementation checks.

**B2. Plan 03's apply precondition can never be satisfied by existing B0 proof.** The plan requires that "a verified connection must correspond to the expected native page account" and forbids adding a heuristic if B0 cannot prove it. B0 cannot: "verified" means a session frame with an object payload arrived (`packages/shared/src/fansly-ws-capture.ts:25`); `fansly_ws_connections` has no account column (migration 0196); the `accountRef` stored on captured observations is the expected id copied from the page row (`apps/runtime/src/services/fansly-ws/worker.ts:117`), not an observed one. As written, apply would always refuse or the implementer would add the forbidden heuristic.
Smallest correct change: remove the account-correspondence requirement. The generation digest already includes `nativeAccountId` from the page row (`fansly-probe-context.ts:56-60`), so a same-page rotation cannot silently change accounts. Require under `lockFanslyWsGeneration`: current generation equals the previewed candidate, the candidate is not `auth_refused` (`isFanslyWsGenerationBlocked`), the policy parses and is enabled. Report, but do not require, an open connection with `verified_at` set and a recent `last_guard_at`.

**B3. Plan 03 must not feed `/health/sync`.** Decision 366 classifies a post-rotation mismatch as an accepted latency regression. `/health/sync` is the deploy gate; making mismatch a stall reason would degrade deploys for a state the decision accepts. No runtime code reads `fansly_ws_connections` or the hint receipts today except erasure, so there is no "existing" health integration to extend. Put the mismatch in the detailed sync status where the A1 policy is already read per page (`sync-status.ts:964`) as an informational field, plus a runbook SQL check.

## Recommended changes and tests

Ordered by importance.

1. **Plan 02, attribution rule.** The wrapper emits a `failed` event for the admitted requestId and then rethrows the raw error (`packages/shared/src/http-request.ts:112-126`). Capture that terminal event in the existing `observer` in `fansly-ws-hints.ts:75`, keyed by the admitted requestId. In the catch block, defer only when the caught error is not `HintDeferred`/`FanslyApiError`, the observed event exists for that requestId, and `failureKind` is not `"policy"` (lease-lost cancellation uses `"policy"`, `http-request.ts:101-107`). Anything else, including errors thrown from `owned()`, staging validation and `upsertPageDmMessages`, keeps propagating. Also replace `defer("admission_deferred")` at line 229 with `defer(error.message)` so `budget_exhausted`, `admission_expired`, `type_disabled` and `generation_changed` are visible.
2. **Plan 02, backoff without new columns.** `subject_refresh_state.consecutive_failures` already exists (migration 0134) and `advanceFanslyWsHint` never touches it. Increment it on deferrals, reset on completion, and compute `retryAt` as `min(60s * 2^n, 1h)`. Routing R+1 already leaves `retry_after_at` alone (`fansly-ws-hints.ts` repository, lines 50-70), so a new signal cannot erase the backoff.
3. **Plan 01, settlement derived in the view.** The subject row's `applied_revision` advancing is already the operational settlement. Redefine `fansly_ws_hint_status` to compute `settlement_kind` as `rest_materialized` when `hot_applied_at` is set, `source_deleted` when the exact delete receipt exists, `group_checked` when `applied_revision >= routed_revision` with neither, else null. `hot_applied_at` keeps its meaning untouched, existing stamping at repository lines 210-217 already excludes deleted rows, and the deletion evidence reference is the delete receipt's `event_id`. `CREATE OR REPLACE VIEW` with appended columns is forward-only and safe for an older binary.
4. **Plan 04, five-line fix.** At `fansly-dm-conversations.ts:356-359` resolve `boundaryMs` from `previousSchedule?.lastCertifiedFull?.completedAt` when the proof parses and is not in the future, else the current legacy completed-certified rule. `previousSchedule` (line 289) already covers both the bounded document and a legacy completed document with polling. Completion time is the right A0 boundary: Decision 367 records that the seven-day evidence was collected under it, and A1's stop keeps `startedAt - 60s` in `advanceDmBoundedStop`. Do not add persistence: diagnostics already ride every page write (`line 975`) and existing diagnostics win on resume (`line 354`). A crash between the fresh-sweep checkpoint (line 342) and the first page leaves no diagnostics but `pageCount === 0`, so `completeCoverage` is true and the boundary is recomputed from `polling`, which is correct.
5. **Plan 03, one function not a service.** Read `fanslyWsHintsPolicies`, replace only `generation` for the one label, write through `applyConfigPatchesInTx` inside the same transaction that holds `lockFanslyWsGeneration`, with `expectedVersion` from the preview. A second apply with the stale version conflicts; report "already applied" only when the live policy generation already equals the candidate. Note the effective-config propagation delay the runbook calls "all-role convergence" in the preview output.
6. **Tests to add.**
   - Plan 01 (extend `tests/fansly-ws-hints-runtime.integration.test.ts` fixture): create then delete then REST head without the target settles with `hot_applied_at` null; mixed deleted and present targets; wrong group, null group, other generation, delete received before create all stay debt; a delete arriving after a stuck claim completes on the next due visit; five-page `walk_limit` is not bypassed by a delete; replaying the delete event is idempotent; R+1 during settlement survives.
   - Plan 02: adapter emits `started` then `failed(transport)` and throws a `TypeError`; hint subject gets the outcome and backoff, the ordinary loop still runs, `page_sync_states.consecutive_failures` unchanged. Negative cases: 401, 429 with Retry-After, lease-lost abort, DB error inside `owned()`, staged-page invalid all still propagate. Hint-only dispatch with a transport failure ends `skipped` with the quality hold and open incidents untouched (mirror the test at lines 344-373).
   - Plan 03: stale version, rotated credentials between preview and apply, disabled and expired policy, `auth_refused` generation all refuse with zero config and attempt writes; sibling page policies byte-identical after apply.
   - Plan 04: unit tests for the resolver on bounded, legacy certified, legacy uncertified, in-progress and future-dated documents; integration certified full then bounded then full reports `complete` with the prior completion as boundary, plus a below-stop changed-head witness so the comparator is proven to run (`tests/fansly-dm-shadow.integration.test.ts` has the harness).

## Complexity to remove, verdicts and order

Remove:
- Plan 01's new receipt columns, second settlement write path and new index. The `(page_id, group_ref)` index already serves the exact lookup.
- Plan 02's separate "classified failure" abstraction; the observer already receives the classified terminal event.
- Plan 03's service layer, account-correspondence proof and health-path coupling.
- Plan 04's extra persistence of the boundary.
- Plan 05's "provenance checker" as a framework; one read-only CLI producing a manifest is enough.

Plan 05 verdict on the six Ari messages: the read-only manifest is straightforward with existing pieces and should ship in this change. Sources: the WS observation and decode receipt, the hint receipt for group and message ids, `queryFanslyDmReaderHeads` for archive presence across `message_archive`, `dm_message_archive` and hot, `page_dm_threads` for membership, later mutation_debt receipts for tombstone ordering, `erasure_log` for fencing. Print only text length and a hash, never the text. There is no WS-to-archive projector: `canonicalize/fansly-ws.ts` emits addresses and debt only, and `message_archive` is fed by REST sync-pull events and hot-table backfill. Materializing these messages therefore is B2, which Decisions 344 and 366 keep separate. The plan is right not to enable it here; the `fansly-1970-repair` superseding-event pattern is the shape a future B2 slice should take.
