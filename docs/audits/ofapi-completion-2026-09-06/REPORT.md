## Scope and evidence

The remaining mandatory reads are implemented through captured responses, `ofapi.read_snapshot_observed`, a registered rebuildable snapshot projection, the local owner collection report and financial Agent dataset. This includes expired/latest/top fans, subscription history, all three following reads, blocked/restricted users, current profile, notifications/counts/search/order, post detail/comments/inline replies/stats/labels, stories/archive/details/stats/viewers/highlights, mass-message and engagement history, and the selected overview/subscriber/payout snapshots. Financial Agent reads require both `read:datasets` and `read:money`, plus a page grant; existing Fansly datasets were not opened to OnlyFans.

User-list index/detail/member/pinned-member reads retain named system IDs and exact fan IDs. Metadata previews are distinct from complete membership pages; empty pages with explicit continuation advance. The owner report combines membership with existing local last reply and spend, preserves history, and does not remove a member absent from a partial response. Original desktop gateway admission and validation remain compatible.

S7 provides owned source bytes → approved async Vault/CDN upload → captured lifecycle/readiness → usable reusable ID or one-use material. Vault inventory/lists/item/detail, release forms and taggable users are available through bounded reads. S9 provides scoped existing-link attribution plus Smart Link creation/deletion, tags, pixels and postbacks through closed owner commands. Administrative responses retain their own replayable safe state; local accounting or projection recovery never repeats an external command.

Webhook diagnostics now include captured free `/webhooks/events`, registration inventory, durable delivery attempts, explicit manual redelivery and local replay. Refreshing the available-event catalog does not request new subscriptions. Its live example lists only 13 names, so Hub presents the actual returned inventory rather than treating the example as the complete 32-event contract. Unknown names remain unsupported and unrequested. Queue progress and post likes are retained evidence; queue completion does not certify that every message was sent.

## What remains off and how the owner enables it

Before collecting, open **OFAPI Credits → Сверка с провайдером и права ключа → Прочитать права ключа**. Grant the intended rights in the vendor console, then record the known capability set, allowed account IDs and visibility with **Сохранить ограничения для этого ключа**. This declaration is tied to the credential fingerprint and version; Hub enforces it at dispatch and does not infer write permission through a trial command.

Deployment does not create optional collection policies. Three baseline categories continue under existing configuration until an explicit policy overrides them. New callers, categories, detail fanout and optional event groups stay off. `defaultCollect` in the catalog only chooses operations *after* the owner authorizes a schedule; it is not an activation flag.

For a new category that supports bounded read tasks: after the reviewed release is deployed, open **Settings → Collection**, select one mapped OnlyFans page, inspect binding/key/capture health and the current policy revision, and create **one bounded task** with the selector below. Enter explicit call, credit and byte ceilings and a closed date window where indicated. The Collection date inputs use the browser’s local time; for the visitor daily collector enter values that convert to UTC midnight (03:00 in Moscow), with the end at the next UTC midnight. A one-off task does not enable recurring work. Review its stored source, window, coverage, credit evidence and errors. Only then, in a separate policy change, select **Расписание** (`scheduled`), enter interval minutes, daily credit limit, maximum calls per run and the detail setting, press **Проверить и применить**, review the change and confirm against the current revision. Change one category at a time. An on-demand policy allows explicit interactive reads but creates no schedule. The three core categories have no new generic one-off/backfill job; use their existing specialized workflows. The `vault_files` row opens the separate owned-upload workflow described below and cannot create a generic collection job.

Global background pause blocks the next managed physical dispatch; in-flight results and callbacks still settle into retained evidence. Turning a category off preserves its checkpoint/history. Resume is a separate owner CAS action that retains original caps and cursor. A one-off job with exhausted allowance cannot be resumed; authorize a separately bounded continuation. An exhausted scheduled run is marked `failed` with `scheduled_run_exhausted`, retaining its cursor/history for inspection. At the next interval, the still-authorized schedule may create a fresh current window under the then-current policy and caps; it does not silently refill or resume the exhausted run. For uploads and typed exports, use their own **Resume approved …** control so both linked jobs resume together. No unknown POST may be revived by that control.

The 12 optional event subscriptions form five separately applied groups: `subscription_expiry` (1), `account_lifecycle` (1), `media_uploads` (2), `data_exports` (7), `engagement` (1). In Events and recovery, choose one group, save the selection, then **Apply events** and verify remote readback. Enable delivery-history collection separately if desired; it reads a bounded page every five minutes and does not request redelivery. Manual redelivery requires a retained missing receipt and explicit preview/approval. The free event-catalog button only refreshes diagnostics. Keep `fan_summary.completed` unrequested.

### Existing gates required for lifecycle consumers

Check these effective values in **Settings → Configuration** before applying the related event group. They are staged **boot** flags, not editable collection toggles. If already enabled, preserve them. If disabled, the owner must approve the individual flag change in the active deployment's `.env.production` and run the approved deployment/recreation workflow for API, worker and scheduler; re-read effective configuration afterward. Do not assume that saving a collection policy changes a boot flag. Do not enable a missing prerequisite implicitly.

Async upload/export status handling and the content event projection do not require a new boot flag. Their optional remote subscriptions remain separate owner actions. No gate was changed during implementation.
