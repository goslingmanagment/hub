# 18 — Test Suite & What It Pins Down

**Scope.** This document covers the `core` repo's test territory: every file under `tests/**` (163 `*.test.ts` suites plus two non-vitest simulation scripts under `tests/audit-artifacts/`, the shared helpers under `tests/helpers/`, and the JSON fixtures under `tests/fixtures/ofapi-webhooks/`), plus the two config files that govern how the suite runs — `vitest.config.ts` and `docker-compose.test.yml`. It also reads the `test*` scripts in the root `package.json` because they define the gating that splits the suite. The tests are treated here as an **executable specification** of the system's boundaries and invariants: this doc catalogs what each cluster of tests asserts and, for every point where data crosses into or out of `core`, which tests pin the contract. Actual production code lives in the sibling territory docs; this doc points into them via cross-references.

## 1. Runner configuration & how the suite is split

### `vitest.config.ts`
- `test.environment = "node"`; include glob is `tests/**/*.test.ts` (`vitest.config.ts:22`). Files not ending in `.test.ts` are never collected — this is why the two `tests/audit-artifacts/*.ts` scripts are excluded from vitest and run only by hand.
- `hookTimeout` and `testTimeout` are both `INTEGRATION_TEST_TIMEOUT_MS` (`tests/helpers/timeouts.ts:1` = `30_000`), asserted by `tests/vitest-config.test.ts` ("aligns hook and test budgets with the shared integration timeout").
- Module aliases map the workspace packages (`@agency_hub_core/contracts|shared|db|fansly|onlyfans`) to their `src/index.ts`, and `@/`, `react`, `react-dom`, `react-router` to the dashboard app's copies (`vitest.config.ts:8-18`) so React component tests import the same React instance as the app.
- Coverage reporter is `text` + `lcov`.

### Root `package.json` test scripts (the gating)
| Script | What it runs | Purpose |
|---|---|---|
| `test` | `vitest run` (everything), `--max-old-space-size=8192` | Full suite, needs Docker for Testcontainers |
| `test:unit` | `vitest run` **excluding** `tests/**/*.integration.test.ts`, `schema-guard.test.ts`, `http-client.test.ts`, `network.test.ts` | Pure unit/component tests with no Docker and no socket binding |
| `test:sync-critical:db` | the integration + `schema-guard`/`http-client`/`network` tests, `--no-file-parallelism`, **excluding** `api.integration.test.ts` | Docker/socket-dependent suites run serially |
| `test:sync-critical:api` | `api.integration.test.ts` only, with `--testNamePattern "auto-queues\|initial sync\|retry path\|latest light sync\|detailed sync health\|stored proxy\|sync runs\|page credentials\|admin verify\|inline proxy\|sync monitor\|sync block\|manual block controls\|recent sync requests\|sync request limits\|system health"` | Runs only a named subset of the 9,874-line monolith |
| `test:sync-critical` / `test:prerequisites` | `db` then `api` above | Pre-deploy smoke gate |

The `--testNamePattern` on `test:sync-critical:api` means the fast pre-deploy gate exercises only ~16 of the ~80 `it()` blocks in `api.integration.test.ts`; the rest run only under the full `pnpm test`.

### `docker-compose.test.yml` — name vs. behavior
Despite the name, **this compose file is not used to run the vitest suite.** The integration tests spin their own ephemeral Postgres via Testcontainers (`GenericContainer("postgres:16")`, `tests/helpers/db.ts:39`). `docker-compose.test.yml` builds the `agency_hub_core/runtime:local` image and runs four services — `postgres:16` (persistent volume, exposed `5432`), a one-shot `migrator` (`node packages/db/dist/migrate.js`), an `api` (`startup.js api`, port `3000`), and a `worker` (`startup.js worker`) — all reading `.env.docker` and mounting `.sessions`/`.om-token` read-only. Its only consumer inside the test tree is `tests/compose-config.test.ts:36`, which reads it as **text** to assert structural invariants (it iterates `["docker-compose.yml", "docker-compose.test.yml"]`). So the file is a deploy-shaped artifact that tests treat as a lint target, not as the DB backing the suite.

## 2. Test taxonomy

Four kinds of suites coexist, distinguished by file-name convention and by what external resource they need:

1. **Unit / pure-logic tests** (`*.test.ts`, majority): import a function or React component and assert on return values / rendered output. No Docker, no sockets. Examples: `money.test.ts`, `mapping.test.ts`, `spender-retention.test.ts`, `ofapi-event-mapping.test.ts`, all `dashboard-*`, `workboard-v2-engine.test.ts`, `config-registry.test.ts`.
2. **Testcontainers integration tests** (`*.integration.test.ts`, ~45 files): call `startIntegrationTestDatabase()` (`tests/helpers/db.ts:76`) in `beforeAll`, `resetIntegrationDatabase()` in `beforeEach`, and drive real SQL against a real migrated Postgres. These are the suites that pin DB write shapes, transactions, and end-to-end HTTP+worker flows.
3. **Socket / network suites** run serially but not always with Docker: `http-client.test.ts` and `network.test.ts` bind ephemeral loopback TCP servers (HTTP CONNECT proxy, SOCKS5 proxy, plain HTTP target) to exercise the shared HTTP client; `schema-guard.test.ts` mixes a mocked-pool unit case with three Testcontainers cases. `test:unit` excludes all three.
4. **Non-vitest simulation scripts** (`tests/audit-artifacts/*.ts`, 2 files): standalone `node --import tsx/esm` programs that self-report pass/fail and `process.exit`. Not collected by vitest (no `.test.ts` suffix). See §3.5.

**Prerequisite gating.** Testcontainers and socket-binding tests do not hard-fail a machine that lacks Docker or socket permission. They funnel resource acquisition through `acquireTestPrerequisite()` (`tests/helpers/prerequisites.ts:47`): if the env var `ALLOW_MISSING_TEST_PREREQUISITES=1` is set, a failure to start returns `null` and the test `context.skip()`s (`tests/prerequisites.test.ts`); otherwise it throws a descriptive "Missing test prerequisite" error. Every integration `it()` opens with `if (!testDb) { context.skip(); return; }`.

**The `api.integration.test.ts` monolith.** One 9,874-line file, one shared `describe("api integration")`, ~80 `it()` blocks, all against a single Testcontainers Postgres started once in `beforeAll` and truncated between tests (`resetIntegrationDatabase`, `tests/api.integration.test.ts:1610`). Each test rebuilds the Fastify app via `buildApiServer(appContext)` and drives it with `server.inject()`. It is the single broadest exercise of the HTTP surface (auth, admin CRUD, reporting, spenders, fan profiles, sync health/monitor/blocks, DM previews, workboard, AI-usage ingestion). The `test:sync-critical:api` `--testNamePattern` gate (§1) selects the sync/health/proxy subset for the fast lane.

## 3. Shared test infrastructure

### 3.1 `tests/helpers/db.ts` — the Testcontainers backbone
- `startTestDatabase({from?, through?})` (`:35`) boots `postgres:16`, builds a `pg` `Pool` + Drizzle `db` via `createPool`/`createDb`, waits for readiness (`select 1` poll, `:16`), then applies migrations. Returns `{ container, connectionString, pool, db, logger: createLogger("silent"), stop() }`.
- `applyTestMigrations` (`:111`) reads `packages/db/migrations/*.sql` (51 files as of this territory), sorts lexically, filters by optional `from`/`through` bounds, and applies each inside its own `begin/commit`, recording `schema_migrations(id)`. This is a **re-implementation of the production migrator** used only to let tests pin migrations to a version range (e.g. running a single migration file to verify a backfill — see `db-write.integration.test.ts` applying `0013_*.sql`/`0017_*.sql` by hand).
- `resetIntegrationDatabase` (`:89`) `drop schema pgboss cascade` then `truncate … restart identity cascade` over every `public` table except `schema_migrations`. Called in each integration `beforeEach`, so pg-boss's own schema is torn down and rebuilt per test that uses a worker.
- `seedFanslyPage` (`:162`) creates a model + Fansly page + encrypted session for the smaller suites.

### 3.2 `tests/helpers/runtime.ts` — `createTestAppContext`
Builds a full `AppContext` (`bootstrap.ts` shape) from a started test DB (`:4`). Its `config` object is the canonical **default flag/tuning matrix** for tests, and is the clearest single enumeration of the runtime's feature flags and their test defaults. Notable defaults (all overridable per test): every OFAPI feature flag defaults **off** (`ofapiDmProjectionEnabled`, `ofapiDmSyncEnabled`, `ofapiAccountHealthEnabled`, `ofapiCreditLedgerEnabled`, `ofapiAudienceSyncEnabled`, `ofapiPresenceProjectionEnabled`, `ofapiSpendProjectionShadowEnabled`, `ofapiSpendTransactionIngestEnabled`, `ofapiDesktopReadGatewayEnabled`, `ofapiDesktopCommandOutboxEnabled`, `ofapiDesktopCommandExecutionEnabled`, `chatMuseAiGatewayEnabled`, `onlyFansTopSpendersEnabled`), `encryptionKey = Buffer.alloc(32, 7)` version 1, `ofapiCreditFloor = 500`, `ofapiDmDailyCreditBudget = 500`, `ofapiBurnAlertCreditsPerHour = 300`, `chatMuseAiGatewayDailyMicroUsdLimit = 5_000_000`, `syncSharedRateLimitEnabled = false`, `telegramEnabled = false`. `adapter`/`onlyFansAdapter`/`ofapi`/`aiGatewayProvider` are left as `{}`/`undefined` unless a test injects a fake. Comment at `:145` notes `rawConfig === config` because tests apply no boot overrides.

### 3.3 `tests/helpers/adapter-harness.ts` — Fansly/OnlyFans adapter mocking
`loadAdapters()` (`:79`) `vi.resetModules()`, stubs `node:timers/promises` `setTimeout` to a real timer, then **spies on `undici.fetch`** (via `createRequire` so the spy lands on the exact module the adapter imports) and on `createRequestDispatcher`/`createProxyRequestDispatcher` from `packages/shared/src/http-client.ts`, returning fake dispatchers that record label + a `close` mock. Ready-made response builders (`fanslyAccountResponse`, `fanslyTransactionsResponse`, `fanslyFollowersResponse`, `onlyFansAccountsResponse`) return `Response` JSON envelopes matching the real provider shapes. `captureEvents()` collects sanitized `HttpRequestEvent`s emitted by the adapter observer. Used by the `adapter-*` cluster to assert proxy reuse, retry/backoff, request serialization, and observer redaction **without real network**.

### 3.4 `tests/helpers/network.ts` — SSE / socket approach
`listenOnLoopback(server, purpose)` (`:5`) binds a Node `net.Server` to `127.0.0.1:0` (ephemeral) through `acquireTestPrerequisite`, so any socket-permission failure degrades to a skip. This is the shared primitive behind the SSE end-to-end tests, the scripted-HTTP-server OFAPI tests, and the proxy tests: **start a real server on loopback, then `fetch()`/`inject()` against it**. The SSE suites additionally implement a minimal streaming reader over `fetch` + `response.body.getReader()` that parses `id:`/`event:`/`data:` frames on `\n\n` boundaries (`tests/ofapi-sse.integration.test.ts:59-147`, `class SseClient`) and a `waitForFrames(n)` poll.

### 3.5 `tests/audit-artifacts/` — standalone simulation scripts
- `money-prop-test.ts`: a deterministic property/boundary sweep over the **real** `packages/shared/src/money.ts` converters (`toMills`, `dollarsToMills`, `formatUsdFromMills`, `millsToDecimalString`, `sumMills`, `calculateNetMillsFromGross`/`FromNet`). It documents concrete behaviors: `dollarsToMills("0.0009") === 0n` (4th decimal silently dropped), `formatUsdFromMills` **truncates** (floor-div) while a replica of reporting's `millsToRoundedCents` rounds half-up, so the same stored mills can display 1¢ apart. Run by hand (`node --import tsx/esm tests/audit-artifacts/money-prop-test.ts`), exits non-zero on any mismatch.
- `sse-b3-sim.ts`: a deterministic control-flow model of the OFAPI webhook→SSE pipeline that reproduced ("audit B3") frame-loss/dup/reorder defects; its header cites the exact `events-stream.ts`/`ofapi.ts`/`server.ts` line ranges it mirrors. It has been **superseded** by the vitest suite `tests/ofapi-sse-delivery.test.ts`, which ports the same scenarios (A/B/B'/C/D) against the real `createSyncEventHub`/`createMonotonicSeqGuard` and asserts in-order, exactly-once, loss-free delivery.

### 3.6 `tests/fixtures/ofapi-webhooks/` — captured OFAPI webhook payloads
12 JSON files + `README.md`. Anonymized live captures (2026-06-10 Phase-0 spike) of the OnlyFansAPI webhook wire format, one file per event type: `messages_received`, `messages_sent`, `messages_deleted`, `messages_ppv_unlocked`, `transactions_new`, `subscriptions_new`, `unverified_subscriptions_renewed`, `unverified_tips_received`, `users_online`, `users_offline`, `users_typing`. The `README.md` documents the **live-verified delivery contract** that the tests replay: envelope `{event, account_id, payload}` with **no event-id in the body**; dedupe key is the `x-ofapi-idempotency-key` header (`evt_<40 hex>`); signature is `signature` header = hex `HMAC-SHA256(rawBody, signing_secret)` over **raw bytes**; user-agent `OnlyFansAPI.com/Webhook-Client`; at-least-once, ≤5 retries, 15 s timeout. Each fixture carries a `_meta` provenance block that tests strip before signing (`delete raw._meta`). `unverified_*.json` are documented-but-not-live-captured shapes. Consumed by `ofapi-event-mapping.test.ts`, `ofapi-presence.integration.test.ts`, and the `ofapi-*.integration.test.ts` suites.
- A **second fixture source lives outside `tests/`**: `reference/responses/*.json` (real Fansly REST envelopes — `messaging_groups.json`, `group_detail.json`, `message.json`, `account_me.json`, etc.) loaded by `fansly-dm-fixtures.test.ts` (`loadResponseFixture`, path `reference/responses`, `:14`) and other adapter tests.

### 3.7 Worker-startup mock-factory convention
`worker-startup.test.ts` demonstrates the repo's pg-boss/worker mocking pattern: `vi.hoisted(() => ({ … vi.fn() }))` factories declared before `vi.mock(...)` for `@agency_hub_core/db`, `bootstrap.ts`, and every `services/*` module the worker wires (`executor`, `sync-queue`, `planner`, `ofapi-events`, `ofapi-credits`, `ofapi-command-executor`, `ofapi-dm-analytics`, `telegram-report`) (`tests/worker-startup.test.ts:3-82`). The tests pass a hand-rolled fake `boss` (`start/stop/schedule/work/complete/fail/fetch/send/touch`) and assert **ordering** (orphan cleanup before queues/executor), scheduling registration, and the Telegram catch-up handler's date math under `vi.useFakeTimers()` + `vi.setSystemTime`.

## 6. Name-vs-behavior discrepancies worth flagging

1. **`docker-compose.test.yml` is not the test database.** The vitest integration suites use Testcontainers (`tests/helpers/db.ts:39`); the compose file is only read as a text asset by `compose-config.test.ts:36`. It provisions a persistent prod-shaped stack (`migrator`/`api`/`worker`) that the suite never launches.
2. **`applyTestMigrations` (`tests/helpers/db.ts:111`) is a second migrator.** It re-implements migration application (read `.sql`, sort, per-file `begin/commit`, record `schema_migrations`) rather than invoking the production `packages/db/src/migrate.ts`, so it can apply a bounded `from`/`through` range for backfill tests. Behavior should track production but is a parallel implementation.
3. **The fast pre-deploy gate under-covers the monolith.** `test:sync-critical:api` runs `api.integration.test.ts` with a `--testNamePattern` allow-list (§1), so most of its ~80 cases run only under full `pnpm test`.
4. **`tests/audit-artifacts/*.ts` never run in CI.** They lack the `.test.ts` suffix required by the vitest include glob and are hand-run scripts; `sse-b3-sim.ts` is explicitly superseded by `ofapi-sse-delivery.test.ts`.
5. **OFAPI journal-only events settle `skipped`, not `processed`.** `ofapi-webhook.integration.test.ts` shows `transactions.new` for a *mapped* page settles `skipped` with error text "journaled without fanout" — the `skipped` status here means "no SSE fanout", not "ignored"; the row is still journaled and drives credit accrual/spend projection.
6. **Two fixture roots.** Webhook fixtures live in `tests/fixtures/ofapi-webhooks/`; Fansly REST fixtures live outside the test tree in `reference/responses/` (`fansly-dm-fixtures.test.ts:14`).
