# Territory 03 — API Contracts & Client Codegen

**Scope.** This document covers the `@agency_hub_core/contracts` package, which is the single source of truth for the shape of every request and response that crosses `core`'s HTTP boundary. Files read in full: `packages/contracts/src/routes.ts` (5533 lines — every Zod schema plus the `routeSchemas` operation catalog and the `z.infer` type exports), `packages/contracts/src/generate.ts` (the `contracts:generate` codegen entrypoint), `packages/contracts/src/index.ts` (barrel), `packages/contracts/src/generated/api-types.ts` (14 753 lines — machine-generated), and `packages/contracts/package.json`. Value constraints are imported from `@agency_hub_core/shared`; the exact source enums/functions were read in `packages/shared/src/types.ts`, `packages/shared/src/time.ts`, and `packages/shared/src/spender-retention.ts`. Consumption was traced into `apps/runtime/src/api/server.ts` (route registration, OpenAPI generation) and `apps/dashboard/` (type-only imports). Route→handler wiring lives in Territory 02 (`apps/runtime/src/api/server.ts`); this doc describes the contract shapes those routes carry.

> **Note on `routeSchemas`:** the entries in `routeSchemas` (routes.ts:3717) carry only a Fastify route *schema* (tags, summary, `security`, `body`, `querystring`, `params`, `response`). The **HTTP method and URL path are not in this file** — they are assigned at registration in `apps/runtime/src/api/server.ts` via `server.get/post/patch/delete(path, { schema: routeSchemas.<key> }, handler)`. So `routeSchemas.login` etc. are keyed by operation name, not by path.

## 1. What this package is

`@agency_hub_core/contracts` (package.json: `"name": "@agency_hub_core/contracts"`, `private: true`, `type: module`) has exactly two runtime dependencies: `zod@^4.1.5` and `@agency_hub_core/shared` (workspace). Its single export map entry is `".": "./src/index.ts"`. The barrel `src/index.ts` re-exports everything from two modules:

```ts
export * from "./routes.ts";              // Zod schemas + routeSchemas + z.infer types (hand-written)
export * from "./generated/api-types.ts"; // OpenAPI `paths`/`components` TS types (machine-generated)
```

Two artifacts therefore coexist:
- **`routes.ts`** — hand-authored Zod schemas. This is where the contract is *defined*. It exports both the runtime schemas (e.g. `authStateSchema`) and their inferred TypeScript types (e.g. `export type AuthState = z.infer<typeof authStateSchema>`, routes.ts:5349–5532).
- **`generated/api-types.ts`** — a derived OpenAPI-to-TypeScript rendering produced by `pnpm contracts:generate`. It is committed to the repo and re-exported through the barrel, but no code imports its `paths`/`components`/`operations` symbols (verified by grep). It exists as a reference/OpenAPI-consumer surface.

## 2. Codegen pipeline (`generate.ts`)

Run via the root script `contracts:generate` (`package.json:21`): `node --import tsx/esm packages/contracts/src/generate.ts`.

`generate.ts` does **not** parse the Zod file. It boots the real Fastify API server in-memory and reads the OpenAPI document Fastify produces from the registered route schemas:

1. `buildApiServer(...)` (imported from `apps/runtime/src/api/server.ts`) is called with a fully stubbed `AppContext`: a zero-filled 32-byte encryption key, empty `databaseUrl`, `pool`/`db`/`adapter`/`onlyFansAdapter` cast to `never`, `logLevel: "silent"`, Telegram disabled, and the various sync/timing knobs set to fixed defaults (generate.ts:11–51). No DB connection or network is opened — only route schemas are registered.
2. `await server.ready()` then `server.swagger()` yields the OpenAPI 3.1 document (Fastify + `@fastify/swagger` + `fastify-type-provider-zod@^6.1.0` transform Zod schemas → JSON Schema).
3. `normalizeOpenApiDocument(spec)` (server.ts:410) mutates one path: for `GET /api/v1/admin/ofapi/credits/ledger.csv` it moves the `200` response's `application/json` content object under a `text/csv` media type instead. This is because the Zod-Fastify transformer only accepts Zod schemas (the CSV route declares its success body as `z.string()`), so the media type is rewritten post-hoc.
4. Two files are written:
   - `reference/agency-hub.openapi.json` — the pretty-printed OpenAPI JSON (`JSON.stringify(spec, null, 2)`).
   - `packages/contracts/src/generated/api-types.ts` — produced by `openapiTS(spec)` then `astToString(...)`, prefixed with the header `// Generated by \`pnpm contracts:generate\`.`
5. `server.close()` runs in `finally`.

**Shape of `generated/api-types.ts`.** It is a single `export interface paths { … }` mapping URL strings (115 `"/api/v1/…"` keys) to per-method request/response object types, plus trailing `export type webhooks = Record<string, never>`, `export interface components { schemas: never; … }`, `export type $defs = Record<string, never>`, `export type operations = Record<string, never>` (api-types.ts:14742–14752). Because the Zod-Fastify transform inlines every schema per-operation, `components.schemas` is `never` — there are **no shared `$ref` components**; every response body type is fully expanded inline (e.g. the health response object literal is duplicated across its `200` and `503` entries, api-types.ts:22–70). Enums render as string unions (`status: "ok" | "degraded"`).

## 5. Request/response schema catalog by domain

Below, each domain lists the important schemas with concrete field shapes. All `…Mills` fields are signed integer mills; all `…At`/timestamp fields are ISO strings; `platform` is `fansly|onlyfans`.

### 5.1 Auth & identity (routes.ts:83–112, 1949–1982)
- `pageRefSchema` — `{ id, label, platform, modelSlug, modelName }`. The canonical "page" reference embedded in most responses.
- `authUserSchema` — `{ id, username, role (userRoleEnum), assignedPages: pageRefSchema[] }`.
- `authStateSchema` — `{ authMethod: "session"|"api_key", user: authUserSchema }`. Returned by `login` and `me`.
- `adminUserSchema` = `authUserSchema` + `apiKeyStatus: { activeKeyPrefix, activeKeyCount, activeKeyCreatedAt, activeKeyLastUsedAt } | null`.
- `loginBodySchema` — `{ username (1–254), password (1–1024) }` (bounded to keep the audit table small, per comment).
- `adminCreateUserBodySchema` — `{ username (1–100), role (creatableUserRoleEnum), password? (8–256) }`.
- `apiKeyItemSchema` / `issuedApiKeyResponseSchema` — `issuedApiKeyResponseSchema` carries the **plaintext** `key` (only response that does), plus `keyPrefix` and `assignedPages`.

### 5.2 Pages, models, connections (routes.ts:470–488, 1567–1638, 2735–2811)
- `assignedPageSchema` = `pageRefSchema` + `{ username?, displayName?, followerCount: pageMetricSchema, subscriberCount: pageMetricSchema, lastLightSyncAt?, lastFollowerSyncAt? }`, where `pageMetricSchema = { value: int|null, available: boolean }`.
- `modelListItemSchema` — `{ id, slug, name, pageCount }`; `adminModelListItemSchema` adds `sortOrder`.
- `connectionItemSchema` — page connection health for the admin/connections view: adds `connectionStatus` (`active|stale|error|expired|never_synced|unverified`), `lastLightSyncAt`, `lastFollowerSyncAt`, `lastSyncError`, `proxyUrl?`, `proxyHasAuth`, and `syncUx: syncUxSummarySchema`.
- `overviewResponseSchema` — agency dashboard payload: `counts { models, pages, fans }`, `revenue { "7d": {...}, "30d": {...} }` (each with `revenueMills/adjustmentMills/unclassifiedMills/netEarningsMills/previousNetEarningsMills/deltaPct`), `overall.syncUx`, a `pages[]` array of per-page revenue+sync summaries, and `setup { hasPages, hasFanslyPages, hasOnlyFansPages }`.

### 5.3 Revenue (routes.ts:243–585, 1640–1725)
- `revenueQuerySchema` — a **union** of `standardRevenueQuerySchema` (`period ∈ today|7d|30d|all`, optional `from`/`to`) and `customRevenueQuerySchema` (`period: "custom"`, mandatory `from`/`to` with `from ≤ to`).
- `revenueWindowSchema` (base of the revenue responses) — `revenueSummarySchema { revenueMills, adjustmentMills, unclassifiedMills, netEarningsMills, totalNetMills }` + `{ period, from?, to?, currency: "USD", breakdown: {canonicalType, bucket, netAmountMills}[], comparison: {from, to, netEarningsMills, totalNetMills, deltaNetMills, deltaPct}|null, platformWindows: {platform, from, to, comparisonFrom, comparisonTo}[] }`. `platformWindows` exists because OnlyFans trailing windows span one extra calendar day (comment routes.ts:504–509).
- `overviewRevenueResponseSchema` / `modelRevenueResponseSchema` / `pageRevenueResponseSchema` extend it with `models[]`, `pages[]`, `model`, or `page`.
- `revenueDailyResponseSchema` — `{ series: { businessDate, netAmountMills, transactionCount, canonicalType? }[] }`.

### 5.4 Transactions (routes.ts:587–622, 1666–1725)
- `transactionItemSchema` (per-page) — `{ transactionId, rawType (int|string), canonicalType (transactionTypeEnum), transactionState, amountMills, destinationAmountMills, netAmountMills, walletId?, correlationId?, correlationAccountId?, occurredAt, sourceUpdatedAt?, fan }`. `fan` = `{ platformUserId, pageAlias?, username?, displayName? } | null`.
- `transactionListResponseSchema` — `{ page: assignedPageSchema, items[], limit, offset, total }` (standard offset pagination envelope reused across list endpoints).
- `crossPageTransactionItemSchema` adds `pageLabel` + `platform` and uses a fan shape without `pageAlias`. `crossPageTransactionListQuerySchema` adds `sortBy (occurredAt|grossAmountMills|netAmountMills)` + `sortDir`.
- `fanTransactionItemSchema` — the same transaction fields without the `fan` object (already scoped to one fan).

### 5.5 Subscribers & followers (routes.ts:624–704)
- `subscriberItemSchema` — `{ platformSubscriptionId, platformUserId, pageAlias?, username?, displayName?, endsAt?, autoRenew?, autoRenewOffDetectedAt?, subscriptionTierName?, startedAt?, totalSpentCents (int), lastTransactionAt? }`. Note `totalSpentCents` is **cents**, not mills.
- `followerItemSchema` — follower + subscription + embedded `dm { hasConversation, platformConversationId?, unreadCount, lastMessageAt?, lastFanMessageAt?, lastModelMessageAt?, lastMessagePreview? }` + `presence { status: active_now|recently_active|offline, lastSeenAt?, observedAt? }`.
- `subscriberListQuerySchema` / `followerListQuerySchema` — pagination + filters (`expiringWithinDays 1–90`, `startedWithinHours`, `autoRenew`, `followedWithinHours`, `subscriber`, `dmStatus: none|has_dm`, `activeWithinMinutes`).
- Daily rollups: `subscriberDailyItemSchema { businessDate, newSubscribers, activeSubscribers }`, `followerDailyItemSchema { businessDate, newFollowers, knownTotalFollowers? }`.

### 5.6 Fans & profiles (routes.ts:706–815, 1532–1555, 1727–1750)
- `fanBaseSchema` — `{ platform, platformUserId, username?, displayName?, createdAtExternal? }`; `pageScopedFanBaseSchema` adds `pageAlias?`.
- `fanListItemSchema` — fan + `totalCreatorNetMills`, `currency: "USD"`, follower/subscriber flags, `autoRenew?`, `subscriptionExpiresAt?`, `lastTransactionAt?`.
- `pageFanDetailResponseSchema` — `{ fan, platformTotalSpendMills, page: fanPageContextSchema, flags: fanFlagSchema[] }`. `fanPageContextSchema` embeds `notes: fanNoteSchema[]` and `summaries: fanSummarySchema[]`. `crossPageFanDetailResponseSchema` returns `pages[]` instead of one `page`.
- `fanFlagSchema` — `{ flag (fanFlagEnum), createdAt, createdByUserId? }`; `setFanFlagsBodySchema` — `{ flags: fanFlagEnum[] }`.
- **Fan intelligence profiles** — `fanProfileDocumentSchema { version (int≥1), body (string), source: "chatmuse", createdAt, createdByUserId? }`. `upsertFanProfileBodySchema { body (1–50 000) }` (bearer/chatter-authed write). `createFanNoteBodySchema { body (1–10 000) }`. These carry free-text PII about fans across the boundary.

### 5.7 Spenders / "top spenders" (routes.ts:292–1037)
The spenders surface is the most cross-field-validated part of the contract. Because Zod 4's `.merge()`/`.pick()`/`.partial()` silently drop `superRefine` checks (comment routes.ts:287–291), scope/period cross-field rules are implemented as plain issue-returning helpers (`spenderScopeIssues`, `spenderPeriodIssues`, routes.ts:316–366) applied once in each composed schema's `.superRefine()`.

- **Scope fields** (`spenderScopeFieldsSchema`) — `{ scope: page|model|agency, pageLabel?, modelSlug?, platform? }`. Rules: `page` requires `pageLabel`; `model` requires `modelSlug` + `platform`; `agency` requires `platform`.
- **Period fields** (`spenderPeriodFieldsSchema`) — `{ period (spenderPeriodEnum), from?, to? }`; `from`/`to` allowed only when `period=custom`, and `from ≤ to`.
- `spenderListQuerySchema` = scope + period + pagination + `{ query?, sortBy?, sortDir?, retentionStatus? }`.
- `spenderListItemSchema` — `{ fan, metrics: spenderMetricsSchema, lifetimeLastTransactionAt?, lastFanMessageAt?, conversation: spenderConversationSchema, lastTransaction?, retentionStatus (excludes "all") }`. `spenderMetricsSchema` = `{ window: {grossAmountMills, creatorNetAmountMills, posted/pending/unknown gross+net mills, transactionCount, lastTransactionAt}|null, lifetime: {scope/platform gross+net mills}, comparison: {previous/delta gross+net mills, deltaPct}|null }`.
- `spenderListResponseSchema` wraps `{ scope: spenderScopeResponseSchema, period: spenderPeriodMetadataSchema, diagnostics: {…attributed/unattributed mills…}, items[], limit, offset, total }`.
- `spenderBatchBodySchema` — scope + optional period + `{ fans: fanLookupParamsSchema[] (1–200) }` — the batch resolve endpoint takes up to 200 `{platform, platformUserId}` pairs.
- `spenderSeriesResponseSchema` — zero-filled time buckets with `granularity` (excludes `auto` in the response).
- **Page auto-lists** — `pageSpenderAutoListsResponseSchema` (dollar-band buckets `0-25`…`600-plus`) and `pageSpenderAutoListDetailResponseSchema` (fans within one band).

### 5.8 Conversations / DM previews (routes.ts:446–460, 1068–1104, 1517–1530)
- `pageConversationPreviewResponseSchema` — `{ page, fan?, conversation: pageConversationStateSchema, messageSyncUx: syncUxSummarySchema, messages: pageConversationPreviewMessageSchema[] }`. Preview message = `{ platformMessageId, senderPlatformUserId?, senderRole: fan|model|system|unknown, createdAt, content, totalTipAmountCents }`.
- `pageConversationStateSchema` — `{ platformConversationId, storedMessageCount, messageCoverageStatus: pending_backfill|partial_window|complete, messageBackfillComplete, messageSyncEligibility: eligible|excluded|unresolved_identity, messageSyncExcludedReason?, lastMessageSyncAt?, unreadCount, lastMessageAt? }`.
- `pageConversationMessagesResponseSchema` — full cached message list, message = `{ messageId, senderRole, content, createdAt, tipAmountCents }`.

### 5.9 Workboard v1 & v2 (routes.ts:1106–1515)
- **v1** (`workboardResponseSchema`) — four buckets (`subscribers`, `activeSpenders`, `inactiveSpenders`, `snoozed`), each `{ total, items[] }`; item schemas embed `ltv.creatorNetAmountMills`, `conversation`, `subscription`, `touchpoint`. `workboardPresenceResponseSchema` includes `bestEffort: literal(true)` and presence buckets whose `presence.source` is `fansly_followers_last_seen | ofapi_last_seen`.
- **v2** (priority engine) — `workboardV2ItemSchema` is the richest item in the contract: `{ fanId, fan, tab (subscribers|spenders|fresh_mass|old_mass|service), massSubstate?, value {score, tier: whale|vip|payer|new, confidence}, urgency {score, severity}, rankScore, secondaryStatus (recent_purchase|need_reply|due_now|later|dont_touch_today), needsReply, needsHumanTriage, isPurchaseFollowup, whyNow, reasonChips[], quality {qScore?, qConfidence}, closingVerdict {layer, needsReply, state, reason}|null, online, ltv, subscription, conversation, serviceReason? }`.
- **v2 AI (L2 closing classifier) analytics** — `workboardV2AiReportSchema` returns `settings` (`workboardV2AiSettingsSchema`: `enabled, hasApiKey, model, dailyCapMin/Max, envEnabled, source {enabled/dailyCapMax/model: override|env}, override {…}`), `usage {today, last30d, daily[]}` with `aiUsageBucketSchema {calls, inputTokens, outputTokens, costUsd}`, `coverage {…spender diagnostics…}`, `states[]`, and `recent[]` classified message tails. `workboardV2AiSettingsBodySchema` (owner write) = `{ enabled: bool|null, dailyCapMax: int 1–5000|null, model: string 1–120|null }`. `workboardV2AiClassifyResponseSchema` runs async and returns `{ ok, runId, status, alreadyRunning }`.

### 5.10 Sync health / monitor / blocks (routes.ts:114–200, 1984–2405)
This is the largest domain. Three overlapping surfaces:
- **`syncHealthResponseSchema`** (monitoring/`healthSync`) — `{ status: ok|degraded, timestamp, thresholds {lightMaxAgeMinutes, followerMaxAgeMinutes}, overall {pageCount, unhealthyPageCount, runningStreams, failedStreams, stalledStreams, pendingStreams, recentFailedRuns, recent429s, recent5xxs}, pages: syncHealthPageSchema[] }`.
- **`syncStatusResponseSchema`** (dashboard sync monitor) — per-stream detail with `extendedSyncStreamEnum` streams (`light, fan_identities, followers, transactions, top_spenders, subscribers, dm_conversations, dm_messages, followers_reconcile`), rate-health, recent runs/errors, deep-backfill progress, and `syncUxSummarySchema` at every level. `syncMonitorStreamItemSchema` and `syncRunDetailResponseSchema` also expose raw `stats`/`details`/`requestShape`/`responseShape` as `z.record(z.string(), z.unknown())` (untyped JSON blobs).
- **`syncOverviewResponseSchema`** (6-block model) — five fixed blocks per page (`connection, financials, audience, messages_live, messages_history`), each a `syncBlockStatusSchema` with `state` (10-value `syncBlockStateEnum`), progress, error, substreams, and cadence intervals; plus `syncDiagnosisSchema { code: worker_offline|stalled_run|auth_blocked, severity, headline, detail, actionKind }`.
- `syncUxSummarySchema` (routes.ts:134) is the shared human-facing status widget: `{ state: healthy|syncing|catching_up|retrying|attention|setup|off, label, headline, detail?, progressLabel?, nextRetryAt?, updatedAt?, requiresAction }`.
- Sync trigger writes: `syncTriggerBodySchema { pageLabel, scope: light|followers|all|data|messages }`, `adminSyncBlockBodySchema { pageLabel, block }`.

### 5.11 AI usage & AI gateway (routes.ts:1752–1946) — **boundary to the AI provider**
- `aiUsageBatchBodySchema` — `{ events: aiUsageEventInputSchema[] (1–100) }`. Each event: `{ clientEventId, feature (aiUsageFeatureEnum), model, inputTokens, outputTokens, cacheWriteTokens, cacheReadTokens, conversationId?, durationMs?, isCacheHit, isRegeneration, completedAt }`. Chatter/desktop clients POST their locally-run generation usage here (bearer auth). Response reports `receivedCount/insertedCount/invalidCount/dedupedCount`.
- **`aiGatewayStreamBodySchema`** (routes.ts:1788, strict object) — the request to proxy an LLM generation through core: `{ clientRequestId (uuid), feature, pageLabel, platform, platformUserId, conversationId?, model, reasoningEffort (off|low|medium|high|max), temperature? (0–2), maxTokens? (≤100 000), isRegeneration, prompt { systemBlocks: promptBlock[] (1–64), userBlocks: promptBlock[] (1–64) } }`. `aiGatewayPromptBlockSchema` = `{ text (1–100 000), cache: 1h|5m|none }`.
- **`aiGatewayStreamFrameSchema`** (routes.ts:1821) — a discriminated union of SSE frame types written back to the client: `meta` (with `provider: anthropic|openrouter`, `providerResponseId?`, `quota`), `content_delta`, `reasoning_delta`, `usage` (`aiGatewayUsageSchema {inputTokens, outputTokens, cacheWriteTokens, cacheReadTokens, costMicroUsd, costApproximate}`), `error` (`{code, message, retryAfterMs?}`), `done` (`{stopReason?}`). The route's declared `200` response is `z.unknown()` (the handler hijacks and writes `text/event-stream`); this union documents the frame payloads.
- `adminChatterUsageResponseSchema` — owner aggregation per chatter, with token counts, cost (`microUsd`, `approximate`), gateway request counts, and provider breakdown (`anthropic|openrouter`).

### 5.12 Notifications / Telegram (routes.ts:2521–2664) — **boundary to Telegram**
- `notificationsSettingsResponseSchema` — `{ configured, botTokenSet, chatId?, botTokenSource: db|env|none, chatIdSource, enabled, dailyReportEnabled, syncFailureAlertsEnabled, reportHourUtc (0–23), connectionStatus: not_configured|untested|connected|last_message_failed, lastMessageAt?, lastMessageError? }`.
- `notificationsSettingsUpdateBodySchema` — accepts `botToken` (validated by `telegramBotTokenSchema`: regex `^\d{5,}:[A-Za-z0-9_-]{30,}$`) and `chatId` (`telegramChatIdSchema`: numeric id or `@username`), both nullable/optional. These are **credentials written across the boundary**.
- `notificationsIncidentItemSchema` — incident with `kind` (`auth_blocked|proxy_failed|stream_failed_threshold|ofapi_auth|ofapi_low_credit|ofapi_webhook_silence|ofapi_burn_rate`), `status: open|resolved`, timestamps, error fields.
- Delivery history / report preview/send responses expose the rendered report text and delivery status.

### 5.13 Credentials & page onboarding (routes.ts:2666–2807) — **inbound platform secrets**
- `fanslyCredentialsSchema` — `{ platform: "fansly", session { authorization, fanslyClientId?, fanslyClientCheck?, fanslySessionId? }, proxy? { url, username?, password? } }`.
- `onlyfansCredentialsSchema` — `{ platform: "onlyfans", auth { token }, username, proxy? }`.

### 5.14 OFAPI webhook + SSE sync events (routes.ts:2813–3021) — **inbound webhook + outbound SSE**
This block is core's copy of the ChatGoose desktop `SyncEvent` protocol (comment routes.ts:2814–2820). `accountId` is the OFAPI account id (`acct_…`); `chatId`/`messageId` are raw OnlyFans numeric ids serialized as strings.
- **`syncEventSchema`** — a discriminated union over `type`: `chatListUpdated`, `messageReceived`, `messageSent`, `messageDeleted` (core extension — no chatId), `ppvUnlocked`, `tipReceived` (`amountUsd?`), `presence` (`online`, `lastSeenAt?` epoch-ms), `typing`, `accountAuthChanged` (`authenticated`). `normalizedSyncMessageSchema` carries `{ id, text (OFAPI HTML), createdAt, isSentByMe, price, isOpened?, isTip?, tipAmountUsd?, tipText?, mediaCount?, media[]?, replyTo? }`.
- `ofapiWebhookReceive` route: **authenticated by HMAC-SHA256 of the raw body** (`signature` header) against the registered signing secret; deduped by `x-ofapi-idempotency-key`; the body is the raw OFAPI envelope `{event, account_id, payload}` and is intentionally NOT schema-validated before signature verification (comment routes.ts:3798–3802). Ack response = `{ received: true, duplicate: bool }`.
- `eventsStream` route: outbound `text/event-stream` of `event: sync` frames whose `data` is a JSON `SyncEvent` and `id` is the journal fanout sequence; supports `Last-Event-ID`/`lastEventId` replay from the ~7-day journal. On a replay gap it returns `409` with `syncSnapshotRequiredResponseSchema { error: "sync_snapshot_required", requestedSeq, oldestAvailableSeq?, currentSeq, snapshotPath }`.
- `eventsSnapshot` route: `syncSnapshotResponseSchema` — a paginated durable state snapshot (`threads[]` with `messages[]`, `unresolvedTombstones[]`, `coverage.durableDomains`, `nextPageCursor?`) for replay-gap recovery, scoped to one assigned OFAPI account.

### 5.15 OFAPI credits & spend ledger (routes.ts:3018–3511) — **admin financial + chatter-scoped**
- `ofapiWebhookStatusResponseSchema` — registration state + `pages: ofapiPageMappingSchema[]` + `credit { lastBalance?, lastBalanceAt?, spentToday }`.
- `ofapiWebhookRegisterBodySchema { endpointUrl (url, ≤2000) }` → registers the team webhook (`account_scope=global`) and returns a `signingSecretMask` + page-to-account mapping.
- `ofapiCreditsSummaryResponseSchema` (owner) — the flagged (`OFAPI_CREDIT_LEDGER_ENABLED`) credits dashboard: `enabled`, `balance {value?, observedAt?}`, `today {day, total, bySource: {rest, webhookAccrual, external, adjustment}}`, `budgets[]`, `floor {value, blocked}`, `forecast {avgDailySpend7d, daysLeft?, runOutDate?, monthToDateSpend?, monthEndProjection?, refillRecommendation?}`, `incidents[]`, `reconciliation`, `accrual`, `recentBurn?`, `pricing? {microUsdPerCredit}`. Credits are integer counts; USD is derived from `pricing`.
- `ofapiCreditsChatterSummaryResponseSchema` (bearer/chatter) — page-scoped REST + webhook-estimated spend for the chatter's assigned pages only; deliberately omits owner-only global balance/refills/drift.
- Admin ledger: `ofapiCreditsLedgerResponseSchema` (paginated rows with `source (ofapiCreditLedgerSourceEnum: rest|webhook_accrual|external|refill|adjustment)`, `operation?`, `pageId?`, `credits`, `estimated`, `balanceAfter?`, `requestId?`, `accrualDay?`), plus CSV export (`adminOfapiCreditsLedgerCsvQuerySchema`; the success body is `z.string()` rewritten to `text/csv` in `normalizeOpenApiDocument`).
- `ofapiSpendComparisonResponseSchema` — read-only shadow-projection-vs-core-truth reconciliation, with per-status aggregates (`matched|missing_in_core_truth|…|other`).

### 5.16 OFAPI command intake & read gateway (routes.ts:3212–3352) — **chatter writes proxied to OFAPI**
- `createOfapiCommandBodySchema` — `z.discriminatedUnion("kind", …)` over five strict command kinds: `send_text_message_v1` (`payload {text 1–10 000, non-blank}`), `send_media_message_v1` (`payload {text ≤10 000, price (0 or 3–200), mediaFiles[] (1–50, no dups), previews[] (subset of mediaFiles)}`), `typing_active_v1`, `unsend_message_v1` (`payload {messageId}`), `mark_chat_read_v1`. Common fields: `clientCommandId (uuid)`, `accountId (^acct_…$)`, `conversationId (numeric string)`. `ofapiCommandResponseSchema` returns `state` (`queued|in_flight|confirmed|failed_retryable|failed_terminal|indeterminate|cancelled`), `payloadHash` (64-hex), `platformMessageId?`, `deduplicated` — but never echoes message text.
- `ofapiReadGatewayParamsSchema` — a wildcard `"*"` path param (1–1000 chars) for the allowlisted OFAPI GET compatibility gateway. Its route declares every response status as `z.unknown()` (opaque passthrough).

### 5.17 Runtime configuration surface (routes.ts:3524–3715) — **owner-only config**
- `configViewResponseSchema` — `{ generatedAt, roleStatuses[], instances: configInstanceSchema[], subsystems: [{subsystem, items: configItemSchema[]}] }`. `configItemSchema` is a large descriptor with two orthogonal axes: `editability (never|staged|editable)` and `runtimeApply (live|boot|none)`, plus server-computed effective-state fields (`source`, `desired`, `runningState (on|off|unknown)`, `desiredEffective`, `overrideVersion`, `pendingApply`, `drift`, `live`, `running[]`). Secret values are masked (`masked: bool`).
- Writes: `configUpdateBodySchema` (live keys; `expectedVersion` optional, last-write-wins), `configClearQuerySchema` (revert to env; DELETE via query params), `configStagedBodySchema` (boot-applied flags; `expectedVersion` **mandatory**, `ack: bool` must be true, recorded to `config_audit_log`). Config notes are bounded to 1024 chars.

## 6. The `routeSchemas` operation catalog (routes.ts:3717–3346)

`routeSchemas` is a single `as const` object mapping ~130 operation names to Fastify route schemas. Each entry has `{ tags, summary, security?, body?, querystring?, params?, response: {<statusCode>: schema} }`. `export type RouteSchemas = typeof routeSchemas` (routes.ts:3348) is consumed in server.ts as the typed schema table. Operations are grouped by `tags`: `system`, `auth`, `usage`, `ofapi`, `events`, `admin`, `pages`, `models`, `revenue`, `dashboard`, `transactions`, `subscribers`, `followers`, `fans`, `spenders`, `conversations`, `workboard`, `notifications`. A few responses are intentionally opaque: `aiGatewayStream.200 = z.unknown()`, `eventsStream.200 = z.string()` (SSE), `ofapiReadGateway.*` all `z.unknown()`, `openApiJson.200 = z.any()`, and the CSV export `200 = z.string()`.

Error responses are uniform: `errorResponseSchema = { error: string, message: string, statusCode: int }` (routes.ts:77) attached at `400/401/403/404/409/429/503` where relevant. Two non-standard error responses: `eventsStream.409 = syncSnapshotRequiredResponseSchema` and the OFAPI webhook receiver's error set.

## 7. How the contract is consumed

- **`apps/runtime/src/api/server.ts`** (Territory 02) imports `routeSchemas` and registers each entry against a concrete method+path with `server.<method>(path, { schema: routeSchemas.<key> }, handler)`. `fastify-type-provider-zod`'s `validatorCompiler`/`serializerCompiler` (set at server.ts:429–430) validate inbound bodies/query/params and serialize responses against these Zod schemas at runtime. The same registrations feed `@fastify/swagger`, which is what `generate.ts` reads. Runtime service modules (`apps/runtime/src/services/*`) import the `z.infer` **types** (e.g. `reporting.ts`, `spenders.ts`, `sync-monitor.ts`, `ofapi-events.ts`) to shape their return values.
- **`apps/dashboard`** consumes the package purely as **type-only imports** — every observed import is `import type { … } from "@agency_hub_core/contracts"` pulling the `z.infer` aliases (`AuthState`, `PageConversationPreviewResponse`, `WorkboardV2Item`, `SyncUxSummary`, `AdminChatterUsageResponse`, …). The dashboard's `vite.config.ts:14` aliases `@agency_hub_core/contracts` → `packages/contracts/src/index.ts` (the TS source), so it compiles against the hand-written schemas directly. No dashboard code imports runtime Zod schema *values*, and **no code imports the generated `paths`/`components`/`operations` types** — the generated `api-types.ts` is a committed reference artifact, not part of the dashboard's type graph.
- **External clients** (desktop chat workspace, browser extension — documented separately) are the counterparts on the bearer-auth (`bearerOnlySecurity`) routes: AI usage ingest, AI gateway stream, SSE events stream/snapshot, OFAPI chatter-credits/read-gateway/command endpoints, and fan-profile upserts. They consume the JSON shapes described in §5.11/§5.14/§5.15/§5.16 (and the `reference/agency-hub.openapi.json` OpenAPI doc), not the `contracts` TS package directly.

## 8. Discrepancies / things a reader should not assume

- **`isoTimestamp` is just `z.string()`** (routes.ts:20) — despite the name and the OpenAPI rendering, timestamps carry **no format validation** on input; any string passes. `businessDate` is the only date type that is actually validated (regex + real-calendar-date refine).
- **`generated/api-types.ts` has no shared components.** `components.schemas`, `operations`, `webhooks`, and `$defs` are all `never`/empty (api-types.ts:14742–14752). Every response body is inlined and duplicated per status code — the file is large (14 753 lines) for this reason, not because there are that many distinct types.
- **Names vs. units.** `subscriberItemSchema.totalSpentCents`, `followerItemSchema.totalSpentCents`, and `pageConversationPreviewMessageSchema.totalTipAmountCents` are in **cents**; almost every other money field (`*Mills`) is in mills; AI gateway/credit costs are in **micro-USD** (`costMicroUsd`, `microUsdPerCredit`). Three money units coexist in the contract.
- **`routeSchemas` does not encode HTTP method or path.** A reader wanting the URL/method for an operation must look at the registration in `apps/runtime/src/api/server.ts` (Territory 02); this file only supplies the request/response *shapes* and `security`.
- **The OFAPI webhook body is deliberately unvalidated by Zod** before HMAC verification, so the `{event, account_id, payload}` envelope is not enforced by a schema in this territory (only the internal `syncEventSchema` normalization is).
- **`generate.ts` boots the whole API server with stubbed DB/adapters** just to read its OpenAPI document; a failure in `buildApiServer`'s route registration (Territory 02) will break `contracts:generate`.
