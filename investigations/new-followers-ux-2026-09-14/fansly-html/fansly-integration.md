# Подключение к Fansly: решения для следующего этапа

Это контракт предлагаемой реализации. Текущий `index.html` остаётся автономным макетом с демонстрационными данными. Настоящие платформенные вызовы в него не добавлены.

После первоначального июльского источника перепроверен более новый извлечённый клиент **2026.909.1354**. Подробное сравнение и точные ссылки на новый исходник — в [fbuddy-comparison.md](fbuddy-comparison.md). Главные уточнения: Mass DM Fbuddy также отправляет `type: 1`, поэтому это не доказательство личной прописи; общие автоматические повторы POST из Fbuddy не переносим.

## Отображение

- Выбран второй вариант из `variants/index.html`: очередь слева, переписка справа. Открытие окна или выбор фоловера только показывают контекст; генерация начинается по явному клику «Сгенерировать». Ранее подготовленный или отредактированный черновик появляется сразу.
- Периоды: 1, 3, 6, 12, 24, 48, 72, 168, 336, 720 часов; начальный — 48.
- Возраст фоловера — прошедшее время с `followedAt`, всегда в часах, включая дробь для первого часа: `0,5 ч`, `30 ч`, `58 ч`. В реальной реализации вычислять относительно текущего времени, а не сохранять готовое число. Это время follow, а не время платной подписки; источники не смешивать.
- Основное имя и затем кастомное в скобках: `Jay (Джей / Аляска)`. Ник остаётся отдельной строкой. Длинное имя в списке сокращается с полным текстом в title; в чате переносится.
- Аватар из account payload Fansly. Отсутствующее или не загрузившееся изображение заменяется инициалом без ошибки всей строки. В макете используются 9 сгенерированных вымышленных фотографий, встроенных в HTML.
- Кастомное имя берётся существующим `customNameFromAccount`: `notes[].contentType === 12002`, поле `note`. CRM-заметки типа 12000 не подставлять в имя. Для AI использовать отдельное `fanCustomName` согласно текущему E115; не подменять им `fanDisplayName`.
- Ник, био, фактический аватар, история и персона входят в контекст приветствия. Кастомное имя может содержать внутренние теги; целиком обращаться им к фану нельзя.

## Живое чтение через расширение

Фоловеры — через текущую Fansly-сессию расширения. В разобранном клиенте Fbuddy подтверждён `GET /account/{ownAccountId}/followersnew` с пагинацией и параметрами before/after. Account payload подгружается пачкой через `GET /account?ids=…`: идентификатор, имя, ник, био, аватар и доступные account notes. Точный путь к изображению аватара в актуальном payload нужно подтвердить живым чтением перед реализацией: текущий `FanslyAccountResponse` расширения его ещё не описывает.

Проверка переписок — отдельно от ограниченного периода новых фоловеров: личное сообщение могло быть раньше, в том числе до повторного follow. Welcome и массовые сообщения не считаются; для welcome достаточно совпадения с сохранённым текстом по принятому владельцем правилу ниже. Полнота истории обязательна. Неизвестный результат оставлять неизвестным, не включать как доказанное «Не писали». Не создавать пустые чаты во время анализа списка.

## Кэш и повторные проходы

Предлагаемая схема учитывает, что тексты автоматических приветствий меняются редко. Настройки welcome общие для страницы: не запрашивать их отдельно для каждого фоловера и не отправлять все переписки в AI для определения факта личной прописи.

### Автоматические сообщения страницы

- При первом использовании получить определения через `GET /message/automated` из текущей Fansly-сессии. Такой метод уже есть в Hub-адаптере; для окна нужен живой источник через расширение.
- Хранить последний успешный ответ отдельно для каждого creator account: определения с исходными идентификаторами, условиями, текстами, вложениями, хешами содержимого и временем проверки. При последующих открытиях сразу использовать кэш; если ему больше 24 часов, обновить в фоне. Закрытое окно само по расписанию не опрашивает Fansly.
- Один выполняющийся запрос на аккаунт для всех вкладок. При ошибке оставить последний успешный ответ; ошибка не означает, что welcome отсутствуют. Первое неуспешное чтение оставляет зависимую от него классификацию неопределённой.
- Ручное обновление окна обновляет и этот кэш. Если расширение наблюдает изменение настроек автоматических сообщений, обновить раньше TTL. При подозрении на неизвестный автоматический шаблон допустима одна дополнительная проверка на проход, а не запрос на каждого фана.
- Сохранять предыдущие версии: изменение текста сегодня не превращает вчерашний welcome в личное сообщение. В Hub уже есть события `automation.definition_observed`, различаемые по хешу; использовать этот механизм для общей истории определений. Первая загрузка не восстановит шаблоны, изменённые до начала наблюдения.
- Решение владельца: совпадения непустого текста с текущим или сохранённым прежним welcome этой страницы достаточно, чтобы исключить сообщение из личной прописи. Отдельного подтверждения через automation ID не требуем. Сохранять исходный текст; при сравнении нормализовать пробелы и переносы, без смыслового сравнения через AI. Это продуктовое правило: вручную отправленный тот же текст тоже будет исключён. Для welcome без текста пустое совпадение не использовать; опираться на доступные признаки происхождения. Отдельно исключать массовые отправки: `type: 1` этого не решает.

### Фоловеры, переписки и генерация

1. При открытии получать свежих фоловеров напрямую из Fansly за выбранный период. Профили загружать пачкой; аватар, био и имена переиспользовать при переходах между списком и чатом.
2. Подтверждённый факт личной отправки сохранять с messageId и основанием классификации. Такого фана можно исключать без повторного полного чтения истории. Статус «Не писали» не считать постоянным: другой чаттер мог написать после проверки.
3. Первый анализ идёт до подтверждённой личной отправки либо до доказанного конца истории. Сохранять полноту проверки и последнюю проверенную позицию; следующий проход читает новые сообщения, если API позволяет надёжно продолжить с этой позиции. Обрыв или неполная страница не доказывают отсутствие личной прописи. Новые версии шаблонов требуют пересмотра зависимой от них классификации сохранённых сообщений.
4. Показывать проверенных фанов постепенно. Проверка выбранного чата и отправка имеют приоритет перед фоновым анализом очереди. При смене периода переиспользовать уже полученные данные, дочитывать недостающий диапазон.
5. Генерировать текст только по кнопке «Сгенерировать», сохраняя черновик при переходах. Открытие окна, выбор фана, смена периода и обновление списка сами генерацию не запускают. Можно написать и отправить сообщение вручную. Повторная генерация — также явное действие. Контекст включает профиль, персону и фактическую переписку, в том числе уже отправленный welcome, чтобы его не повторять. Предварительной генерации очереди нет.
6. Непосредственно перед отправкой перечитать свежие сообщения выбранного фана. Если другой чаттер уже написал, убрать из очереди и сохранить черновик. Для двух одновременно работающих окон нужна короткая общая блокировка отправки на аккаунт + фана; одна повторная проверка не устраняет гонку. Такая блокировка координирует наши приложения, но не внешнюю отправку напрямую из Fansly.

В результате повторное открытие окна не запускает полный анализ заново: обычно нужны свежий список фоловеров и изменения в ещё не обработанных чатах. Черновик генерируется отдельно по клику чаттера. TTL и внутренние состояния кэша не добавляют настроек в интерфейс чаттера.

## Отправка по механизму Fbuddy

Используем собственный транспорт ChatGoose через текущую браузерную сессию Fansly. Не вызываем код Fbuddy и не зависим от его DOM или установленного расширения. Hub продолжает отвечать за генерацию AI, но сообщение отправляется непосредственно из расширения в Fansly.

После явного клика «Отправить»:

1. Зафиксировать accountId, fanId, groupId и текст; заблокировать повторный клик. Перепроверить текущий аккаунт и отсутствие новой личной прописи перед отправкой.
2. Если groupId уже известен — использовать его после проверки участников. Если нет — создать/разрешить 1:1 чат через `POST /group?ngsw-bypass=true`. В разобранном Fbuddy тело: `users: [{userId: fanId, permissionFlags: 0}, {userId: ownAccountId, permissionFlags: 0}]`, `recipients: []`, `lastMessage: null`, `userSettings: null`, `type: 1`. Невалидный groupId блокирует отправку.
3. Необязательный индикатор typing: `POST /message/typing?ngsw-bypass=true`, `{groupId}`, без ожидания результата перед send, как в Fbuddy. Его неуспех не должен повторять сообщение.
4. Один `POST /message?ngsw-bypass=true` на `https://apiv3.fansly.com/api/v1` через существующую сессию/транспорт расширения. Тело для текста по quick-reply Fbuddy: `type: 1`, `attachments: []`, `likes: []`, `content`, `groupId`, `scheduledFor: 0`, `inReplyTo: null`, `createdAt: Date.now()`.
5. Только подтверждённый результат с messageId меняет статус на «Писали». Проверять возвращаемую привязку к группе, когда она присутствует; формат текущего ответа подтвердить на интеграции. Обновить локальную историю, счётчик и доступный журнал личных отправок.
6. При неопределённом исходе сохранить текст, запретить автоматический повтор и сопоставить результат с живой историей. Явный отказ до успешной отправки можно показать как исправляемую ошибку. В прототипе неоднозначный ответ моделируется консервативно: «Не удалось подтвердить отправку» и повтор заблокирован.

Открытие основного чата Fansly, подстановка текста в нативный composer и DOM-клик по его send не нужны. Текущая страница и выбранная переписка не меняются. После успеха пользователь сам переходит стрелкой к следующему фоловеру.
