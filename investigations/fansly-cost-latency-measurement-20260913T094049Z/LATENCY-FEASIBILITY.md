# Latency feasibility and bounded polling receipt sample

The accepted metric remains event **receipt → required reader**, separately for chat list, archive and Agent Read Plane: p95 ≤30s / p99 ≤120s for an enabled event path (accepted migration plan §1, line 18). Provider message creation time, endpoint response duration and repeated material observation timestamps are different measurements. W0 is draft and B0/B1 are absent in the coordinator's current deployment state: there are **zero event-driven samples for this metric**, not a measured zero latency. This audit did not run a socket or provider probe.

## Existing permitted query and result

One production SELECT used the already deployed `fansly_dm_head_debt_report` view granted to `read_only` by migration 0172. Transaction was READ ONLY with 5s statement timeout and 1s lock timeout. Full SQL, stdout, stderr, client start/end and SHA receipt are saved beside this note as `head-latency-sample*`. No base-table/payload access was attempted.

Frozen database bounds: **08:47:14.306804 ≤ first_observed_at < 09:47:14.306804 UTC on 2026-09-13**. Also required provider `message_at` inside that hour and `message_at ≤ first_observed_at`; ordered newest first with LIMIT 20. Returned **7 rows on 5 pages**, below the limit: 6 with a historical exact-hot receipt and 1 without a receipt. All head-debt recovery attempt counters were 0; these are not physical HTTP attempt counters. IDs are retained in the local JSON for a possible subsequent exact-ID reader probe; they are not reproduced here.

This excludes migration seed history and old message timestamps from this selection. It does **not** produce an unbiased sample of all fresh messages: debt is inserted only when a list-observed non-null head lacks an exact live hot row (`packages/db/src/repositories/fansly-dm-head-debt.ts:6–20`). It is observed even with the recovery flag off (`fansly-dm-conversations.ts:1004`; flag affects later scheduling).

The 6 paired `captured_at − first_observed_at` markers span about **12–701 seconds**. These are **list-discovery/debt → exact-hot-receipt markers, not event→reader latency**, and no percentiles were computed. `captured_at=now()` is written when an exact hot identity is found (`fansly-dm-head-debt.ts:26–35`), sometimes in a later finalizer (`page-dm.ts:979`) and sometimes in the message transaction. PostgreSQL `now()` is transaction-start time, not commit/first-visible completion. A historical receipt also does not certify current hot residency after later pruning/erasure. The unreceipted row is not, by this view alone, proven absent from the current hot/archive reader.

## What can be measured next without changing the system

The existing permitted Agent `transcript` operation can read one retained stable conversation/message ID within a frozen recent provider-time window. A successful response proves that reader served the exact message by the probe completion (subject to request timing and clock alignment). A preceding bounded negative probe followed by positive probe could bracket when that **reader observation** changed; no retrospective first-visible instant is reconstructed. For an already captured row, a one-off probe yields only current availability and a loose receipt-to-probe upper envelope, not the missing event→reader metric.

The current `dm_threads` dataset can find recent conversations (`lastMessageAt` is its window/sort field) but has no last-head ID or local visibility timestamp. Agent transcript is a separate operation, not a dataset. Actual current capabilities receipt grants both required read surfaces; no new dataset/reader was implemented.

To measure the accepted event metric requires the later accepted receiver/application stages to provide a real event receipt with stable identity and coordinated observations of each required reader. This is stage work, not permission to probe a socket, deploy, flip flags or enter B0/B1. The present result is **event-driven latency N=0/unmeasured**, plus 7 tightly scoped polling-debt observations; no SLA, savings, freshness non-regression or gate acceptance follows.

Only the coordinator-authorized bounded read-only view query was performed by this analyst. Local evidence and this feasibility note were saved. No provider calls, socket probes, permission changes, code changes, tests, git mutations, PR, recovery or deployment occurred.
