## Вывод

Hub уже имеет хорошую основу для гибридного режима: capture journal, resumable REST walks, pg-boss wakeups, DB leases, shared proxy pacing, canonicalization и отдельные projection watermarks. События можно добавить как ещё один источник материала и адресных dirty-сигналов. Заменить ими весь polling одной перестановкой scheduler нельзя: 17 Fansly streams читают разные поверхности; часть таблиц обновляют непосредственно sync handlers, а не canonical events; у части поверхностей нет доказанного потока событий или полного исторического API.

Основная экономия в Hub вероятна от сокращения полных conversation/subscriber walks и повторных overlapping financial reads. Она должна измеряться по физическим HTTP attempts, включая hydration, retries и recovery. Число jobs и входящих событий этой цели не измеряет.

## 1. Реальный путь данных

1. `sync.planner` вызывается раз в минуту (`apps/runtime/src/services/sync-queue.ts:241`). Planner материализует stream states, rollout gates и due work, затем даёт один page wakeup (`services/sync/planner.ts:49–87,154–168`). Наличие capability не означает активный stream: bulk gates переводят flag-off/non-allowlisted lanes в durable pause (`services/sync/fansly-stream-scheduling.ts:40–142`).
2. Истина о работе — `page_sync_states`, checkpoints/cursors, leases и request generations. pg-boss job — disposable wakeup с `retryLimit:0`, page singleton; complete→send делается атомарно (`services/sync-queue.ts:19–23,78–85`; `services/sync/executor.ts:1045–1135`). Это следует переиспользовать; новая очередь на каждую WS frame не нужна.
3. Executor берёт lease, создаёт chunk budget и heartbeat (`services/sync/executor.ts:520–597`). Номинальный chunk — 5 started requests / 45 s; проверки выполняются между units (`services/sync/chunk-budget.ts:5–54`). Это не универсальный жёсткий максимум физических calls: старые contexts не передают `remainingAttempts`; retries и вложенная hydration могут происходить внутри unit. Новые lanes имеют отдельную durable attempt admission — см. §4.
4. Каждый adapter GET получает page session/proxy/egressKey и проходит observed transport. По умолчанию до трёх retries; transport errors и 429/selected 5xx повторяются; 401/403 не повторяются (`packages/fansly/src/adapter.ts:1949–2146`). Shared DB rate limiter резервирует слоты по provider+egress+scope (`services/sync/rate-limiter.ts:25–79`). Это изоляция egress, а не общий математический суточный лимит всех Fansly запросов.
5. `persistRawPayload` сначала сохраняет CAS при включённой соответствующей политике, затем raw row, затем `observations(source='pull', producer='sync:fansly:<stream>')`; отказ обязательного capture ломает chunk, а checkpoint должен остаться до ответа (`services/sync/shared.ts:83–227`). Два insert не являются одной общей транзакцией: raw без observation возможен при промежуточной ошибке, повторный fetch создаёт новую observation. Dedup фактов происходит ниже.
6. «Raw» здесь не сетевые байты: adapter возвращает `envelope.response` (`adapter.ts:2136–2141`), некоторые lanes применяют утверждённый account field allowlist перед journal (`shared.ts:230–260`; conversation trim в `executor-handlers.ts:2924–2935`). Нельзя случайно расширить capture до auth tokens/volatile account fields под лозунгом полного WS capture.
7. Далее существуют ДВА пути: legacy handler непосредственно пишет serving tables; canonicalization отдельно читает journal и пишет domain events, затем projections. Families определяются по source+kind (`services/canonicalize/index.ts:120–258`). Новому source `fansly_event`/`client_capture` нужны явная family/producer registration и contract, а не просто row с произвольным kind.
8. Canonicalization и projection ticks идут отдельно с rotating budgets (`worker-services.ts:381–418,443–463`). Даже мгновенная доставка frame не гарантирует мгновенную видимость в базе клиентов: нужен end-to-end latency SLO на capture→canonical→projection→reader.

## 3. Скрытые зависимости и риск потери совместимости

**Bootstrap dependencies не являются cascading refresh.** `dm_conversations` зависит от light/top_spenders/transactions/subscribers/followers; dm_messages добавляет conversation; purchase_history зависит от light; media_stats от catalog (`page-sync.ts:482–501`). Но `dependencyMet` требует только прежнего `succeededAt` либо `appliedSeq>0` (`:1705–1707`). Было бы неверно утверждать, что каждое DM событие сейчас вызовет пять prerequisite запросов. Для нового live lane можно требовать verified own identity и разрешаемый thread/fan, не подвешивая новые сообщения за историческим финансовым bootstrap.

**Domain events не заменяют legacy writers.** Subscribers/followers/account identity ещё не имеют sync-pull canonicalizers (`canonicalize/sync-pull.ts:10–17,52–62`). Transaction event имеет `dedupKey=txn:<id>`, а direct upsert обновляет status/amount/sourceUpdatedAt при повторном REST (`sync-pull.ts:85–106`; `transactions.ts:415–440`; `db/repositories/transactions.ts:130–159`). Следовательно pending→settled или поздняя correction нельзя восстановить новым событием того же `txn` через нынешнюю family. Нельзя считать «canonicalized=true» доказательством актуального revenue projection.

**Нельзя без guard пустить competing stale writers.** Transaction upsert last-writer по amount/state, не sourceUpdatedAt CAS (`db/repositories/transactions.ts:130–143`). При параллельном WS/REST необходимо определить source precedence и field-level material timestamp/version. Старый REST response, начатый до нового события, не должен откатить новое состояние; redelivery event не должен воскресить deleted message. Для v1 проще сохранить money authoritative REST, а events использовать как signal.

**DM data plane многослоен.** Fetch пишет raw, materializes exact tip contexts, нормализует hot messages; thread finalization и checkpoint в следующей транзакции. Если второе падает, возникает repairable `projection_debt`, а не повтор всех fetch (`fansly-dm-messages.ts:232–251`; `executor-handlers.ts:4094–4150`). Новый path обязан сохранять эти эффекты либо явно перевести соответствующих readers. В противном случае archive будет свежим, а thread list, PPV relations/точные заметки к tips или fan identity — устаревшими.

**AI и клиенты не доказывают свежесть базы.** Features принимают Fansly `clientContext`, который extension загружает live (`modules/ai/features/index.ts:97–110`). Kernel transcript loader читает archive/опциональный union (`modules/ai/context/index.ts:93–171`), spending — `transactions`, subscription — `page_fans` (`:187–245`). Успешная генерация со свежим браузерным контекстом не подтверждает Hub ingestion. Нельзя одновременно убирать clientContext и менять capture без независимой parity-проверки.

**Agent Read различает planes и coverage.** Transcript/timeline/search используют разные поверхности и сообщают отсутствие archive/read/index coverage (`modules/agent-read/handlers-threads.ts:145–158,790–900,1118–1145`). Переключение writer следует проверять через эти же реальные readers: item presence, history floor и непрерывность — разные утверждения.

**Presence зависит от polling побочно.** Followers sidecars создают lastSeen signals и buckets <30 min / <120 min (`services/fansly-presence.ts:7–8,42–79`). Снижение follower polling меняет online/activity UX, даже если follow-event ничего не потерял. WS presence можно подставлять только после отдельной проверки смысла и охвата сигналов; иначе нужен explicit stale/unknown.

**Уже есть событийные побочные очереди.** `media.purchase_notification_observed` только marks точный `subject_refresh_state` dirty; fetch не происходит в projector; missing correlationRef не заменяется whole-page invalidation (`projections/fansly-engagement.ts:212–234`). Это правильный reusable pattern. Domain hub также triggers debounced per-fan workboard recompute (`services/workboard-event-recompute.ts:28–63`). Replay historical events может породить CPU/job нагрузку даже без HTTP; outbox/replay semantics должны её ограничивать.

**Projection state и operational state разделены сознательно.** Registry запрещает truncate capture cursors/floors/blockers при rebuild, иначе вся коллекция будет заново «новой» и начнёт historical crawling (`projections/registry.ts:28–35`). Новый dirty/task state должен сохраняться отдельно от rebuilt fact tables. Message archive rebuild — bespoke shadow, не обычный truncate+replay (`:138–151`).

## 4. Физическая стоимость и bounded event reaction

Считать за одинаковое окно:

`R_total = head/list GET + pagination + hydration + financial rechecks + catalog/stats + history + retries + session/probe/reconnect HTTP + browser-origin API HTTP`.

Затем отдельно полезные новые/изменённые факты на attempt, zero-change response ratio, bytes и read freshness. Уменьшение Hub HTTP при росте forced browser REST не является достигнутой целью.

Production baseline координатора ограничен разрешённым read plane: `observations` доступен, `sync_http_attempts` — нет. Счёт observation rows не может быть выдан за physical requests: failed attempts, nested hydration, один fetch с несколькими journal representations, selective capture и refresh/probe paths нарушают такое равенство. `parse_version=0` у `account_me`, `subscribers`, `followers`, `dm_conversations`, `account_lookup` также не означает само по себе backlog: family для них намеренно не зарегистрирована. Сравнивать parse debt следует только по declared family и её требуемой версии.

Скрытые множители, подтверждённые выше: subscriber страница обычно 2 calls; transaction страница ещё identity batch; non-empty timeline страница ещё tips call; fan_earnings 2 calls/spender; conversation page иногда несколько group/head repair; full top-spenders result splits окна. Один WS→`requestPageSync(messages)` не означает один GET.

Новые Fansly lanes используют `createDurableFanslyAttemptBudget`: `started` сначала повышает/сохраняет `callsToday`, при исчерпании бросает до physical request; adapter ограничивает retries оставшимся allowance (`fansly-lane.ts:135–225`; adapter `:1990–1991`). Это лучше переиспользовать, чем считать только логические jobs. Defaults на страницу/UTC-day: stats 25, notifications 96, catalog 60, replies 100, payouts 20, media_stats 300; purchase_history 100; post engagement отдельные 40 (`config-registry.ts:185,191,198,206,216,230,240`; `fansly-purchase-history.ts:61–62`). Эти числа — defaults, не текущая production настройка и не их фактическая сумма расходов.

Нужные свойства нового live reaction:

- Ключ work item `(page, resource family, subjectRef)`; входящие события повышают dirty generation/target watermark, а не размножают jobs.
- Capture raw event до acknowledgement. Минимальная достаточная event material сразу идёт в общий reducer; отсутствие полей означает unknown, а не null/zero/удаление существующего поля.
- Для partial message максимум bounded head repair конкретного group, затем keyset до известного якоря при дыре. Catch-up хранит свой cursor и всё время уступает live.
- Handler забирает поколение G. После HTTP закрывает только G; событие G+1, пришедшее во время fetch, оставляет item dirty. Один `dirty=false` без CAS теряет этот wakeup.
- Debounce с максимальным ожиданием, минимальная частота per subject, общий page/egress admission; money changes сливаются в bounded time window. Missing identity/ref открывает bounded resolution task, не sync-all.
- Сохранить manual pause/auth/proxy gates и generation fencing. Event source не имеет права оживить owner-paused stream или сменить page identity по username.
- Установить измеряемый допустимый budget для disconnected-mode REST и catch-up. Браузер/WS outage не должен приводить к recovery storms или сбросу completed history cursors.

## 5. Полнота и отказовые сценарии для архитектурного review

| Сценарий | Что требуется от нового режима |
|---|---|
| WS подключён, событий нет | Отдельно connection/auth health и business freshness. Тишина не означает отсутствие изменений или исправную server subscription. |
| Браузер закрыт / Mac sleep | Backend REST продолжает работать с доступной сессией; event coverage gap фиксируется. Если collector зависит от desktop browser, нельзя обещать круглосуточную realtime freshness. |
| Сессия умерла | Нынешний 401/403 path pauses whole page (`executor.ts:769–818`). Raw/resume cursors сохраняются; новый collector также прекращает auth retry loop. После reverify — bounded reconnect+reconciliation, не автоматический full reset. |
| Frame дублирован / потерян / пришёл не по порядку | Stable provider id + material hash/version, durable delivery dedup, field precedence. Нельзя использовать локальную receive time как provider causal order. Отсутствующий server replay cursor означает REST gap repair, а не «exactly once». |
| WS message пришёл пока REST head in flight | Не позволить старому head откатить latest message, unread/read state или deletion; retain G+1 dirty. |
| Event содержит лишь tip/purchase notification | Не считать notification бухгалтерской транзакцией. Сохранить source и semantic uncertainty, адресно reconcile ledger/order target; деньги/PPV контент — разные facts. |
| Новая покупка старого media | Revisit target, даже если purchase_history прежней версии уже пометил его complete. |
| Fan/DM появился до subscribers/followers bootstrap | Создать stable scoped identity stub и отдельную hydration, не терять событие и не блокировать realtime до окончания всей аудитории. |
| Новый liker/delete, который уже исчез из REST | Если event не был сохранён, после outage это может быть невосстановимым forward-only gap. Не скрывать под `sync success`; bounds/retention требуется измерить. |
| Full sweep с offset движется из-за активности | Сохранять existing unique/count/repeat guards; не маркировать пропавшие items при incomplete/partial snapshot. События не дают полного roster для destructive reconciliation. |
| Projection lag / parse error / unknown type | Raw event сохраняется, unknown parser material не исчезает. Status отдельно capture, parse, serving; replay локально, без Fansly calls. |
| DB отказал после raw capture / после projection | Raw durable custody и cursor transaction boundary проверяются crash tests; repair materialization из local evidence должен предпочитаться повторному API fetch. |
| Суточный cap исчерпан | Deferred с oldest-unreconciled watermark и visible degraded freshness; не silently complete. |

Существующие `messageCoverageStatus='complete'` не равны всей истории аккаунта: helper выставляет complete при provider exhaustion **или overlap**, а incremental сохраняет прежний status (`fansly-dm-messages.ts:39–62`). Deep backfill может быть ограничен retention flag; initial live backfill capped, deep идёт порциями (`executor-handlers.ts:3783–3890,4070–4078`). В migration baseline необходимо отдельно перечислить known conversations, exhaustive inventory proof, per-conversation floor/exhaustion и capture-time gaps. Аналогично stats heuristic floor, post-reply pagination unknown и target-scoped purchase history не следует превращать в универсальное «100% база».

## 6. Рекомендуемые точки встраивания

1. Добавить отдельный transport producer и source contract, сохранив existing REST adapters и capture policy. Source envelope должен нести verified page/native account, session generation, collector generation, connection/gap markers, received time и provider event identity/version когда существуют.
2. Добавить canonicalizer по наблюдённым schemas; tests на один факт, пришедший REST+event; не направлять partial event в REST canonicalizer через поддельную полную page shape. Transaction state transitions для v1 оставить authoritative REST.
3. Вынести только нужный material apply из DM direct paths в общую idempotent функцию с identity, hot rows, head ordering, tip contexts и subsequent event/projector contract. Сохранить новый источник и provenance. Не делать полную universal ingestion DSL ради первой версии.
4. Для неполных событий дать coalesced subject refresh на existing DB/pg-boss execution infrastructure. Сначала bounded DM head resource; затем notification/order targets. Адресная работа должна вызываться без generic full conversation walk и не сдвигать history checkpoints.
5. REST policies менять по одному stream только после shadow comparison. В production snapshot собрать actual attempts by stream/endpoint/status + capture freshness/projection lag; задать target reduction на реальной базе, а не из nominal cadences.
6. Проверить настоящих readers: thread list/head, archive/union/search, AI context, exact tips, PPV orders, revenue/subscribers, presence, health и workboard. Cutover успешен, когда все требуемые readers согласованы, а не когда растёт `observations`.
