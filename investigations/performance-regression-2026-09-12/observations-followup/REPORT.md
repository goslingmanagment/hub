# Повторные чтения observations — проверка и исправление

**Исправление выложено и проверено. Фоновый проход в наблюдавшихся окнах ускорился
в 3,1 раза; суммарный CPU четырёх сервисов снизился на 17%, число повторных посещений
строк журнала — на 60%.** Замеры завершены, исходные данные сохранены.

Фикс: `14219b68`; измеренная версия: `ea7a629ceb3c`. API, worker и scheduler
подтверждены на этой версии во всём окне, здоровы, без перезапусков. Данные не
перепроигрывались; версия для отката сохранена.

После замера соседняя задача выложила релиз `5e703b4a35cd`. Независимая проверка
в 21:42:42 UTC подтвердила его на всех трёх здоровых сервисах без рестартов;
`git diff` подтвердил побайтовое сохранение нашего селектора и его тестов.
Цифры ниже относятся к ранее завершённому окну на `ea7a629ceb3c`.

Пока готовился фикс, другая задача выложила `4310680dc2f9`. Проверка перед нашей
первой попыткой выкладки остановила её до изменений. Релиз другой задачи сохранён
слиянием; независимый агент проверил итоговое дерево и отсутствие пересечения
исполняемого кода. Для сравнения снят новый исходный замер на `4310680dc2f9`.
Прежний замер на `96a86c1fcdde` сохранён как исторический.

пустого прохода отдельно доказано парой SQL на одном снимке и отрицательным тестом.

## Ошибки и оставшаяся дорогая работа

В API/worker/scheduler нет error/fatal, рестартов нет, все 13 снимков здоровы на
одной версии; контейнеры, наборы таблиц/индексов и маркеры сброса статистики внутри
каждого окна стабильны. Новых deadlock нет. Итоговая проверка состояния выполнена
в 21:34:15 UTC; свободно 19,42 GB. Обе блокировки завершённой выкладки сняты.

В журнале PostgreSQL после 21:28 есть 11 ERROR: три до основного окна и восемь
внутри него. Это диагностические SQL с неверными столбцами/enum или недостаточными
правами: `ordinal_position`, `schema_migrations.version`, неоднозначный `status`,
`tip_contexts`, запрос без корректной группировки и проверки доступа. Эти формы
не относятся к новому селектору; восемь ошибок внутри окна согласуются с восемью
rollback. Источник конкретного оператора не установлен. Поэтому утверждение
«вообще никаких ошибок в базе» к этому замеру неприменимо.

Зафиксированы три временных файла на 48,49 MB; счётчик `blks_read` PostgreSQL:
45 082 → 253 372; это не число физических операций диска.
Рост этих счётчиков не скрывается и не объявляется доказанной
регрессией фикса: окно содержит другой объём диагностики и мониторинга. Точное
распределение временных файлов/CPU между запросами не измерялось.

Оставшиеся медленные запросы, которые этот фикс не устраняет:

- Существующий расчёт p50/p95 задержки канонизации: 12,393 с. SQL совпадает с
  [golden-signals.ts](/Users/dmitriy/code/goose/.worktrees/hub-performance-fixes-20260912/apps/runtime/src/services/golden-signals.ts:135); этот код не менялся
  относительно исходной production-версии. Это кандидат для следующего
  отдельного профилирования, а не уже доказанная ошибка нового релиза.
- Существующий запрос монитора синхронизации: 4,908 с; его исходный код также
  сохранён побайтово. Дополнительные диагностические запросы: 2,079 и 4,496 с.
- Один запрос нового replay-селектора: 2,085 с. Значения параметров и число

  исходный упорядоченный проход по данным сохраняется. Обещания, что теперь
  любой replay-запрос занимает несколько миллисекунд, этот результат не даёт.

## Подтверждённая причина

Первая страница `listObservationsForReplay` запрашивает ещё не разобранные записи
в порядке числового `id`. Для полностью обработанных семейств PostgreSQL выбирает
первичные ключи месячных разделов и отбрасывает все строки после чтения. Три
проверенные пустые выборки прочитали примерно 2,39 млн строк каждая, чтобы вернуть
ноль. Это объясняет существенную часть наблюдавшихся повторных чтений, но не
приписывает этому запросу все счётчики таблицы.

Доказательства: `metadata-before.json`, `queries-before.json`, `plans-before.json`,
`analyze-before.json`. Наши SQL для этих проверок выполнялись ролью `read_only`,
с принудительным read-only, statement timeout 5 секунд и lock timeout 1 секунда.
Доступ к таблице курсоров у этой роли отсутствует; привилегии не менялись.
Глубокий курсор 2 000 000 в матрице запросов — проверочный параметр, не прочитанное
значение текущего рабочего курсора.

## Проверенный кандидат

Один SQL сначала находит фактически существующие версии разбора, затем проверяет
наличие записи точечными запросами по версии, источнику и типу записи. Используется
уже существующий индекс 0144. Если записей нет, полный проход по первичным ключам
не запускается; если есть — выполняется исходная выборка в том же снимке данных.

Оптимизация касается первой страницы без ограничения по аккаунту/датам и с указанным
источником. Продолжения по курсору, точечные чтения и запросы по аккаунтам/датам сохраняют
исходный SQL. Отрицательные и разреженные версии не отбрасываются. Схема, индексы,
факты, параметры захвата и курсоры не меняются.

| Запрос | Исходный SQL | Финальный SQL | Строк в ответе |
|---|---:|---:|---:|
| Статистика | 1542,805 мс | 2,378 мс | 0 |
| Уведомления | 1181,404 мс | 1,181 мс | 0 |
| Результаты команд | 1162,798 мс | 1,105 мс | 0 |
| Заполненная webhook-очередь | 0,581 мс | 1,675 мс | 200 |

Это execution time из EXPLAIN ANALYZE на живой базе, без времени планирования и
сети, а не оценка CPU всего сервиса. С планированием: статистика 1544,463 → 7,909 мс,
уведомления 1182,713 → 5,633 мс, команды 1164,106 → 5,214 мс,
заполненная webhook-очередь 2,959 → 6,751 мс. Полезная непустая выборка платит
небольшую дополнительную стоимость проверки наличия данных.

Финальный исходный код проверен против исходного SQL в одном read-only
repeatable-read снимке: все четыре полных результата совпали, включая payload,
ссылки и даты. Это однократные прогретые пары с выполнением старого SQL первым;
точный универсальный коэффициент ускорения по ним не вычисляется. Порядок строк
дополнительно проверен интеграционными тестами на границах числовых ID и месяцев.
Доказательство: `pair-final-source.json`; наружу выведены только совпадение,
количество строк и планы. Буферы трёх пустых запросов: примерно 999 400 каждый
→ 730, 83 и 82. Полезный webhook: 46 → 118 обращений. Оба варианта в этой паре
показали ноль `Shared Read Blocks`: измерено сокращение работы с буферами и
строками, а не физических чтений диска.

Первый, более простой вариант с общим диапазоном версий и IN-списком был отклонён:
webhook-запрос вырос до 1613 мс. Артефакты `analyze-guard.json` и
`independent-strategy-review.md` сохраняют отрицательный результат. Выкладка этого
варианта не проводилась.

## План измерения сервиса, выбранный заранее

До и после: по 13 снимков через 30 секунд. Первую минуту исключаем заранее;
основное окно — ровно пять минут между снимками с индексами 2 и 12. Измеряем CPU
PostgreSQL/API/worker/scheduler, счётчики таблиц/индексов, WAL, вставленные
observations/domain_events, исходящие HTTP-попытки и длительность полных циклов.
Проверяем неизменность контейнеров и stats_reset внутри каждого окна. Нагрузочные
EXPLAIN не запускаются во время этих окон.

Окна идут на реальной меняющейся нагрузке: уменьшение CPU нельзя безоговорочно
приписывать фиксу без проверки объёма работы. Буферные обращения и индексные
чтения не равны уникальным строкам или физическим операциям диска.

## Проверки кода и релиза

Два независимых агента проверили корректность, архитектуру, сохранность порядка
и состава результатов, планы чтения и методику измерений. Новый тест на 240 тысячах
строк воспроизводит лишнее чтение старым кодом и подтверждает его устранение.
Матрица из 30 запросов проверяет 15 оптимизированных первых страниц и 15 остальных
вариантов с прежними SQL и параметрами. Удаление персональных данных, чтение payload
и долговечные курсоры сохраняют прежние границы.

На отдельном коммите исправления прошли `pnpm check`, 2139 DB/schema/network тестов,
27 критических API-тестов и production build — всего 5630 успешных тестов.
На окончательной объединённой версии повторно прошли `pnpm check` (3467 тестов),
116 совместных интеграционных тестов, 27 критических API-тестов и production build.
Полный DB-набор второй раз после непересекающегося слияния не запускался;
исходный код фикса и его тесты сохранились побайтово. Такой объём повторной
проверки одобрен независимым ревьюером.

Остаются 9 прежних пропусков основных тестов и 77 некритических API-кейсов вне
выбранного gate. TypeScript ratchet допускает прежние 1897 ошибок в 120 файлах;
новых ошибок нет, но это не чистая компиляция без долга.

Штатная выкладка проверила совместимость сборки, health/sync health, выдачу
dashboard и версии всех трёх сервисов. Проверка после выкладки подтвердила
действующие настройки надёжности PostgreSQL и ограничения логирования параметров.
Индекс метрик остаётся valid/ready. В измеряемой версии решение зафиксировано как
Decision 314. В последующем объединённом релизе `5e703b4a35cd` тот же текст
перенесён на номер 315 из-за параллельно занятого номера в main;
опубликованная история нашего релиза не переписывалась.

## Основания SQL-решения

Поведение материализации и ограничения составного индекса сверено с официальной
документацией PostgreSQL 16: [WITH](https://www.postgresql.org/docs/16/queries-with.html)
и [составные индексы](https://www.postgresql.org/docs/16/indexes-multicolumn.html).
Приём принят по фактическим планам этой базы, а не только по описанию оптимизатора.
