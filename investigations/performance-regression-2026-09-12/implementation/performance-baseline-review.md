# До релиза: что действительно можно сравнивать

Независимая проверка сохранённых артефактов. Production не опрашивался, тесты/сборки не запускались, код не менялся.

**Есть прямой парный замер ресурсов за 31,1 секунды на ревизии `31b73a9691f3` и отдельно восстановимая оценка среднего CPU за первые 45 минут жизни контейнеров — около 0,443 ядра.** Второй расчёт и его предпосылки описаны в [lifetime review](performance-lifetime-baseline-review.md). Для общего вывода «сервер разгрузился на X%» нужны оговорки о составе нагрузки, старте и фазе задач.

## 1. Ресурсы и объём работы в одном окне

Первичный файл: [production-performance-snapshot.json](../followup/production-performance-snapshot.json), поля `before`, `after`, `identity`. Сборщик: [production-performance-probe.py](../followup/production-performance-probe.py). Все значения ниже пересчитаны из первичных счётчиков, а не скопированы из округлённого summary.

- Границы: **12 сентября 2026, 16:35:59.915–16:36:31.016 UTC** (19:35:59.915–19:36:31.016 МСК).
- Интервал монотонных часов: **31.1010956727 s**. Команды внутри snapshot последовательны; отдельные счётчики прочитаны с небольшим сдвигом, и сами диагностические чтения входят в нагрузку.
- API/worker/scheduler: `31b73a9691f3`, все запущены около 15:50 UTC, restarts = 0. PostgreSQL стартовал 15:50:34 UTC. То есть это прогретый после прежнего деплоя сервис, примерно 45 минут после старта.
- `pg_stat_database.stats_reset = null` с обеих сторон; WAL reset одинаковый `2026-09-07T06:19:16.577613+00:00`. Отрицательных нужных дельт нет.

Это единицы CPU-core, не доля всего сервера. Формула: `(usage_usec_after − usage_usec_before) / 1e6 / seconds`. Throttled CPU delta = 0; это не доказательство отсутствия гипервизорных ограничений. Другие контейнеры/host CPU в сумму не входят.

`blks_read` не равен физическому I/O устройства: чтение может удовлетворить OS cache. Buffer hits и index fetch — повторные обращения, не число уникальных строк. Суммы lifetime counters после пересоздания контейнера сравнивать нельзя.

Объём полезной/внешней работы в том же окне: **12 новых observations, 2 domain_events, 3 sync_runs, 9 sync_http_attempts**. Кроме того, 48 точек метрик. По observations partitions суммарно **18 114 412 index fetch**, по domain_events partitions — 613 904. Июльский capture catalog: 4000 поисков в `capture_payload_objects`, 4000 в `capture_json_hot_bodies`, ещё 4000 безрезультатных index scans в `capture_byte_hot_bodies`. Это особенно полезный счётчик для проверки batching. Это не 4000 SQL на каждую таблицу сверх общей работы: один lookup может искать несколько связанных таблиц.

**Ловушка фазы:** этот замер начинается прямо перед границей минуты и содержит первый занятый 31-секундный участок, судя по catalog-счётчикам, примерно один sweep. Если после деплоя взять 60/120 s и просто сравнить CPU/s, паузы между sweep могут создать ложное уменьшение примерно вдвое. Одна привязка нового окна к той же минутной границе этого не исправляет: после рестарта job polling может сдвинуться. Фактическое пересечение нового окна со sweep нужно восстановить по completion timestamp минус durationMs. Более длинные окна и среднее от старта показывать отдельно.

## 2. Канонизация: отдельные 30 минут логов

Источник: тот же первичный snapshot, `worker_logs`; сборщик берёт `--since 30m`, tail = 30000, реально 308 строк, ограничения tail не достигнуты. Точные wall-clock границы log fetch не записаны: примерно 16:06:32–16:36:32 UTC. Это другое окно, не те же 31,1 s ресурсов.

- **30 завершённых canonical sweep**: сумма **364459 ms**, среднее **12148.63 ms**, максимум **15053 ms**. Атрибуция проверена по исходникам прежней ревизии, см. ниже.
- Сохранённые суммы: `scanned = 116736`, `skippedUnmapped = 116533`, `appended = 1746`, `stamped = 181`, `skippedUnparseable = 0`. **Scanned здесь объединяет canonical и projection сообщения**, поэтому 99.826% — отношение к общему pipeline scanned, не точная доля внутри canonical sweep.
- При грубой нормализации получается 3891.2 pipeline scanned на canonical completion; использовать эту величину лишь с оговоркой о смешанных счётчиках. Это не число уникальных фактов.
- Проверка кода на `31b73a9691f3`: `worker-services.ts:408` пишет верхнеуровневый durationMs для canonical completion; обычный projection completion в `projections/registry.ts:652` его не пишет. Другие такие сообщения — budget warnings с порогом 600000 ms, что исключено сохранённым максимумом 15053 ms. Поэтому все 30 timing records относятся к canonical completion. Исходных строк и распределения длительностей нет; P50/P95 восстановить нельзя. При новом измерении сохранять числовые поля каждой canonical completion отдельно от projection.
- В выборке нет error codes; info: 113, warning: 32. Нельзя называть warnings ошибками.

Сравнивать duration одновременно с scanned/skipped/appended/stamped и backlog. Сокращение времени за счёт прекращения полезной обработки выигрышем не считать. Число appended может превышать stamped: одна observation даёт несколько событий.

## 3. Медленный SQL метрик

[known-slow-shapes.json](../followup/known-slow-shapes.json), снят в 16:39:43 UTC, за предшествующие 30 минут: два точных совпадения прежней формы `listRecentOpsMetricSamples` — **12931.694 ms и 10138.744 ms**. Это сильное доказательство стоимости прежнего SQL, но всего два наблюдения. Они могли быть вызваны диагностическими чтениями, поэтому обычная пользовательская частота не установлена.

[slow-log-aggregate.json](../followup/slow-log-aggregate.json), снят в 16:38:15 UTC, другое за предшествующие 30 минут окно: 11 медленных запросов, 59.619 s суммарной wall duration; среди них 3 безагрегатных запроса к ops_metric_samples — 28.556 s, плюс 1 агрегатный 2.165 s. Остальные формы: sync monitor — 4.777 s, observations parse_version — 4.589 s/2, percentile — 2.070 s, domain_events count — 14.643 s/2, capture catalog — 2.819 s.

Slow threshold — 2000 ms. Отсутствие записи после фикса означает лишь, что наблюдаемый запрос не попал в этот порог, а не даёт новую измеренную latency. Новый EXPLAIN/latency подтверждает конкретный путь; локальный парный benchmark отдельно доказывает алгоритмический эффект. Ни одно не означает такой же коэффициент ускорения всего сервера.

## 4. Что не следует выдавать за baseline

- [statement-stats-snapshot.json](../followup/statement-stats-snapshot.json): 30 верхних строк, 29 без видимой query identity. Кумулятивный snapshot с reset 13:02:48 UTC охватывает прежние ревизии; дельт нет. Для query-by-query до/после непригоден.
- [production-snapshot.json](../production-snapshot.json): ранний 16:15 UTC одноразовый docker stats и 3 секунды vmstat. Это иной workload/фаза, не длительное использование CPU/RAM.
- [production-metrics.json](../production-metrics.json) и [production-metrics-followup.json](../production-metrics-followup.json): последние 30 точек 89 серий, включая старые остановившиеся серии с июля. Без фильтра по sampledAt нельзя усреднить все 2670 строк и назвать это свежим окном. Lag gauges — не latency API.
- [predeploy-db-counters.json](predeploy-db-counters.json), 19:29:25 UTC: deadlocks = 33 и накопленные temp counters. Это точка, не rate. За раннее 31 s deadlocks тоже 33→33; нельзя заявить измеренное уменьшение deadlock rate после фикса.
- Последние predeploy settings/disk snapshots не содержат cgroup CPU/DB-WAL interval. Длинного прямого двухточечного resource baseline в указанной папке нет; для CPU доступна отдельная оценка от старта по lifetime counters. Из старых DB counters такой же 45-минутный интервал не восстановить.

## 5. Рекомендуемая трактовка результата

После завершения миграции, трансфера образов, прогрева и первичного catch-up снять синхронные CPU/DB/WAL/table/index/workload дельты на новой ревизии: отдельное окно нескольких полных sweep и короткие окна с фактически установленным пересечением с работой. Не считать совпадение границ минут совпадением фазы заданий. Проверить отсутствие рестартов внутри каждого окна. Сохранить реальные длительности, объём работы и ошибки.

Формулировка для пользователя: «Конкретный запрос/проход ускорился с A до B; за наблюдаемое окно PG расходовал C вместо D ядра при таких-то объёмах работы. Общий стабильный процент экономии пока оценён ограниченно». Не складывать проценты разных оптимизаций; не переносить локальные ускорения в производственный CPU.

Машиночитаемая выборка с полными ненулевыми table/index дельтами: [performance-baseline-review.json](performance-baseline-review.json).
