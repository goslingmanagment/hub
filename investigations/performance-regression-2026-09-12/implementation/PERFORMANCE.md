пустых replay-очередей. Новые заранее выбранные пятиминутные окна показали
11,1 → 3,6 с на фоновый проход, 0,539 → 0,447 ядра суммарного CPU сервисов и
91,2 → 36,6 млн посещений строк `observations` по сумме индексного и последовательного
счётчиков. В окнах различается нагрузка и присутствует сторонняя диагностика;
точный причинный процент CPU не заявляется. Исправление прошло независимое ревью
и выложено. [Полный новый отчёт и ограничения замера](/Users/dmitriy/code/goose/hub/investigations/performance-regression-2026-09-12/observations-followup/REPORT.md).
Ниже сохранены исторические результаты предыдущего релиза `96a86c1fcdde`.

**Выдача метрик стала быстрой. Общая экономия CPU и ускорение полного фонового прохода пока не подтверждены.** Новая версия обработала больше данных; наблюдения до и после нельзя считать контролируемым A/B.

Релиз `96a86c1fcdde` выложен в 23:05 МСК. API, worker и scheduler здоровы на этой ревизии, без рестартов; sync health — 200. Все 11 отдельных коммитов прошли независимое ревью, обязательные проверки и production build. Проверки: 3464 основных теста, 2135 DB/schema/network и 27 критических API; 9 прежних skips и 77 API-кейсов вне выбранного repository gate. TypeScript ratchet сохраняет прежние 1897 ошибок, это не чистая компиляция без долга.

API вернул 2670 точек по 89 сериям и 46 метрикам, максимум 30 точек на серию. Прогревочный запрос занял 142,6 мс. Измерение выполнялось на сервере через штатный `/api/v1/ops/metrics`, включая авторизацию, SQL, чтение smoke checkpoint и передачу JSON. Это не пользовательская задержка через интернет и не p95.

Прямой EXPLAIN таблицы метрик недоступен роли `read_only`. Первый диагностический запрос получил отказ; последующие пробы проверяют права заранее. Права не менялись. Парный SQL-инструмент подготовлен, но production A/B не выполнялся. Локальный контроль на одинаковом миллионе строк отдельно подтверждает эффект алгоритма: 89–96 → 0,48–0,61 мс и около миллиона → около 620 посещений записей индекса по счётчикам плана (значения rows/loops округлены). Локальные цифры не перенесены в процент экономии всего сервера.

CPU после измерялся 23:13–23:18 МСК: 0,3274 ядра PostgreSQL, 0,1873 worker, 0,0134 API, 0,0058 scheduler. Это около 27% суммарного CPU-времени двух ядер только для этих сервисов. Прежняя длинная оценка — сумма их собственных cgroup CPU-счётчиков за общий интервал около 45 минут, примерно 22% суммарного CPU-времени двух ядер; она включает запуск, прогрев и диагностику. У контейнеров подтверждены прежние StartedAt и отсутствие рестартов. Точный причинный процент между такими окнами не вычисляется.

Единственный старый синхронный срез CPU/DB/workload длится 31,1 с и захватывает занятую фазу минутной задачи. Его CPU 0,604 ядра нельзя напрямую сопоставить с новым средним за целые минуты. В новом срезе фаза задания меняется: в 23:13 и 23:14 проход попал во вторую половину минуты, затем в первую. Поэтому выбор только первых полминут дал бы ложное улучшение.

В новом пятиминутном окне записаны 225 observations, 1093 domain events и 217 физических HTTP-попыток к провайдерам. В старом 31,1-секундном окне — 12, 2 и 9 соответственно. После нормирования новых observations записывалось в секунду примерно в 1,94 раза больше, HTTP-попыток было в 2,50 раза больше; это разный объём и состав работы, а не одинаковая нагрузка. Один новый canonical sweep добавил 923 события. Всего пять проходов просмотрели 20106 observations, отметили 106 обработанными и добавили 1090 событий; 20000 посещений остались unmapped. Старые агрегаты `scanned` смешивают canonical и projection, поэтому точная нормализация по ним не применяется.

За новое окно PostgreSQL выдавал 133592 buffer hits/s, читал в shared buffers 134 blocks/s и записывал WAL 173064 B/s. Старый короткий срез: 247296 hits/s, 58 blocks/s и 61917 B/s. Различаются фаза задач, состав записей и полнота прогрева; падение hits/s нельзя объявлять процентом экономии, а рост WAL — регрессией. `blks_read` не равен физическим чтениям устройства, WAL относится ко всему PG cluster.

Основной оставшийся след для профилирования — чтение `observations`: **91,06 млн повторных index fetch за 5 минут**, около **18,21 млн в минуту**, 95,69% наблюдаемого количества table index fetch. Это повторные обращения к строкам, не уникальные записи, не число SQL-запросов и не доля CPU. Следующая узкая диагностика должна привязать этот объём к конкретному SQL и плану чтения. Кандидат по независимому ревью — listObservationsForReplay с ORDER BY id и фильтрами parse/source/kind: проверить первую и глубокую страницы, а также пустой результат. Текущие счётчики сами по себе не доказывают ошибку конкретного cursor или index.

Для catalog batching локально подтверждено 4000 → 500 SQL-вызовов на контрольном unmapped-корпусе и 1379 → 467/414 мс. Production index counters считают обращения к индексам, поэтому их нельзя выдавать за число SQL round trips. Полный production sweep пока остаётся около 12 секунд.

После выкладки все 16 зафиксированных canonical завершений прошли без `errored`, `partitionBlocked` и потери бюджета. В логах API/worker/scheduler нет error/fatal. Единственная PostgreSQL ERROR — отказ нашему read_only EXPLAIN метрик. Медленная запись 8,824 с при старте относится к созданию нового индекса, что проверено по форме DDL, а не к новому SELECT метрик. Обе настройки логирования bind-параметров равны нулю; специальный медленный read-only запрос подтвердил, что SQL и длительность остаются в логах, а синтетическое значение параметра отсутствует. Свободно 20,45 GB; rollback-образ сохранён, GC не запускался.
