# Независимое ревью итоговых замеров

**Вердикт: approve для публикации измерений с ограничениями ниже.** Арифметика нового окна верна. Доказательств стабильного общего снижения CPU или ускорения полного canonical sweep пока нет. Быстрый текущий API метрик измерен; точный производственный коэффициент «до/после» для него не измерен.

Ревью выполнено по сохранённым первичным JSON и локальному коду ревизии `96a86c1fcdde`. Production не опрашивался, код и сервисы не менялись, тесты не запускались.

## Проверка целостности и формул

- `performance-after-snapshots.json` содержит все 13 точек 20:12–20:18 UTC. Основное окно — точки 2→12: **20:13:00.000161–20:18:00.000117 UTC, 299.999673 секунды по монотонным часам**.
- Во всех точках совпадают StartedAt, health, status и ревизии. API/worker/scheduler — `96a86c1fcdde`, все четыре сервиса healthy/running. Snapshot не сохраняет RestartCount и container ID; стабильные StartedAt и монотонные CPU counters подтверждают непрерывность доступной выборки, но не являются полным журналом событий Docker.
- DB `stats_reset` остаётся null; WAL reset во всех точках одинаковый. Нет отрицательных дельт нужных CPU, DB, WAL, table и index counters ни в одной соседней паре. Состав наблюдаемых таблиц и индексов не меняется.
- CPU пересчитан из `(usage_usec_end − usage_usec_start) / 1e6 / elapsed_seconds`; суммы и все четыре сервиса точно совпали с `performance-comparison.json`. WAL rate проверен таким же способом. Первичный старый 31.101096-секундный CPU baseline также пересчитан независимо.
- Snapshot собирается последовательно, за 1.24–1.64 секунды. Поэтому CPU/table/WAL границы не атомарны; числа следует округлять, не выдавая микросекундную точность за точность измерения. Диагностические процессы входят в счётчики. Между вариантами отличается и частота наблюдений.

| Показатель нового окна | Проверенное значение |
|---|---:|
| Суммарный средний CPU четырёх сервисов | **0.534 ядра** |
| PostgreSQL / worker / API / scheduler | 0.3274 / 0.1873 / 0.01344 / 0.005804 ядра |
| WAL | 51,919,056 байт; **173,064 байт/с** |
| DB commits | 19,669; 65.56/с |
| Shared-buffer hits / blocks read | 40,077,433 / 40,129 |
| Новые observations / domain_events | 225 / 1,093 |
| Новые sync_runs / sync_http_attempts | 51 / 217 |
| Новые deadlocks / rollbacks / temp files / temp bytes | **0 / 0 / 0 / 0** |

Это расход выделенного CPU, а не спрос на CPU, время ожидания или полный расход хоста. `blks_read` не равен физическому чтению устройства. WAL относится ко всему PostgreSQL cluster. Нулевые deadlocks в новом окне полезны для контроля, но в коротком старом окне их тоже было ноль: снижение частоты этим не доказано.

## Общая разгрузка: вывод пока открыт

Старое занятое окно 31.1 секунды показывает 0.6039 ядра, новое пятиминутное — 0.5340. Восстановленный старый средний расход за примерно 45 минут жизни контейнеров — около 0.443 ядра. Последний включает запуск, прогрев и catch-up; это допустимая приблизительная lifetime-оценка, а не полноценный тёплый парный интервал.

Простое сравнение даёт противоположные знаки: −11.6% относительно короткого старого окна или +20.4% относительно старого lifetime-среднего. **Ни одно число не следует публиковать как эффект релиза.** Полезная работа также различалась: старые 12 observations / 2 events / 9 HTTP attempts за 31.1 секунды против новых 225 / 1,093 / 217 за 300 секунд. В новом окне есть крупная пачка событий. WAL вырос с 61,917 до 173,064 байт/с при иной записи и числе full-page images; это не доказательство регрессии WAL.

Фаза минутных работ особенно существенна. В 20:13:00–20:13:30 и 20:14:00–20:14:30 не было ни одного canonical sweep; они начались в 20:13:37.485 и 20:14:36.422. Сравнение «первых 30 секунд каждой минуты» ошибочно приписало бы перенос работы ускорению. Пятиминутное окно включает пять полных проходов, без обрезания первого или последнего.

## Полный canonical sweep не ускорился доказуемо

| Выборка | Проходов | Средняя длительность | Медиана | Диапазон |
|---|---:|---:|---:|---:|
| До релиза, сохранённые 30 минут | 30 | **12.149 с** | неизвестна | максимум 15.053 с |
| После релиза, основное окно | 5 | **12.762 с** | 12.380 с | 11.382–14.923 с |

Новое среднее арифметически на 5.05% выше. Это не установленная регрессия: распределение старых значений не сохранено, объём и состав работы отличаются. Нельзя исключить длинный проход как «выброс» для получения нужного вывода: он обработал 923 новых события и 686 повторных событий.

За новые пять проходов: scanned 20,106; skippedUnmapped 20,000; appended 1,090; deduped 1,001; stamped 106. `errored`, `skippedUnavailable`, `skippedUnparseable` и `partitionBlocked` равны нулю; `truncatedByBudget` везде false. DB зарегистрировала 1,093 inserts в domain_events, что не обязано совпасть с 1,090 appended только данного обработчика. В старом baseline scanned объединяет canonical и projection логи; делить старую длительность на него и называть результат стоимостью одной canonical observation некорректно.

Дополнительные шесть прогретых проходов до основного окна (20:06–20:11) имели среднее 11.499 с. Их нельзя выборочно подставлять вместо заранее выбранного пятиминутного окна. Вместе эти наблюдения показывают естественную вариативность, а не уверенное изменение производительности всего прохода.

## API метрик: сильный локальный результат, ограниченный производственный baseline

`metrics-api-latency-live.json` действительно содержит один warmup и пять успешных измерений существующего API через loopback. После warmup: **медиана 35.953 мс, минимум 28.669 мс, максимум 54.471 мс**. Первый запрос — 142.573 мс. Во всех ответах 2,670 точек, 89 серий, не более 30 точек на серию, одинаковый размер ответа 288,573 байта.

Старые два точных совпадения SQL `listRecentOpsMetricSamples` занимали 10.139 и 12.932 секунды. Честная формулировка: **«Старый запрос к истории метрик попадал в логи с временем 10–13 секунд; сейчас весь прогретый API метрик отвечает примерно за 29–54 мс на сервере»**. Это разные слои и непарные наблюдения, поэтому не нужно превращать их в точный коэффициент ускорения, p95 или процент экономии CPU.

На production индекс валиден и ready. Но `read_only` не имеет SELECT на `ops_metric_samples`, и сохранённый `postdeploy-final.json` явно помечает EXPLAIN как skipped. Не писать, что производственный план был проверен или что SQL на production занял 0.5 мс: такие числа относятся к локальному парному benchmark. Файл `metrics-plan-failure.json` — старый локальный неудачный вариант плана на другой выборке, его нельзя принять за production plan финального решения.

Локальный финальный benchmark также проверен: одинаковый результат на 1,000,002 строках, 88.627–96.447 мс у старого SQL и 0.475–0.613 мс у нового. Его `rowsVisited = 617` получено суммированием `Actual Rows × Actual Loops`, в том числе `27 × 22`; это оценка из округлённых средних EXPLAIN, а не точный census посещённых записей. Для отчёта корректнее «около миллиона → около 620 по счётчикам плана».

Дополнительный `postdeploy-cleanup-and-index-ddl.json` подтверждает, что запись 8,823.616 мс при старте относится к `CREATE INDEX CONCURRENTLY` ожидаемого индекса. Это не медленный SELECT финального пути.

## Следующая узкая цель профилирования обоснована

За новое окно таблицы семейства observations дали **91,060,468 index tuple fetch**, или **18,212,094 за полный минутный проход**. Это **95.69% всего наблюдаемого table-level idx_tup_fetch**. В старом занятом окне было 18,114,412, что соответствует примерно одному проходу: величина на проход сохранилась, а не исчезла.

Большая часть находится в primary key индексах трёх партиций:

| Индекс | Fetch за пять минут |
|---|---:|
| observations_2026_08_pkey | 37,176,885 |
| observations_2026_07__skinny_pkey | 31,991,066 |
| observations_2026_09_pkey | 14,472,137 |
| Три parse_version_received_at индекса суммарно | 7,061,708 |

Почти весь этот объём прирастает именно в полуминутках с canonical sweep: примерно 18.20–18.23 млн против почти нуля в соседних полуминутках без него. Однако одновременно работают и другие минутные задачи; это сильная корреляция, а не атрибуция каждого fetch одному SQL. `idx_tup_fetch` — повторные обращения к heap tuples, не уникальные факты, не SQL round trips и не число физических чтений. Table- и index-level суммы не обязаны совпасть из-за разных правил учёта, в частности bitmap scans. Поэтому 95.69% нельзя назвать долей CPU или всей физической дисковой нагрузки.

**Рекомендованный следующий шаг:** профилировать список кандидатов канонизации `listObservationsForReplay` (`packages/db/src/repositories/domain-events.ts:1012`) на один полный sweep с разбивкой по family, pass и позиции cursor. Его `ORDER BY o.id` вместе с source/kind/parse-version фильтрами — конкретный кандидат на дорогой обход PK для бедных или пустых результатов. Нужны длительность и число вызовов каждого SQL shape, число возвращённых строк, `EXPLAIN (ANALYZE, BUFFERS)` для самого дорогого shape и сравнение первой/глубокой страницы. Отдельно проверить владельца parse_version_received_at обходов, а не заранее приписывать их тому же запросу. Использовать только разрешённый read plane; при отсутствии доступа воспроизвести план на изолированной копии, не расширяя роли и не переключаясь на superuser.

Этих данных достаточно для постановки такого узкого профилирования. Их недостаточно для назначения нового индекса, изменения fair scheduling или объявления конкретного SQL корневой причиной без плана. Контроль будущего изменения должен сохранить тот же объём capture/replay, явную обработку unmapped и текущие границы erasure.

Batching тела тоже нельзя оценивать по числу PK probes: один batched SQL по-прежнему выполняет несколько индексных поисков. Производственные 20,000 probes старого каталога за пять проходов не опровергают уменьшение SQL round trips; восьмикратное сокращение запросов доказано отдельным локальным тестом, не этими table counters.

## Допустимые итоговые формулировки

- «API метрик сейчас отвечает за десятки миллисекунд; до исправления соответствующий старый SQL наблюдался с временем 10–13 секунд».
- «Сервисы потребляли в среднем около 0.53 CPU-ядра в пятиминутном окне. Общий процент экономии после релиза пока не установлен».
- «Весь проход канонизации остался примерно на уровне 12–13 секунд; полезная обработка продолжается, ошибок и бюджетного обрыва в пяти проходах нет».
- «Следующий заметный резерв — повторные обходы observations: около 18.2 млн обращений за минутный цикл. Следующим шагом измеряем конкретные запросы и планы».

Не одобряются формулировки «сервер разгрузился на 12%», «канонизация ускорилась в три раза», «API ускорился ровно в 300 раз», «исчезли все регрессии» или «96% CPU тратится на observations». Последняя цифра описывает только долю выбранного счётчика чтений.
