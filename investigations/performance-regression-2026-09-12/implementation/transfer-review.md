# Проверка медленной передачи production-образа

Проверено 2026-09-12, примерно 22:52–22:55 MSK. Анализ read-only; текущий деплой не останавливал, сеть и конфигурацию не менял. Локальный замер сжатия завершён.

## Факты

- `load_candidate_image()` в `scripts/deploy-production.sh:1155` передаёт `docker save | ssh docker load`. SSH-сжатие отключено.
- Соединение PID 57980 шло через `utun6`, MTU 1420, RTT 156–178 мс. За два снимка nettop (52.97 с) bytes_out вырос с 31,816,202 до 36,229,370: около 83 KB/s. Общий повторно переданный объём во втором снимке — 1,127,232 байта, около 3.1% bytes_out. CPU процессов `docker save` и `ssh` около 0%.
- Это подтверждает медленную передачу по текущему маршруту. Конкретную причину ограничения внутри VPN/провайдера эти показания не устанавливают.
- Полный локальный `docker save` точного candidate дал 364,143,616 байт. gzip level 1 уменьшил его только до 361,412,105 байт (0.75%, 6.3 с). Сжатие не является полезным решением для этого образа.
- Координатор отдельно проверил ProxyJump через личный `winpc`: случайные 2 MiB дошли до `wc -c` на VPS за 1.38 с вместе с подключением, exit 0, точный размер. Данные на промежуточный диск не сохранялись. Это существенно быстрее наблюдаемого текущего маршрута.

## Безопасный путь повторного запуска

Текущая стадия `Loading` находится до quiesce, миграций, синхронизации release-файлов и переключения сервисов. При свежем подтверждении этой стадии и PID допустим TERM только дочернему SSH-процессу передачи. Закрытие pipe завершает `docker save`; `pipefail` возвращает ошибку из `load_candidate_image`; вызывающий `fail` при `STACK_RECREATED=0` и `LEGACY_SYNC_QUIESCED=0` не меняет сервисы. EXIT-trap `cleanup_deploy()` освобождает принадлежащие этому запуску locks и локальный TEMP_DIR.

Перед новым запуском необходимо дождаться завершения старого deploy, проверить освобождение обоих locks и прежние healthy-сервисы. Не использовать SIGKILL родительского bash и не запускать второй deploy одновременно.

Подготовленный координатором `deploy-via-winpc.sh` проверен: экспортируемая bash-функция вызывает абсолютный `/usr/bin/ssh -J winpc`, затем `exec bash` запускает неизменённый штатный deploy-скрипт. Функция наследуется всем прямым SSH-вызовам скрипта; рекурсии нет. Репозиторий, общая SSH-конфигурация и системные маршруты не меняются. `-o ForwardAgent=no` можно добавить для явного закрепления этого свойства.

Штатный повторный full build использует локальный Node-base после runtime-проверки, без обязательного pull, и BuildKit cache. Не следует обходить его health, rollback и migration gates.

## Проверка идентичности runtime

Исходный образ:

- revision: `96a86c1fcdde`
- runtime manifest: `sha256:6598104f9f2afae8854d65ef22b1a6e127ade36c26eb1fb24d875ddc94e2942a`
- config: `sha256:b1ab65c7e0a2cd2ed15a20e6e1d1968d52bcc9e71e16794a8fdffea868f2a79f`
- manifest list / docker inspect Id: `sha256:7b716b3c712b0fe0aae57cf08a32fa5d54eb74130dbc8a377935c96cbe767bc8`

BuildKit экспортирует attestation отдельно; новый manifest-list ID после cached build может отличаться из-за неё. Для подтверждения той же программы сравнивать runtime manifest/config/RootFS, revision и dependency checksum, а не требовать совпадения только верхнего manifest-list ID.

Вывод: при подтверждённом быстром ProxyJump повторный запуск через task-local SSH override обоснован. Стоперов в проверенном callpath не найдено; сжатие почти ничего не экономит, а ожидание на прежнем маршруте могло занять ещё около часа.

## Дополнение: оставшийся remote docker load

После штатного завершения локального первого deploy старая SSH-сессия осталась на VPS. Координатор сопоставил её в 19:59:41 UTC: peer `194.58.37.39:59294` → sshd PID `899859` → дочерний `docker load` PID `899926`. Новый поток: peer `91.197.106.248:17275` → sshd `908186` → docker load `908206`. Независимый read-only `ps` подтвердил две пары PID/PPID и различие времени жизни (~15 и ~4 минуты). Установленный daemon сообщил версию 29.6.1.

Новый поток остановился после ~5.98 MB. Гипотеза: оставшийся старый импорт удерживает ресурс загрузки, которого ждёт новый. Сам факт ожидания конкретной блокировки этими снимками не доказан.

Разрешённый узкий cleanup: непосредственно перед сигналом повторно сопоставить старые peer, PPID, полную команду `docker load` и время запуска; отправить TERM только PID 899926. Не трогать новый PID 908206, dockerd, sshd целиком или контейнеры. Это завершает orphaned клиент импорта и закрывает его собственные дескрипторы. В [исходнике Docker CLI](https://github.com/docker/cli/blob/master/cli/command/image/load.go) путь load передаёт stdin в один `ImageLoad`-запрос daemon; публичный master использован только для понимания клиентского пути, не как доказательство точного механизма блокировки установленной версии.

Ожидаемое подтверждение восстановления: старый PID исчезает, bytes_received новой SSH-сессии снова растёт и текущий deploy продолжает работу. До такого наблюдения нельзя считать import-lock гипотезу установленной причиной. Если новый поток не продвинется, это основание для дальнейшей read-only диагностики, а не расширения cleanup.
