# Средний CPU до фиксов за первые 45 минут контейнеров

**Да, по сохранённым данным можно восстановить обоснованную приближённую оценку: около 0,443 CPU-core суммарно для PostgreSQL, worker, API и scheduler.** Это среднее от их текущего старта, включающее запуск и диагностику. Оно не является замером только прогретого режима или доказательством причинного эффекта фиксов.

Предыдущее утверждение «длинного CPU baseline нет» было слишком категоричным. Нет длинного интервала с двумя измеренными границами счётчика, но есть его накопленное значение и дата старта того же контейнера. Это позволяет вычислить среднее при явно указанных предпосылках.

## Расчёт

Источник: [production-performance-snapshot.json](../followup/production-performance-snapshot.json), `identity`, `before.cpu`, `before.at`. Снимок сделан **12 сентября 2026, 16:35:59.915 UTC**. Три runtime-контейнера имеют ревизию `31b73a9691f3`; PostgreSQL не имеет source-revision label.

`CPU-core = usage_usec / 1 000 000 / (время снимка − StartedAt этого контейнера)`

| Сервис | StartedAt, UTC | Возраст, с | CPU за жизнь, с | Среднее CPU, ядра |
|---|---|---:|---:|---:|
| PostgreSQL | 15:50:34.642 | 2725.273 | 808.0918 | **0.296518** |
| Worker | 15:50:46.228 | 2713.687 | 338.1062 | **0.124593** |
| API | 15:50:40.388 | 2719.528 | 44.4385 | **0.016341** |
| Scheduler | 15:50:40.369 | 2719.546 | 16.0231 | **0.005892** |

Сумма средних, нормированных на собственные возрасты: **0.443343 ядра**. Возрасты отличаются максимум на 11,586 секунды, поэтому это сумма чуть разных временных интервалов.

Для одного общего интервала от старта PostgreSQL **15:50:34.642–16:35:59.915 UTC**, 2725.273 секунды, правильная агрегированная форма — **1206.6596 CPU-секунд / 2725.273 = 0.442766 ядра**. До старта каждого из остальных трёх новых контейнеров их CPU в этом интервале считается нулём; старые контейнеры сюда не включаются. Разница двух способов суммирования — 0,13%; для понятного отчёта оба округляются примерно до **0,44 ядра**.

Контроль по `after`, на 31,101 секунды позже: общий интервал 2756.374 секунды, 1225.4415 CPU-секунд, **0.444585 ядра**. Сумма отдельных средних — 0.445154. Это подтверждает арифметическую согласованность, но не создаёт второй независимый 45-минутный эксперимент.

## Почему расчёт допустим

`cpu.stat` считает CPU процессов соответствующей cgroup, в микросекундах, включая user/system time. Время CPU и wall uptime — разные единицы; их отношение и даёт среднее число занятых ядер. CPU нескольких процессов суммируется, поэтому величина в принципе может превышать одно ядро. [Документация Linux cgroup v2](https://cdn.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

Сохранены разные container IDs и разные CPU counters для четырёх сервисов, `restarts = 0`. Для API/worker/scheduler одинаковые StartedAt и revision повторяются в снимках 16:15, 16:36, 17:00 и 19:37 UTC. Последние два state-снимка также сохраняют одни PIDs, `FinishedAt = 0`, running и отсутствие pause/restarting/OOM. Это хорошее подтверждение непрерывности обычного Docker lifecycle; одних `restarts = 0` для этого было бы недостаточно.

В эталонном коде Docker/Moby StartedAt берётся из wall-clock времени около создания/старта task: метка записывается до NewTask, затем передаётся в SetRunning после task.Start. Поэтому это разумная приближённая начальная граница CPU учёта, но не измеренная дата рождения kernel cgroup. Проверена семантика опубликованного Moby v28.3.0, а не версия установленного на сервере engine. [start.go](https://raw.githubusercontent.com/moby/moby/v28.3.0/daemon/start.go), [state.go](https://raw.githubusercontent.com/moby/moby/v28.3.0/container/state.go).

## Пределы пригодности

1. **Старт и cgroup.** В артефактах нет события создания cgroup, её inode/начального нуля и полной истории pause/manual stop/start. Нет признаков внешней замены task, checkpoint restore или переноса процессов; обычная связь текущего контейнера с текущей cgroup — рабочее предположение. При таком внешнем вмешательстве оценку надо пересмотреть. StartedAt и CPU нельзя механически брать от разных жизненных циклов.
2. **Часы.** StartedAt и snapshot.at — wall clock, точного monotonic timestamp старта нет. На сохранённом коротком интервале wall и monotonic расходятся всего на 22,67 микросекунды, однако это не доказывает отсутствие более раннего скачка часов. Ошибка возраста в 10 секунд изменила бы результат примерно на 0,37%; это иллюстрация чувствительности, не измеренный предел ошибки. CPU читается немного позже timestamp начала snapshot, поэтому точность до многих знаков здесь условна.
3. **Запуск и миграции.** Среднее включает запуск PostgreSQL, recovery, приложения, миграционные проверки, прогрев, первоначальный backlog, healthchecks и диагностику. При этом сохранённая дата применения последней старой миграции 0185 — **12:10:58 UTC**, до старта этих контейнеров в 15:50; нельзя объяснять всё старое среднее новой DDL 0185 внутри окна. CPU в момент готовности после прогрева не сохранён, вычесть стартовую стоимость невозможно. Новый релиз с построением индекса 0186 имеет другой стартовый профиль.
4. **Причинность.** За эти 45 минут были диагностические чтения, включая старый дорогой SQL метрик. Их стоимость отдельно не выделяется. Нельзя сопоставить это старое среднее от старта с новым прогретым пятиминутным окном и назвать всю разницу экономией фиксов. Это допустимое описательное сравнение с указанными окнами и объёмами работы.
5. **Охват.** Это фактически полученное CPU четырёх сервисов, не CPU demand, I/O wait, latency или загрузка всего хоста. Другие контейнеры/host daemons исключены. Длинные DB/WAL/temp rates так восстановить нельзя: эти счётчики накоплены ещё до начала текущих контейнеров.

**Рекомендуемая формулировка:** «До фиксов эти четыре сервиса расходовали в среднем около 0,44 ядра за первые 45 минут после предыдущего запуска; отдельно измеренная занятая полуминута давала 0,60 ядра. Новое наблюдение сравниваем с обоими контекстами, не выдавая разницу за контролируемый A/B». Делать процент от всех CPU хоста можно только с подтверждённым числом vCPU и отдельно оговорённым охватом сервисов.

Подробная арифметика, raw counters, подтверждающие состояния и предпосылки: [performance-lifetime-baseline-review.json](performance-lifetime-baseline-review.json). Production для этой проверки не опрашивался; использованы только сохранённые файлы и публичная первичная документация.
