## 1. Последний завершённый запуск: лучший первый кандидат

Сейчас `listSyncMonitorStreamRows` ранжирует исторические ключи завершений через `row_number()`, выбирает победителя и лишь затем читает его payload. Предыдущее исправление уже убрало чтение исторических payloads, но не ранжирование всей истории.

Предложение: для каждого уникального рабочего ключа `(page_id, stream)` получать один id с порядком `finished_at DESC, id DESC` через подходящий частичный индекс. Полную запись по PK читать после выбора. Дедупликация применяется только к ключам работы, исходная кратность строк ответа сохраняется.

Кандидат индекса: `(page_id, stream, finished_at DESC, id DESC) WHERE outcome <> 'running' AND finished_at IS NOT NULL`. Без stats/error в INCLUDE.

| Модель: 240 тыс. исторических запусков | Исходный вариант | Кандидат |
|---|---:|---:|
| Время компонента | 35–37 ms | 0.034–0.083 ms |
| Local Blocks | около 2976 | 31 |
| Дополнительный индекс | — | 9.76 MB в модели |

Один индекс без изменения SQL почти не помог: основной выигрыш даёт изменение способа выбора победителя. Полный monitor-запрос на production ещё не измерен; из этих чисел нельзя получить ускорение страницы в сотни раз.

Проверены равные finished_at с разными id, running с заполненным finished_at, NULL finished_at, отсутствующие запуски, старые завершения, повторённый stream у вызывающего кода. Полные результаты модельных запросов совпали; полный ответ приложения ещё не проверялся. Независимое ревью не нашло семантического контрпримера в прототипе.

Архитектурно это локальное изменение чтения. У `sync_runs` уже индексируются finished_at и предикат outcome='running', поэтому новый индекс не впервые делает переход running→terminal несовместимым с HOT. Однако дополнительная запись индекса и его размер остаются расходами.

**Решение:** готовить отдельный application fix с forward-only миграцией после выбора свободного номера на актуальной ветке. При переносе сохранить фильтры страниц/платформ/RBAC, порядок, конечные LEFT JOIN, типы и payload после выбора id. Проверить реально сгенерированный полный SQL, пустые scopes, несколько страниц и полный ответ сервиса. Затем отдельное ревью diff, обязательные проверки репозитория, отдельный коммит и контролируемый релиз в рамках согласованного процесса. Исследование само миграцию не применяет.

## 2. Здоровье HTTP-попыток: чтение можно сузить, индекс выбирать осторожно

Текущий код читает всю сохраняемую историю выбранных потоков, вычисляет последний success оконной функцией, затем recent-счётчики и исторический долг. В актуальном каталоге есть отдельный started_at и run-id индексы, но нет подходящего page/stream индекса.

Правильное разбиение в одном SQL snapshot:

1. Последний success по всей сохраняемой истории.
2. Отдельный recent-диапазон для последних суток.
3. Отдельный диапазон долга строго после последнего success; если success отсутствует — вся история этого ключа.

Первый прототип был недостаточно хорош: он сократил время примерно с 35 до 29 ms, но увеличил обращения к буферам с 1775 до 14211. Actual plan показал две причины: LIMIT выбирал глобальный started_at индекс и фильтровал чужие страницы; условие `last_success IS NULL OR started_at > last_success` оставалось фильтром после широкого чтения.

После независимого review точный поиск закреплён полным порядком ключей; NULL/non-NULL ветви долга разделены и взаимно исключают друг друга. Для простого индекса обе границы tuple ограничивают поиск своим ключом. У partial-success варианта внешний equality отвергает возможную первую строку следующего ключа.

| Профиль | Старый SQL | Новый SQL с простым индексом |
|---|---:|---:|
| В основном старая история | 35–38 ms /1775 blocks | 0.31–0.40 ms /99 blocks |
| 24 потока и 200 тыс. дополнительных failures без единого success | 278–283 ms /45538 blocks | 55–56 ms /4830 blocks |
| 24 потока, почти вся история попадает в recent | 233–260 ms /86579 blocks | 79–87 ms /43649 blocks |

Это пары на одинаковом наборе индексов внутри своего профиля. Между профилями и наборами индексов planner выбирал разные планы. Вариант с покрывающим и partial-success индексами в recent-профиле ускорился по времени, но увеличил buffer accesses с 3539 до 43906. Следовательно, нельзя обещать универсальное снижение чтения от любого из вариантов.

Простой кандидат индекса: `(page_id, stream, started_at DESC)`. Он сохраняет возможность HOT при обновлении state. У него остаётся цена: без success поиск должен пройти историю своего ключа, а recent/debt могут физически перечитать пересекающиеся диапазоны. В модели это всё равно было быстрее; на production требуется оценить действительную частоту чтения и завершений запросов.

Отдельный опыт на 10 тыс. UPDATE, обычные локальные таблицы с fillfactor=60:

| Набор индексов | HOT updates | WAL | UPDATE time |
|---|---:|---:|---:|
| Аналог нынешних | 6544 | 3.06 MB | 28 ms |
| Плюс простой page/stream/time | 6544 | 3.54 MB | 43 ms |
| Covering state плюс partial success | 0 | 7.22 MB | 72 ms |
| Один индекс с state в ключе | 0 | 6.29 MB | 62 ms |

Это демонстрация механизма и цены индексов, не production HOT-процент: fillfactor и форма обновления заданы моделью; реальное завершение также меняет responseShape и другие поля. Индекс по изменяемому столбцу лишает UPDATE возможности HOT; для HOT также нужно место на странице. [PostgreSQL16 HOT](https://www.postgresql.org/docs/16/storage-hot.html).

Проверены: recent/stale точные границы, одинаковое время success/failure, будущий success, отсутствие попыток, очень старый долг, '-infinity', отсутствие success с существующим success у соседнего ключа. Recent и debt вычисляются отдельными aggregates; UNION ALL соединяет только взаимоисключающие NULL/non-NULL ветви долга. Срезать долг последними 24 часами или заменять отсутствие success временем '-infinity' нельзя.

**Решение:** второй кандидат, предпочтительно с одним простым индексом. Не принимать два state-sensitive индекса только ради быстрого SELECT. До реализации/приёмки нужны полный repository SQL, сохранение ::int/public types и snapshot, план на характерном объёме страниц, цена INSERT/UPDATE и реальный read/write баланс. Это не готовый к деплою патч.

## 3. Golden signal: два популярных варианта не обоснованы

Метрика считает p50/p95 задержки по событиям, добавленным за последние 10 минут, с весом каждой строки JOIN. Sampler запускается раз в минуту; HTTP endpoint читает уже сохранённые samples. Прямо ограничивать старые observations или партиции нельзя: replay старой записи должен оставаться видимым.

Проверка принудительного LATERAL-соединения:

| Недавние события | Старый SQL | Принудительный LATERAL |
|---|---:|---:|
| 100 событий /100 разных observations | 17–18 ms | 18 ms |
| 200 тыс. событий /200 тыс. observations | 205–245 ms | 937–941 ms |
| 200 тыс. событий /100 observations | 185–198 ms | 134–135 ms |

При разных observations кандидат выполнял 2.6 млн обращений к листовым партициям, а исходный SQL выбирал hash join. При повторении observations помогал Memoize. **Универсальный LATERAL отклонён: семантической правильности недостаточно, он регрессирует примерно в 4.2 раза на массовой обработке.**

Также проверен covering btree по created_at. Сначала у существующего BRIN явно заполнены summaries только в локальном fixture. После этого малое окно исходный SQL считал примерно за 0.5ms; btree дал лишь небольшую абсолютную разницу. На больших окнах planner вовсе не использовал новый индекс, buffer count не изменился. Индекс не обоснован.

Локальный эффект summarization стал новой диагностической гипотезой. Он **не доказывает**, что production BRIN требует обслуживания. BRIN summaries создаются и обновляются по определённым правилам; наличие индекса само по себе не доказывает качество отсева страниц. [PostgreSQL16 BRIN](https://www.postgresql.org/docs/16/brin-intro.html).

**Решение:** сейчас оставить SQL/schema. Следующий шаг здесь — разрешённые доказательства actual plan, распределения recent events, BRIN summary coverage и обслуживания, без обхода ACL и без production VACUUM/ANALYZE/summarization «на всякий случай». Подробный [разбор исследователя](/Users/dmitriy/code/goose/hub/investigations/performance-research-2026-09-13/golden-signals-research.md).

## 4. Replay: текущий вариант сохраняем, новый универсальный алгоритм не принимаем

Захвачены 30 реальных SQL-форм текущего repository-кода: семейства, head/deep и режимы unparsed/replay. Для экспериментального семейства baseline также сгенерирован самой функцией, не перепечатан по памяти.

Кандидат: перечислить фактически существующие версии, взять top200 каждого `(version,kind)` через новый индекс, объединить в общий top200 и получить payload по `(id,received_at)` в одном SQL. Это сохраняет порядок по id при соблюдении границ; JOIN только по id размножает записи и был пойман отрицательным контролем. Microsecond timestamps нельзя передавать через JS Date для обратного соединения.

| Нагрузка, всего 300 тыс. observations | Текущий вариант | Prefix-прототип |
|---|---:|---:|
| Осталось 100 записей | 0.15–0.18 ms | 0.34–0.41 ms |
| Большой плотный backlog с начала | 0.22–0.31 ms | 1.01–1.19 ms |
| Осталось 30 тыс. записей в конце | около 26 ms | 176–177 ms |
| 1000 разных допустимых parse_version | около 0.3 ms | 261–293 ms |
| Нет работы | около 0.1 ms | около 0.1 ms |

В tail-прототипе планировщик снова выбирал невыгодный доступ; само добавление индекса его не устранило. Many-version случай показывает структурный риск перечисления всех prefixes вместо ранней остановки. Отдельное упрощение «сначала материализовать всё ожидающее, потом сортировать» на плотном backlog замедлилось до 116ms и записало 8154 временных 8KBблоков. Такие решения нельзя внедрять универсально.

Oracle проверил отрицательные и разреженные версии, разные source/kind, дубликаты kinds, id с разными received_at вплоть до микросекунд, несовпадение хронологии и id. Равные id непосредственно на границе LIMIT имеют unspecified порядок в исходном SQL; полной одинаковости выбранных физических строк для этого случая не обещаем. Новый tie-breaker означал бы отдельное изменение контракта. Source-free, account/exact/time/deep scopes, dynamic limit/version bounds должны сохранять исходный fallback и отдельно тестироваться при любом будущем переносе.

**Решение:** действующий guard 315 сохраняем. Медленное историческое выполнение 2.085s не воспроизведено с известными теми же параметрами; назвать его исправленной ошибкой нельзя. Для следующего шага нужны безопасные query-shape/границы/cursor/rowcount и фактический план конкретного медленного вызова. Текущий standalone прототип не идёт в приложение.

## Дополнительные факторы и план приёмки

- **Частота и реальные потребители.** `useSyncMonitor` объявляет 10-секундный polling, но в текущем dashboard исходнике не найдено его использования: считать это текущим потоком запросов нельзя. Есть активные отдельные hooks overview/page/message blocks; overview уже сужен до dm_messages, preview — до DM streams. CLI и sync/status тоже вызывают полный monitor. Рекомендация — атрибутировать фактические обращения перед оценкой экономии, не умножать максимальное время на число потенциальных hooks.
- **Prepared plans.** `Database.execute` в установленном Drizzle вызывает prepareQuery с name=undefined; node-postgres не получает именованный запрос. Проблему generic-plan cache отдельного Python-exporter нельзя автоматически объявить причиной runtime SQL. Глобальный force_custom_plan не предлагается. [node-postgres: named prepared statements](https://node-postgres.com/features/queries).
- **Не удаляем полезную работу.** Audience/message счётчики используются в monitor response. Удаление точных счётчиков, исторического долга, sampler frequency или редких событий меняет продуктовый контракт. Приближённые оценки, кэш и материализованная projection требуют отдельного решения по свежести, RBAC, erasure, восстановлению и инвалидации; сейчас они не оправданы.
- **Не вмешиваемся в capture.** Новые схемы чтения должны сохранять capture→canonicalization→projection, однообразное продвижение durable cursors и изоляцию exact/dry-run replay от фоновых курсоров. Никаких новых provider-запросов, повторной отправки сообщений, удаления истории или ремонта данных ради бенчмарка.
- **Следующий замер.** Для каждого принятого фикса отдельно: исходный/новый полный SQL на одинаковых данных, фильтрах и cutoff; фактические планы, buffers, heap fetches, temp spill, planning/execution, query count, rowcount. Затем сопоставимые production-окна по объёму входящих observations/events/attempts, конкурирующим диагностическим запросам, CPU каждого процесса, WAL/диску, latency и свежести сигналов. Таймаут старого запроса — нижняя граница, не измеренная длительность. Одних wall-time чисел и зелёных старых тестов недостаточно.

Первая очередь — **completion lookup**. Вторая — **attempt health с одним простым индексом**, если подтверждается баланс полного чтения и записи. Golden/replay остаются диагностическими направлениями с отклонёнными универсальными прототипами. Применение новых фиксов, независимое ревью application diff, отдельные коммиты и релиз — следующий этап, не результат этой исследовательской фазы.
