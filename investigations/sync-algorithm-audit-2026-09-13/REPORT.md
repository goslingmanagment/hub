## 3. Три приоритетных исправления

### F1. Backfill транзакций не восстанавливается после изменения total

**Код:** [transactions.ts:1247](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/transactions.ts:1247), обработка ошибки около строки 1415 и возобновление сохранённого backfill около строки 1515.

Первая страница фиксирует `providerReportedTotal=200`, затем сохраняются `offset=100` и незавершённый backfill. После новой транзакции сервер возвращает total=201. Обработчик корректно замечает изменение списка, но только бросает ошибку. Сохранённые total и offset не инвалидируются. Следующие попытки вновь сравнивают 201 с 200 и снова падают. `snapshotEnd` в checkpoint не делает offset-запрос снимком: запрос здесь передаёт только `limit` и `offset`.

**Воспроизведение:** три вызова реальной `syncTransactionsBackfill` дали offsets `[100,100,100]`, одинаковую ошибку изменения total и ноль записей сброса checkpoint. См. [результат независимого повторного запуска](evidence/fansly-root-recheck.json), F1.

**Исправление:** на структурном изменении списка закрывать попытку обхода как несертифицированную, сохранять уже захваченные факты и создавать новый проход от головы. Применить подход инвалидирования, уже используемый incremental-путём. Не просто менять сохранённый total, продолжая старый offset: так можно замаскировать пропуски. Чтобы активный аккаунт не начинал весь обход бесконечно, отдельно реализовать обход по устойчивому курсору/границе, если провайдер это позволяет, либо перекрывающиеся проходы с доказуемым составом и ограниченным числом рестартов.

**Приёмка:** рост и уменьшение total после успешно записанной страницы; падение сразу до/после checkpoint; повторное получение страницы. Уже сохранённые транзакции сохраняются, курсор выходит из тупика, отсутствие дублей не подменяет проверку отсутствия пропусков.

### F2. Подписчики: равенство количества строк не подтверждает полноту

**Код:** [executor-handlers.ts:1493](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:1493), [финализация:1590](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:1590).

Обработчик складывает длины страниц и сравнивает результат с provider total. Список из 200 подписок может вернуть страницу 1 с ID 1–100 и страницу 2 с ID 100, 102–200. Сумма равна 200, но уникальных записей 199: ID 101 не получен. После этого `deactivatePageSubscriptionsByGeneration` деактивирует его как отсутствующий.

**Воспроизведение:** реальная `fanslySubscribersChunk` завершилась с `satisfied=true`; поддельно отсутствующая активная подписка 101 была деактивирована. Внешний API и хранилище подменены, управляющая логика обработчика выполнена из исходника. Это не просто арифметическая модель. См. F2 в [результатах](evidence/fansly-root-recheck.json).

**Исправление:** проверять число уникальных сохранённых subscription IDs поколения внутри той же транзакции, что и финализация; фиксировать межстраничные повторы и невставленные записи. Использовать ограничения, аналогичные более строгому followers reconciliation: без доказанного полного состава выполнять только недеструктивное обновление. Само равенство уникального количества total тоже не создаёт snapshot у изменяемого внешнего списка; при отсутствии snapshot/cursor-гарантий провайдера отсутствующие записи должны оставаться подозрениями до подтверждающего обхода или отдельного факта деактивации.

**Приёмка:** duplicate+omission при равном total, изменение total, пустая страница, пропуск после hydration, повтор после commit, действительно завершившаяся подписка. Проверять итоговые `page_subscriptions` и `page_fans`, а не только `satisfied`.

### F3. Совпадение с локальным DM не доказывает, что история дочитана

**Код:** [fansly-dm-messages.ts:39](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/fansly-dm-messages.ts:39), [executor-handlers.ts:3032](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:3032), разделённые транзакции около строк 3060–3135.

Для не-incremental режима `providerHistoryExhausted || overlapFound` возвращает `complete`. При deep backfill совпадение возможно с данными собственной предыдущей попытки, а не с доказанно полной историей.

Достижимый сценарий: summary считает oldest=200; следующая страница 199–175 записалась; вторая транзакция, обновляющая summary/checkpoint, не выполнилась. Повтор `before=200` получает те же 199–175. Они уже локально существуют, поэтому обнаруживается overlap и выставляется `complete`, хотя 1–174 ещё не запрашивались. Очередь ремонта может успеть исправить summary раньше и избежать конкретного случая, но атомарной гарантии такого порядка нет.

**Воспроизведение:** реальные функции получения страницы и определения coverage вернули `overlapFound=true`, `providerHistoryExhausted=false`, coverage=`complete`. Проверка полного executor с реальным аварийным завершением процесса не проводилась; окно сбоя подтверждено порядком двух транзакций в коде. См. F3 в [результатах](evidence/fansly-root-recheck.json).

**Исправление:** в deep backfill считать полным только доказанное исчерпание источника или стык с уже сертифицированным непрерывным диапазоном. Хранить устойчивую границу обхода/receipt страницы вместе с фактами; тяжёлый rebuild summary оставить отдельным. Не возвращать summary в транзакцию с фактами без анализа прежних ошибок constraint: разделение имеет обоснованную цель, неверно именно использование overlap как доказательства.

**Приёмка:** остановить исполнение между commit фактов и commit summary, затем повторить; coverage остаётся неполным и обход продолжается до настоящего конца. Дополнительно проверить пересекающиеся targeted/history проходы.

### F4. Известный media никогда не получает новый purchase-history проход

[executor-handlers.ts:3406](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:3406) строит множество targets по всей истории captures. При обнаружении новых purchase transactions [фильтр:3532](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:3532) исключает target, который когда-либо уже захватывался. Возраст результата и появление нового покупателя не меняют решение.

Контрпример реального handler: media однажды вернул пустую terminal history; позже transaction 11 сообщает о покупке того же media. `purchaseHistoryRequests=0`, transaction cursor продвигается до 11, `satisfied=true`. Сама финансовая транзакция сохранена; потеря всех PPV-данных во всех источниках не утверждается. Сломано обновление конкретного списка заказов/покупателей.

**Исправление:** разделить дедупликацию факта capture и право на новый refresh. Новая транзакция после target watermark делает media dirty; coalesce несколько покупок в один bounded head walk до подтверждённого known-order anchor. Хранить generation, последний успешный refresh и границу заказов. Проверить empty→first sale, second buyer, повтор после сбоя и завершённый старый tail с новой головой. Доказательство F4: [независимый повтор](evidence/fansly-root-recheck.json).

### F5. Stats guard проверяет локальный offset вместо прогресса ответа

[fansly-stats.ts:1709](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/fansly-stats.ts:1709) сравнивает previousOffset с offset, но после каждой полной страницы код сам сохраняет offset+100 и previousOffset=offset. Провайдер, игнорирующий offset и возвращающий ту же страницу, этот guard не активирует.

Контрпример реального handler с искусственным daily cap=3: за два дня offsets `[0,100,200,300,400,500]`, шесть одинаковых страниц, ноль repeat anomalies; оба дня завершаются исчерпанием лимита на step 2. Дневной cap работает, а downstream steps остаются недоступны. Факт такого поведения провайдера в production не установлен.

**Исправление:** сохранять fingerprint стабильных IDs/границ полученной страницы, сверять прогресс содержимого, иметь предел страниц/времени на step. При нарушении помечать соответствующее покрытие неполным и давать независимым следующим steps работу; не объявлять проблемный step полностью собранным. Для страниц с законно одинаковыми метриками fingerprint должен опираться на идентичности/границы, а не только значения сумм. Проверить ignored offset, нормальные одинаковые суммы разных записей, сутки/рестарт и продвижение последующих steps. Доказательство F5: [независимый повтор](evidence/fansly-root-recheck.json).

## 4. Повторы, пауза и справедливость выполнения

### C1. Потеря причины retry

[page-sync.ts:1925](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/page-sync.ts:1925) переводит созревшую попытку в pending с `retry_kind=null`. Далее [executor.ts:436](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor.ts:436) использует это поле для цепочки 404, а [executor.ts:295](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor.ts:295) — для снятия OFAPI credit incident.

В обычном маршруте через planner повторный 404 снова выглядит первым: `consecutiveFailures` сохранился, но проверяемый класс потерян. Восстановительный OFAPI chunk аналогично не узнаёт предшествующий 402. Это не означает, что incident никогда не снимется другим монитором: сломан конкретный предусмотренный путь восстановления.

**Исправление:** pending — готовность к исполнению, а причина прошлого отказа — отдельный сохраняемый контекст. Стирать её при подтверждённом успехе/новом независимом поколении, не при enqueue. Отдельно считать повторы одного класса: после серии 500→404 общий consecutiveFailures не равен числу 404. Проверить смешанные последовательности отказов. Приёмка должна проходить весь маршрут retry → planner → lease → error/success; тест одного classifier недостаточен.

### C2. Ручная пауза теряется при auth recovery

[pausePageSync:2831](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/page-sync.ts:2831) не меняет владельца уже auth-paused состояния так, чтобы последующая [clearPageSyncAuthBlock:2756](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/page-sync.ts:2756) сохранила ручное решение.

SQL-контрпример: auth pause → оператор Pause → recovery → `pending`. Область вывода — Fansly/generic auth recovery; исправленный OFAPI `ofapi_user_paused` путь не объявляется сломанным.

**Исправление:** хранить ручную паузу отдельно от технического блокера авторизации; восстановление снимает только свой блокер. Приёмка: обе последовательности manual→auth и auth→manual, а также повторная авторизация и явный Resume.

### C3. Просроченные разрешения rate limiter

[sync.ts:2712](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/sync.ts:2712) берёт локальное время до ожидания блокировки строки. Если ожидание превышает интервалы выдаваемых слотов, обе транзакции получают разрешения, которые уже в прошлом. Вызывающий код вычисляет нулевую задержку.

В тесте два клиента ждали один row lock, интервал был 100 мс, блокировка удерживалась 300 мс: оба получили `waitMs=0`. Это доказывает слабость гарантии pacing при задержке БД, а не реальный burst в production в момент аудита.

**Исправление:** вычислять свежий момент допуска после получения блокировок, предпочтительно DB-clock, и хранить будущую reservation. Для строгой гарантии проверять допуск непосредственно перед физической отправкой: остановка event loop уже после reservation также способна сжать интервалы. Проверки: задержка DB lock, задержка процесса, две ноды, перенос Retry-After и смена lease.

### C4–C5. Координация нескольких процессов

В установленном pg-boss воспроизведены две разные проблемы: две конкурентные выборки берут jobs одной группы до видимости чужого `active`; отдельно кандидат занятой группы попадает под `LIMIT 1` до фильтрации группы, и свободная следующая группа не выбирается. Локальные `activeGroupIds` и сериализация fetch защищают один процесс, но не составляют общий межпроцессный lock.

**Исправление:** отдельное атомарное владение egress lane либо подтверждённо корректный shared admission на уровне БД; выбирать допустимые группы до ограничения batch. Увеличение batch само по себе не устраняет гонку. Обновление зависимости допустимо только после прогона тех же контрпримеров на конкретной версии. Row locks и `SKIP LOCKED` защищают выбранные строки, но не произвольный агрегат «в группе сейчас ноль активных»: это согласуется с [семантикой Read Committed PostgreSQL 16](https://www.postgresql.org/docs/16/transaction-iso.html) и [правилами SELECT/locking](https://www.postgresql.org/docs/16/sql-select.html).

**Приёмка:** два независимых процесса, общая группа и независимая группа; барьер прямо перед commit fetch; один процесс падает; другой продолжает. Проверять и число активных chunk, и фактические timestamps сетевых отправок.

### R1. Ремонт проекций может голодать

[projection-debt.ts:61](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/projection-debt.ts:61) берёт самые старые unresolved debts, [projection-debt-sweep.ts:58](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/projection-debt-sweep.ts:58) обрабатывает не более 20. Ошибка увеличивает attempts/last_attempt, но сортировка остаётся по неизменному `first_seen_at`.

Двадцать постоянно ошибающихся записей навсегда вытесняют двадцать первую, даже если она уже ремонтируется успешно. Настоящий SQL-контрпример трижды выбрал первые 20; attempts последней записи остался равным 1.

**Исправление:** durable `next_retry_at`, backoff, выборка созревших задач и справедливая ротация; отдельное состояние требующих вмешательства без удаления фактов. Приёмка: 20 poison + 1 repairable, затем смешанные ошибки/успехи и рестарт worker.

## 5.1. OnlyFans и граница capture: отдельная оценка уверенности

**В действующем OFAPI mirror нового P1 не воспроизведено.** Проверены capture bytes до parse, отказ всей страницы на malformed message, обязательная pagination, подтверждённый anchor вместо произвольного overlap, а также отделение coverage proof от готовности archive serving. Дополнительный reproduction проверяет strict parser. Это положительные результаты по конкретным инвариантам, а не гарантия отсутствия других ошибок.

| Замечание | Основание и область | Исправление / обязательная проверка |
|---|---|---|
| O1, P2: stale audience REST может вернуть active после более нового expired webhook | Полный write path; DB-interleaving не воспроизведён. Audience пишет lifecycle поля через upsert без симметричного clock guard | Явная свежесть и владелец lifecycle-полей; задержать REST, применить webhook, затем отпустить REST и проверить final row |
| O2, P2: оставшиеся list collectors парсят до raw capture | `observedListRequest` делает JSON/list mapping до возврата в audience; ручной transaction backfill вообще не вызывает raw journaling | Провести их через capture receipt до parse; non-JSON/shape drift должен оставаться полностью воспроизводимым без нового HTTP |
| O3, P2: исторический pull DM parser теряет chat/direction | Реальные parser-функции расходятся на старом payload; область — retained legacy replay, новый mirror использует иной строгий путь | Scoped repair с сохранённой lineage и явными corrections; одного bump parser при прежнем dedup key недостаточно |

Точные цепочки, строки и ограничения: [события и OnlyFans](events-ofapi/REPORT.md). Сходный риск до-capture shape parsing найден в Fansly adapter: вычисление response summary может бросить ошибку до возврата raw в handler. Это статически установленная граница для дополнительной проверки, а не доказанная потеря полного production body.

Отключённый `executeOfapiDmMessagesChunk` отдельно воспроизвёл false complete на malformed item. Он не вызывается текущим platform registry; использовать его как rollback без исправления нельзя, но его ошибка не является текущим P1 mirror.

## 6. Оптимизации и улучшение архитектуры

| Изменение | Для чего | Как доказать пользу |
|---|---|---|
| Сначала согласовать рабочую ветку с production release | Не потерять уже работающие исправления при следующем релизе | Сравнить конкретные hot paths и запустить проверки на итоговом merge |
| Page-scoped выборка runnable вместо fleet-wide scan на каждый chunk | `resolveContinuationPriority` и `executeNextPageWorkChunk` запрашивают все страницы, затем ищут одну | Число SQL/строк и p95 времени chunk при 8/50/200 страницах |
| Aging/квоты между потоками одной страницы | FIFO страниц не мешает долгому более приоритетному потоку постоянно обгонять notifications/catalog | Максимальный возраст ожидания каждого lane при непрерывном backfill |
| Переход от счётчиков строк к типизированным доказательствам обхода | Единообразно различать done, overlap, truncation, parse failure и несертифицированный список | Общий набор adversarial pagination checks для каждого lane |
| Durable retry context и единая модель ручной паузы | Устранить потерю причин и конкурирующие владельцы состояния | Таблица переходов + реальные interleavings, а не тесты отдельных функций |
| Явный repair budget и честный head/history/projection status | Видеть незакрытые факты, даже когда HTTP и обычный sync зелёные | Возраст oldest debt, invalid rows, unresolved expected IDs, уровень сертификации coverage |
| Строго определить request/time budget | 5 запросов/45 с сейчас проверяются в точках цикла; один медленный вызов/его ретраи может пережить границу | Инъекция transport delay и проверка фактического числа отправок, времени и отмены |
| Ограничить повторные scan/parse/upsert на подтверждённых hot paths | Снизить CPU, WAL, pool occupancy и время удержания lease | Дельты операций, буферов и WAL на единицу полезно обработанных фактов |

**Не начинать с увеличения числа workers, сокращения интервалов polling или глобального повышения PostgreSQL memory settings.** Сначала устранить неправильное завершение обходов и доказать admission для выбранной топологии. Иначе более быстрый алгоритм будет чаще выполнять те же ошибки.

В production-ревизии уже есть отсутствующие в текущем `main` оптимизации: отмена HTTP при потере lease, ограничение лишнего follower count при preflight, изменения финализации sync, сокращение повторной canonicalization/чтения capture payloads, no-op fan writes и индексы hot paths. [Сравнение ревизий](evidence/deployed-vs-main.txt). Их наличие на сервере — основание использовать release-ревизию как точку сверки, а не повторно обещать эти изменения как новые результаты аудита.

План измерения оптимизаций: одинаковые ревизии и конфигурация внутри каждого окна; подтверждённые неизменные контейнеры и DB statistics epoch; фиксировать количество и тип полезной работы. Сравнивать HTTP на полученный факт, SQL/rows/buffers на chunk, WAL на изменённый факт, p50/p95 ожидания и долю времени в retry. Одного падения CPU на спокойном отрезке недостаточно.

## 7. Порядок исправлений

1. **Зафиксировать общий base с production.** Перенести/сохранить уже deployed исправления без автоматического выката всего текущего main. Составить окончательный diff будущего релиза.
2. **Исправить F1–F3 отдельными небольшими изменениями.** Сначала отрицательные регрессии, затем реализация. Проверять данные и coverage после повторов и сбоев. До исправления F2 не считать равенство raw count основанием для деструктивной финализации.
3. **Исправить C1, C2, F4, F5 и R1.** Сохранение причины повторов, независимость ручной паузы, обновление старых purchase targets, обнаружение повторных stats-страниц и справедливая очередь ремонта. O1/O2 подтвердить отдельными boundary-тестами перед изменением действующих OnlyFans collectors.
4. **Исправить pacing и межпроцессный admission.** Контрпримеры C3–C5 должны перестать воспроизводиться до масштабирования worker.
5. **Провести отдельный аудит последствий на реальных данных.** Найти незавершённые transaction walks с застывшим total; проверить подозрительные деактивации подписок; установить, какие DM complete появились после overlap/repair. Сначала read-only список кандидатов, затем узкий replay/reconciliation из сохранённого raw там, где он достаточен. Новые provider reads и production-изменения — отдельное действие владельца.
6. **Оптимизировать измеренные hot paths и добавить SLO полноты.** Canary одной страницы/потока, сравнимые окна и проверка данных, затем расширение. Нагрузку увеличивать только после проверки качества.

Для исправлений F1–F3 недостаточно изменить условие и получить зелёный unit test: нужен сценарий до/после commit и сравнение полученного множества IDs с эталоном. Для C4–C5 недостаточны два async вызова внутри одного сериализованного worker: нужны две независимые транзакции или процесса.
