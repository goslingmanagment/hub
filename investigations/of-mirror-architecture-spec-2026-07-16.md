## 1. Цель

Иметь в нашей БД **полный, доказуемо полный и свежий слепок** всего происходящего в
OnlyFans-аккаунтах (DM-план + массовые рассылки), чтобы вся работа — чаттеры,
дашборд, ИИ, аналитика — шла из нашей БД, а не через платные живые запросы к
вендору. Архитектура обязана **исключать петли и клины по построению**, а не
заплатками.

Целевое состояние чтений: БД — единственный источник; OFAPI остаётся для трёх
вещей — захват (вебхуки + дешёвые сверки), отправка (командный аутбокс, без
изменений), точечный ремонт дыр. Переход — через измеряемый гибрид (§7):
поверхность переводится на «только БД», когда доля платных fallback-чтений по
ней стабильно ≈ 0.

## 2. Охват

Входит:
- вся переписка: живая (уже захватывается вебхуками) + историческая (докачка по когортам);
- PPV-факты: цены, открытия, анлоки;
- массовые рассылки как объекты: кампания (агрегаты) → получатели только по
  эвидансу, tri-state поля с provenance (§5.3);
- уже синкающиеся планы (деньги, фаны, подписки) — без изменений, они вне этой спеки.

Не входит (осознанно, отдельные будущие решения): посты/лента, vault, стори,
комментарии, сами медиафайлы (только метаданные). Fansly не трогается вообще —
у него другая модель приобретения, она работает.

История — **по когортам, конечное состояние — весь флит** (v3, фикс
противоречия из ревью): когорты задают ПОРЯДОК, не финальный охват. Сначала
спендеры и чаты с реальной перепиской (сотни), затем активные, затем хвост. До
закрытия хвост остаётся **явным видимым coverage-долгом** (табло §9) — членство
в кампании историю чата НЕ сертифицирует (§5.3). Важно для решения по хвосту:
worst-case «~125k кредитов» считался от глубины 200 сообщений; для действительно
одно-сообщенческих холодных тредов экспорт стоит порядка сотен–полутора тысяч
кредитов (~8k тредов × 1–3 строки при 1 кр/20 строк). Фактическую цену даёт
котировка S5a — решение принимается на её числах, а не на worst-case.

## 3. Не-цели

- Никакого переписывания общего планировщика/executor/лизингов — они здоровы
  (доказано расследованием: лизинги, pg-boss, fairness не являются причиной аварий).
- Никакого **self-seeded unbounded** краула истории — ни сейчас, ни после
  фиксов. (Формулировка v3.1: bounded, бюджетированная пагинация по явным
  заданиям допустима и на масштабе флита — это fallback-бэкенд S5; запрещено
  само-порождение работ из состояния.)
- Никакого удаления улик: карантин-строки, health-записи, сырые захваты,
  observations остаются (family law: capture first, never delete).
- Legacy-краулер `dm_messages` не возвращается ни при каком откате.

## 4. Инварианты защиты от петель

**I0 — правило трёх исходов (несущее; из внешнего ревью).** Для
**background**-попытки после локального settlement (`awaiting_parse` разобран)
происходит ровно одно из трёх: (а) курсор действительно продвинулся; (б)
выставлен `next_attempt_at > now()`; (в) задание перешло в `blocked | complete`.
Немедленный возврат в `ready` при нулевом прогрессе запрещён; повтор того же
курсора/страницы несколько попыток подряд = `blocked_protocol`, а не новая
итерация. **Interactive**-попытка (у неё нет job/курсора) терминальна сама по
себе: `captured+served | captured_error | indeterminate` (§5.5/§5.6). I3 и I8
ниже — следствия I0.

Далее восемь правил для **любого** кода, говорящего с вендором. Каждое привязано
к конкретной случившейся аварии (указатели — на текущий код с дефектом).

## 5. Модель данных

Всё аддитивно; существующие таблицы не переписываются; имена финализируются по
конвенциям репо на этапе плана.

**5.1. Задание докачки (acquisition job)** — единица платной работы:

```
{ kind: chat_history | tail_reconcile | campaign_snapshot | head_repair | export_import,
  target — ЗАМОРОЖЕН при создании:
    chat_history:    (chat, anchor|depth) — фиксируется текущий head; новое сверху
                     приходит вебхуками и НЕ двигает финишную черту,
    tail_reconcile:  (chat, new_head, verified_anchor, max_pages, max_credits, reason) —
                     anchor не достигнут в лимитах → результат `gap_open`
                     (не ложная непрерывность и не рекурсивное новое задание),
    campaign_snapshot: campaign_id,   head_repair: (chat, message_id),
  target_generation: версия цели (новая голова после 404-блока = новая generation —
          снимает блок, но задание НЕ создаёт: I6),
  уникальность намерения (v3.1.1, фикс coalesce-противоречия): стабильный
          active_slot_key = (kind, page, chat) — partial-unique по активным
          состояниям; target_hash НЕ содержит new_head, generation — атрибут
          задания, не часть ключа. Сдвиг головы при открытом задании = no-op
          (head-факт уже записан; следующий проход стартует от нового head по
          новому НАМЕРЕНИЮ после terminal текущего задания),
  next_attempt_at: обязательное поле (I0-исход «б»),
  cursor: СВОЙ у каждого задания,
  pending_observation: (observation_id, observation_received_at) — PK журнала
          составной (партиционирование по received_at), одиночного id недостаточно,
  state: ready → leased → awaiting_parse → ready | complete
                       └→ retry_wait | blocked(_protocol|_auth|_notfound),
  исполнение (v3.1.1, выбор из ревью): вариант А — задания дренируются
          существующим executor'ом как новый SyncStream-чанк; page-lease =
          «лизинг» из I5, задание = единица намерения/курсора, чанк = единица
          планирования; per-page эксклюзивность и egress-fairness наследуются
          от pg-boss singletonKey/groupConcurrency, второй планировщик не
          строится; per-job CAS остаётся для повторной обработки awaiting_parse,
  lease_token + lease_until + CAS,  attempts + zero_progress_count,
  budget_credits + spent_credits (per-job),
  created_by: owner | cohort_seed | product_signal | interactive_open | anti_entropy_sample,
  результат: принято/отброшено строк, причина завершения,
             terminal_observation(id, received_at) }
```

Ключевое отличие: сегодня у страницы один чекпоинт на все чаты
(`schema.ts:534–557`) — два недокачанных чата не могут сосуществовать, прогресс
одного стирается работой над другим. Курсор в задании закрывает это.

**5.2. Доказательство полноты — терминальная observation + проекция покрытия.**
Отдельная таблица сертификатов НЕ создаётся (в v1 была — избыточно): append-only
хранилище доказательств в системе уже есть, это журнал. Завершение фиксируется
observation `capture.completed.v1` (далее по тексту «сертификат» = это событие):

```
{ scope: chat | campaign | page,
  source: export_artifact | pagination_exhausted | harvest_import,
  range: from(message_id/ts) → to  (стыковка диапазонов — anchor следующего задания),
  evidence: чексумма артефакта / EOF-страница вендора / счётчики строк,
  parse_debt: сколько строк источника не разобрано }
```

Обязательные поля терминального факта (из ревью): замороженный target/head;
точный запрос + версия source-контракта; версии парсера; ссылки на observations
или хэш цепочки страниц; счётчики raw/accepted/rejected; тип доказательства
(EOF / verified artifact / непрерывные anchors); `supersedes` для переразбора.
Различаются два класса фактов: `item_presence` (это сообщение есть) и
`continuous_history` (диапазон непрерывен) — наличие одного сообщения или
кампании никогда не является continuous-доказательством.

Терминальная таксономия чата (v3.1.1 — финальный гейт §13 её использует, тело
обязано её производить): `continuous_history` (сертифицированный диапазон до
головы) | `verified_unavailable` (терминальное событие с evidence-типом:
404/410 на актуальной generation + отсутствие в верифицированном экспорте) |
`explicit_open_debt` (owner-решение поверх gap_open/несертифицированного
остатка — durable-запись «кто/когда/почему»). Все три — строки табло §9;
продюсер `verified_unavailable` — правило эскалации §6.1, продюсер
`explicit_open_debt` — только явное owner-действие.

Импорт аккаунт-уровневого экспорта эмитит терминальные события **по-чатово**.
Быстрое «что сертифицировано» для слоя чтения — обычная rebuildable-проекция над
этими событиями (штатный путь observations → domain_events → projections), не
ручная таблица. `message_coverage_status` остаётся кэш-вью и записывается только
из терминальных событий. Миграция: текущие 12 `complete` (≥1 доказанно ложный)
переводятся в «не сертифицировано» — показывать можно, fallback разрешён,
переаттестация в слайсе 5. Возврат в `pending_backfill` запрещён до ворк-гейта
(I1), иначе они снова попадут в сломанный краулер.

**5.3. Кампании — проекции; агрегаты сначала, получатели только по эвидансу**
(v3, фикс из ревью — вендор отдаёт агрегаты):

```
campaign  { vendor queue_id, page, sent_at, content_ref, price,
            sentCount/viewedCount/… — агрегаты }
recipient { campaign_id, chat_id,
            sent_observed / message_present,
            opened_observed_at + source,
            purchased: TRI-STATE (true|false|unknown) + provenance }
```

Обе — **rebuildable-проекции** над журналом (`chat_queue.*` вебхуки + задание
`campaign_snapshot` для сверки обзорным эндпоинтом). Ограничения вендора,
принятые как рамка: `chat_queue.updated/finished` несут агрегаты
(pending/total), Mass Message — sentCount/viewedCount, user-level известен для
покупателей — списка всех получателей исторически НЕТ. Поэтому: recipient-строка
создаётся только при явном `user_id/chat_id`-эвидансе (per-recipient
`messages.sent` — проверяется canary на естественной рассылке; покупатели — из
buyers-среза; unlock — из PPV-событий); `unknown` никогда не пишется как
`false`; **membership не является сертификатом истории чата** — историю
холодного хвоста закрывает экспорт/докачка (§2), не кампания. Историческая
рассылка 30 мая восстанавливается как агрегат + те получатели, что доказуемы
задним числом; остальное — честный unknown. Семантика полей (v3.1):
`sent_observed/message_present` вместо «delivered» — вебхук не является
delivery-acknowledgement; `opened_observed_at + source` вместо вечно-свежего
boolean — документированного события обновления «opened» нет.

**5.4. Счётчик fallback-чтений:** каждый случай «в БД не хватило → сходили к
вендору» пишется с причиной (`no_certificate | stale_head | gap`). Это метрика
миграции чтений (§7).

**5.5. Транспорт: capture-before-parse (несущий протокол; из внешнего ревью).**
У одного транспорта **два входа** (v3.1):

```
background:  job lease → durable-попытка → HTTP → конверт в observations
             → локальный разбор → курсор/исход (I0)
interactive: логическое чтение → durable-попытка → HTTP → COMMIT конверта
             → только затем ответ клиенту (без acquisition-job и курсора;
             исходы попытки: captured+served | captured error | indeterminate)
```

Interactive-путь заменяет сегодняшний gateway-капчер (асинхронный, fail-open и
только для 2xx — `ofapi-read-gateway-capture.ts`): ответ клиенту не уходит до
коммита захвата. **Режим деградации interactive (v3.1.1):** по умолчанию
fail-closed — диск-гейт/недоступность записи = честный 503 + алерт; допустимый
break-glass — owner-флаг `serve-without-capture` только для GET, со счётчиком
пропусков (аналог сегодняшнего fail-open, но явный и видимый). Приёмка S1
включает p95-латентность interactive-пути под нагрузкой. Background-путь по шагам:

1. worker арендует задание;
2. адмиссия (I5: бюджет ∧ лизинг ∧ дедлайн ∧ диск-гейт), fail-closed фиксация попытки;
3. ровно один HTTP-запрос, без скрытых ретраев;
4. **любой** полученный ответ — включая 404/429/5xx/невалидный JSON — сначала
   сохраняется в observations самодостаточным конвертом: {account, scope,
   endpoint + точные параметры, request cursor, status + значимые headers,
   verbatim body, версии source-контракта и парсера};
5. в той же короткой транзакции задание → `awaiting_parse` + составная ссылка
   на observation (термин v3.1.1: состояние ЗАДАНИЯ называется `awaiting_parse`,
   чтобы не коллидировать с состоянием ПОПЫТКИ `response_captured` из §5.6);
6. отдельный **локальный** шаг парсит уже сохранённый ответ, обновляет проекции
   и лишь затем двигает курсор;
7. упавший парсер не вызывает вендора повторно — починенный парсер перечитывает
   observation.

Следствия: нынешняя дубль-запись сырья (`sync_raw_payloads` + observation без
request-контекста — `sync/shared.ts:80–135`, потеря `conversationRef` исходящих —
`canonicalize/sync-pull.ts:99–140`) для новых вызовов упраздняется — один
самодостаточный конверт; ошибки вендора становятся журналируемыми фактами (и
атрибутируемыми кредитами — сейчас 27% July-трат неатрибутируемы); crash-safe
**после захвата**: рестарт дообрабатывает `awaiting_parse`-задания (и
`response_captured`-попытки) локально. Окно
«после dispatch, до записи конверта» неустранимо — оно закрывается статусом
`indeterminate` попытки (§5.6): для GET допустим контролируемый повтор после
reconciliation, для stateful-операций (export-start; отправки уже покрыты
аутбоксом) автоповтора нет. Новые источники/виды observations регистрируются в
canonicalizer-реестре (сегодня он не знает readthrough/operator-источников —
`canonicalize/index.ts`), иначе конверты лягут в журнал мёртвым грузом.

Два дополнения v3.1.1 к транспорту:
- **Один писатель проекций.** Канонический путь (observations → domain_events →
  проекции) — единственный писатель проекций; job-локальный шаг разбора
  ограничен курсором/исходом/coverage задания и потребляет разбор через события
  (или ту же family-функцию с общим dedup-ключом). Два конкурирующих писателя
  одного конверта (job-парсер и canonicalizer-replay) запрещены.
- **Отвязка от легаси-синка кредитов.** Governed-вызов передаёт `attempt_id` и
  БАЙПАСИТ best-effort `onCreditSpend` (ofapi.ts: «a sink failure must never
  fail the API call» + собственная транзакция синка = двойной settlement с
  новым CAS-протоколом). Одна CAS-транзакция фиксирует: конверт, исход попытки,
  ledger-settlement, job-link. Немигрированные лейны (enumerated: Fansly-всё,
  legacy OFAPI fan_identities/tx-backfill/chargebacks до их миграции) остаются
  на старом синке.

**5.6. Durable-попытки (`ofapi_request_attempts`) — correctness-plane** (v3, из
ревью). Существующие `sync_http_attempts` — операционная телеметрия: привязаны к
sync-run (interactive-гейтвей ранов не имеет), планово удаляются
(`sync.ts:745–750`), запись не fail-closed — на них нельзя строить ни кредитный
цикл, ни правило I1. Добавляется маленькая durable-таблица (или эквивалентное
расширение кредитного леджера): атомарно {резервация, определённость отправки,
привязка job|scope, исход, ссылка на observation}. Записать нельзя → запрос не
отправляется. Health §9 считается по ней; телеметрия остаётся телеметрией.

Контракт идентичности попытки (v3.1; словари сведены в v3.1.1): `attempt_id`
создаётся ДО dispatch и уникален; активное намерение уникально по
`active_slot_key` (§5.1); `observation.idempotency_key = attempt_id`; строка
кредитного леджера уникально связана с попыткой; завершения защищены CAS.

Единая таблица состояний ПОПЫТКИ (interactive-исходы §5.5 — проекции этих же
состояний): `denied → ∅` (pre-dispatch отказ адмиссии: attempt-строка в
состоянии `denied` пишется в той же fail-closed транзакции, что и неудавшаяся
резервация — без HTTP и без кредита; это и есть источник метрики
budget_denied для I2/§9) | `reserved → dispatching → response_captured |
indeterminate`. Поверх состояния — поле `outcome` с доменом I2, заполняемое
на шаге локального разбора; `captured+served = response_captured ∧ success`,
`captured_error = response_captured ∧ error-исход`. Состояние ЗАДАНИЯ
`awaiting_parse` — другая сущность (§5.1). Окно между dispatch и записью
конверта неустранимо и закрывается `indeterminate`; GET после reconciliation
допускает контролируемый повтор (лимит повторов — из бюджета задания/скоупа),
stateful-операции — нет (§5.5).

## 6. Контуры захвата

**6.1. Живой контур** (бесплатный, realtime; работает — дополняем):
- вебхуки `messages.sent/received` + PPV — как есть (проверено: 100% событий за
  сутки дошли до всех трёх хранилищ);
- List Chats свип — как есть, плюс **материализация `lastMessage` как
  факт-сообщения** через штатный редьюсер: он уже дословно захвачен в каждом
  свипе и сейчас выбрасывается (replay-проверка: 606/606 совпадений
  нормализованного текста с архивом). Провенанс `list_chats_last_message`;
  coverage НЕ двигается; проекционный `last_message_preview` не используется
  как факт никогда;
- **Get Specific Chat Message** — новый метод клиента (в `OfapiClient`
  отсутствует): точечный ремонт известной отсутствующей/бедной головы,
  ~1 кредит, только `(chat, message_id)`-цель;
- **bounded tail-reconcile** (v3; триггеры пересмотрены в v3.1 — сдвиг головы
  сам по себе работу НЕ создаёт, иначе одна рассылка на 8k чатов = 8k платных
  заданий, тот же fanout, от которого уходим): голова совпала ≠ дыр нет (вебхук
  101 потерян, 102 пришёл — голова сходится, 101 исчез навсегда, его id
  неизвестен и Specific Message не поможет). Сдвиг головы записывает только
  head-факт (`item_presence`, бесплатно). Задание `tail_reconcile` (один
  страничный проход до verified anchor, лимиты страниц/кредитов, `gap_open`
  при недостижении) создаётся ТОЛЬКО по независимому намерению: входящее от
  фана / открытие чата чаттером (interactive) / членство в когорте
  spender-active / ручной запрос / sampled anti-entropy (≤K чатов/день).
  Известный кампания-всплеск идёт в campaign-lane без per-chat fanout;
  неизвестный массовый всплеск голов проходит grace-окно и общий admission-cap.
  Повторные сдвиги одного чата coalesce в уже открытое задание (§5.1).
  Внутренний fanout «вебхук дошёл до всех хранилищ» не доказывает, что вендор
  прислал все события — tail-reconcile это единственная дешёвая проверка.
  Уточнения v3.1.1 к намерениям: (а) **открытие чата** порождает задание только
  если у чата НЕТ continuous-сертификата до текущей головы (иначе шаг 1 §7
  отвечает из БД и ничего не создаёт); постановка асинхронна, не блокирует
  ответ; действует coalesce и дневной cap — так выполняется обещание §11 про
  стремящийся к нулю interactive-фон; (б) **anti-entropy-сэмплер**: домен =
  несертифицированные чаты МИНУС (quarantined ∪ blocked_* ∪ недавний gap_open ∪
  сэмплированные за N дней), исход — durable-запись, месячный под-бюджет внутри
  live-скоупа — иначе сэмплер по построению смещён в патологическую
  May-30-когорту и дожигает K×кредиты/день вечно; (в) **кросс-generation память
  провалов**: durable-счётчик по (chat, endpoint-класс), переживающий
  generations — после M `blocked_protocol` подряд эскалирующий карантин
  (день → неделя → owner-ревью) и перевод в `verified_unavailable` (§5.2);
  интерактивное открытие такого чата отвечает из БД + fallback-флаг БЕЗ платной
  попытки — иначе спендер-чат из 60s-когорты легально жжёт кредиты каждый день
  через новые входящие; (г) **гашение по gap_open**: после `gap_open` новые
  автоматические намерения того же чата подавляются на T (или до нового
  verified anchor из S5b); gap_open-долг — строка табло §9 и приоритетный вход
  котировки S5b;
- **закачки истории в этом контуре не существует.** Стрим `dm_messages` в
  текущем виде выводится из эксплуатации.

**6.2. Контур кампаний** (новый, почти бесплатный):
- подписка `chat_queue.updated/finished` — сначала **journal-only**: наблюдаем

## 7. Слой чтения и миграция десктопа

Десктоп не меняется (он уже ходит в kernel) — меняется порядок разрешения за
теми же операциями read-gateway:

```
запрос чтения → 1) БД, если поверхность свежа и сертифицирована      ← цель ~100%
              → 2) иначе ограниченный ремонт (Specific Message / 1 страница)
              → 3) иначе платный fallback: причина в лог, бюджет interactive
```

Контракт свежести:

| Поверхность | Источник БД | Сигнал свежести |
|---|---|---|
| Список чатов | `page_dm_threads` | возраст последнего вебхука + последнего свипа |
| Переписка | hot store + архив | голова БД == голове вебхука/List Chats; глубина — по сертификату |
| Профиль/транзакции/списки | существующие проекции | штатные ватермарки |

Миграция — по поверхности за раз, флаг на поверхность, ритуал #70:

```
shadow (отдаём live, считаем из БД, логируем расхождения)
  → расхождения ≈ 0 → db+fallback (счётчик причин)
  → fallback ≈ 0 стабильно N дней (параметр, стартово 7) → db-only
```

`fallback ≈ 0` — необходимое, но НЕ достаточное условие (v3, из ревью: чаттеры
могли просто не открывать глубокую историю). Гейты db-only, все одновременно:
доказанное покрытие нужной глубины (deep-history — только после S5b);
достаточная shadow-выборка по каждой форме запроса; ноль критических
расхождений (message id, порядок, PPV/цены, принадлежность странице); p95
latency/error/DB-load в норме; автоматический rollback-порог. Ранними на db-only
переходят List Chats и текущие головы; глубокая история — последней. db-only
относится к **in-scope поверхностям** (§2): vault/media/upload и прочие
исключённые поверхности gateway продолжают обслуживаться live и не участвуют в
cutover-метрике.

Три дополнения v3.1.1 к слою чтения:
- **Watermark-гейт:** db-only для диапазона требует не только терминального
  coverage-события, но и `serving_projection_watermark ≥ seq терминального
  события` — canonicalize и проекция архива асинхронны, «полный» диапазон не
  должен объявляться раньше, чем его последние строки доехали до выдачи.
- **Контракт поверхности List Chats:** текущая проекция `page_dm_threads` НЕ
  несёт serving-критичных полей (`canSendMessage`, `canNotSendReason`,
  `lastReadMessageId`, `hasUnreadTips`, `isMutedNotifications`), которые
  десктоп читает, а отсутствующий `canSendMessage` мапит в true → отправки в
  закрытые чаты. До db-only List Chats: зафиксировать полный per-surface
  response contract, добавить поля в проекцию (питаются свипом §6.1), включить
  их в shadow-гейты (sendability/read-state/фильтрация/пагинация, не только
  id/порядок).
- **Дизайн shadow-фазы:** diff-лог = отдельная таблица с retention-классом
  (+вход в retention-deleters-пин); sampling-cap по поверхности; сравнение —
  воркером, не inline в gateway; семантика off/shadow/serve с откатом; явная
  оговорка §11 — shadow-период кредитов НЕ экономит (live-риды продолжаются) и
  добавляет двойную читающую нагрузку — планировать ПОСЛЕ DB-наблюдаемости и
  memory-trial Postgres (диагностика 16.07: 128MB shared_buffers).

Отправка (аутбокс: одна попытка, fail closed) не меняется. **SSE v2 — меняется
одним правилом (v3.1.1, blocker из воркфлоу-ревью):** события из источников
`export_import | harvest_import | list_chats_replay` помечаются **non-fanout**
и не попадают в v2-стрим (v2 отдаёт domain_events per-account гэплесс — импорт
истории 12.5k чатов иначе вольётся в replay-окно каждого десктопа; флуд рвёт
соединения с lossless resume → reconnect-циклы = класс инцидента #155, а
исторические PPV — ровно подавленный сейчас kind). Приёмка в S2/S5b: реплей
свипов и импорт 10k сообщений → 0 кадров на v2, client-watermarks не тронуты.

## 8. Бюджеты и кредитная бухгалтерия

**Четыре раздельных скоупа** вместо общего котла (сегодня: один глобальный
счётчик; desktop-риды без гейта раздувают его — `ofapi-read-gateway.ts:426–439`,
19.7k кредитов с 06.07 — а DM-воркер по нему голодает):

```
общий hard cap дня + credit floor (существует: 500) + провайдерские rate/concurrency
        ↓
caps по скоупам:  live | interactive (C5) | campaign | archive
        ↓
per-job бюджет
```

Иерархия (v3, фикс из ревью): физический баланс OFAPI ОДИН — скоуп-капы это
аллокации, а не независимые кошельки; от пожирания live/command-остатка архивом
защищают верхний cap и floor, не сами скоупы. Строится расширением существующих
счётчиков (`ofapi_credit_state`: global + audience + backfill уже есть —
`schema.ts:2250`, `repositories/ofapi.ts:1206`), не изобретением новых.
Резервация всех уровней (global + scope + floor) и создание durable-попытки —
**одна fail-closed транзакция** (сегодняшний reserve работает с одним счётчиком
за раз — расширяется). Неудачные попытки списывают бюджет (I5).

Три дополнения v3.1.1: (а) **per-principal sub-cap внутри interactive** (≤N
кредитов и ≤M запросов/час на актора) — иначе reconnect-шторм одного десктопа
(реплей 14–15.07) выедает общий C5-котёл за часы и до UTC-полуночи ослепляет
budget_denied'ом ВСЕХ легитимных чаттеров; (б) **анти-шторм**: K budget_denied
подряд от одного актора → временный отказ на уровне gateway ДО создания
durable-попытки + алерт (иначе шторм заливает таблицу попыток denied-строками);
(в) **семантика floor**: существующий floor — probe-through и freshness-gated
(на stale-балансе пропускает пробу; failed-попытки не несут `_meta` → баланс
стареет именно во время инцидента). В новой адмиссии: probe-through разрешён
одному выделенному лейну (live), остальные скоупы на stale-балансе fail-closed;
баланс-ping — штатный источник свежести. 429 обслуживается по `Retry-After` с
джиттером; timeout после возможной отправки — `indeterminate` в существующем
леджере (новая финансовая система не строится).

**Жизненный цикл кредита** (вместо подсчёта постфактум):

```
reserved → settled(факт из _meta) | released(точно не отправлено) | indeterminate(таймаут после возможной отправки)
```

привязан к физической попытке + логическому запросу + заданию/скоупу. Сегодня:
резервации по брошенным вызовам висят до UTC-полуночи без записей
(`ofapi-dm-sync.ts:167–180,227–250`, `repositories/ofapi.ts:1105–1113`), одна
логическая резервация покрывает до 4 транспортных попыток. Основание считать,
что вендор биллит failed-попытки: три точных уравнения `spent−ledger=failed`
(662=662, 776≈774, 787≈785+2 in-flight — локальная сторона), одно прямое
balance-окно 13.07 (−307 при известных 18.78; residual 288.22 ≈ 288 failed) и
дневная корреляция r≈0.92 при базлайне external ~600/день из других источников.
Финальная валидация — биллинг-экспорт вендора (открытый запрос).

## 9. Наблюдаемость: два раздельных табло

**Живое здоровье** (алертится): доля успешных физических попыток по лейну;
«N попыток без успеха» = инцидент (I7); лаг вебхуков/свипов; аут/лимит-блоки;
бюджеты по скоупам с прогнозом и алертами 70/90%; fallback-rate по поверхностям.

**Историческая полнота** (информационное, НЕ инцидент и НЕ 503): % чатов с
сертификатом; терминальная таксономия (continuous_history /
verified_unavailable / explicit_open_debt — §5.2); gap_open-долг;
несертифицированный объём; долг парсинга; отказы адмиссии (attempts в состоянии
denied); ёмкостной headroom журнала; очередь заданий
(running/backoff/quarantined/terminal, возраст старейшего); доля
неатрибутированных кредитов (цель ~0 после конверта).

Разделение обязательно: сегодня «холодная история не докачана» и «лейн умер»
смешаны в одном статусе — health/sync постоянно деградирован и его перестали
читать.

## 11. Экономика (приблизительно, честно)

- Сегодня: ~47k кредитов July MTD, из них ~12.8k неатрибутированных, до
  ~800/день — бесполезные failed-попытки мёртвых лейнов, 19.7k — небюджетированные
  desktop-риды.
- После слайсов 0–4: фон сжимается до вебхук-аккрула (~1.5–2k/мес) + свипы +
  отправки + ремонты ≈ **5–8k/мес**; interactive-fallback → 0 по мере
  сертификации.
- Разовая цена истории: по котировке S5a, когортно (спендеры ориентировочно
  5–20k кредитов; хвост — от сотен кредитов при подтверждённой мелкой глубине
  до worst-case ~125k при глубине 200; решение по хвосту — на числах котировки,
  см. §2).
- **Ёмкость журнала (v3.1.1):** verbatim-конверты — новый класс записи на
  100-летнем retention при диске 80%: interactive (~2k чтений/день × 10–100KB)
  ≈ +0.6–6 ГБ/мес поверх текущих ~4 ГБ/мес observations; разовый импорт 12.5k
  чатов ≈ +1–2 ГБ. Решения: tier-класс конвертов (компрессия тел, ранний выезд
  в bucket/lake), retention-класс новых таблиц с обновлением
  retention-deleters-пина, headroom-критерий диск-гейта («осталось < N ГБ», а
  не «кончился»). Диск-гейт — гарантия доступности, НЕ замена ёмкостного плана.
- Shadow-период (§7) кредитов не экономит: live-риды продолжаются до
  per-surface флипов.

## 12. Риски и открытые вопросы

1. **Пригодность экспорта не доказана** (полнота/срезы/усечение/поля) —
   гейтится пилотом; провал → бэкенд B по инвариантам.
2. **Семантика `chat_queue.*` не доказана** (включая гарантию per-recipient
   fanout) — journal-only фаза обязательна; снимок майской рассылки подтверждает
   кампанию и её агрегаты, но per-thread membership остаётся `unknown` до
   явного эвиданса (§5.3).
3. **Биллинг failed-попыток** — сильно поддержан, не доказан; биллинг-экспорт.
4. **Причина 60s-таймаутов вендора неизвестна** — пробы слайса 5 дают диагноз;
   для архитектуры не блокер (закачка уходит из живого пути в любом случае).
5. **Покрытие харвеста десктопа неизвестно** — источник опциональный.
6. Vendored OpenAPI не документирует «10-летний фолловер-сентинел» бесплатных
   страниц — free audience помечать отдельно от платных подписок (смежный фикс
   вне этой спеки, зафиксирован в бэклоге диагностики).
7. **Существующие OFAPI-лейны в обход журнала** (подтверждено по коду 16.07):
   fan identities, transactions backfill и chargebacks пишут проекции напрямую,
   без observations (`ofapi-fan-identities.ts`, `ofapi-transactions-backfill.ts`,
   `ofapi-chargebacks-sync.ts`) — нарушение capture-first уже в сегодняшнем коде.
   Их унификация на транспорт §5.5 — первый follow-up после сообщений (§2
   «уже синкающиеся планы без изменений» относится к продуктовому поведению,
   не отменяет этот транспортный долг).
8. **Erasure (Stage 28.4 / DP 8) против конвертов (v3.1.1):** новые конверты по
   построению мультифанные (List Chats свипы, campaign_snapshot,
   экспорт-артефакты на тысячи чатов) с verbatim-телами, а erasure-модуль
   удаляет только одно-фанные observations; чексумма артефакта — улика
   сертификата, пофановое вырезание её ломает. Требуется: регистрация новых
   kind'ов в erasure-lineage; семантика пофанового вырезания из артефакта
   (filter-out → re-checksum → supersedes-цепочка сертификата, по образцу
   lake-rewrite) ЛИБО явное owner-решение «артефакты erasure-immune»;
   приёмочный erasure-тест в S5b; retention-deleters-пин обновляется для всех
   новых таблиц.
9. **AI-читатели архива (v3.1.1):** материализованная голова — новейшая строка
   чата и попадает в вершину fast-reply транскрипта; для media/PPV-голов она
   fill-grade (без цены/контента — 25/606 по данным расследования, которое
   прямо запрещало кормить архив урезанными превью). Правило: media/PPV-голова
   без обогащения не сервится в AI-транскрипт (Specific-Message-обогащение до
   подачи либо фильтр по provenance + rich-flag в транскрипт-лоадере);
   приёмка S2/S5b — transcript-parity до/после материализации и импорта.

## 13. Критерии приёмки (по слайсам, измеримо)

- **S0:** 0 запросов легаси-лейнов; инцидент #40 закрыт; failed-бёрн лейнов → 0;
  «N без успеха» видно на дашборде.
- **S1:** 100% ответов **governed-путей** с конвертом (DM-задания, campaign,
  interactive-гейтвей; legacy-лейны вне охвата — enumerated-список, симметрично
  retention-пину, до их миграции по §12.7); ноль платных governed-запросов без
  durable-попытки (fail-closed доказан тестом); задания создаются/арендуются/
  проходят `awaiting_parse`; неатрибутированные кредиты дня < 5%;
  interactive-скоуп реально отсекает (нагрузочный тест); **шторм-тест**: реплей
  reconnect-цикла 14–15.07 → burn ≤ per-actor cap, прочие акторы обслуживаются,
  таблица попыток не заливается (анти-шторм до создания попытки); p95
  interactive-латентность с sync-commit конверта в норме.
- **S2:** ≥99% голов из List Chats материализованы фактами; 0 full-history
  запросов; ремонт головы ≤ 1 запрос; **fanout-тест**: 8 000 кампания-сдвигов
  голов → 8 000 head-фактов и НОЛЬ автоматических tail-заданий (либо ≤K
  sampled anti-entropy); реплей материализации свипов → **0 кадров на v2-SSE**;
  сэмплер-тест: неделя на прод-подобном корпусе → burn ≤ под-бюджета, повторных
  сэмплов провальных чатов 0; transcript-parity: fill-grade media/PPV-головы не
  попадают в AI-транскрипты (§12.9).
- **S3:** рассылка 30.05 восстановлена как агрегат; каждая существующая
  recipient-строка имеет явный user/chat-эвиданс и provenance; недоказанные
  получатели остаются `unknown` (никогда не `false`); холодные треды остаются
  видимым coverage-долгом до S5b; canary на естественной рассылке либо
  подтвердил per-recipient fanout, либо отрицательный результат записан.
- **S4:** ноль критических shadow-расхождений (id/порядок/PPV/принадлежность)
  на достаточной выборке по каждой форме запроса; ≥1 неглубокая поверхность
  (List Chats / текущие головы) на db-only с автоматическим rollback-порогом;
  deep-history остаётся на fallback до S5b; fallback-причины видны на дашборде.
- **S5a:** котировки получены (включая полный хвост — для owner-решения на
  реальных ценах); пилот сертифицирован или отклонён с записанной причиной;
  бэкенд выбран; после `start_indeterminate` автоматический повторный POST не
