# Стоимость CI Hub — исследование 16 сентября 2026

**Рекомендация: сохранить набор проверок и GitHub Actions, сначала испытать более дешёвый Linux x64 runner, параллельно убрать повторную сборку и лишние запуски от отчётов.** Основная статья — минуты выполнения тестов. Очистка артефактов и отмена nightly почти не повлияют на счёт.

Сейчас есть отдельная блокировка: бюджет Actions **$50 из $50, Stop usage = Yes**, а GitHub сообщает об ошибке авторизации платежа. Свежие workflow уже заканчиваются `startup_failure` до старта заданий. Решение о платеже/увеличении бюджета — отдельное действие владельца; этот аудит ничего в оплате или CI не меняет.

## Куда уходят минуты

Выгружены **292 запуска** за 1–16 сентября на момент начала аудита: 198 PR, 78 push, 16 schedule. В ответах 1,507 записей jobs, 1,415 реально получили runner и ненулевое время. Повторные попытки включены через `filter=all`; пропущенные jobs без runner исключены из стоимости.

При восстановлении стоимости по округлению каждой job вверх получается 10,741 минута, $64.45. В billing Hub Linux — 10,606.67 минуты, $63.64. Расхождение около **1.3%**: job timestamps не являются billing ledger; срезы обновляются в разное время, есть границы суток и повторные попытки. Поэтому ниже — **оценка распределения**, не бухгалтерская разбивка счёта. Суммы из Billing имеют приоритет.

| Этап | Округлённые runner-минуты | Оценка gross | Доля |
|---|---:|---:|---:|
| 3 интеграционных shard | 7,010 | $42.06 | 65.3% |
| Static checks: typecheck, сборки, unit-тесты | 2,975 | $17.85 | 27.7% |
| Nightly full suite | 413 | $2.48 | 3.8% |
| Quality Gate | 273 | $1.64 | 2.5% |
| Публикация проверенного Docker image | 70 | $0.42 | 0.7% |

По событиям: PR — около 67% времени, push в main — 29%, nightly — 4%. Отменённые и завершившиеся ошибкой запуски вместе уже использовали около 1,077 фактических runner-минут; это около 11% всех минут. Не вся эта работа лишняя: проверки действительно находили ошибки.

## Почему выросло 14–15 сентября

| Период | Запусков | Успешный CI, медиана суммы времени jobs |
|---|---:|---:|
| 1–12 сентября | 185 за 12 дней | 35.2 runner-мин |
| 14 сентября | 62 за день: 38 PR, 23 push, 1 nightly | 39.7 runner-мин |
| 15 сентября | 33 за день: 20 PR, 12 push, 1 nightly | 42.9 runner-мин |

Причина скачка — прежде всего число запусков, одновременно типичный запуск стал примерно на 22% тяжелее относительно 1–12 сентября. Изменения в тестовом наборе и исходниках есть; приписывать весь рост одному коммиту без одинакового benchmark нельзя.

Runner-минуты суммируются по параллельным машинам: 12 минут ожидания четырёх jobs могут означать около 40–45 оплачиваемых минут. Три shard сокращают ожидание, но сами по себе не сокращают объём вычислений втрое.

Полный набор запускается на PR и затем снова на `push main`. Внутри открытого PR он также запускается после каждого обновления. Отмена устаревших PR-запусков уже настроена; предлагать её как отсутствующую оптимизацию неверно.

Сравнение последовательных PR heads в одной ветке нашло **26 обновлений только документов/исследований, около 874 фактических runner-минут**. В 14 случаях предыдущий запуск уже был зелёным: около 464 минут. Например, ветка `feat/fansly-c1-followers` несколько раз полностью проверялась после добавления наблюдений и отчётов:

- [12 сентября, 12:55 UTC](https://github.com/goslingmanagment/core/actions/runs/34695008820): три Markdown-файла, 36.7 runner-минут.
- [12 сентября, 20:08 UTC](https://github.com/goslingmanagment/core/actions/runs/34716212438): отчёты и validation.json, 36.9 runner-минут.

Это кандидаты на сокращение, **не доказательство, что все 874 минуты можно безопасно убрать**: сравнивались PR heads, не обязательно одна и та же merge-версия; предыдущие запуски иногда были отменены, а часть документов читают тесты. Данные: `evidence/docs-only-between-runs.json`.

## Конкретные изменения внутри CI

### 1. Убрать отдельную повторную production-сборку

Сейчас цепочка такая:

1. Отдельный `pnpm typecheck`.
2. `pnpm build:production`, который снова вызывает typecheck и собирает приложение.
3. `docker build`, внутри которого опять выполняется `pnpm build:production`.

На последнем успешном main-run отдельная host-сборка заняла **85 секунд**. Её выход не передаётся Docker-сборке: Docker копирует исходники и строит всё заново. Можно оставить ранний typecheck, сборку внутри финального image и оба smoke-теста, убрав отдельный host `Production build`. Предварительная экономия — около **3% всего CI** при нынешней структуре. Проверить отсутствие зависимостей последующих unit-тестов от оставленных host dist перед удалением шага.

### 2. Добавить межзапусковый Docker BuildKit cache

В CI обычный `docker build` на новой VM, без `cache-from/cache-to`. Cache mounts в Dockerfile полезны внутри builder, но сами не переживают исчезновение GitHub runner. Каждый раз повторяется установка production-зависимостей и Chromium.

Измеренная Docker-сборка — примерно 1.8 минуты на успешный запуск. Это верхняя граница возможной экономии этого шага, не обещание убрать его целиком. Сначала проверить cache hit в двух последовательных сборках; сохранить проверки source revision, image ID, Linux/amd64, Chromium и startup capabilities.

### 3. Сократить запуски из-за отчётов

Простейшее изменение рабочего процесса: пакетировать записи о валидации/ревью до push, не делать последовательность «зелёный CI → добавить только отчёт → полный CI заново» без необходимости.

В workflow можно добавить дешёвое определение изменённых файлов и ветвление тяжёлых jobs. Но нельзя просто пропускать весь `docs/**`: например, `tests/agent-read-docs-commands.test.ts` проверяет команды из документации. Нужен небольшой явный список безопасных путей. `Quality Gate` должен успешно завершаться только после предусмотренных проверок или доказанного разрешённого пропуска; незапущенный required workflow не должен оставаться Pending. Для main сохранить привязку публикуемого image к проверенному commit.

### 4. Оптимизировать устройство тестов по профилю

В [последнем успешном main-run](https://github.com/goslingmanagment/core/actions/runs/35013876329) unit-suite: 349 файлов, 4,078 passed, 9 skipped, **458 секунд**, Vitest сообщает **262.5 секунды import** и 125.1 секунды tests. У shard 1: 79 файлов, 736 passed, 622 секунды; отдельно API subset 27 passed, 77 skipped, 41 секунда.

Это основание исследовать стоимость повторных импортов большого backend graph, запусков worker и смешение чистых unit-тестов с DB-тестами. Общий мигрированный PostgreSQL template и отдельные cloned DB уже реализованы — повторно предлагать их с нуля не надо. Не отключать isolation глобально и не включать параллельные DB suites без проверки общей среды, портов и cluster-global views. Процент выигрыша без benchmark неизвестен.

### Что пока сохранять

- **Проверки main.** Они занимают около 29% времени, но это не безопасная готовая экономия. API сейчас отвечает `protected: false`, а endpoint rulesets — 403 с требованием Pro. Причина расхождения с показанной подпиской отдельно не установлена. Есть реальные post-merge failures: [#186](https://github.com/goslingmanagment/core/actions/runs/34794319085), [#202](https://github.com/goslingmanagment/core/actions/runs/34906550737). Удаление main-test требует восстановления защиты и доказанной эквивалентности проверенного дерева/артефакта.
- **Nightly.** Экономия от полного удаления лишь около $5 gross/месяц при текущем объёме, а это проверка полного набора и rebuild proofs.
- **Полный состав интеграционных проверок.** Path-based выбор тестов для большой связанной системы — отдельная задача, не первый способ экономии.

Все тарифы проверены 16 сентября 2026. Сравнение цены минуты предполагает одинаковую длительность; заявления провайдеров о двукратном ускорении не учтены.

| Ubicloud Premium | $0.002 | $21.21 | GitHub App, оплата провайдеру, сначала benchmark |

Суммы в таблице **до квот и кредитов**, поэтому $21.21 нельзя вычитать напрямую из $46.28 billed. У Ubicloud есть $2.50 месячного кредита; его применение и конкретный тариф следует проверить при подключении. Уже накопленный GitHub-счёт миграция не отменит.

Источники: [GitHub rates](https://docs.github.com/en/billing/reference/actions-runner-pricing), [Ubicloud pricing](https://www.ubicloud.com/docs/about/pricing), [Blacksmith pricing](https://www.blacksmith.sh/pricing), [GitHub self-hosted billing](https://docs.github.com/en/actions/concepts/billing-and-usage).

У Ubicloud разные страницы расходятся по старым Standard-тарифам и доступности новым клиентам: [обновление от 27 апреля](https://www.ubicloud.com/blog/ubicloud-price-adjustment-2026) закрывает Standard x64 для новых клиентов, тогда как pricing docs допускают переключение. Поэтому расчёт намеренно основан на **Premium $0.002**, совпадающем в актуальной подробной таблице и сравнительной таблице продукта; обещать старый $0.0008 нельзя.

Для выбора остаются существенные неизвестные: реальная скорость Hub/Testcontainers, стабильность на полном наборе, доступная concurrency и возможность оплаты. [Runner types](https://www.ubicloud.com/docs/github-actions-integration/runner-types) описывает x64 Ubuntu 24.04, Docker-совместимые GitHub images; это не заменяет запуск нашего набора. [Подключение](https://www.ubicloud.com/docs/github-actions-integration/quickstart) требует GitHub App и карты, а не только правки YAML.

Домашний winpc — возможный вариант с Linux VM и Docker, но **во время аудита `ssh winpc` завершился timeout**. Текущие RAM, свободное место и установленная виртуализация не подтверждены. Поэтому он не выбран как основной способ восстановить CI. Для собственного runner нужны отдельная среда без личных/production credentials и устойчивый режим работы; production VPS для тестов не использовать.

Пример месячной чувствительности, **не прогноз счёта**: при 21,000 runner-минут GitHub стоит $126 gross, Ubicloud Premium $42; при 62,000 — $372 и $124. Первый объём близок к удвоению первой половины месяца, второй — к продолжению темпа 14–15 сентября. Реальный объём зависит от активности, ускорения и нынешней блокировки.

## Порядок внедрения

1. **Владелец:** решить текущую блокировку оплаты/лимита. Проверить защиту main после восстановления платёжного состояния. Просто расширить бюджет — восстановление доступности, не экономия.
2. **Небольшой PR:** убрать повторный host build после проверки зависимостей, добавить Docker cache; сохранить имена и смысл проверок, release metadata и image smoke. Замерить полную стоимость run до/после на одинаковом commit.
3. **Пилот Ubicloud:** после подключения провайдера проверить один интеграционный shard и static job на том же commit и тех же наборах тестов. Затем полный PR и main image pipeline. Критерии: те же passed/skipped, успешные Docker/native dependencies, оба smoke, корректные metadata/artifact, отсутствие новых flakes. Сравнивать сумму оплачиваемых минут и очередь, не только длительность самой быстрой job.
4. **При успешном пилоте:** перевести тяжёлые jobs и nightly; публикацию GHCR можно оставить на GitHub с узким `packages: write`. Сохранить возможность явного возврата на GitHub runner. Затем сделать безопасный режим для отчётов и профилировать импорт unit-suite.

Новые аккаунты, подключение App, установка runner, изменение бюджета, платёж, workflow dispatch, push и deploy в рамках исследования **не выполнялись**. Подготовлен результат для выбора направления; экономия не выдается за уже достигнутую.
