## DM02-01. Один материал читается дважды для одной операции

**Действующий путь и условия.** `apps/runtime/src/services/ofapi-read-gateway.ts:475,615` выбирает старый gateway tee, когда `captureFirst=false`; `ofapi-read-gateway-capture.ts:123,138,148` сначала фиксирует observation, затем вызывает immediate `projectReadthroughObservation`. Нужен `ofapiDmReadthroughReconcileEnabled=true`; новый `ofapiMirrorInteractiveCaptureEnabled=true` направляет интерактивный запрос в другой materializer. Независимо от появления новых tee, `worker-services.ts:437` вызывает `runOfapiDmReadthroughReconcile`, а `ofapi-dm-readthrough.ts:368,392` повторяет сохранённые v2 observations при том же readthrough gate. Текущие live flags и наличие v2 долга неизвестны: это **условно активный путь**, не утверждение о нынешней основной OFAPI нагрузке. Новый capture-first mirror этим proposal не ускоряется.

В `apps/runtime/src/services/ofapi-dm-readthrough.ts:308` вызывается `findDmMessageArchiveByPlatformMessageId`, чтобы посчитать только конфликты. Repo helper (`packages/db/src/repositories/dm-message-archive.ts:282`) возвращает полную строку, включая text/media/provenance. Сразу после этого `:316` вызывает archive adapter (`dm-message-archive.ts:247`), затем reducer (`dm-message-candidate.ts:308`), который после erasure checks снова делает `SELECT * ... FOR UPDATE` (`:286,336`). Оба чтения идут последовательно для каждого сообщения. Первый результат не нужен merge: решение целиком вычисляется из второй, заблокированной строки.

**Измерено.** Actual-function harness выполняет настоящий parser/control flow, archive adapter, reducer и erasure query builders с подменой внешнего I/O. На 100 unchanged DM с 8 media каждый: 100 telemetry reads, 100 locked reads, 100 fence-lock queries, 100 fence-check queries, 100 транзакций, один parsed stamp; `upserts=0`, `noops=100`. Это 401 явный SQL-вызов включая stamp плюс транзакционный протокол. `BEGIN/COMMIT` отдельно не моделировались и в 401 не включены. Фикстура 100 элементов — bounded probe, не заявление о текущем размере vendor page.

**Изменение.** Убрать первый `find...`. Добавить в reducer опциональный возврат pre-merge material/признаков строки, нужных только для telemetry, и считать конфликты из этой уже прочитанной версии. Возвращать ссылку/минимальный tuple в том же JS-процессе, не делать новый SQL. Нельзя считать конфликты из произвольного post-merge результата: sentinel/stub hydration может изменить область измерения. Для новых INSERT нет prior material; проигранный INSERT race использует строку победителя после повторного locked SELECT.

Бизнес-семантика не меняется: capture уже завершён, fence и row lock остаются на месте, merge/provenance/emitted fingerprints и stamp-after-project сохраняются. Изменится момент telemetry: она увидит авторитетный locked snapshot, а fenced/deferred строки могут больше не участвовать в conflict counter. Это следует явно определить как улучшение измерения и отдельно учитывать dropped/deferred, а не тихо обещать побайтную идентичность прежнего race-dependent counter.

**Модель пользы.** Для `V` valid items убираются `V` reads и примерно `V × W` переданных/распакованных байт при среднем размере старой строки `W`. Для no-op path явных запросов `4V+1 → 3V+1`; транзакции, две erasure операции и locked read не исчезают. При реальной query overhead `r` верхний локальный выигрыш компонента включает `V×r`, но `r` здесь не измерялся. Нельзя переводить 25% этих SQL в 25% sync latency.

**Проверка перед merge/canary.** Фикстуры unchanged, конфликтующая REST запись, sentinel fill, deleted/stub, INSERT race, DB failure и deferred/fenced. Сверить материал, source/rest provenance, conflicts и exact observation stamp. Метрики: reads/valid item, returned-row bytes, mean/p95 readthrough projector duration, распределение written/noop/fenced. Если readthrough выключен и долга нет, текущая экономия равна нулю; изменение стоит отложить или объединить с плановым reducer cleanup.

## DM02-02. Reducer повторно доказывает уже вычисленное равенство

`packages/db/src/repositories/dm-message-candidate.ts:175` функция `pick` записывает каждое изменившееся поле в `fieldsSetByCandidate`. Для media `:219–229` сравнение безусловно сортирует и сериализует обе стороны, даже когда merge выбрал **тот же объект массива** `old.mediaMetadata`. После полного merge `:423` вызывается `materialEquals`, который `:134–149` ещё раз сравнивает все поля и ещё раз сортирует/сериализует media. Для no-op с непустым media это четыре сериализации reducer. Readthrough telemetry (`ofapi-dm-readthrough.ts:213–217`) добавляет ещё две; на 100 probe items подтверждено ровно `400+200` JSON.stringify.

**Минимальное решение проверено в изолированном in-memory варианте actual TS source:** media comparator сначала проверяет `x !== y`; окончательный no-op guard использует `merged.fieldsSetByCandidate.length === 0`. Каждый из 13 полей material tuple проходит через `pick`, даты сравниваются по миллисекундам, media — прежним sorted-key comparator. Поэтому пустой change-set является уже вычисленным доказательством `materialEquals`; заново вычислять его не нужно. При необходимости сохранить отдельный equality helper оставить его для тестов, но убрать из hot path.

216 differential cases дали одинаковый merge и одинаковый change/no-change verdict: webhook/REST/command, sparse values, timestamp freshness, rest ownership, stub, text/sender changes, opened/tip monotonicity, reply, media content и media order. Actual optimized no-op reducer дал ноль JSON.stringify внутри reducer и сохранил все три SQL-операции fence/fence/locked-read. Fingerprint stub бросает ошибку при вызове: проверенный no-op ни разу не пытался считать hash. Это не тест fingerprint compatibility и не SQL integration.

**Достижимость шире readthrough.** Webhook archive adapter (`dm-message-archive.ts:106` ← `apps/runtime/src/services/ofapi-dm-archive.ts:243`, cold-archive gate `:190`) и command material (`ofapi-command-executor.ts:328`) используют тот же reducer. Exact workload/flags не измерены. Для REST/command, где непустое старое media сохраняется, old array reuse устраняет первые две сериализации; change-set устраняет повторную пару. Для webhook, выбравшего отдельный incoming array, сравнение media остаётся — это необходимая работа.

Модель: исключается до `4 × O(M log M + B)` на no-op, где `M` — число media, `B` — сериализованный размер массива. Общий выигрыш CPU может быть мал на text-only DMs и фоне HTTP/SQL. Поэтому **P3/S**, а не новая архитектура и не обещание кратного sync speedup. Invalidation/cache нет: оптимизация относится к одной функции и одному вызову. Нельзя вводить постоянный cache media по message id или делать `===` единственным comparator: отдельные массивы сохраняют прежнюю проверку.

Приёмка: null/undefined, одинаковый array reference, разные равные массивы, повторные media IDs и порядок вложенных ключей; все 13 полей должны оставаться в change-set contract при будущих расширениях. Canary: CPU/allocations per reducer item и materialChanged/noop распределение. Capture, locks, clocks, erasure и денежные типы не меняются.

## DM02-03. Fansly reply пишет одну archive-строку двумя SQL подряд

**Путь.** `apps/runtime/src/services/canonicalize/sync-pull.ts:772–862` создаёт material sidecar для attachments и для присутствующего parent/root поля, включая explicit null. Обычный message event сохраняется отдельно. `services/projections/registry.ts:149–160` регистрирует message archive; `services/projections/message-archive.ts:93–122` читает events в account-seq порядке, вызывает writer, после успеха двигает watermark. Writer `packages/db/src/repositories/message-archive.ts:230,262` сначала делает body upsert. При `replyContractVersion===1 && fieldPresence.reply===true` `:354` вызывает `applyReplyMaterial`; `:149–200` выполняется ещё один SQL с row-lock CTE и UPDATE той же строки.

**Actual call-count proof.** Набор из 25 обычных received events плюс 25 корректных Fansly reply-v1 material events вызвал 75 `db.execute`: 25 ordinary insert, 25 material body upsert, 25 reply update. Generated statements сохранены в `reply-current-statements.sql`. Для одной material-only replay страницы из `R` reply records это `2R` statements; обычные immutable message events могут быть уже deduped и вообще не поступить в этот batch. Доля reply-v1 сообщений production неизвестна.

**Предлагаемый SQL-дизайн.** Оставить один ordered вызов на material event. Сделать один `INSERT ... ON CONFLICT DO UPDATE`, где body replacement и reply parent/root имеют **разные условия по прежним часам полей**. Внутренний expression/subselect сначала вычисляет виртуальную строку после сегодняшнего body merge, затем применяет неизменный алгоритм reply к ней. Это важно для legacy fallback через `material_observed_at`, content-pending и serving-contract upgrade. Не просто добавить reply columns к существующему `SET`: существующий общий body `WHERE` может отвергнуть старый body, который обязан восстановить ещё неизвестный reply.

INSERT сразу выставляет значения и clocks фактически наблюдённых parent/root. UPDATE допускается при body_due **или** принятом parent/root; body columns сохраняются при stale body. Сохраняются explicit clears, parent-change invalidation старого root, защита более нового root и отсутствие reply observations у v5 sidecar. Source event/body provenance меняется только по сегодняшнему body guard. `deleted_at` остаётся sticky; target whitelist для shadow/live не меняется. Если запись падает, watermark не проходит событие. Ordinary received/sent event не удаляется из ledger и не переставляется.

**Ожидаемое:** `2R → R` DB round-trips для reply material, а новый DM с парой ordinary+material даёт `3 → 2`. При двух реально принятых UPDATE текущий код создаёт два tuple revisions; новый может создать одно, но величина WAL/TOAST экономии не измерена. Это локальное сокращение writer, не половина синхронизации. Простого CTE, который INSERT/UPDATE-ит одну таблицу, а потом повторно UPDATE-ит ту же строку, предлагать не следует: нужен один row write с вычисленными полями.

**Уровень доказательства ограничен.** Нынешняя амплификация доказана actual-function harness. Новый SQL ещё не реализован и не проверен PostgreSQL — это M proposal с обязательным shadow differential, не готовая к merge правка. Нужны: stale reply под новым sparse body; оба explicit null; только parent/только root; изменение parent при старом/новом root; равные timestamps; legacy null clocks; пропуск watermark после commit; replay и shadow rebuild parity. Canary: archive SQL/material item, tuples updated/item, WAL per changed material, projection lag и scoped reply acceptance. Account sequence и erasure/capture boundaries остаются прежними.

## DM02-04. Точное уточнение известного полного summary scan

Это **не новый discovery**: предыдущий `sync-algorithm-audit-2026-09-13/fansly/REPORT.md:126` уже описал повторный history scan и incremental counts. Здесь добавлены точная версия алгоритма без нового durable state, обнаруженный неполный index ordering и ограниченный algebra probe.

`packages/db/src/repositories/page-dm.ts:788–824` ранжирует весь live conversation в обоих направлениях, затем считает count/newest/oldest/max sender timestamps. `finalize...:982`/`refresh...:901` применяют prune до summary; основной Fansly executor финализирует каждый deep page (`executor-handlers.ts:3032,3075`). Изменения production executor касаются followers; этот DM участок остаётся прежним.

Для растущей истории при page size `b=25` сумма просмотренных history rows за заполнение `N=kb` составляет `b*k*(k+1)/2`; при `N=50,000` это 50,025,000 строк **на один проход summary каждого размера**, плюс ranking work. Если `N0` уже существует и поступает `k` chunks, нижняя модель `k*N0+b*k*(k+1)/2`. Это не число физических heap reads: cache, pruning и PostgreSQL план здесь не измерены. При реально ограниченном hot cache 200/1000 экономия гораздо меньше.

**Безопасный первый этап:** `count(*)` и `max(created_at) FILTER (...)` одним aggregate scan; newest/oldest — два `ORDER BY ... LIMIT 1` в той же SQL-команде/снимке. Полный дизайн запроса в `summary-proposed.sql`. Сохраняются точный text-ID tie order, tombstone filter и пустая история. Существующий `page_dm_messages_conversation_created_idx` (`schema.ts:1314`, migration `0000_baseline.sql:710`) имеет `(conversation_id, created_at, id)` и **не покрывает** tie order `(created_at, platform_message_id, id)` полностью. Поэтому обещание двух точных O(log N) seeks требует проверенного partial index с `platform_message_id` между timestamp/id либо честного учёта сортировки timestamp ties. Предложенный index описан рядом с SQL; создавать его без проверки write cost не требуется.

CPU algebra probe с mixed sender/timestamp ties/tombstones показал идентичность двух сортировок и одного линейного accumulator на 25, 1,000, 10,298 и 50,000 строк. На синтетических 50,000 JS-объектах медиана пяти повторов была 12.26 ms против 0.55 ms. **Это не PostgreSQL benchmark и не прогноз latency.** Probe доказывает достаточность summary algebra, а generated SQL — конкретный способ избавиться от полного ranking. SQL executor/коллация/ties требуют отдельного PostgreSQL differential.

Count scan остаётся O(N) на finalize; следовательно, эта первая правка **не устраняет квадратичную сумму history scans**. Полное устранение потребует идемпотентного delta-счётчика и устойчивой границы получения страниц в transaction фактов. Baseline F3 уже доказывает, почему нельзя использовать отложенную summary как receipt/coverage proof. Здесь не предлагается смешивать этот correctness fix с минимальной сортировочной оптимизацией.

Приёмка: identical summary и head/coverage до/после; tie timestamps с разными textual IDs, deletions, pruning и older edits. `EXPLAIN (ANALYZE, BUFFERS)` на локальной представительной DB; elapsed/buffers/temp bytes per finalize, write/index size cost, доля времени finalize в chunk. Это source+CPU candidate, не измеренная production hot spot.

## Отброшенные гипотезы и границы

- **«Просто пропустить одинаковые hot upserts».** `upsertPageDmMessages:558–594` действительно пишет `syncedAt` заново при overlap, но это время используется snapshot readers (`ofapi-sync-snapshot.ts:478,726`). Не предложен blanket no-op, пока не определена сохранность serving/freshness semantics и явных null clears. Не смешивать с уже deployed no-op fan writes.
- **«Закэшировать erasure/fence между сообщениями».** Межтранзакционная memoization нарушает erasure serialization. Batch внутри одной транзакции возможен только с общим shared lock, проверкой всех timestamps/refs и пересмотром partial-error semantics; он увеличивает время удержания fence/row locks. Без evidence DB bottleneck в этот report как surviving proposal не включён.
- **«Убрать sidecar/обычный message event».** У них разные dedup/provenance и field-presence semantics. Их физическая SQL стоимость не разрешает удалять captured facts или менять account-seq.
- **«Ускорить архив обычным time filter».** Window-ref selection и scoped tombstone lookup уже внедрены (Decisions 281/282). Фильтровать каждую material arm по времени нельзя: приоритетный out-of-window material всё ещё подавляет старую версию. Здесь новых savings нет.
- **«Использовать старый OF DM crawler как main hot path».** Текущий capture-first mirror другой; старый crawler не включён в оценку. Readthrough тоже явно помечен gated/conditional.
- **«Ускорение всего sync = сокращение SQL одного writer».** Нет: HTTP pacing, queues, parsing, projection debt и нагрузка других lanes вне этого измерения. Money units, provider backoff, leases, capture-first, manual controls не меняются ни одним предложением.
