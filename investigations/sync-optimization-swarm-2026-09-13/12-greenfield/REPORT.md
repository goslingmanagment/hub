# Hub с нуля для одной агентской команды

Проектное предложение, **не разрешение переписывать продукт**. Проверены `main@b48f173d93e3693550e2db139de3b11107d44ce2` и production `74aac5093cfc`; текущие gates и нагрузка не измерялись.

Три наиболее сильных изменения:

1. **Изменение само адресует потребителей.** Транзакционный fanout в маленькие задачи `(page, consumer, target)` заменяет обнаружение работы общими minutely sweeps. Лента событий остаётся; каждый потребитель читает только свои типы.
2. **Один receipt захваченного ответа.** Тело, provenance, продолжение обхода и его доказательства имеют единую долговечную связь; повтор после сбоя продолжает локальную обработку receipt, прежде чем снова обращаться к провайдеру.
3. **Один владелец material каждого объекта.** Версии полей, corrections и производные итоги проходят общий reducer; readthrough, webhook и backfill перестают независимо пересобирать одни данные. Повторное структурное декодирование можно переиспользовать только с полным контекстом.

**Что действительно обязательно.** Hub хранит платформенные факты, сообщения, деньги, контентный каталог, AI-контекст и качество; desktop/extension/dashboard/workboard — его клиенты. Сохраняются:

- Capture до бизнес-парсинга, исходные поля/байты и provenance; scheduled deletion фактов запрещён. Ошибка парсера исправляется по сохранённому материалу без платного повторного получения. Не обязательны: два metadata-журнала одного pull-ответа, отдельный discovery sweep каждого слоя, фильтрация событий после передачи JSON, shadow/direct/event writers одного material, конкретная упаковка cron в pg-boss. Сами PostgreSQL, модульный монолит и разделение API/worker разумны и остаются.

**Выбранная архитектура.** Один PostgreSQL, один deployable TypeScript-монолит: отдельные API и worker-процессы, таймер планирования под leader lease внутри worker; Caddy, dashboard, generated SDK. Worker имеет ограниченные пулы interactive ingest, sync, repair/replay и тяжёлых сводок; ни один не занимает весь connection pool. Начать с малого числа исполнителей, масштабировать по измеренной очереди и egress capacity. Отдельный scheduler можно сохранить ради изоляции сбоев, но отдельный инфраструктурный сервис ему не нужен.

Хранилище состоит из трёх различных классов. **Evidence:** immutable response/command/AI receipts и CAS bodies в PostgreSQL, partition по capture time, durable dedup keys; restricted контент отделён правами и custody. **Business:** versioned facts, field clocks/source precedence, immutable canonical events, typed money/credit ledgers. **Operational/serving:** leases, desired/applied generations, walk manifests, budgets, projections, API cursors. Rebuild serving никогда не обнуляет capture progress и не запускает повторный HTTP: этот запрет уже явно записан в [registry.ts:32](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/projections/registry.ts:32).

На каждом HTTP: проверка policy/binding/egress → резерв физического attempt → получение → commit body+receipt+задания parse. Для pull receipt включает endpoint/query, account/binding/session generation, predecessor, continuation, временные границы. Тело хранится один раз; повторяемые чтения остаются самостоятельными receipts. Нынешний [persistRawPayload:83](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/shared.ts:83) последовательно пишет CAS, `sync_raw_payloads`, `observations`; новая модель объединяет metadata и не нуждается в компенсации промежуточного raw/observation состояния. Исходный формат старых captures не улучшается задним числом.

Если процесс умер после сохранения ответа, продолжение использует receipt и parser debt. Если до сохранения — safe read может повториться по бюджету, stateful command становится indeterminate. Transport/capture checkpoint говорит «ответ сохранён»; accepted/coverage checkpoint продвигается только после успешной проверки. Walk manifest связывает страницы и distinct IDs; mutable offset-list без snapshot-гарантии не получает абсолютную полноту только из равенства total. Деактивация требует соответствующего доказательства отсутствия, неоднозначность остаётся debt.

Canonicalization — pure decode вне длительной транзакции, затем короткий atomic commit: проверить erasure/liveness и binding, применить field revisions, append events с account counter, отметить receipt обработанным, поднять desired generation адресных потребителей. Неизменившийся snapshot сохраняет receipt, но не переписывает material; наблюдения времени/списков/присутствия сохраняют собственную семантику. `A→B→A` — три состояния во времени, а не два глобально уникальных hash. Money posting и correction identities не зависят от coalescing.

Task `(page, consumer)` содержит `wanted_seq`, `applied_seq`, lease token/expiry. Append повышает `wanted_seq` в той же транзакции. Worker фиксирует `g`, читает только нужные `type` при `applied_seq < account_seq ≤ g`, атомарно сохраняет результат и `applied_seq=g` при действующем lease. При новом событии `wanted_seq>g` остаётся работой; старый worker не может закрыть новую задачу. Индекс `(account_id,type,account_seq)` обслуживает именно этот запрос. `NOTIFY` ускоряет пробуждение, correctness обеспечивает due-index и lease recovery. Ошибка одного consumer не мешает другим; repair имеет квоту и следующий retry deadline. Неизвестный account паркует receipt на зависимости binding; её изменение адресно возобновляет эти receipts. Регистрация нового consumer требует backfill до фиксированного cut и сверки tail, иначе старые события не породят fanout.

DM имеет единственный material reducer с независимыми clocks для body, links, tombstone, purchase. Thread summary, revenue days, media relations и workboard — зависимости изменившихся ключей; компактные итоги обновляются delta, сложные пересчёты coalesce по ключу и ревизии. AI features читают подтверждённую версию context с состоянием completeness, используют действующий prompt manifest и gateway; генерация/отмена сохраняют usage и partial completion. REST/Agent Read/SSE получают page ACL и явные watermarks; текущие client contracts можно обслужить compatibility facade.

**Parse reuse — условная оптимизация.** Ключ: body digest+representation/codec, parser/schema version, endpoint+query, platform, page/account/native binding generation, direction/self identity, producer/kind, все влияющие flags/context/accepted refs. Кэш содержит только структурный результат, никогда старые observation ID, timestamp, lineage, account_seq. Нужен ограниченный lifecycle/объём; erasure инвалидирует извлечённый material, а перед append всё равно заново проверяются body liveness и material-time fence внутри writer transaction. Новые receipts инстанцируют собственную временную семантику. Если невозможно перечислить зависимости функции — её результат не кэшируется. Уже deployed reuse внутри одного observation не считается этой экономией.

**HTTP и управление.** Dirty hints объединяются по target и minimum required revision. Capture receipt может удовлетворить несколько consumers только при одинаковых scope/query/binding/coverage requirements; наличие старого body не доказывает текущую свежесть. Приоритет interactive ограничен квотой, reconciliation имеет deadline и гарантированную долю; абсолютный provider cooldown применяется ко всем физическим попыткам соответствующего egress. Webhooks ускоряют известные изменения, периодический discovery сохраняется. Недоказанный Fansly WSS replay не является условием проекта. Owner видит отдельно паузу, auth block, бюджет, последние доказательства и ожидаемую работу; recovery auth не снимает owner pause.
