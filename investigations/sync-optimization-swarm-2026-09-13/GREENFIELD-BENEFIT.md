# Что даст предложение «Hub с нуля»

13 сентября 2026. Разбор GF12 по запросу owner. Использованы проверенные исходники/локальные probes первого аудита и волны13; новых замеров production-нагрузки и реализации архитектуры нет.

**Наибольший доказуемый резерв — убрать повторное чтение и пересчёт одних данных. Сам PostgreSQL-монолит уже есть. Полная перестройка не имеет доказанного дополнительного выигрыша относительно узких исправлений текущей системы.**

## Механизмы и эффект

| Механизм | Что меняется | Что можно оценить |
|---|---|---|
| PostgreSQL-монолит | Сохраняем один PostgreSQL и приложение с API/worker | Практически нулевой самостоятельный выигрыш: это уже текущая основа |
| Событие адресует нужного потребителя; SQL выбирает нужные типы | Остальные проекторы не загружают ненужное тело события | Для mapped account, одного и того же полностью прочитанного delta и события одного из48 непересекающихся типов: **14→1 загрузка тела**, то есть **−92,9% этих чтений**. Это не −92,9% всей БД. Доступно отдельным изменением typed reads |
| wanted/applied generation | Например, нужно применить версию107, применена103: задача остаётся, пока не обработан требуемый диапазон. При arrivals во время работы новое требование не теряется | Дедупликация ожидающих пересчётов; меньше фонового поиска работы и ожидания cron. Новые durable task updates/indexes/claims/completions имеют собственную цену |
| Один владелец производного состояния | Несколько источников передают изменения одному reducer с общими clocks; повторные задания одного ключа объединяются | Workboard probe дал105 enqueue INSERT для6 ключей. Цель **105→6 пересчётов** (**−94,3% /17,5× меньше**) для одной пачки до начала выполнения. Это модель предлагаемого coalescing; DB/reducer в probe подменены, runtime production queue policy не проверялась. Ingress updates могут остаться105; arrivals во время исполнения требуют следующего пересчёта |
| Единый capture receipt | Одна долговечная связь ответа с телом, provenance, шагом обхода, продолжением и долгом парсинга; получение, принятие и готовность serving остаются разными состояниями | Меньше промежуточных противоречивых состояний; после сбоя можно продолжить по сохранённому ответу. Потенциально одна лишняя raw/observation metadata-копия на ответ. CAS уже разделяет тела: это не двукратная экономия всего хранилища |

Все исходные факты и денежные события сохраняются и обрабатываются. Объединять можно повторный пересчёт итогового состояния, но нельзя просто выбросить промежуточные факты или обязательные переходы.

## Свежесть и простой

На пути, который ждёт минутного sweep, немедленное пробуждение устраняет ожидание следующего cron: **0–60 секунд на такой шаг**, в среднем30 секунд только в модели равномерного прихода относительно таймера и без backlog. Это не наблюдённый latency percentile. При загрузке bottleneck/очередь остаются; новый дизайн должен выделять ограниченные порции и квоты.

Текущий тест пустого projection tick на шести mapped accounts дал230 SQL. Их можно заменить одной metadata readiness-выборкой **без desired-generation архитектуры**. После такого исправления task fanout должен оправдать свою цену экономией оставшегося discovery и меньшим lag; повторно записывать230→1 в выигрыш полной переписи неправильно.

Изолировать ошибку одного аккаунта и сделать bounded fair processing также можно в текущем registry. Это отдельные исправления корректности и задержки, не эксклюзивная выгода greenfield.

## Повторные HTTP и расходы

Экономия единого receipt равна только тем повторным запросам, для которых уже есть пригодный ответ с точным scope, query, binding, периодом и достаточной свежестью. Исторический ответ не заменяет свежее наблюдение. У OFAPI часть этого уже работает через awaiting_parse и существующий reuse — их нельзя считать новой выгодой.

Частота лишних повторных запросов не измерена, поэтому ни процент HTTP/credits, ни денежная сумма для unified receipt не установлены. В схожем конкретном split_31 сценарии сохранение завершённых окон дало модель до40% экономии запросов режима; это отдельный уже посчитанный кандидат FH07-2 и его нельзя прибавить ещё раз как greenfield benefit.

## Как частные проценты превращаются в общий результат

Если устраняемая работа занимает долю f CPU **одного рассматриваемого процесса**, а внутри неё можно убрать90%, то до новых накладных расходов экономится f×90% его CPU:

| Условная доля такой работы | Экономия CPU процесса до новых расходов | Теоретический рост CPU throughput |
|---:|---:|---:|
| 10% | 9% | 1,10× |
| 30% | 27% | 1,37× |
| 50% | 45% | 1,82× |

Это **сценарии, не оценка текущей доли Hub**. Процент сокращения rows нельзя автоматически подставить вместо CPU savings. Реальная экономия меньше на стоимость fanout/task updates, индекса, lease/completion и cache invalidation. HTTP-bound или disk-bound задержки подчиняются другой модели. При прежнем VPS-тарифе счёт может не измениться.

## Решение по порядку работ

1. Typed event reads, readiness одним запросом и безопасное объединение workboard recomputes: получить конкретную экономию внутри текущего продукта.
2. На одном consumer сравнить тот же event prefix в старой реализации и в desired/applied tasks: rows, CPU, WAL, lock/connection time, p95 freshness, old debt; одинаковые итоги при crash, конкурентных arrivals, erasure/reset и replay.
3. Расширять архитектуру, только если она улучшает **остаточные** затраты/свежесть после первого шага. Unified receipt внедрять ради измеренных повторных запросов и упрощения восстановления; глобальную замену ingress выполнять последней.

Доказательств, что полная перепись окупится лучше этого поэтапного пути, сейчас нет. При редких изменениях task-индекс может помочь; при большом потоке transactional updates могут стоить дороже одного readiness-запроса.
