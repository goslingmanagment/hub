# Root evaluation rules

The thirteen agents search independently. Their reports are candidates, not automatically accepted claims. The final synthesis must deduplicate by the repeated operation and proposed ownership boundary, not by headline wording.

For each proposal record one of: verified by an actual-function or SQL-cost witness; established from active source; requires workload measurement; rejected/already deployed. Do not sum overlapping reductions. An optimization to payload hydration and one to query projection may eliminate the same bytes; mark the interaction.

Separate resource effects: vendor HTTP and credit spend, DB round trips, scanned/returned rows, WAL writes, serialized bytes, application CPU/RSS, lock/connection occupation, queue latency, and end-to-end freshness. A cap, lower concurrency or fairness improvement can reduce peak load while keeping total work unchanged. A correctness repair can increase useful work.

Use code-derived counts or measured synthetic results only with their dataset and assumptions. No whole-fleet percentages from a small code loop. Amdahl illustration: speedup = 1 / (1-f + f/s), where f is the measured baseline fraction attributable to the changed code and s its measured local improvement. Without f there is no whole-system prediction.
