## 1. История подписчиков: interval sweep вместо day × subscription join

**Путь исполнения.** `fanslySubscribersChunk` вызывает `rebuildSubscriberRollups` после финализации активного прохода и после одноразового expired backfill: [executor-handlers.ts:1590](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:1590), [1624](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:1624). Действующий OnlyFans audience делает это после завершения сертифицированного прохода: [ofapi-audience-sync.ts:546](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/ofapi-audience-sync.ts:546). Функции Fansly subscribers совпадают между ревизиями; OFAPI audience и файл rollup совпадают целиком. Live flags и частота production-вызовов здесь не измерены.

**Работа.** [transactions.ts:549–617](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/transactions.ts:549) удаляет производные daily rows, строит даты от самой ранней подписки до сегодня, затем сопоставляет даты с подходящими интервалами `page_subscriptions`. Рост зависит от S подписок, D дней и их длительности: потенциально S×D проверок, число подходящих пар — сумма покрытых дней всех интервалов. План PostgreSQL может сократить проверки; из исходника нельзя назначить ему фактические buffers или latency. Все D daily rows остаются заменяемыми и в минимальном предложении.

**Изменение.** Прочитать нужную страницу подписок один раз; вычислить диапазон дат; для каждого непустого интервала дать +1 в начале и −1 в день после inclusive конца; сгруппировать границы и выполнить cumulative SUM по календарю. `new_subscribers` оставить количеством subscription rows по дню начала, без дедупликации по fan. Готовый [SQL-кандидат](proposed-subscriber-rollup.sql) заменяет вычислительную часть внутри прежней транзакции. Модель — O(S+D), SQL дополнительно требует группировки и упорядочивания дней; исчезает разворачивание каждого интервала по всем покрытым дням. Миграция и новый persistent state не нужны.

**Семантика.** В текущем SQL обе timestamp-границы явно приведены к UTC `date`: начало округляется вниз, конец включён. Даже reversed timestamps внутри одного UTC-дня дают один активный день; reversed *dates* — пустой интервал. Для retired строки конец равен UTC-дню `least(ends_at,last_seen_at)`; PostgreSQL LEAST игнорирует NULL, `last_seen_at` в схеме NOT NULL. NULL start не ограничивает нижнюю границу и должен начинаться с минимума всего календаря. NULL end у текущей подписки не ограничивает верхнюю границу. All-NULL starts дают только сегодняшний день; future-only starts — пустой календарь. Всё это сохранено. Смена схемы на timestamp midnight/ceil(start) здесь изменила бы результат.

**Проверка.** [probe.mjs](probe.mjs) исполняет реальную rollup-функцию с SQL-заглушкой и сохраняет [точный SQL](current-subscriber-rollup.sql). Отдельная differential-модель совпала на 10 граничных случаях и 300 seeded корпусах, всего 12 354 подписки. При S=8 000, D=1 096: долгие интервалы дают 8 768 000 matched pairs, интервалы по 30 дней — 240 000; в обоих вариантах альтернатива создаёт ≤16 000 границ. Это арифметические результаты, **не benchmark PostgreSQL и не доказательство исполнения SQL-кандидата**.

**Приёмка/риски.** Сравнить обе SQL-версии через `EXCEPT ALL` в одном snapshot; UTC и несколько session timezones, пустые/all-null/future/reversed intervals, expiry/early cancellation, несколько tiers одного fan, повтор backfill и erasure. Затем `EXPLAIN (ANALYZE, BUFFERS)` на коротких и длинных интервалах, p95 terminal transaction и время lease. На малой истории выгода может быть несущественной; цена реализации S–M. Canary — одна страница, исходный SQL остаётся вариантом отката. При ошибке действует прежний rollback всей транзакции; rebuilding читает оставшуюся material-таблицу и не восстанавливает удалённые факты из raw.

## 2. Убрать последовательный N+1 в page identity reconciliation

**Путь исполнения.** [fan-hydration.ts:174–190](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/fan-hydration.ts:174) вызывает `reconcileFanslyFanPageIdentity` для каждого account с массивом `notes`. Реальные callers: transaction pages [transactions.ts:391–405](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/transactions.ts:391), subscribers [executor-handlers.ts:1530](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:1530), followers [1796](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:1796) / reconciliation [2448](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/executor-handlers.ts:2448), DM conversation sweep [fansly-dm-conversations.ts:965](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/sync/fansly-dm-conversations.ts:965). Hydration и identity repository одинаковы в обеих ревизиях.

**Работа.** [fan-page-identity.ts:98–230](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/fan-page-identity.ts:98) делает SELECT предыдущего alias, optional note INSERT, UPDATE отсутствующих notes, optional alias-history INSERT и UPDATE membership. Для H полных snapshots: Q=3H+число непустых notes snapshots+число snapshots с непустой alias-history. `notes` отсутствует → эта ветвь не вызывается. [Actual-function trace](probe-results.json) подтвердил 300/500 SQL на 100 accounts, включая второй идентичный проход; **общие `upsertFans`/`upsertFanPages` были заглушены и в SQL-сумму не входят**.

**Минимальное изменение.** Добавить batch-форму repository API для одной страницы: один SELECT предыдущих aliases; один multi-row notes upsert; один UPDATE/anti-join для деактивации отсутствующих notes только у переданных fan; один alias-history upsert; один `UPDATE ... FROM` для memberships. Пустые общие наборы пропускают соответствующие INSERT: получается 3–5 SQL. Пакеты ограничить accounts/bytes, никогда не разрезать полный snapshot одного fan. Сохранить существующие helpers выбора freshest note, blank-alias clearing, timestamps и статистику возврата.

**Конфликты и история.** Дедупликация обязана использовать реальные conflict keys: notes `(page,provider,externalNoteId)`, alias history `(page,fan,alias)`, membership `(page,fan)`. Иначе единый `ON CONFLICT` может попытаться обновить строку дважды. Полный последний snapshot определяет *active notes/current alias*, а накопленная alias history не должна исчезать. Простое «оставить последний account» теряет aliases, увиденные в более раннем дубликате. Минимальный безопасный rollout пакетирует только уникальный fan snapshot без конфликтов note ownership; при повторном fan snapshot или неоднозначном note key оставляет исходный последовательный путь. Последующая полная batch-поддержка таких случаев требует сохранить union истории и состояние последнего snapshot отдельно.

**Польза/приёмка.** Сокращение на 297–495 round-trips для fixture из 100 accounts. Если один последовательный DB round-trip занимает r миллисекунд, устраняется примерно `(Q−Qbatch)×r`; r и доля notes-bearing accounts в production неизвестны. Точные `seenAt/pageAliasSyncedAt` остаются обновляемыми: **снижение row writes/WAL не заявляется**. Сложность M. Проверки: absent против `[]`, новая/изменённая/удалённая/blank alias, tie по note-id, повтор batch, конфликт keys, один global fan на двух страницах, rollback и erasure во время обработки. Сохранить прежние transaction/lease/erasure boundaries и общий порядок захвата locks; не вводить параллельную запись по fan. Canary: SQL calls и p95 transaction на одинаковое число полных snapshots, locks/deadlocks и полное равенство notes/membership/history. Ошибка откатывает batch, повтор использует тот же capture; отдельного cache/cursor не появляется.

## Границы и отклонённые идеи

- Deployed no-op `fans/page_fans` writes, follower conditional COUNT и filtered membership уже внедрены; новая экономия по ним исключена. Изменение notes SQL не даёт права перестать хранить alias refresh timestamps.
- Глобальный hydration/negative cache отклонён: notes привязаны к странице, miss сегодня не доказывает удаление завтра. Без явного refresh/invalidation при появлении identity, account switch и erasure он способен скрывать актуальные данные. Existing follower aggregation уже используется до fallback HTTP; поддержка bulk lookup по 100 ID уже есть.
- F2 completeness и O1 stale REST lifecycle известны из предыдущего аудита. Эти две оптимизации их не исправляют и не усиливают основание для деактивации подписок. Anti-deletion, active-history guard решения #194, capture-first, account ordering, money units, provider pacing и ручные controls сохраняются.

Без Vitest, PostgreSQL, installs, production или новых provider requests. Требуются SQL-equivalence и canary до заявления production-эффекта.
