# OFAPI mirror: три локальные оптимизации

Проверены `main=b48f173d93e3693550e2db139de3b11107d44ce2` и production reference `74aac5093cfc` из общего `production-revision.txt`. Восемь файлов исследованных путей побайтно совпадают; три используемые функции агрегирования кредитов также совпадают, хотя остальная часть `repositories/ofapi.ts` отличается. Ниже новые предложения, ещё не реализованные ни в одной из этих ревизий. Их эффект — SQL, блокировки и задержка локальной обработки; **экономия оплаченных HTTP/кредитов не заявляется**. Текущие флаги, число страниц и нагрузка production неизвестны.

## 08-1. Не блокировать глобальный бюджет повторной проверкой точного receipt — P2

**Путь и включение.** При работающем background mirror `executeOfapiCaptureJobChunk` сохраняет ответ и уточняет кредиты ([ofapi-capture-jobs.ts:1534](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/ofapi-capture-jobs.ts:1534)). Следующий локальный parse снова вызывает уточнение ([строка 853](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/ofapi-capture-jobs.ts:853)). Это нужно после crash между capture и первым уточнением. Повтор возникает при доступных credit metadata и успешной первой сверке; export/upload ceiling имеет отдельные исключения. Аналогичный вызов есть при чтении сохранённых collection responses ([ofapi-collection-read-transport.ts:84](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/ofapi-collection-read-transport.ts:84)).

**Лишняя работа.** `reconcileOfapiCapturedAttemptCredit` сначала блокирует общий `ofapi_credit_state`, затем principal при наличии, затем attempt; только после этого проверяет `credit_estimated=false` и возвращает no-op ([ofapi-capture.ts:2373](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/ofapi-capture.ts:2373)). Реальная функция на mock DB выполняет **4 SELECT + транзакцию + 2 row locks**, либо **5 SELECT + 3 locks** с principal. Это не запись повторного расхода, а повторная синхронизация вокруг уже завершённой записи.

**Минимальное изменение.** Уже существующий `loadOfapiCaptureObservation` делает JOIN с attempt ([строка 688](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/ofapi-capture.ts:688)). Включить в этот результат `state`, `credit_state`, `credit_estimated`, `settled_credits`. Только при committed `response_captured / settled / false` и совпавшей нормализованной сумме пропустить вторую сверку. Это короткое доказательство из БД, привязанное к exact observation/attempt, без TTL-кэша. При estimated/unknown, несовпадении суммы либо crash до settlement остаётся нынешняя функция и её порядок блокировок. Несовпадение должно по-прежнему давать invariant error.

**Модель пользы.** Для D таких повторов и доли principal q устраняются `D×(4+q)` SELECT, D транзакций и D захватов глобального budget lock. Дополнительных SQL не требуется благодаря существующему JOIN; первый финансовый settlement полностью сохраняется. Удаление ожидания бюджетной блокировки может ускорить parse и освободить admission для других запросов, но общий выигрыш зависит от D и фактической конкуренции.

**Риск и проверка.** Размер небольшой. Нужен pin монотонности exact receipt: capture duplicate уже не переписывает settled attempt, replay меняет parser fields, а operator certainty repair принимает indeterminate. Нельзя распространить shortcut на эти промежуточные состояния. Регрессии: crash до/после certainty commit, параллельный replay, reported zero с нулевым delta, signed correction, несовпадающие credits, export/upload ceiling. Canary: duplicate-settlement rate, credit lock wait, SQL/parse; ledger/counters и outcome должны совпасть побайтно. Probe воспроизводит текущую стоимость и сохранённую ошибку; новый SQL shortcut не исполнялся.

## 08-2. Выбирать действительно due collection policies до транзакций — P2

**Путь и включение.** `startOfapiCollectionWorker` регистрируется без проверки collection mode ([worker-services.ts:572](/Users/dmitriy/code/goose/hub/apps/runtime/src/worker-services.ts:572)); minutely sweep передаёт шесть read categories и два handlers ([ofapi-collection-runner.ts:391](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/ofapi-collection-runner.ts:391)). Даже при всех восьми default-off `enqueueDueOfapiCollectionSchedules` перебирает каждую mapped OnlyFans page × category ([ofapi-read-collections.ts:171](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/ofapi-read-collections.ts:171)). Каждый effective-policy lookup — отдельные state SELECT и policy SELECT ([ofapi-collection.ts:37](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/ofapi-collection.ts:37)).

**Измеренная модель.** При P страницах, C=8 и всех off: **1+2PC SQL за sweep**. Mock actual-function probe: P=2 →33, P=20 →321. При одном sweep в минуту первое соответствует 47 520 SQL/сутки, но это условный пример, не production census. Если все категории scheduled, ещё не due, pending jobs отсутствуют: **1+8PC SQL, PC транзакций и PC global-policy locks**; P=2 →129 SQL и 16 транзакций, ноль созданных jobs. Проверка due сейчас происходит после этих блокировок.

**Изменение.** Один согласованный SQL snapshot эффективных page/default policies, state, actor, schedule и pending status; выдать только scheduled, unpaused, due candidates. Важно сначала применить precedence page override → default: explicit page off подавляет scheduled default. Для каждого кандидата сохранить короткую существующую транзакцию с повторной проверкой revision/pause/policy/pending и conditional schedule insert. Не держать один глобальный lock на весь census. Физическая reservation по-прежнему отдельно перечитывает полномочия.

**Польза и ограничения.** При отсутствии кандидатов — один census вместо `1+2PC`/`1+8PC` round-trips и ни одной scheduling transaction. Это сокращает control-plane tax при том же расписании, scope и discovery. Строки в snapshot ещё растут с P×C; «O(1) CPU» не заявляется. Размер средний. При малой fleet абсолютная нагрузка может быть несущественной; измерять SQL/sweep и lock wait до реализации.

**Проверки.** Default scheduled + page off, global pause, interval decrease, actor custody, concurrent sweeps, deleted/rebound page, paused job blocker и потерянный wakeup. Никакой долгоживущей кэш-инвалидации: snapshot живёт один sweep, кандидаты повторно проверяются под lock. Canary сравнивает набор созданных jobs, точные окна/caps и policy revisions со старым dry planner; pending/paid checkpoints не меняются.

## 08-3. Считать интервалы credit reconciliation двумя агрегатами — P3

**Путь.** Часовой credit worker при `ofapiCreditLedgerEnabled=true` берёт до 500 balance observations. После фильтра ID и минимального интервала 60 секунд planner для каждой принятой пары последовательно вызывает ledger sum и webhook count ([ofapi-credits.ts:201](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/ofapi-credits.ts:201), [wiring:290](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/ofapi-credits.ts:290)).

**Цена.** A принятых интервалов →2A aggregate round-trips. Actual-function probe: 500 receipts с минутным шагом →1 000 вызовов; 500 с секундным шагом →16. Верхний пример означает накопленный backlog; в ровном часовом steady state минутный фильтр ограничивает A примерно 60. Имеющиеся диапазоны непересекающиеся: это N+1 запросов, не доказанный квадратичный scan истории.

**Изменение.** Сначала тем же правилом выбрать интервалы, затем передать их пачкой в два SQL: суммы `rest/adjustment` по `(fromLedgerId,toLedgerId]`, число webhook receipts по `[fromTime,toTime)`. Map результатов подставляется в неизменную residual-формулу. Суммировать можно индексными range probes внутри одного SQL; более сложный prefix-sum стоит рассматривать только после EXPLAIN. Источники и границы заданы в [ofapi.ts:1772](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/ofapi.ts:1772) и [1835](/Users/dmitriy/code/goose/hub/packages/db/src/repositories/ofapi.ts:1835), production —1796/1859.

**Польза/риски.** Сокращение на `2A−2` round-trips при A>0; ожидаемая экономия задержки `(2A−2)×R`, где R — измеренная DB latency. Aggregate tuples могут остаться прежними. Размер небольшой/средний, при редких receipts выигрыш мал. Не смешивать observed balance, estimates и оплаченные attempts: webhook estimate остаётся `count/100`, daily accrual — отдельным `ceil`, signed corrections сохраняются, external/refill/accrual не становятся known spend. Регрессии: пограничные timestamps/IDs, внепорядковые receipts, skipped intervals, negative adjustments, crash/повтор и атомарное продвижение cursor с ledger append. Canary: одинаковые adjustments/cursor, SQL и длительность reconciliation. Probe проверил эквивалентность входов planner; PostgreSQL batching не тестировался.

## Отклонено и воспроизводимость

- Повтор оплаченного HTTP при `awaiting_parse`, certified-anchor reuse, compatible hydration coalescing и CAS sharing уже решены; экономия повторно не засчитывается.
- Кэшировать одинаковый collection target между разными scheduled windows нельзя без отдельного freshness-контракта. Наличие raw не доказывает актуальность нового окна или continuous history.
- Прореживание webhook subscription, polling, scope или retention не предлагается. Retired DM crawler исключён; stale audience lifecycle и capture-before-list-parse — известный baseline, не новые результаты.
- Все три предложения сохраняют reservation/finalize/402/indeterminate semantics, page binding/auth/pause, egress, raw-before-parse, leases, account ordering и erasure fences. Capture proof, freshness, history и serving readiness остаются разными состояниями.
