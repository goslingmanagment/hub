## Вердикт

Общее направление «native WS как ускоритель + независимый REST» обосновано. **Ни D, ни I не доказали готовность самостоятельного серверного сокета**: M3 (fan-out/влияние на браузер), T1 (реальная стабильность), G1 (поведение при пропуске), P1 (presence) остаются открыты. Кросс-рецензия правильно признаёт это для I, но переоценивает доказательность D: подробный reverse engineering клиента не становится контрактом сервера. Более того, рекомендуемый D инструмент живой проверки сохраняет реальный формат auth token без маскирования. **Не копировать и не запускать `ws-tap-snippet.js` на аккаунте до исправления и повторной offline проверки.** Эта находка относится к исследовательскому snippet, не к deployed Hub/extension; факта утечки реального токена в этом исследовании нет.

Достаточно короткого управляемого теста на отдельном тестовом аккаунте, затем ограниченного shadow; не нужно сначала проверять все 31 гипотезу, искусственно провоцировать reconnect storm, logout или лимит 10 соединений. Ниже — точные границы доказательств и минимальный набор.

Второй дефект live ladder — инструкция `File → Work Offline` на строках 2/27 затрагивает Firefox целиком и принудительно вызывает новый цикл соединений/дочитки; её нельзя описывать как пассивное наблюдение без влияния на работу чаттеров. Сам tap не создаёт соединение при установке, но предложенный сценарий его создания/перезапуска требует.

Минимальная замена для исследования: штатный Firefox Network Monitor, выбранный `wsv3` request → Response → **Received**. Firefox документирует просмотр sent/received frames и отдельный фильтр; это не требует патчить `window.WebSocket`. Если уже открытый сокет не попал в monitor, ждать обычного reconnect либо использовать отдельный тестовый профиль/разрешённую навигацию тестовой вкладки. Не применять глобальный Work Offline. Не выгружать outbound auth, full frames или clipboard; сохранять field names, transport/service types, времена, размеры и псевдонимизированные business-ID для сравнения. Полные fixtures нужны только для отдельно согласованного тестового аккаунта в защищённом evidence store. [Mozilla, WebSocket Inspector](https://firefox-source-docs.mozilla.org/devtools-user/network_monitor/inspecting_web_sockets/index.html).

## 3. Auth ACK, account binding и хранение management token

Текущий evidence корпус **не содержит реального t1 payload**. Официальный consumer принимает argument, но не валидирует в нём account/session identity. D A:94 ссылается на third-party форму `session.id`; это ещё не установленный native contract для текущего бандла или Management Session. Следовательно, не строить account binding на предположении, что t1 содержит `accountId`, и не считать base64-prefix token надёжной серверной верификацией. Такое legacy decoding есть в [extension session-capture:5](/Users/dmitriy/code/goose/fansly-ext/src/background/session-capture.ts:5).

Минимальный план проверки: credential bundle уже должен быть привязан к ожидаемому page/account; bounded `GET /account/me` через тот же session bundle/proxy возвращает ожидаемый account; собственный connection generation связывается именно с этим проверенным credential generation. На выбранном сокете наблюдается t1, затем известный тестовый business object сопоставляется с REST и ожидаемой account/group принадлежностью. Если в реальном t1 есть session/account refs, сохранить **схему** и сравнить с trusted bundle; mismatch→quarantine/stop. Если refs отсутствуют, прямо записать, что binding обеспечивается проверенным credential и controlled parity, а не несуществующим upstream identity assertion.

D-extension:145–147 и :704 преувеличивают отсутствие custody. Верно: extension хранит свой session in-memory и не отправляет его Hub. **Неверно: для server socket обязательно изобретать передачу browser token.** В `origin/main` уже есть:

- `apps/runtime/src/services/page-onboarding.ts:84–105`: non-null proxy + `verifySession`; :117–130 encrypted storage и page identity из `verified.account.id`.
- `packages/fansly/src/adapter.ts:1251–1252`: `verifySession` вызывает `/account/me`.
- `apps/runtime/src/services/page-context.ts:103–117,238–247`: encrypt/store и decrypt существующего session bundle.

Локальные навигационные ссылки: [onboarding](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/page-onboarding.ts:98), [adapter](/Users/dmitriy/code/goose/hub/packages/fansly/src/adapter.ts:1251), [custody](/Users/dmitriy/code/goose/hub/apps/runtime/src/services/page-context.ts:103). Строки `origin/main` на 2 отличаются в onboarding; полный ref зафиксирован выше. Бандл подтверждает reuse session.token между REST authorization и WS auth ([REST:22703](/Users/dmitriy/code/goose/hub/artifacts/fansly-app-bundle-2026-08-20/analysis/main.pretty.js:22703)); **успешная переносимость именно Hub token через server socket пока не проверена**. Это gate существующего custody path, не доказанное требование новой browser→Hub передачи.

Management Session — разумный кандидат с меньшими правами. Fansly официально подтверждает контролируемые permissions, одноразовый link и revoke/logout lifecycle, но не portability, WS scopes и coverage. [Fansly Management Sessions, 01.12.2025](https://help.fansly.com/en/articles/12328641-management-sessions). Поэтому D A:702 «если verify проходит, model full token больше не нужен на servers» неверно: одно auth success не доказывает DM/ledger/subscription REST права, область WS events, срок жизни и восстановление после отзыва. Принимать management bearer в существующую encrypted custody можно только по отдельному проверенному контракту; не логировать link/token, не авто-create/claim/revoke и не заменять рабочие REST credentials в этом исследовании. Вход по отдельной management session также требует M3 между двумя **разными** sessions, если это выбранный production вариант; тест same-token один это не покрывает.

WS401 также не доказывает смерть REST-сессии. D main:176 уже изменён относительно кросс-рецензии: есть bounded REST probe. Осталась слишком широкая ветка REST401/**403**→auth_blocked: 403 может означать permission/WAF restriction; код/тело ошибки и известный auth classifier важнее одного HTTP status. Не выполнять `/logout`: [native handler:20778](/Users/dmitriy/code/goose/hub/artifacts/fansly-app-bundle-2026-08-20/analysis/main.pretty.js:20778) именно это делает, через [POST implementation:13566](/Users/dmitriy/code/goose/hub/artifacts/fansly-app-bundle-2026-08-20/analysis/main.pretty.js:13566). Receiver должен остановить свой retry и оставить здоровые REST потоки работающими.

## 5. Самая короткая лестница до выбора сокета

1. **Offline до любой новой авторизации.** Проверить capture redaction/exclusion и decoder на synthetic fixtures; не использовать опубликованный D snippet. Разделить auth/readiness и pong, credential/account generation, unknown frame quarantine. Для наблюдения достаточно Firefox native inspector; MAIN-world extension, custom relay и production schema пока не требуются.
2. **Passive current-client schema.** На существующей разрешённой вкладке/изолированной тестовой вкладке получить ограниченное received-only наблюдение. Не отключать Firefox, не переключать production sessions, не отправлять тестовые сообщения без отдельного разрешения на тестовый аккаунт. Отсутствующие типы явно оставить неизвестными. Одночасовой capture измеряет frames/hour, не frames/day (ошибка D main:281).
3. **Один тестовый аккаунт, один server receiver, один сопоставимый browser.** Использовать корректные официальные URL/version/heartbeat и тот же proxy arrangement, который предполагается внедрять; не экспериментировать с отсутствующим/wrong Origin, bad token, protocol variants или10 sockets. В этом одном прогоне совместить credential identity+t1, M3, P1, два controlled gap caseG1 и T1≥6h. Stop при auth failure, необычном error/close, browser disruption или source cooldown; ограниченный incident/REST diagnostic, без logout и reconnect storm.
4. **Решение о target.** При успешном прогоне native Hub receiver остаётся предпочтительным, поскольку не зависит от браузера. Если portability/M3/P1 не проходят, отдельная management session с повторением relevant test или browser relay — кандидаты; relay всё равно не решает browser-off freshness. Сохранить независимый REST. Можно выбрать условную архитектуру уже сейчас, но не объявить readiness до этих проверок.
5. **Production canary — отдельное действие после одобрения владельца**, с исходным polling, raw journal/custody и budget controls. Добавление авторизованного соединения к production account является production interaction, даже если не меняются DB/config; фраза D main:283 «ничего в prod не меняется» это затушёвывает. На нём нужен72h+shadow корпус и parity/gap evidence до снижения cadence. Необязательные negative tests A1/A4/A5/T2/T5/M1/S2 из D не являются gate первого сокета; не проводить deliberate logout/revoke/reconnect storm на рабочей сессии.

Ни эта лестница, ни список неизвестных не являются разрешением запустить тесты: текущая задача архитектурная, browser/prod здесь не трогались. Минимальный gate технически конкретен и может быть отдельно одобрен без одобрения всего плана реализации.

## 6. Сопутствующие замечания к силе кросс-рецензии

- Фраза «D доказал полный протокол и отсутствие message edits» смешивает хорошо восстановленную клиентскую реализацию с серверным контрактом. Его детализация полезна для decoder/test design; она не закрывает M3/T1/G1/P1. I's conservative evidence labels — реальное качество, а не недостаток подробности.
- I:154 необходимо исправить как условную mutation policy; иначе читатель разумно примет edit за доступный trigger. При этом удалять из архитектуры восстановление старых corrections нельзя только потому, что dedicated WS type не найден.
- D extension:576–602,698 утверждает «CSP-proof MAIN» шире проверенного доказательства. [Mozilla content_scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts#world) подтверждает shared page world и возможность page interference, а не гарантию безопасности/неизменности tap. Для выбора минимального исследования спор CSP не нужен: native inspector снимает эту зависимость. Не объявлять доверенным любой MAIN→postMessage→Hub payload без account binding и producer capability.
- D main:180 разрешает после frames/hour cap считать, но не журналировать business frames. Это не raw-first custody. При выборе такого backpressure требуется durable explicit coverage gap и REST recovery; иначе «все кадры raw first» из кросс-рецензии:10 неверно. Сам cap не предотвращает потерю краткоживущего факта.
- I не «без чисел»: его текущий переход содержит72h/7d, ≥50/70% request reduction targets, p95/p99 и parity/failure checks. Они являются proposed gates, не измеренными результатами. Это различие надо сохранить и для D's прогнозов экономии, и для live test claims.

Итог по узкому направлению: архитектурный выбор возможен **условно**, но перенос D's snippet, auth permissiveness и абсолютных отрицаний в implementation сейчас недопустим. Доказательств достаточно для короткого безопасного test plan; доказательств завершённых M3/T1/G1/P1 пока нет.
