# Независимая перепроверка Fansly и планирования

14.09.2026. Исследование кода, без product edits, SSH, SQL к production, provider calls, installs и широких tests. Проверены все назначенные A1–A5, B1–B3/B5, C1–C3/C5, Fansly-части C7/D3/E2/H, O1-01…12 и O2-01…10. В [checks.json](checks.json) 63 отдельных проверки, включая групповые подпункты, сводные обещания и дополнение §5. Вердикт `conditional` может означать подтверждённый механизм при недоказанном исправлении или числе; эти три аспекта в JSON разделены.

Статическая база — main `b48f173d`. Root отдельно подтвердил production `380326368fe3` и идентичность sync-кода с Opus `74aac509`; результат лежит в [production-identity.json](../production-identity.json). Исторические 13Sep показатели текущими данными не подменялись. В Opus сохранены SQL и скрипты, но не необходимые `trace_obs.csv`, `generations.json`, `matrix_7d.csv`, `fe_new.csv`, `fe_bodies.csv`, `topsp_last.csv`, `tx_trace_*.csv` и результаты. Здесь эти числа не воспроизведены.

**Совпало с нашим аудитом.** B3 — F1 (backfill сохраняет старые total/offset и бесконечно повторяет ошибку); B2 — F5 (guard сравнивает собственный offset, а не продвижение содержимого); C7 PPV — F4 (старый target больше не refresh после новой покупки); D3 coverage — F3 (overlap не доказывает exhaustion); D3 retry-kind/pause — C1/C2; H group coordination — C4/C5; H media-stats 429 — FH07-1. A1 уже присутствовал как `control/O3`, но Opus добавляет историческое измерение масштаба, которое без трасс нельзя независимо повторить. O2-03/06/08 пересекаются с QSQL-01…04. Их экономию нельзя добавлять к нашему каталогу как независимую.

**Существенные новые механизмы относительно наших F1–F5/C1–C5.**

1. **C1: уведомления действительно могут перескочить непрочитанную страницу после временного сбоя.** Handler ставит `lastRequestedBefore` до отправки; `createDurableFanslyAttemptBudget.onRequestEvent(started)` сохраняет весь state до physical request. Следующий chunk видит repeat, завершает forward walk и может commit `pendingHeadRef`; backfill объявляет себя done. Это подтверждённая составная цепочка, а не вывод из наличия guard. Page-cap имеет соседнюю ошибку: сохраняет прежний cursor, отчего следующий chunk попадает в тот же guard. Нужны раздельные attempt reservation и accepted response progress. [Код](../../../apps/runtime/src/services/sync/fansly-notifications.ts), строки 745–759, 815–843, 932–960; [attempt observer](../../../apps/runtime/src/services/sync/fansly-lane.ts), строки 204–216.
2. **A2: history и head notifications действительно делят один daily cap.** Переключение `phase=forward` после deadline не восстанавливает расходованный allowance; при cap обе ветки откладываются до следующей UTC-даты. Reserve должен учитывать многостраничный head и physical retries. Назначить notifications priority31 без этого исправления означает повысить и их history traffic. Код: `fansly-notifications.ts:484,723,893,1061`.
3. **C3: legacy DM candidate может пропустить последнее сообщение, появившееся между head fetch и finalize.** Caller не передаёт `lastMessageSyncAt`, repository пишет время завершения; выбор треда сравнивает provider head time с этим временем. Head ID/debt — более надёжный ориентир, чем предложенное «минус одна секунда», которое не закрывает все clock/precision границы. Код: `executor-handlers.ts:3075`, `page-dm.ts:976,1093`.
4. **C2: 429/408 ошибочно считаются отказом notification type filter.** Handler переключает форму запроса вместо передачи Retry-After executor. Пункт Opus «навсегда одна группа» следует сузить: следующий отказ способен сменить group, но широкая форма автоматически не восстанавливается. Для 5xx rethrow уже существует. Код: `fansly-notifications.ts:415,596–644`.

B5 дополнительно показывает реальные, но менее срочные границы: смена cadence без rebase epoch-slot может отложить следующий запуск на десятилетия; fan-local 400/410 удерживает весь contiguous keyset walk; successful old-month probe не делает последующие пустые месяцы доказательством exhaustion. Простая команда «skip fan» здесь теряет durable refresh obligation: нужен отдельный target debt. C5 указывает отсутствующий completeness gate lifetime endpoint; факт обрезки именно двух названных фанов и $3,731.95 без исходных тел остаётся неперепроверенным.

**Четыре главных возражения к “без потерь”.**

- **O1-01, monthly из lifetime.** Скрипт сравнивает только сумму gross/net по `(year,month)`. Каноническая запись хранит ещё breakdown типов, а C2b — независимые endpoint receipts, claim revisions и provenance. В локальном [контрпримере](probes.json) суммы совпадают при разных breakdown. Число строк `<100` не является provider completeness certificate. Derivation возможна после проверки полной семантики и с честной derived provenance; нельзя поставить monthly endpoint `checked` по ответу другого endpoint.
- **O1-02, остановка на первой “старой” транзакции.** Нужно определить границу. Первая известная запись или старый checkpoint не закрывает pending→posted/late correction на следующей странице, даже при идеальной сортировке creation time. First older-than-lookback может быть допустим только при доказанной стабильной сортировке/границах и отдельном recovery старых pending. `an_tx_pages.py` проверяет изменения `st/upd/amt` лишь у уже увиденных IDs, а отсутствие изменений глубже в ~1,170 наблюдённых runs не проверяет неувиденные изменения. New-only fan lookup дополнительно меняет freshness профилей и notes.
- **O1-03, top_spenders из tx.** `an_topsp.py` проверяет net только каждого provider fan; не сравнивает полный fan set и gross. Поэтому “52/52” может быть истинным при разных рейтингах — [контрпример](probes.json). Legacy `page_fan_identities` и актуальная board из `fan_earnings_stats` — разные читательские пути. Отказ от legacy capture можно обсуждать отдельно; он не исправляет C5 и не доказывает эквивалентность source data.
- **O1-05/06/07, stale metadata как основание пропуска.** Reuse `account_me` до 30min может сломать независимый start/end count proof follower reconciliation. Existing-subscriber lookup обновляет profiles/notes, а не только создаёт IDs. `replyCount=0` в старом post snapshot не доказывает отсутствие новых ответов. Все три меры требуют явного max-age и safety path; это не гарантированно неизменная freshness.

O1-08/09/10/11 допустимы как согласованные сценарии свежести, с сохранённым bounded recovery. Transaction trigger не доказывает тихие earnings corrections; latest mass-message head может скрывать предшествующий fan reply; full list раз в 6h закрывает задержку лишь при успешном завершении sweep. O1-12 (5→8s) и O2-05 (5/45→16/60) требуют совместного расчёта offered load/fairness после этих изменений.

**В O2 aging расходятся сам отчёт, SQL и симулятор.** OPTIMIZATIONS обещает `greatest(finished_at,requested_at,retry_at)` без миграции. `p1_sketch.sql` прямо предлагает новую колонку `runnable_since`; `sim_sched.py:121` использует `pending_since/last_served_end`. `requestPageSync` перезаписывает `requested_at` и для уже pending demand. Чистая [модель](probes.json) с новым intent каждые 5min держит вычисляемый возраст ниже 5min даже после 180min без обслуживания. Это не production-replay notifications, но прямой контрпример универсальности предложенного якоря. Нужен один согласованный durable runnable-age contract; порог30min не превращается в математический bound32min при overload/long chunks.

O2-04 частично совпадает с исправлением нашего C3. DB `clock_timestamp()` нужно читать **после всех locks**: само наличие CTE этого порядка не гарантирует. Process cache допустим только для профиля `(provider,egress,scopes,config revision)` с invalidation/reset и retry failed ensure; reservation и `next_available_at` не кэшируются. Сейчас ensure cache уже есть внутри waiter, но waiter создаётся заново на chunk. O2-07 heartbeat30→120s меняет скорость восстановления, а monitor300s — наблюдаемость. O2-06 может сделать число round-trips почти постоянным, но scanned rows, locks и WAL продолжают расти с количеством страниц. O2-08 single dispatcher полезен как QSQL-04, а 32 slots/pool25 не подтверждены load test.

**Дополнение §5: fencing, handoff и proxy.** Прочитаны текущий код и существующие tests; новых запусков tests не было. Проверенные terminal transitions требуют token/leased generation/running/DB-clock TTL, а valid старый lease может законно завершиться при более новом pending request. Атомарный `complete→send` использует один SQL client/transaction; proxy guards стоят в page context, egress resolver и самом adapter до `fetch`. Эти узкие гарантии поддержаны исходниками и существующими тестовыми сценариями, но не являются новым исчерпывающим crash/network доказательством. Отдельный **пробел у checkpoint-helper**: его `owned_task` проверяет token+leased_seq под lock, но не status/expiry (`sync.ts:683`). Прямые calls есть в `fan-earnings.ts:133,150`; executor создаёт AsyncLocal context, а не охватывающую owned DB transaction. Поэтому expired-but-not-reclaimed token сам helper не отвергает. Existing integration test:437 проверяет pause с очищением token, не истечение TTL при сохранённом token. Статическая граница отмечена `S5-checkpoints=conditional` с конкретным следующим boundary test; production occurrence или повреждение данных не заявляются.
